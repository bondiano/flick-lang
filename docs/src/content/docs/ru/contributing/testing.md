| Команда | Что запускается |
| - | - |
| `just check` | fmt, clippy (`-D warnings`, в том числе для `wasm32`), `cargo test --workspace` |
| `just e2e` | `pnpm install --frozen-lockfile`, тесты среды выполнения, `tests/run/**` на Node, `flick test` на примерах проектов |

Снимки проверяются через [`insta`](https://insta.rs); просматривайте изменения
командой `cargo insta review` или принимайте их через
`INSTA_UPDATE=always cargo test`.

## Примеры для проверки типов — `tests/check/`

- `tests/check/pass/**/*.fl` должны проверяться без диагностик и не должны
  содержать аннотаций. Каждый файл проверяется отдельно, поэтому объявляет
  используемые им типы и сервисы.
- `tests/check/fail/**/*.fl` перечисляют все ожидаемые диагностики в комментариях
  с аннотациями. Отсутствующие и неожиданные диагностики выводятся для каждого файла.

Формы аннотаций:

```flick
let x : Number = "hi"
//               ^^^^ FLICK-T012 expected `Number`
//~ FLICK-E003 @4:1-6:9 effect row is not closed
//~ FLICK-P001 cannot read
```

- **Указатели** `// ^^^ CODE text` отмечают столбцы ближайшей предшествующей
  строки, которая не является аннотацией. За одной строкой исходного кода
  может следовать несколько строк с указателями.
- **Явный диапазон** `//~ CODE @L:C-L:C text` задаёт диапазон с нумерацией от 1
  и невключённым конечным столбцом; используйте его для многострочных диапазонов
  и диапазонов, начинающихся в столбцах 1–2, которые заняты `//` в строке указателей.
- **Без диапазона** `//~ CODE text` соответствует диагностике без позиции
  в исходном коде.

Каждый каталог в `tests/check/projects/` — целый проект, проверяемый как
`flick check` без путей: `flick.toml`, корневые каталоги исходников и тестов,
а также `package.json` с искусственным `node_modules/`, если примеру нужны
пакеты. Аннотации допустимы в любом файле проекта, а в `flick.toml` вместо
`//` используется `#`; диагностики без диапазона аннотируются в `flick.toml`.
Проект без аннотаций должен проходить проверку без диагностик.

Столбцы считают символы, а не байты. `text` необязателен и должен быть
подстрокой сообщения диагностики, к которому каждая строка help
дописана как `: help`. Предупреждения о неиспользуемом коде
(`FLICK-R012`–`R014`) учитываются только в файлах, где упомянут их код:
фикстуры других правил связывают имена, которые не используют. Коды должны быть зарегистрированы
в `flick-core/src/diagnostics/codes.rs`.

## Сквозные программы — `tests/run/`

Каждый `<name>.fl` собирается командой `flick build <name>.fl --out-dir …`,
а его запускающий модуль выполняется через `node --enable-source-maps`.
Ожидаемые результаты лежат рядом:

| Файл | Значение по умолчанию при отсутствии |
| - | - |
| `<name>.stdout` | обязателен |
| `<name>.stderr` | пусто |
| `<name>.stderr.contains` | вместо `<name>.stderr`: строки, которые должны присутствовать в stderr |
| `<name>.exit` | `0` |

Каждый пример запускается трижды: после компиляции в JS, после компиляции
с `--emit ts`, когда Node выполняет `flick-main.ts` напрямую, и после компиляции
в JS в профиле release, который должен вести себя как отладочная сборка. Внутри
каждого прохода примеры идут параллельно, по `FLICK_E2E_JOBS` за раз (по умолчанию —
по числу процессоров; `FLICK_E2E_JOBS=1` запускает их по одному). Затем `tsc --noEmit`
в строгом режиме проверяет весь сгенерированный TypeScript. Результаты
записываются в `target/tmp/e2e/` и импортируют `@flick-lang/runtime` из рабочего
пространства. Внешний модуль рядом с примером (`./tags.mjs`) импортируется
оттуда же. `just e2e` также собирает каждый пример `tests/check/pass/**`
и запускает `node --check` для результата, а `e2e_numbers.rs` сравнивает
случайную арифметику `Number`, скомпилированную из Flick, с теми же выражениями в JS.

## `flick test` — `flick/tests/test_command.rs`

Создаёт примеры проектов в `target/tmp/test_command/` и запускает для них
`flick test`: каждый вид исхода — провал утверждения, типизированная ошибка,
дефект, ошибка очистки — выводится отдельно; seed позволяет повторить те же
значения; применяются `--filter` и `--jobs`; в режиме `--watch` следующий запуск
начинается только после освобождения ресурсов предыдущим.

Стандартная библиотека объявляет все сигнатуры из спецификации дословно:
`flick-core/tests/stdlib_signatures.rs` читает их из блоков `text` спецификации.

## Тесты среды выполнения — `runtime/test/`

Среда выполнения написана на TypeScript 7 (`runtime/src/*.ts`) и собирается
в `runtime/dist/` вместе с декларациями; `just e2e` проверяет её типы через
`tsc` в строгом режиме с `noUncheckedIndexedAccess` и
`exactOptionalPropertyTypes`, включая тесты, проверяет её через
`oxlint --type-aware` — без `any`, необработанных промисов и непроверенных
утверждений о типах без пояснения рядом — и запускает тесты.

`node --test` в `runtime/` выполняет файлы `.test.ts` с удалением аннотаций
типов самим Node после сборки `dist/` и проверяет контракты адаптера напрямую
на Effect: таблицу восстановления `try … with`, инертные отчёты о причинах,
двухфазное закрытие владельцев, дочерние задачи и супервизоры, конкурентность,
гонки и слои, закреплённую версию Effect `4.0.5` и её матрицу возможностей,
кодеки в сравнении с их скомпилированными декодерами. Тесты запускающего модуля
создают дочерний процесс `runtime/fixtures/entry.ts` и посылают ему сигналы.

## Синтаксический корпус и фаззинг — `flick-core/tests/{corpus,fuzz}.rs`

- Каждый блок ```` ```flick ```` в спецификации и в `docs/` должен разбираться
  без диагностик. Примеры спецификации закреплены отпечатками в
  `tests/syntax/spec_examples.txt`: новый или изменённый пример ломает тест,
  пока его разбор не проверен и напечатанная строка не добавлена в этот файл.
- Каждый файл `.fl` в `tests/` и каждый блок документации должны проходить
  обратное преобразование через дерево без потерь байт в байт; примеры
  без диагностик должны форматироваться идемпотентно, а форматтер повторно
  проверяет, что AST не изменилось.
- `tests/syntax/*.fl` проверяют только грамматику: они должны разбираться
  без диагностик, но разрешение их имён не требуется.
- `fuzz.rs` изменяет корпус и проверяет, что парсер не паникует и не зависает,
  остаётся без потерь и сохраняет диапазоны в границах, а проверка типов
  не паникует на успешно разобранных входных данных. `FLICK_FUZZ_ITERATIONS`
  задаёт число входов: 20 000 в `just check`, 1 000 000 в ночной задаче CI
  (`just fuzz`).
- `DUMP=out.txt [DUMP_FILE=x.fl] cargo test -p flick-core --test corpus dump -- --ignored`
  записывает деревья примеров спецификации или одного файла для просмотра.

## Время проверки — `flick-core/tests/scaling.rs`

Проверяет запись из 200 полей, читаемых по одному, и функцию из 2000 строк,
а также каждую из них в четверть размера: полный размер должен укладываться
в лимит времени, а соотношение времени между размерами должно оставаться линейным.
