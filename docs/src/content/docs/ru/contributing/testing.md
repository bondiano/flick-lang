Установите проверку зависимостей, используемую локально и в CI:

```sh
cargo install cargo-machete --version 0.9.2 --locked
```

| Команда | Что запускается |
| - | - |
| `just lint` | fmt, clippy (`-D warnings`, в том числе для `wasm32`), `cargo machete` (неиспользуемые зависимости Rust) |
| `just check` | `just lint`, `cargo test --workspace` |
| `just e2e` | `pnpm install --frozen-lockfile`, тесты среды выполнения, `tests/run/**` на Node, `flick test` на примерах проектов, `just language` |
| `just language` | языковые тесты `tests/language` на Node и исполняемым файлом Go: оба запуска должны пройти с одинаковым отчётом |
| `just bundle-size` | release-сборки `tools/bundle-size/pure.fl`, `tests/run/ui/counter.fl`, `tests/run/ui/atoms.fl` и плейграунда, собранные для браузера через rolldown; падает, если размер в gzip превышает бюджет из `tools/bundle-size/index.mjs` |

Тесты сравнивают результаты с эталонными снимками через [`insta`](https://insta.rs).
Просмотреть изменения можно командой `cargo insta review`, а принять их —
через `INSTA_UPDATE=always cargo test`.

## Примеры для проверки типов — `tests/check/`

- `tests/check/pass/**/*.fl` должны проходить проверку без диагностик и не должны
  содержать аннотаций ожидаемой диагностики. Каждый файл проверяется отдельно,
  поэтому сам объявляет используемые типы и сервисы.
- `tests/check/fail/**/*.fl` перечисляют все ожидаемые диагностики в комментариях
  с аннотациями. Для каждого файла тест сообщает об отсутствующих ожидаемых
  и о неожиданных диагностиках.

Формы аннотаций:

```flick
let x : Float = "hi"
//               ^^^^ FLICK-T012 expected `Float`
//~ FLICK-E003 @4:1-6:9 effect row is not closed
//~ FLICK-P001 cannot read
```

- **Указатели** `// ^^^ CODE text` отмечают столбцы ближайшей предшествующей
  строки, которая не является аннотацией. За одной строкой исходного кода
  может следовать несколько строк с указателями.
- **Явный диапазон** `//~ CODE @L:C-L:C text` задаёт диапазон с нумерацией от 1;
  конечный столбец в него не входит. Используйте эту форму для многострочных
  диапазонов и диапазонов, начинающихся в столбцах 1–2: в строке указателей
  эти столбцы заняты `//`.
- **Без диапазона** `//~ CODE text` соответствует диагностике без позиции
  в исходном коде.

Каждый каталог в `tests/check/projects/` проверяется как самостоятельный проект
вызовом `flick check` без путей. В нём находятся `flick.toml`, корневые каталоги
исходников и тестов, а если примеру нужны пакеты — ещё и `package.json`
с тестовым `node_modules/`. Аннотации допустимы в любом файле проекта;
в `flick.toml` вместо `//` используется `#`. Диагностики без диапазона
аннотируются в `flick.toml`. Проект без аннотаций должен проходить проверку
без диагностик.

Столбцы отсчитываются в символах, а не в байтах. Необязательный `text` должен быть
подстрокой сообщения диагностики, к которому каждая строка help
дописана как `: help`. Предупреждения о неиспользуемом коде
(`FLICK-R012`–`R014`) учитываются только в файлах, где упомянут их код:
фикстуры других правил связывают имена, которые не используют.
Коды должны быть зарегистрированы
в `flick-core/src/diagnostics/codes.rs`.

## Сквозные программы — `tests/run/`

Каждый `<name>.fl` собирается командой `flick build <name>.fl --out-dir …`,
а модуль запуска выполняется через `node --enable-source-maps`.
Файлы с ожидаемыми результатами лежат рядом:

| Файл | Значение по умолчанию при отсутствии |
| - | - |
| `<name>.stdout` | обязателен |
| `<name>.stderr` | пусто |
| `<name>.stderr.contains` | вместо `<name>.stderr`: строки, которые должны присутствовать в stderr |
| `<name>.exit` | `0` |

Каждый пример запускается трижды: после компиляции в JS, после компиляции
с `--emit ts`, когда Node выполняет `flick-main.ts` напрямую, и после компиляции
в JS в профиле release, который должен вести себя как отладочная сборка. Внутри
каждого прохода примеры идут параллельно, по `FLICK_E2E_JOBS` за раз (по умолчанию —
по числу процессоров; `FLICK_E2E_JOBS=1` запускает их по одному). Затем `tsc --noEmit`
в строгом режиме проверяет весь сгенерированный TypeScript. Результаты
записываются в `target/tmp/e2e/` и импортируют `@flick-lang/runtime` из рабочей
области. Внешний модуль рядом с примером (`./tags.mjs`) импортируется
оттуда же. `just e2e` также собирает каждый пример `tests/check/pass/**`
и запускает `node --check` для результата, а `e2e_numbers.rs` сравнивает
случайные арифметические выражения с `Float`, скомпилированные из Flick,
с теми же выражениями в JS.

## `flick test` — `flick/tests/test_command.rs`

Тест создаёт примеры проектов в `target/tmp/test_command/` и запускает для них
`flick test`. Провал утверждения, типизированная ошибка, дефект и ошибка
освобождения ресурсов выводятся отдельно. Начальное значение генератора (seed)
позволяет повторить те же значения; применяются `--filter` и `--jobs`.
В режиме `--watch` следующий запуск начинается только после того,
как предыдущий освободит ресурсы.

Стандартная библиотека объявляет все сигнатуры из спецификации дословно:
`flick-core/tests/stdlib_signatures.rs` читает их из блоков `text` русской спецификации (`ru/spec`).

## Языковые тесты — `tests/language/`

Проект на Flick, тестовые модули которого, по одному на область языка
(`Language.Ints`, `Language.Strings`, `Language.Effects`, …), закрепляют его
семантику буквальными ожидаемыми значениями: переполнение `Int`, запись чисел
через `show`, строки UTF-16, равенство, записи, образцы, рекурсию, порядок
хеш-коллекций, ошибки JSON и схем, эффекты и случаи, которые seed даёт тестам
свойств. `just language` запускает их через `flick test --emit js` и
`--emit go` с одним `--seed`; оба запуска должны пройти, а их отчёты — совпасть
байт в байт. Сюда относится тест, на котором обе цели обязаны совпадать;
расхождение между ними исправляется в среде выполнения, а не в тесте.

`flick/tests/unicode_path.rs` собирает, запускает и тестирует проект в
`target/tmp/проект ⭐` на обеих целях, как `test/unicode_path ⭐` в Gleam, и
проверяет, что карта исходников и директивы `//line` Go по-прежнему ведут
к его файлам `.fl`.

## Тесты среды выполнения — `runtime/test/`

Среда выполнения написана на TypeScript 7 (`runtime/src/*.ts`) и собирается
в `runtime/dist/` вместе с декларациями. `just e2e` проверяет её типы и типы
тестов через `tsc` в строгом режиме с `noUncheckedIndexedAccess` и
`exactOptionalPropertyTypes`, затем запускает `oxlint --type-aware` и тесты.
Проверка линтером запрещает `any`, необработанные промисы и непроверенные
утверждения о типах без пояснения рядом.

`node --test` в `runtime/` выполняет файлы `.test.ts` после сборки `dist/`;
аннотации типов удаляет сам Node. Тесты проверяют контракты адаптера напрямую
на Effect: правила восстановления `try … with`, инертные отчёты о причинах,
двухфазное закрытие владельцев, дочерние задачи и супервизоры, конкурентное
выполнение, гонки и слои, закреплённую версию Effect `4.1.2` и её матрицу
возможностей, а также соответствие кодеков скомпилированным декодерам.
Тесты модуля запуска создают дочерний процесс `runtime/fixtures/entry.ts`
и посылают ему сигналы.

## Синтаксический корпус и фаззинг — `flick-core/tests/{corpus,fuzz}.rs`

- Каждый блок ```` ```flick ```` в `docs/` должен разбираться без диагностик.
  Блоки русской спецификации (`ru/spec`), исходного текста, закреплены
  отпечатками в `tests/syntax/spec_examples.txt`: новый или изменённый пример
  приводит к ошибке теста, пока его разбор не проверен и напечатанная строка
  не добавлена в этот файл; закреплённый пример, которого больше нет,
  тоже приводит к ошибке.
- Каждый файл `.fl` в `tests/` и каждый блок документации должны проходить
  обратное преобразование через дерево без потерь, сохраняя исходный текст
  байт в байт. Примеры без диагностик должны форматироваться идемпотентно:
  повторное форматирование не меняет результат. Форматтер дополнительно
  проверяет, что AST не изменилось. Собственный корпусный тест `fmt`
  форматирует каждый файл `.fl` репозитория и падает, если результат
  не является неподвижной точкой или объявление осталось как написано,
  а `fl_sources_are_formatted` следит, чтобы исходники были отформатированы,
  кроме фикстур ошибок проверки (`tests/check/fail`, `tests/check/projects`)
  и грамматики редактора, чьи аннотации указывают на строки и столбцы.
- `tests/syntax/*.fl` проверяют только грамматику: они должны разбираться
  без диагностик, но разрешение их имён не требуется.
- `fuzz.rs` изменяет корпус и проверяет, что парсер не паникует, не зависает,
  сохраняет весь исходный текст и не выводит диапазоны за его границы,
  а проверка типов не паникует на успешно разобранных входных данных.
  `FLICK_FUZZ_ITERATIONS` задаёт число входов: 20 000 в `just check`,
  1 000 000 в ночной задаче CI (`just fuzz`).
- `DUMP=out.txt [DUMP_FILE=x.fl] cargo test -p flick-core --test corpus dump -- --ignored`
  записывает деревья примеров спецификации или одного файла для просмотра.

## Время проверки — `flick-core/tests/scaling.rs`

Тест проверяет запись из 200 полей, читаемых по одному, и функцию из 2000 строк,
а затем каждую из них в четверть размера. Проверка полного размера должна
укладываться в лимит времени, а время при изменении размера должно расти линейно.
