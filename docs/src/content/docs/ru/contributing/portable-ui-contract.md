## Задача

`ui` и `component` уже создают значения Flick `Ui`. Общее дерево JavaScript содержит теги DOM, привязки событий браузера и компоненты React. `Ui.mount_with` принимает фабрику с методом `render`, который принимает `ReactNode`. Исходники `ui` находятся в отдельном пакете для JS, а компилятор вызывает соответствующие обработчики плагина через `Std`. Чтобы выделить пакет и подключить другой рендерер, библиотека должна определять узлы и правила их жизненного цикла. Адаптерам нужны общие входные данные, которые они смогут перевести в представление своей среды. [Дерево JS](https://github.com/bondiano/flick-lang/blob/main/runtime/src/ui/react/nodes.ts) · [Фабрика рендерера](https://github.com/bondiano/flick-lang/blob/main/runtime/src/ui/react/tree.ts) · [Пакет UI](https://github.com/bondiano/flick-lang/blob/main/packages/ui/flick.toml) · [Вызов плагина](https://github.com/bondiano/flick-lang/blob/main/flick-core/src/plugin/first_party.rs)

## Узлы и рендереры

Библиотека UI определяет `Node`, объявления компонентов, типы свойств, слотов и событий, а также правила состояния компонентов. Узел описывает дерево. Его построение ничего не монтирует, не создаёт подписок и не запускает задачи событий. При рендеринге компонент может читать атомы через `Atom.Read`. Состояние создаётся при инициализации экземпляра, а запись и эффекты выполняют задачи со своим владельцем. Компилятор сохраняет общие механизмы работы с блоками, типами, эффектами, захватами и диапазонами исходного текста. Плагин UI определяет смысл своих меток и правила раскрытия компонентов и проверки вызовов. [Раскрытие `ui`](https://github.com/bondiano/flick-lang/blob/main/plugins/ui/src/block.rs) · [Раскрытие `component`](https://github.com/bondiano/flick-lang/blob/main/plugins/ui/src/component.rs) · [Проверки вызовов UI](https://github.com/bondiano/flick-lang/blob/main/plugins/ui/src/calls.rs)

Эскиз типов задаёт границу адаптера. `P` обозначает тип свойств узла, `S` — тип снимка события. Объявление элемента или компонента задаёт имя каждого слота и допустимое устройство его дочерних узлов. `RenderTree` — вычисленное дерево элементов и текста вместе с ключами и расширениями, которые поддерживает целевая среда. Среда выполнения UI раскрывает компоненты Flick и управляет их экземплярами. Адаптер получает виды событий и идентификаторы привязок. Обработчики хранятся в корне.

```text
Node = Text(String)
     | Fragment(List<Node>)
     | Element(ElementKind<P>, P, Slots<Node>, List<Binding<S>>)
     | Component(ComponentDef<P>, P, Slots<Node>)
     | Keyed(Key, Node)
     | Extension(Capability<P>, P, Slots<Node>)

Binding<S> = { event: EventKind<S>, handler: Handler<S> }
RenderBinding<S> = { id: BindingId<S>, event: EventKind<S> }
EventSink
  dispatch(BindingId<S>, S) -> AllowDefault | PreventDefault

Renderer<Target, Handle>
  mount(Target, RenderTree, EventSink) -> Result<Handle, RenderFailure>
  update(Handle, RenderTree) -> Result<Unit, RenderFailure>
  unmount(Handle) -> Result<Unit, RenderFailure>

ServerRenderer<Artifact>
  render(RenderTree, StateSnapshot) -> Result<Artifact, RenderFailure>

Hydrator<Target, Handle>
  hydrate(Target, RenderTree, EventSink) -> Hydration<Handle>

Hydration<Handle> = Attached(Handle, Reused | Rebuilt(Reason))
                  | Mismatch(Reason)
                  | Failed(RenderFailure)
```

Типы `Target` и `Handle` задаёт адаптер. Корень готовит новые экземпляры, наборы чтений и привязки для рендеринга. Адаптер владеет дескрипторами объектов среды и слушателями. При неудачном подключении он освобождает полученные ресурсы. После успешного монтирования, обновления или гидратации корень публикует подготовленные изменения и запускает задачи монтирования новых экземпляров. До этого события идут только через последние зафиксированные привязки. Каждое подключение получает свой `EventSink`. Отключённый `EventSink` или неактивная привязка возвращают `AllowDefault` и не запускают задачи. Корень однократно освобождает неиспользованное состояние инициализации и подписки на чтения. При восстановлении после несовпадения он может использовать подготовленное дерево повторно, пока исходное состояние совпадает. Если обновление завершилось ошибкой после изменения объектов среды, корень закрывает соответствующий дескриптор и сообщает об ошибке своему владельцу.

Каждая цель объявляет, какие элементы, события и расширения она поддерживает. Адаптер DOM преобразует дерево в представление React и отвечает за `ReactNode`, дескрипторы объектов браузера, классы CSS, навигацию и отмену действия браузера по умолчанию. Дерево различает экранируемый текст, безопасные URL и HTML, явно помеченный как доверенный. Сырой HTML, произвольные атрибуты DOM и внешние компоненты React доступны через возможности веб-профиля. Нативный потребитель выдаёт диагностику в исходном тексте для достижимой неподдерживаемой конструкции. Типизированный элемент он может поддержать через собственное отображение. [Действующие конструкторы UI](https://github.com/bondiano/flick-lang/blob/main/packages/ui/src/Ui.fl)

## Идентичность, состояние и владение событиями

- **Идентичность.** Соседние узлы сопоставляются в пределах одного родителя и слота. Для узла с ключом учитываются явный ключ и вид элемента либо объявление компонента. Для узла без ключа учитываются позиция среди соседей и вид элемента либо объявление. Фрагмент группирует дочерние узлы для сопоставления и обходится без отдельного элемента среды. Ключи должны быть уникальны среди соседей с ключами в пределах слота. Дубликат вызывает ошибку рендеринга при этом обновлении. Изменение свойств и перестановка соседей с ключами сохраняют их экземпляры. Смена вида, ключа или родителя, как и удаление узла, завершает экземпляр. При повторной вставке создаётся новый. Ключ экземпляра, идентификатор объявления у компилятора и ключ сериализации атома обозначают разные сущности.
- **Состояние.** Вызывающая сторона предоставляет реестр для корня или запроса. Экземпляр владеет состоянием, созданным при инициализации, и подписками. При рендеринге регистрируются чтения атомов, включая зависимости производных атомов. Когда дерево фиксируется, набор чтений представления заменяется и проверяется, была ли запись между чтением и подпиской. Изменённое значение вызывает ещё один проход рендеринга. При удалении экземпляра освобождаются его подписки и локальное состояние. Атом, предоставленный внешней областью, живёт столько же, сколько эта область.
- **События.** Адаптер копирует типизированный снимок события, пока действителен обратный вызов среды. При диспетчеризации веб-события корень синхронно выполняет чистый предикат `prevent_default` и возвращает решение адаптеру до завершения обратного вызова. Идентификатор привязки сохраняется между обновлениями для того же экземпляра узла и слота события. Новые события принимает последний зафиксированный обработчик. При пересоздании замыкания обработчика выполняемые и ожидающие задачи привязки сохраняются. У обычного обработчика состояние политики принадлежит привязке. Все использования одного `Action` в пределах корня разделяют его состояние политики, а `Action.with` даёт каждой привязке собственное. `exhaust` игнорирует события, пока обработчик занят. `latest` прерывает предыдущий запуск и дожидается его окончания перед запуском последнего события. `queue` и `concurrent` соблюдают свои ограничения и сообщают о превышении супервизору корня. При удалении привязка перестаёт передавать события, а её собственная очередь сбрасывается. Очередь общего действия остаётся у владельца действия. Запущенные задачи остаются у своего владельца, корня или экземпляра. Когда владелец закрывается, он прерывает задачи и дожидается их завершения. [Действующие правила событий](../../reference/ui/#обработчики-и-политики) · [Тесты подписок на атомы](https://github.com/bondiano/flick-lang/blob/main/packages/effect-ts/test/ui-atoms.test.ts) · [Тесты `Action`](https://github.com/bondiano/flick-lang/blob/main/packages/effect-ts/test/ui-actions.test.ts)

Решатель может публиковать согласованный снимок через ту же границу чтения и записи. Читатели снимка и подписки подчиняются правилам владения экземплярами. Идентичность ограничений и их решение относятся к [#478](https://github.com/bondiano/flick-lang/issues/478).

## Серверный рендеринг, гидратация и закрытие

Запрос владеет реестром и работой потока. Сервер рендерит с этим реестром и формирует снимок для указанного корня. Каждая запись атома использует его ключ сериализации и кодек. При серверном рендеринге можно читать атомы и вычислять представления. Клиентские обработчики и задачи монтирования экземпляров запускаются только на клиенте. Поток передаёт состояние до разметки, которая его использует. При завершении или отмене потока освобождаются его подписки. Обычный рендерер HTML может сформировать артефакт без подключения на клиенте. [Серверный API](https://github.com/bondiano/flick-lang/blob/main/packages/ui/src/Ui/Server.fl) · [Тесты потокового рендеринга на RT](https://github.com/bondiano/flick-lang/blob/main/runtime/test/rt-ui-stream.test.ts)

Клиент проверяет начальный снимок для своего корня до применения любой записи. Он принимает действительный снимок один раз, применяет его до первого рендеринга и использует те же начальные входные данные и ключи, что и сервер. Корень UI определяет, когда попытка подключения может передавать события и запускать задачи монтирования.

| Результат | Поведение корня |
| - | - |
| Адаптер использует серверное дерево | Зафиксировать одно действующее подключение и сохранить поддерживаемый ввод, сделанный до запуска, а также фокус и выделение. Адаптер браузера может перенести этот ввод в состояние Flick. |
| Дерево не совпадает, снимок действителен | Сообщить, в каком корне возникла проблема и почему. Адаптер освобождает ресурсы неудачной попытки подключения и возвращает `Mismatch`. Корень один раз монтируется заново в том же контейнере со своим уже инициализированным реестром. Состояние браузера, которое хранилось только в заменённом DOM, сбрасывается. Адаптер, который гарантирует тот же результат, может вернуть `Rebuilt` с причиной для диагностики. Корень использует это подключение напрямую. |
| Снимок недействителен или принадлежит другому корню | При несовместимых записях в снимке для этого корня выдаётся диагностика и выполняется новое монтирование с клиентской инициализацией. Ни одна запись из такого снимка не применяется. Снимок для другого корня остаётся у своего владельца. Клиент продолжает гидратацию без снимка, только если профиль позволяет восстановить то же начальное состояние. |
| Ошибка адаптера или единственной попытки нового монтирования | Передать ошибку через канал ошибок корня, освободить полученные ресурсы и завершить работу корня. |

Новое монтирование или результат `Rebuilt` прекращает доставку исходного потока, даже если первое подключение так и не стало действующим. Корень сохраняет уже применённое проверенное состояние. После фиксации дерева он перезапускает незавершённые загрузки средствами клиентской инициализации. Последующие фрагменты оставленного потока игнорируются. Каждый фрагмент состояния действующего потока корень проверяет целиком до применения. При несовместимости он сообщает об ошибке, не применяет ни одной записи и завершает поток. Действующее дерево сохраняет последнее зафиксированное состояние и перезапускает незавершённые загрузки. При восстановлении уже принятый снимок не применяется повторно, а события из оставленного подключения не передаются. При совпадении дерева действующая гидратация сохраняет черновики, введённые в браузере до запуска. При несовпадении адаптер DOM полагается на React. [Адаптер DOM](https://github.com/bondiano/flick-lang/blob/main/runtime/src/ui/dom.ts) · [Тесты гидратации](https://github.com/bondiano/flick-lang/blob/main/packages/effect-ts/test/ui-hydration.test.ts) · [Гидратация в React](https://react.dev/reference/react-dom/client/hydrateRoot)

При закрытии корень сначала прекращает передачу событий и отклоняет дальнейшие фиксации дерева. Затем он отключает своих наблюдателей потока и просит адаптер размонтировать дерево. При размонтировании или откате адаптер снимает своих слушателей и освобождает ресурсы среды, в том числе при ошибках. Корень освобождает подписки экземпляров, сбрасывает ожидающие события, прерывает собственные задачи и дожидается завершения задач и супервизоров до того, как внешняя область освободит ресурсы. За освобождение переданного реестра отвечает вызывающая сторона. При частичном монтировании те же правила применяются к полученным ресурсам. Повторное закрытие безопасно. Ошибка очистки не отменяет освобождение остальных ресурсов. [Закрытие корня](https://github.com/bondiano/flick-lang/blob/main/runtime/src/rt/ui/react.ts#L176-L183) · [Тесты жизненного цикла корня](https://github.com/bondiano/flick-lang/blob/main/packages/effect-ts/test/ui-roots.test.ts)

## Проверенные сведения для нативных целей

Эти сведения собираются после раскрытия блоков и проверки типов, пока доступны метки, типы и диапазоны исходного текста. Нативный потребитель получает их до понижения вызовов UI в общее промежуточное представление или привязки к внешним функциям. Плагин UI распознаёт конструкции по проверенным меткам, а компилятор предоставляет типы, эффекты и диапазоны. По этим сведениям профиль цели определяет, поддерживается ли конструкция. Отображение в целевую среду отдельно учитывает идентичность, время жизни и зависимости. [Сведения о вызовах](https://github.com/bondiano/flick-lang/blob/main/flick-plugin/src/facts.rs) · [Контракт проекций бэкенда](https://github.com/bondiano/flick-lang/blob/main/docs/backends/contract.md) · [Идентичность и время жизни в SwiftUI](https://developer.apple.com/videos/play/wwdc2021/10022/)

| Проверенные сведения | Для чего они нужны потребителю |
| - | - |
| Идентификатор объявления компонента, типы свойств и слотов, операции над элементами и дочерними узлами, выражения ключей | Выбрать представление или виджет, типизировать его входы и сохранить правила идентичности при обновлении. |
| Состояние, объявленное при инициализации, чтения при рендеринге, привязки чтения и записи, объявления наблюдения и монтирования | Определить время жизни хранилища и подписок. Динамические подписки определяются фактическими чтениями при рендеринге. |
| Тип события и его снимок, сигнатура действия и требуемые эффекты, политика и владелец, экземпляр или корень | Привязать событие и запускать его действие с теми же правилами владения и параллелизма. |
| Версия модели, метки возможностей и диапазоны объявлений и использований | Проверить поддержку профилем и указать в диагностике место использования неподдерживаемой конструкции. |

Для счётчика с текстом, кнопкой, типизированным действием и атомом достаточно этих сведений, если профиль поддерживает нужные примитивы. `for` с ключом, который обходит значения времени выполнения, сохраняет типизированное вычисление дочернего узла и выражение ключа. Для рендеринга такого списка профиль должен поддерживать эту операцию. Непрозрачному компоненту React нужна веб-совместимость. Нативный профиль без такой возможности указывает в диагностике помеченный вызов в исходном тексте. Один из вариантов передачи этих сведений — версионированная проекция результатов проверки в `BuildRequest`. [Нативные метаданные #496](https://github.com/bondiano/flick-lang/issues/496)

| Пример | Ожидаемый результат |

| **Счётчик.** Смонтировать текст и кнопку с типизированным действием `exhaust`. Передать один щелчок и обновить атом. | Текст меняется с `0` на `1`. При построении узла действия не запускаются. Монтирование регистрирует одну привязку, после освобождения ресурсов действующих привязок нет. Нейтральные входы включают узел, снимок события и операции с состоянием. Удалить эту строку и вставить под новым ключом. | Оба зависимых представления получают обновление. Чтения независимого представления не требуют его обновления. Изменение свойств и перестановка сохраняют локальное состояние при прежнем ключе. Удаление освобождает подписки, а новый ключ получает новое состояние экземпляра. [Тестовый пример с атомами](https://github.com/bondiano/flick-lang/blob/main/tests/run/ui/atoms.fl) · [Пример с ключами](https://github.com/bondiano/flick-lang/blob/main/docs/tour/app/app-ui.fl) |
| **SSR и гидратация.** Отрендерить корень A с `count = 5` и корень B с `count = 9`. Передать каждый снимок соответствующему корню. Изменить серверную разметку только корня A, чтобы получить несовпадение. | B начинает с `9` и использует свою разметку. A сообщает о несовпадении и получает одно действующее подключение, которое показывает `5`. Первый щелчок выполняется один раз и меняет значение на `6`. Повреждённый снимок для A приводит к клиентской инициализации. После закрытия корня действующих обратных вызовов и наблюдателей нет. При приёмке рендерера проверить ещё четыре перехода.

- Отрисовать кнопку повторно, пока работает её обработчик `exhaust`, и передать ещё один щелчок. Сохранённая привязка игнорирует его, пока обработчик занят.
- Завершить начальное монтирование ошибкой после получения ресурса среды и доставки преждевременного события. Событие не запускает задачу. Полученные ресурсы среды и инициализации освобождаются один раз, вызывающая сторона получает сообщение об ошибке.
- Заменить корень, которому ещё идут фрагменты потока и у которого осталась незавершённая загрузка. Клиент перезапускает загрузку один раз. Поздний фрагмент сервера не меняет новое дерево. Передать действующему потоку фрагмент с одной недействительной записью и проверить, что ни одна его запись не применяется.
- Закрыть корень с работающим обработчиком и событием в очереди. Обработчик завершает очистку до освобождения ресурсов внешней области. Событие в очереди не запускается. Повторное закрытие не освобождает ресурсы ещё раз. [Тесты жизненного цикла корня](https://github.com/bondiano/flick-lang/blob/main/packages/effect-ts/test/ui-roots.test.ts)

## Рассмотренные варианты

**Сохранить фабрику рендерера React.** Это сохраняет существующую точку расширения при небольшом объёме миграции. Каждому потребителю тогда нужен вход в представлении React, на границе которого теряются проверенные сведения для нативных целей.

**Использовать HTML или дерево DOM для обмена.** Это даёт SSR общий артефакт. Идентичность компонентов, типизированные действия и нативные слоты потребовали бы второй модели или восстановления из деталей браузерного представления.

**Использовать типизированные узлы библиотеки и возможности целевых сред.** Счётчик, атомы и SSR получают общую модель. Для каждой среды нужно собственное отображение и явное объявление платформенных расширений. Каждый адаптер может сохранить свой алгоритм рендеринга.
