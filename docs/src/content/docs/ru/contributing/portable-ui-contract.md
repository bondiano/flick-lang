Этот проект заменяет решения, записанные для [#473](https://github.com/bondiano/flick-lang/issues/473): атомы как модель состояния, рендерер, получающий дерево целиком, и адаптер DOM на React. Он задаёт интерфейсы и поведение для работы в [эпике #385](https://github.com/bondiano/flick-lang/issues/385) и метаданные для нативных целей из [#496](https://github.com/bondiano/flick-lang/issues/496).

## Задача

Сейчас UI во Flick — типизированный слой над React 19, который работает только на цели JS. Состояние хранится в атомах. Представление становится мемоизированным компонентом React и подписывается на атомы, прочитанные при отрисовке. Обработчик — задача под супервизором, которая пишет атомы по политике события. Дерево узлов несёт теги DOM и пропсы React, `Ui.mount_with` принимает фабрику рендерера React, а рантайм существует в двух копиях: на основном рантайме и на адаптере Effect. Go и Lua UI не поддерживают. [Дерево JS](https://github.com/bondiano/flick-lang/blob/main/runtime/src/ui/react/nodes.ts) · [Представления на rt](https://github.com/bondiano/flick-lang/blob/main/runtime/src/rt/ui/views.ts) · [Копия в адаптере](https://github.com/bondiano/flick-lang/tree/main/packages/effect-ts/src/ui) · [Пакет UI](https://github.com/bondiano/flick-lang/blob/main/packages/ui/flick.toml)

Три цели требуют другого ядра:

- Типизированный журнал сообщений: повтор, перемотка во времени, тесты без браузера и инструменты разработчика, к которым могут обращаться агенты.
- Нативные приложения на SwiftUI и Compose, мост которых передаёт данные, а не живые подписки.
- Одно небольшое ядро на Flick, которое работает на JS, Go, Lua и VM. Платформенным кодом остаются только операции хоста.

## Компоненты и сообщения

Каждый экземпляр компонента выполняет свой цикл. У него есть Model, тип сообщений, чистый `update`, `view` и его `subscriptions`. Сообщение попадает только в `update` того экземпляра, которому его отправили. Родитель никогда не хранит Model ребёнка и не отправляет ребёнку сообщений: он передаёт пропсы вниз и получает сообщения, которые испускает ребёнок, через заданное им отображение. У каждого экземпляра своя дочерняя область. В ней выполняются его команды, подписки и подключённые сервисы, а закрытие области их завершает. Каждый ребёнок — граница отказа: упавший ребёнок показывает запасной вид, пока не сменится его ключ.

Набросок ниже — синтаксис плагина, поэтому [заморозка синтаксиса ядра](https://github.com/bondiano/flick-lang/issues/944) на него не распространяется. Model и Msg — обычные типы.

```text
type Model = { count : Int, pending : Bool }
type Msg = Increment | ResetLater | ResetDone

command reset_after (delay : Duration) : {Clock} Unit   // policy: exhaust

component counter (start : Int) =
  init = { count = start, pending = false }
  update model msg = match msg
    | Increment  -> { model with count = model.count + 1 }
    | ResetLater -> ({ model with pending = true }, [reset_after 1s |> done ResetDone])
    | ResetDone  -> { count = 0, pending = false }
  view model = ui {
    stack { gap = Space.s }
      text (show model.count)
      button { on_click = Increment } (text "+1")
      button { on_click = ResetLater; disabled = model.pending } (text "Reset")
  }
```

- **update.** Его тип — `Model -> Msg -> Next Model Msg r`, где `Next` — либо одна Model, либо Model с командами. Он не выполняет эффектов. Плагин проверяет, что `match` исчерпывающий.
- **Обработчики.** Обработчик в представлении чистый: это сообщение (`on_click = Increment`) или функция из снимка события в сообщение (`on_input = fun e -> Typed e.value`). Он не запускает задач, поэтому в строке эффектов представления нет `Async`.
- **Команды.** Команда — именованное объявление верхнего уровня со списком аргументов, типом результата, строкой эффектов и политикой: `exhaust`, `latest`, `queue n` или `concurrent n`. Её имя берётся из привязки, а результат отображается в сообщение. Состояние политики принадлежит экземпляру и команде. `exhaust` игнорирует новый запуск, пока предыдущий занят. `latest` прерывает предыдущий запуск, дожидается его и запускает самый новый. `queue` и `concurrent` соблюдают свои границы, а о переполнении узнаёт супервизор экземпляра. Удаление экземпляра прерывает его запуски и дожидается их.
- **Подписки.** `subscriptions model` возвращает список источников с ключами: таймеры, сокеты, URL или хранилище. После каждого обновления рантайм сравнивает ключи. Он запускает новые ключи, останавливает удалённые и сохраняет источник, ключ которого остался. Каждое значение источника — сообщение, поэтому журнал его записывает.

## Хранилища и сервисы

Во Flick один механизм состояния: Model, которую меняют сообщения. Общее состояние — **хранилище** (store): сервис с Model, сообщениями и `update`, но без представления. Компонент читает хранилище в представлении через эффект чтения хранилища и отправляет хранилищу сообщения из команд. Компонент-провайдер — это компонент, который подключает хранилище для своих детей.

```text
store Cart =
  init = { items = [] }
  update model msg = match msg
    | Added item -> { model with items = item :: model.items }

Cart.count : () ->{Cart.Read} Int      // read in a view; holes track it
Cart.send  : Cart.Msg ->{Cart.Write} Unit   // used inside commands

component shop () =
  view _ = ui {
    provide Cart.layer
      header ()      // reads Cart.count
      catalog ()     // a command sends Cart.Added
  }
```

- **Типизированное внедрение.** Тип компонента несёт строку эффектов, которые нужны для чтений его представления, его команд и подписок. Родитель закрывает часть этой строки через `provide` на своём поддереве, иначе требование переходит в строку самого родителя. `mount` и серверный рендерер получают остаток, поэтому отсутствующий сервис — ошибка типов при монтировании, а не сбой во время выполнения.
- **Время жизни.** Хранилище живёт столько же, сколько область, которая его подключила: экземпляр, маршрут, корень или запрос на сервере. Оно закрывается, когда это поддерево размонтируется. Побеждает ближайший провайдер. Код обращается к хранилищу только через его эффект, поэтому ни один дескриптор не переживёт область.
- **Внешние источники.** Маршрут, хранилище браузера, параметры поиска и потоки сервера приходят как подписки. Кэш запросов — сервис-хранилище. Он держит одну запись на запрос и ключ аргументов, удаляет запись через время простоя после ухода последнего читателя и принимает инвалидацию из команд. Неудачная загрузка — это значение; сам кэш её не повторяет.
- **Маршрутизация и формы.** Типизированный маршрутизатор — хранилище, которое питает подписка на URL, с элементом ссылки. `deriving Form` генерирует Model, сообщения и `update` полей формы и их проверки. Оба относятся к пакету UI, поэтому клиентскому приложению не нужен серверный фреймворк.

## Представления

Представление возвращает дерево переносимых элементов. Базовый словарь — то, что поддерживает любой хост: `text`, `button`, `input`, `stack`, `row`, `list`, `image`, `link`, `scroll` и `keyed`. Теги HTML, сырые атрибуты и явно доверенный HTML относятся к модулю-возможности `Web`. Нативный профиль или терминальный хост сообщает о достижимой конструкции `Web` в месте её использования. Дерево по-прежнему различает экранированный текст, безопасные URL и доверенный HTML.

Раскладка и стиль — типизированные пропсы: направление, промежуток, отступы, выравнивание, токены цвета и размера. Каждый хост переводит их сам: DOM — в переменные и классы CSS, терминал — в свойства блоков, SwiftUI — в модификаторы, Compose — в `Modifier`. Строка `class` или таблица стилей — возможность `Web`. Позже решатель ограничений сможет задавать раскладку через те же пропсы. [Системы ограничений #386](https://github.com/bondiano/flick-lang/issues/386)

**Шаблоны с дырками.** Плагин UI компилирует каждый блок `ui {}` в статический шаблон и список дырок. Дырка — это текст, атрибут или пропс, привязка события, ребёнок или список с ключами. Каждая дырка записывает пути, которые она читает в Model, пропсах и хранилищах. Доступ к полю вроде `model.count` даёт статический путь. Любое другое выражение трассируется при вычислении дырки. После обновления рантайм сравнивает старые и новые значения по записанным путям; модели неизменяемы, поэтому это одна проверка ссылки на поле. Затем он вычисляет только дырки, пути которых изменились. Список с ключами сравнивает строки по ключу и обновляет только изменившиеся строки. Статическая структура никогда не сравнивается.

**Правило согласованности.** Для любых значений Model, хранилищ и пропсов применение изменившихся дырок к смонтированному шаблону даёт то же дерево, что и отрисовка представления с нуля. Отслеживание путей — оптимизация, которая никогда не должна менять то, что видит пользователь.

## Интерфейс хоста

Хост реализует операции над узлами. Рантайм управляет ими по шаблонам и дыркам.

```text
Host<Node>
  createElement(ElementKind) -> Node
  createText(String) -> Node
  setText(Node, String)
  setAttr(Node, Name, Option<String>)
  setProp(Node, Name, Value)
  insertBefore(parent: Node, node: Node, ref: Option<Node>)
  remove(Node)
  setEvents(Node, List<RenderBinding>, EventSink)
  commit()                                   // once per flush and after mount
  supports: ElementKinds, Events, Capabilities
  // optional
  clone(Template) -> Node                    // e.g. a cloned <template> on the DOM
  adopt(Node, Template) -> Adoption          // hydration: reuse existing nodes

RenderBinding = { id: BindingId, event: EventKind<S> }
EventSink.dispatch(BindingId, S) -> AllowDefault | PreventDefault
```

Хост владеет своими дескрипторами и слушателями. Привязка хранит обработчик как данные. Хост вызывает `dispatch` для самого внутреннего элемента с обработчиком этого события. Хост копирует типизированный снимок, пока его обратный вызов действителен. Отправка синхронно вычисляет чистый предикат `prevent_default` и возвращает решение до возврата из обратного вызова. Отозванный приёмник или неактивная привязка не отправляет сообщения и возвращает `AllowDefault`. Хост освобождает приобретённое при размонтировании и откатывает неудачное подключение, в том числе на путях ошибок.

Императивные хосты — DOM, запись HTML на сервере, тестовый хост в памяти, терминал и фреймы World of Warcraft. SwiftUI и Compose этот интерфейс не реализуют. Они получают проверенные факты, описанные ниже, и генерируют собственные представления.

## Идентичность, владение и закрытие

- **Идентичность.** Соседние узлы сопоставляются внутри одного родителя и слота. Узел с ключом сопоставляется по явному ключу и виду элемента или объявлению компонента. Узел без ключа сопоставляется по позиции и виду. Путь экземпляра — цепочка имён компонентов и ключей от корня, `Name[key]`. Второй ребёнок без ключа того же компонента в одной позиции — ошибка отрисовки для этого обновления. Смена пропсов или перестановка соседей с ключами сохраняет их экземпляры и Model. Смена вида, ключа или родителя либо удаление узла завершает экземпляр, а повторная вставка начинает новый с `init`.
- **Доставка.** Сообщения одному экземпляру применяются в порядке отправки, по одному `update` за раз. После пачки обновлений рантайм применяет изменившиеся дырки за один сброс, родителей раньше детей, и затем вызывает `commit`. Ребёнок с неизменными пропсами сохраняет свои дырки.
- **Владение.** Каждый экземпляр владеет своей Model, подписками, запусками команд и подключёнными им хранилищами. Начатые команды остаются за своим экземпляром. Закрытие экземпляра прерывает их и дожидается их завершения, прежде чем его область освободит ресурсы.
- **Закрытие.** Закрытие корня сначала останавливает отправку событий и отклоняет дальнейшие сбросы. Оно отключает наблюдателей потоков и просит хост размонтировать дерево. Затем закрывает экземпляры от листьев вверх: подписки, сообщения в очереди, запуски команд, затем подключённые хранилища. Перед освобождением ресурсов объемлющей области оно дожидается задач и супервизоров. Закрытие идемпотентно, и сбой очистки не пропускает следующие освобождения. Частичное монтирование соблюдает тот же порядок для уже существующих ресурсов.

## Отрисовка на сервере и гидратация

Сервер отрисовывает шаблоны прямо в разметку. Статические части сериализуются заранее, а дырки записываются по мере вычисления. Серверная отрисовка вычисляет `init`, обновления от загрузок на стороне сервера и представления. Клиентские обработчики, подписки и команды монтирования запускаются только на клиенте. Запрос владеет областью своих хранилищ и работой потока.

**Снимок** для идентифицированного корня содержит Model каждого отрисованного на сервере экземпляра по пути, Model хранилищ, подключённых в этом корне, и записи кэша запросов, которые прочитала отрисовка. Кодеки выводятся из типов, поэтому автор их не пишет. Поле Model или хранилища, которое нельзя сериализовать, например функция или дескриптор, — ошибка компиляции в месте использования компонента под серверной отрисовкой. Компонент с пометкой `client_only` отрисовывает на сервере заглушку и начинает с `init` на клиенте. Потоковый результат доставляет состояние раньше разметки, которая его использует. Завершение или отмена потока освобождает его подписки.

Клиент проверяет снимок корня до применения любой записи. Он применяет снимок один раз, до первой отрисовки, с теми же пропсами и ключами, что и сервер. Гидратация обходит существующие узлы через `adopt` и сверяет их структуру с шаблонами.

| Результат | Поведение корня |
| - | - |
| Хост принимает узлы сервера | Зафиксировать одно живое подключение. Сохранить поддерживаемые ввод, фокус и выделение до загрузки и разрешить хосту DOM перенести этот ввод в Model сообщениями. |
| Структура не совпадает, снимок корректен | Сообщить корень и причину. Хост освобождает приобретённое неудачным подключением. Корень делает одно новое монтирование в тот же контейнер с уже применёнными Model. Состояние браузера, которое жило только в заменённых узлах, сбрасывается. |
| Снимок некорректен или принадлежит другому корню | О снимке для этого корня с несовместимой записью сообщается, и ни одна его запись не применяется. Корень монтируется заново с `init`. Снимок, адресованный другому корню, остаётся у своего владельца. |
| Хост падает или падает единственное новое монтирование | Сообщить об отказе через канал ошибок корня, освободить приобретённые ресурсы и завершить корень. |

Повторное монтирование завершает исходную доставку потока, даже если первое подключение так и не стало живым. Поздние фрагменты брошенного потока игнорируются. Корень проверяет каждый живой фрагмент состояния целиком. О несовместимом фрагменте сообщается, ни одна его запись не применяется, и этот поток завершается. Дерево сохраняет последнее зафиксированное состояние, а незавершённые загрузки перезапускаются с клиента. Восстановление никогда не применяет снимок дважды и не отправляет событие из брошенного подключения.

## Журнал сообщений и инструменты

Рантайм ведёт один журнал на корень. Запись содержит путь экземпляра, сообщение и его источник (обработчик, результат команды, подписка или хранилище), запущенные им команды, а также момент и исход завершения каждого запуска. Model в записи не копируются. Model на момент записи вычисляется свёрткой `update` по журналу от последнего снимка.

- **Тесты Story** выполняются на тестовом хосте в памяти. Тест задаёт Model, отправляет сообщение, ожидает команды, которые вернул `update`, и разрешает команду сообщением, которое дал бы её результат. Ни один эффект не выполняется. Тесты Scene добавляют представление: находят элементы по роли или подписи, нажимают или вводят текст и проверяют содержимое. Тесты Play выполняют настоящие команды на тестовых часах.
- **Повтор.** Записанная сессия — тестовая фикстура. Повтор на тестовом хосте проверяет, что те же сообщения дают те же Model и команды.
- **Инструменты разработчика.** `flick dev` показывает журнал, причинную цепочку сообщения, Model, пропсы и чтения хранилищ каждого экземпляра на любой записи, а также перемотку во времени: страница отрисовывается на выбранной записи и возвращается к живому состоянию.
- **MCP.** Сервер разработки открывает журнал агентам только на loopback: список сессий, экземпляров и записей, запись или её цепочка, состояние на записи и его разница, показ записи, возврат к живому состоянию, JSON Schema сообщений экземпляра, ожидание запусков команд и отправка сообщений. Схема сообщений выводится из типа. Отправка выключена, пока её не включат.

## Проверенные факты для нативных целей

Эти факты собираются после раскрытия и проверки типов, пока доступны метки, типы и диапазоны исходника. Нативный потребитель видит их до того, как вызовы UI станут обычным IR. Профиль цели решает по ним, что поддерживается, и сообщает о неподдерживаемой конструкции в месте её использования. [Проверенные факты вызовов](https://github.com/bondiano/flick-lang/blob/main/flick-plugin/src/facts.rs) · [Контракт проекции бэкенда](https://github.com/bondiano/flick-lang/blob/main/docs/backends/contract.md)

| Проверенный факт | Потребитель SwiftUI | Потребитель Compose |
| - | - | - |
| ID объявления компонента, типы пропсов и слотов, виды элементов, ключи | `View` на компонент, `ForEach` со стабильными ID | `@Composable` на компонент, `key` в ленивых списках |
| Типы Model и Msg, функция `update` | `@Observable`-модель, которой владеет нативное ядро; сообщения как перечисления Swift | Держатель состояния, которым владеет нативное ядро; сообщения как sealed-классы |
| Дырки шаблона и пути их чтения | Чтения свойств, которые отслеживает наблюдение SwiftUI | Чтения состояния, которые отслеживает рекомпозиция |
| Команды со строками эффектов и политиками, подписки | Выполняются в ядре Flick; мост их не запускает | Выполняются в ядре Flick; мост их не запускает |
| Объявления хранилищ, точки подключения, эффекты чтения | Значения окружения в пределах поддерева | `CompositionLocal` в пределах поддерева |
| Пропсы стиля и токены, теги возможностей, версия модели, диапазоны исходника | Модификаторы; проверка профиля | `Modifier`; проверка профиля |

Мост передаёт **сообщения внутрь и снимки наружу**. Нативное представление отправляет значение сообщения через ABI. Ядро Flick применяет `update`, выполняет команды и публикует версионированный снимок изменившихся путей. SwiftUI вызывает ядро через ABI Swift на главном акторе, Compose — через JNI. Ни одна сторона не держит независимо изменяемую копию Model. Возможность web или тег HTML эти профили отклоняют в месте исходника. Версионированная проекция проверки в `BuildRequest` — кандидат на транспорт. [Нативные метаданные #496](https://github.com/bondiano/flick-lang/issues/496) · [Мост Apple #498](https://github.com/bondiano/flick-lang/issues/498)

## Хосты и бэкенды

Ядро UI написано на Flick поверх ядра примитивов, и только операции хоста остаются внешним кодом. Поэтому один и тот же цикл, команды, хранилища и шаблоны работают на каждом бэкенде.

| Бэкенд | Хосты первой вехи |
| - | - |
| JS | DOM, HTML на сервере с потоком и гидратацией, терминал |
| VM | Тестовый хост в памяти для Story, Scene и повтора; REPL |
| Go | HTML на сервере |
| Lua | Фреймы World of Warcraft поверх помощников событий, таймеров и пулов из [#842](https://github.com/bondiano/flick-lang/issues/842) |
| Swift, Kotlin | Сгенерированные представления SwiftUI и Compose поверх нативного ядра, по проверенным фактам |

Headless-набор в пакете UI даёт поведение клавиатуры, фокуса и ARIA для select и listbox, вкладок, поля и формы, диалога, меню, всплывающей панели, combobox, уведомления, подсказки, флажка, переключателя и радиокнопки. Разметку и стиль задаёт автор.

## Примеры приёмки

| Пример | Ожидаемые наблюдения |
| - | - |
| **Счётчик.** Смонтировать подпись и кнопку, нажатие которой отправляет `Increment`. Нажать один раз. | Подпись меняется с `0` на `1`. Построение дерева не отправляет сообщений. Монтирование регистрирует одну привязку, сброс затрагивает одну текстовую дырку, а закрытие оставляет ноль живых привязок. В журнале одна запись. [Фикстура счётчика](https://github.com/bondiano/flick-lang/blob/main/tests/run/ui/counter.fl) |
| **Строки с ключами.** Переставить две строки с ключами, сменить пропсы одной строки, затем удалить её и вставить снова под новым ключом. | Перестановка и пропсы сохраняют оба экземпляра и их Model. Обновляются только дырки изменившейся строки. Подписки и запуски команд удалённой строки завершаются, а новый ключ начинает с `init`. [Пример с ключами](https://github.com/bondiano/flick-lang/blob/main/docs/tour/app/app-ui.fl) |
| **Общее хранилище.** Подключить хранилище корзины над двумя поддеревьями. Команда в одном поддереве отправляет `Added`. | Обновляются только дырки, которые читают число товаров, в обоих поддеревьях. Компонент вне провайдера, который читает корзину, не проходит проверку типов. Размонтирование провайдера закрывает хранилище один раз. |
| **SSR и гидратация.** Отрисовать корень A с `count = 5` и корень B с `count = 9`, затем изменить только серверную разметку A. | B принимает свои узлы и начинает с `9`. A сообщает о расхождении и заканчивает одним живым подключением, которое показывает `5`. Первое нажатие показывает `6` и применяется один раз. Испорченный снимок для A даёт новое монтирование с `init`. [Фикстура SSR](https://github.com/bondiano/flick-lang/blob/main/tests/run/ui/server.fl) |
| **Повтор.** Записать сессию из трёх нажатий и одной разрешённой команды, затем повторить её на тестовом хосте. | Повтор даёт те же Model и те же запуски команд в том же порядке и не выполняет эффектов. |

Приёмка также проверяет четыре перехода жизненного цикла:

- Перерисовать кнопку, пока выполняется её команда `exhaust`, и нажать снова. Сообщение нажатия применяется, а команда не начинает второй запуск.
- Уронить начальное монтирование после того, как хост приобрёл узел и доставил преждевременное событие. Событие не отправляет сообщения. Хост и экземпляр освобождают ресурсы один раз, а об отказе сообщается.
- Заменить потоковый корень с незавершённой загрузкой. Клиент перезапускает загрузку один раз, а поздний фрагмент сервера не меняет новое дерево. Живой фрагмент с одной некорректной записью не применяет ни одной записи.
- Закрыть корень с выполняющейся командой и сообщением в очереди. Команда завершает очистку до освобождения ресурсов объемлющей области. Сообщение из очереди не применяется, а повторное закрытие ничего не освобождает.

## Формальные обязательства

Эталонная модель исполняет рантайм UI: доставку сообщений каждому экземпляру, политики команд, ключи подписок, время жизни хранилищ и областей, порядок закрытия и решение при гидратации. Lean формулирует и доказывает на модели четыре свойства:

- Свёртка `update` по записанному журналу даёт записанные Model и запуски команд.
- Каждый приобретённый ресурс освобождается ровно один раз при закрытии, восстановлении после расхождения или неудачном монтировании.
- Инварианты политик выполняются: у команды `exhaust` не больше одного запуска, у `latest` не больше одного запуска, очереди соблюдают свои границы.
- Правило согласованности выполняется: обновления дырок дают то же дерево, что и полная отрисовка представления.

Доказательство на модели не доказывает корректность компилятора или рантаймов. Дифференциальные тесты сравнивают каждый рантайм с моделью.

## Миграция

Новое ядро, хосты и плагин строятся рядом с доступным API под внутренними именами. Затем одно изменение переключения переводит всех потребителей: виджеты сайта, playground, главную страницу, тур, курс, клиент Conduit, фикстуры и нагрузочный тест SSR. То же изменение удаляет атомы, React и старые правила плагина. Слоя совместимости нет.

| Доступный API | Замена |
| - | - |
| `Atom.make`, `Atom.local`, setup в `Ui.stateful` | Поле Model и `init` |
| `Atom.derived` | Выражение в представлении, которое отслеживают пути дырок |
| `Action.*`, `Ui.Event.*` | Политика команды и чистый обработчик, возвращающий сообщение |
| `Atom.query`, `loader`, `mutation`, `query_stream` | Хранилище запросов, команды и подписки |
| `Atom.route`, `Ui.route_link` | Хранилище маршрутизатора и его ссылка |
| `Atom.stored`, `search_param`, `on_server`, `client_only` | Подписки и команды хоста; `client_only` у компонента |
| `Atom.serializable*` | Кодеки, выведенные для Model и хранилищ |
| `Form` | `deriving Form`, который генерирует Model, Msg и `update` |
| `Ui.Document` (focus, scroll, measure) | Команды хоста |
| `Ui.Dom.mount`, `Ui.Server.*` | Монтирование на хосте и серверный рендерер |
| `Ui.component`, `Ui.Renderer`, `Ui.mount_with`, `[target.js] ui` | Удаляются. Взаимодействие с React не планируется |

Элементы языка для UI уходят из компилятора. Эффект чтения представления и регион setup становятся обычными сервисами и эффектами. Плагин переезжает из стандартного плагина в пакет UI. Диагностики с U001 по U007 явно выводятся из употребления или заменяются, и их коды не переиспользуются с другим смыслом. [Выделение пакета #474](https://github.com/bondiano/flick-lang/issues/474)

## Рассмотренные варианты

**Атомы с наборами чтений (прежний проект).** Точечные обновления и уже доступный API. Записи происходят внутри задач с эффектами, поэтому нет полного журнала сообщений и повтора без выполнения эффектов, а нативному мосту пришлось бы передавать динамические подписки.

**Зависимость от готовой библиотеки MVU на TypeScript.** Effect UI реализует MVU в каждом компоненте, публичный интерфейс хоста, тесты Story и инструменты разработчика с сервером MCP; это самый близкий прецедент для этого проекта. Как зависимость она привязала бы каждую программу с UI к одному рантайму JS и не дала бы проверенных фактов для нативных целей, Go и Lua.

**Виртуальный DOM в каждом компоненте.** Просто и проверено: представление выполняется снова, результат сравнивается, а сравнение останавливается на детях с неизменными пропсами. Шаблоны с дырками сохраняют ту же границу компонента и избавляют и от повторного выполнения статической структуры, и от сравнения.

**Сигналы рантайма, выведенные из Model.** Каждое поле становится ячейкой, работа компилятора не нужна. Отслеживание было бы только динамическим, а рантайм тяжелее на каждом бэкенде.

**Одна Model на корень.** Классическую раскладку Elm проще всего формализовать. Но каждое сообщение выполняет представление от корня, родители пересылают сообщения детей, а части приложения нельзя загружать отдельно.

**Сохранить адаптер React.** Внешние компоненты React продолжили бы работать. Но React остался бы в бандлах ядра, а у гидратации и событий было бы две семантики.

Прецеденты: Elm и совет его руководства не делать компоненты с состоянием, Composable Architecture для Swift, однонаправленный поток данных Android с Compose, а также рендереры, которые компилируют статические шаблоны с динамическими дырками.
