Начните с задачи, которую нужно решить. Эти рецепты ссылаются на
существующий справочник с полным синтаксисом и контрактами, а не создают
вторую копию руководства по языку. Если понятия незнакомы, сначала пройдите
раздел [Изучение Flick](../learn/).

## Запустить программу

**Цель:** создать приложение для Node и пройти путь от исходного кода до
работающей точки входа.

Если доступны компилятор Flick, Node.js 24.18 или новее и pnpm, следуйте
разделу [Начало работы](../start/getting-started/):

```sh
flick new my-app
cd my-app
flick install
flick check
flick run
```

`flick new` создаёт конфигурацию проекта, манифест пакета, входной модуль и
пример теста. `flick install` устанавливает зависимости с закреплёнными
версиями; `check`, `build` и `run` сами пакеты не устанавливают.

1. Измените `src/App/Main.fl`. Сохраните сигнатуру точки входа `main` и
   обработайте предметные ошибки перед возвратом из неё.
2. Используйте `flick check`, чтобы получить обратную связь компилятора,
   не выполняя программу.
3. Передавайте аргументы приложению через `flick run -- args`, а для
   пересборки и перезапуска после изменений используйте `flick dev`.
4. Используйте `flick build`, если нужны сгенерированные файлы, а не запуск
   процесса. Вывод приложения по умолчанию включает `flick-main.js` — запускатель
   точки входа.

**Дальше:** [Командная строка](../reference/cli/),
[Проект и пакеты](../reference/project/) и
[Генерация кода](../reference/codegen/). При несовпадении версии инструмента
или зависимости начните с `flick doctor`, а не меняйте закреплённую версию
среды выполнения вручную.

## Внедрить сервис и обработать предметную ошибку

**Цель:** отделить логику приложения от конкретной реализации и сделать
ожидаемые ошибки видимыми вызывающему коду.

1. Объявите ошибки через `type error`, используя полезную нагрузку только
   из данных. В runtime-стрелке вызывающей функции перечислите эти ошибки
   в строке ошибок.
2. Объявите внешние операции в `service`. У операций runtime-стрелки;
   например, вызов `Users.get` добавляет `Users` в строку сервисов.
3. Реализуйте сервис записью `S.Impl` и создайте слой через
   `Layer.succeed S impl`. Окружите использующую его логику блоком
   `provide layer { ... }`. Слой с зависимостями передаёт оставшиеся
   требования и ошибки построения окружающему коду.
4. Используйте `try ... with` для ошибок, после которых можно продолжить
   работу. Частичный обработчик или ветка с условием не удаляют ошибку
   целиком из строки.
5. В тесте предоставьте реализацию того же сервиса в памяти; сигнатуру
   функции приложения менять не нужно.

Каждый шаг описан в [справочнике эффектов](../reference/effects/).
[Примеры сервисов и ошибок](../learn/flick-and-effect/) показывают полные
модули рядом с эквивалентами на TypeScript/Effect. Для тестового окружения
используйте [API тестирования стандартной библиотеки](../reference/stdlib/)
и `flick test`.

**Обратите внимание:** `try ... with` обрабатывает типизированные ошибки,
а не произвольные дефекты или прерывание. Если исключение внешнего кода —
предметная ошибка, его нужно явно преобразовать; см.
[Внешние функции](../reference/ffi/).

## Выполнить конкурентную работу и освободить ресурсы

**Цель:** завершить группу задач, не оставив фоновой работы и пользователей
ресурсов.

1. Создайте отложенную работу через `task { ... }`. Runtime-вызов,
   переданный прямо как аргумент, уже выполнится до начала принимающей
   функции.
2. Используйте `parallel` для пары или `parallel_all limit` для списка с
   ограниченной конкурентностью. Выберите `parallel_results`, если
   типизированная ошибка каждой ветки должна стать результатом, а не
   ошибкой всей группы. Дефекты и прерывание остаются ошибками группы.
3. Окружите получение ресурсов блоком `scope`. Область предоставляет
   сервис `Scope` своего региона и владеет зарегистрированными
   финализаторами.
4. Если нужна независимо работающая дочерняя задача, назовите область и
   вызовите `Fiber.spawn owner supervisor task`. Явно определите поведение
   супервизора; дочерняя задача — не promise без владельца в стиле
   «запустил и забыл».
5. Оставляйте ресурс, а также захватывающие его замыкания и задачи, в
   пределах времени жизни региона. Проверка отвергает выходящие за него
   возможности.

Статические правила описаны в разделе
[Регионы и захваты](../reference/regions/), а параллелизм, гонки, тайм-ауты
и порядок завершения — в разделе
[Адаптер среды выполнения](../reference/runtime/).
[Обзор стандартной библиотеки](../reference/stdlib/) указывает на `File`,
`Resource`, `Fiber` и функции конкурентности.

**Обратите внимание:** при закрытии дочерние задачи прерываются и
дожидаются завершения до освобождения ресурсов. Внешний promise, который
игнорирует отмену, тоже ожидается; тайм-аут не обещает мгновенного
завершения. Это важно при привязке JavaScript-ресурса или сетевого клиента.

## Создать браузерный интерфейс

**Цель:** смонтировать представление Flick на React и выполнять работу
событий с явной политикой.

1. Следуйте веб-интеграции из раздела
   [Начало работы](../start/getting-started/): импортируйте модуль `.fl`
   через `@flick-lang/astro` в Astro или его Vite-плагин в Vite.
   Интеграция вызывает локальный компилятор; страница-хост запускает
   точку входа через `runMain`.
2. Подготовьте DOM-контейнер и найдите его через `Ui.Dom.container`. UI-адаптер
   использует React 19 и React DOM — необязательные peer-зависимости среды
   выполнения, устанавливаемые приложением.
3. Храните состояние в атомах (`Atom.make`), а представления пишите через
   `Ui.view`: render представления читает атомы через `Atom.value` и
   возвращает `Ui r e`. Он не запускает обработчики и не обращается к DOM.
4. Осознанно выберите политику событий: `Ui.Event.exhaust`, `latest`,
   ограниченную `queue` или ограниченную `concurrent`. Пишите атомы
   внутри задачи события, а не во время render представления.
5. Внутри `provide Atom.layer { … }` запустите
   `Ui.Dom.mount container supervisor ui` с нужным временем
   жизни. Он работает до прерывания и направляет ошибки обработчиков
   супервизору. Область, владеющая корнем, дожидается завершения
   обработчиков перед освобождением ресурсов.

[Справочник UI](../reference/ui/) описывает props, безопасные URL,
внешние React-компоненты, политики и контракт завершения корня.

**Обратите внимание:** `text` отображает текст, а не HTML. Произвольная
строка не является ни `SafeUrl`, ни `SanitizedHtml`; используйте
документированные конструкторы, а `Ui.trusted_html` считайте явным
решением о доверии данным.

## Использовать библиотеки JavaScript и TypeScript

**Цель:** пересечь границу языков с точным контрактом выполнения и времени
жизни.

### Вызвать JavaScript

По разделу [Внешние функции](../reference/ffi/) выберите режим привязки:
`pure` для функции, чистоте которой вы доверяете; `sync` для синхронной
runtime-работы; `async` для фабрики Promise; `effect` для фабрики Effect.
Укажите арность аргументов, преобразование типизированных ошибок,
необязательные значения, отмену и удержание callback там, где это нужно API.

Для установленного пакета `flick ffi import` может сгенерировать привязки
из файлов `.d.ts`. Изучите отчёт и задайте политики, которые декларации
не могут выразить. Заблокированный экспорт — не работающий запасной путь:
неподдерживаемые формы TypeScript и недостающие политики сообщаются явно.
При изменении зависимостей и проверенных привязок используйте
`flick ffi check`.

### Экспортировать в TypeScript или для вызывающего кода с Promise

В разделе [Генерация кода](../reference/codegen/) выберите публичную форму:

- `flick build --emit ts` создаёт модули TypeScript.
- `--emit-dts` записывает декларации рядом со сгенерированным JavaScript.
- `--promise-facade` добавляет Promise-точки входа для подходящих
  экспортированных runtime-функций без требований к сервисам. Ожидаемые
  ошибки возвращаются как Effect `Result`; дефекты и прерывание отклоняют
  promise. Это не обычное соглашение, при котором любая ошибка приводит
  к отклонению promise.

Не экспортируйте регион, скрытый захват области, переменную высшего рода
или открытую запись так, будто TypeScript сохраняет весь их смысл.
Справочник описывает ограничения проекции и диагностику деклараций.
Держите границу небольшой с помощью
[правил экспорта модулей](../reference/modules/).

## Настроить редактор и исследовать проблему

**Цель:** использовать настоящий анализ компилятора, а не гадать по
сгенерированному JavaScript.

- Следуйте разделу [Редакторы](../reference/editor/), чтобы запустить
  `flick lsp --stdio` или настроить Zed. Hover, переход к определению,
  дополнения и диагностика используют анализ проекта Flick; встроенные
  определения доступны для чтения без редактирования.
- Используйте `flick explain FLICK-E001`, чтобы прочитать объяснение
  диагностического кода.
- Используйте `flick inspect App.Main --emit js` или `--emit ts` для
  исследования преобразования кода, а `--emit mapping` — для проекции
  редактора и соответствий исходным позициям.
- Используйте `flick fmt --check`, `flick check` и `flick test` соответственно
  для форматирования, статической проверки и тестов проекта. Они отвечают
  на разные вопросы.

Параметры и коды завершения перечислены в
[справочнике командной строки](../reference/cli/). Если вы выбираете между
введением Flick и сохранением TypeScript, прочитайте
[Flick и Effect](../learn/flick-and-effect/) до выбора границы интеграции.
