По умолчанию скомпилированный код импортирует `@flick-lang/runtime/rt` —
собственную среду выполнения Flick без зависимости от Effect. Параметр `--runtime rt`
также выбирает её для одного вызова `build`, `run`, `dev`, `test` или `inspect` в проекте,
настроенном на Effect.

Если проект на RT использует библиотечную привязку, пока реализованную через
Effect, для неё импортируется `@flick-lang/effect-ts/bridge`. При использовании
таких модулей добавьте зависимость `@flick-lang/effect-ts`. Мост преобразует
колбэки, эффекты, сервисы, области владения, Fiber, Schedule, Duration,
коллекции, свидетельства схем и кодеки между средами, включая кодеки с эффектами
во время выполнения. Вложенные `Option` и `Result` сохраняют смысл в обобщённых
библиотечных вызовах. Проект, использующий только привязки RT, не загружает мост.

`Schema.number` проверяет значения Float, включая неконечные числа внутри
списков, записей и вариантов. Его JSON-кодек по-прежнему отвергает неконечные числа.

Непрозрачные значения Stream остаются в адаптере. Нативные атомы,
сериализуемые атомы и рендеринг остаются на RT, включая `Ui.Server.stream`:
разметку рендерит RT и отдаёт её в Stream адаптера, и `Atom.query_stream`:
его атом живёт на RT, а Stream запускает адаптер. Если используемая
возможность UI требует адаптера (например, явные спаны действий), атомы, формы, маршруты и рендеринг всего билда
вместе используют совместимые реализации Effect. Трассировка использует реализации Effect вместе с
настроенными экспортёрами.

Процедуры и группы `Rpc` и их унарные вызовы по HTTP (`Rpc.call` и
`Rpc.call_with` в `Rpc.ndjson` или `Rpc.json`) работают на RT и говорят на
протоколе RPC-сервера Effect: браузерный клиент обходится без Effect и
вызывает сервер, собранный с адаптером. Сервер, потоковые вызовы,
`Rpc.websocket`, `Rpc.tcp`, сериализации `json_rpc`, `ndjson_rpc` и
`binary`, `Rpc.connect`, `Rpc.with_headers` и вызовы в памяти остаются в
адаптере, как пока и серверные функции, и остальной Http. `Http.Headers`,
`Http.Cookies`, `Http.Url`, `Http.UrlParams`, `Http.Mime` и `Http.Etag`
работают на RT с кодированием, порядком и сообщениями модулей Effect. Там же
работает HTTP-сервер на Node.js: `Http.Server.serve` и `address`,
`Http.ServerRequest`, `Http.ServerResponse`, `Http.Body`, `Http.Router` и
`Http.Platform.node` отвечают так же, как сервер Effect, а закрытие области
сервера дожидается его запросов в пределах `gracefulShutdownTimeout` по часам
задачи, прежде чем область освободит что-либо ещё. Потоковые тела, файловые
тела `Http.Body`, `Http.Server.log_address` и преобразования в запросы и
ответы клиента и обратно остаются в адаптере. Http, RPC и серверные
функции — одно семейство: билд, который использует привязку семейства,
которая есть только в адаптере, берёт из адаптера всё семейство, так что
запрос, ответ или процедура принадлежат одной реализации.

Чтение тела запроса, сохранение multipart-форм, раздача статических файлов и
чтение потока серверного рендеринга требуют `Async` в строке эффектов вызывающей
функции.
Для HTTP-тела с потоком, которому нужен только `Async`, используйте
`Http.Body.stream_async` или `Http.ServerResponse.stream_async` / `stream_text_async`.

Проекты с `[target.js] runtime = "effect"` используют `@flick-lang/effect-ts` (см. [Ошибки,
сервисы, ресурсы и конкурентность](../../spec/05-errors-and-concurrency/),
[Архитектура компилятора](../../contributing/implementation-decisions/#архитектура-компилятора)).
Адаптер рассчитан на выпуск Effect, закреплённый в
`packages/effect-ts/package.json`, и обеспечивает описанные ниже правила.

## Версия Effect

Адаптер проверен именно с закреплённым выпуском Effect. Перед запуском `main` средство
запуска точки входа проверяет установленную версию. Если версия отличается,
выполнение завершается с кодом `2`:

```text
error: the Flick Effect adapter requires effect 4.1.2, found 4.1.0
```

Матрицу возможностей операций Effect, на которые опирается адаптер,
проверяют тесты среды выполнения и `just effect-bump`, а не средство
запуска: для неё нужны все модули Effect, и браузерный бандл включил бы
весь Effect.

## Владельцы и области

У каждой `scope` есть лексический владелец, а у средства запуска точки входа —
корневой владелец. Владелец учитывает дочерние задачи, начатую ими внешнюю работу
и финализаторы ресурсов, полученных в этой области. После завершения тела —
успешного, с типизированной ошибкой, дефектом или прерыванием — владелец
закрывается в две фазы: сначала завершает дочернюю работу, затем освобождает
ресурсы. Порядок действий:

1. владелец перестаёт принимать новые дочерние задачи и отключает внешние источники событий;
2. прерывает все дочерние задачи и ждёт завершения каждой, включая супервизоры;
   непрерываемая дочерняя задача задерживает закрытие;
3. ждёт завершения всех незавершённых внешних промисов `async`, даже
   если они игнорируют прерывание;
4. запускает финализаторы ресурсов в порядке, обратном порядку получения;
5. область завершается с исходом тела, к которому добавляются все сбои очистки.

Ошибки отключения источников сохраняются вместе со сбоями тела и финализаторов;
они не отменяют прерывание, ожидание дочерних задач и освобождение ресурсов.

Дочерние задачи и ресурсы — отдельные группы: ресурс, полученный после
запуска дочерней задачи, всё равно освобождается после её завершения.

`acquireRelease` регистрирует финализатор без типизированных ошибок у владельца,
в котором выполняется вызов. Это либо самый внутренний владелец, либо владелец
внешней `scope`, если вызов получает ресурс в регион этой области.
Во втором случае компилятор передаёт владельца через `within`.
В отличие от `acquireRelease`, `bracket` освобождает ресурс сразу после
использования и может завершиться с собственной типизированной ошибкой.

## Дочерние задачи

`Fiber.spawn owner supervisor task` запускает `task` как дочернюю задачу `owner`.
Если дочерняя задача завершилась со сбоем, в том числе из-за прерывания при
закрытии владельца, она передаёт свой `Failure` супервизору. Поле
`failure.shutdown` позволяет распознать прерывание при закрытии владельца.
Дефект супервизора передаётся корневому механизму отчётности
и делает весь запуск неудачным; в `flick test` он валит тот тест, во время
которого случился. `Fiber.join` ждёт завершения дочерней задачи
и при её сбое сам завершается сбоем с исходной причиной. Закрывающийся владелец
не принимает новых дочерних задач: попытка запустить в нём задачу приводит к дефекту.
Ресурсы дочерней задачи и её супервизора принадлежат региону владельца,
поэтому задача, получающая ресурсы, указывает `Scope` этого региона.

## Конкурентность

| Операция | Контракт |
| - | - |
| `parallel a b` | оба результата в порядке входных аргументов |
| `parallel_all limit effects` | не более `limit` ветвей одновременно; `limit` должен быть положительным конечным целым числом, иначе дефект |
| `parallel_results effects` | типизированная ошибка каждой ветви в виде `Err`; дефект или прерывание останавливает группу |
| `parallel_exits effects` | непрозрачный `Exit` каждой ветви |

Эти операции доступны через Prelude. Для работы с исходами служат модули
`Exit`, `Failure` и `RawCause`:

```text
parallel : (Eff r e a)^c -> ((Eff r e b)^c ->{r; e} (a, b))^c
parallel_all : Float -> List ((Eff r e a)^c) ->{r; e} List a
parallel_results : List ((Eff r e a)^c) ->{r; none} List (Result (Errors e) a)
parallel_exits : List ((Eff r e a)^c) ->{r; none} List (Exit e a)
race_success : (Eff r e a)^c -> ((Eff r e a)^c ->{r; e} a)^c
race_first : (Eff r e a)^c -> ((Eff r e a)^c ->{r; e} a)^c
timeout : Float -> (Eff r e a)^c ->{r; TimeoutError | e} a
timeout_option : Float -> (Eff r e a)^c ->{r; e} Option a

Exit.value : Exit e a -> Option a
Exit.failure : Exit e a -> Option (Failure e)
Failure.primary : Failure e -> Option (Errors e)
Failure.raw_cause : Failure e -> RawCause
Failure.inspect : Failure e ->{} CauseReport
Failure.rethrow : Failure e ->{; e} a
RawCause.inspect : RawCause ->{} CauseReport
```

Задача может захватывать значения, принадлежащие областям вызывающего кода
(`^c`): комбинаторы завершают её выполнение до возврата результата.

При сбое новые ветви не запускаются. Уже выполняемые ветви прерываются,
а комбинатор ждёт их завершения и сохраняет в результате сбои,
наблюдавшиеся к этому моменту.

| Гонка | Контракт |
| - | - |
| `race_success a b` | первый успех; сбои проигравшей ветви не добавляются |
| `race_first a b` | первая завершившаяся ветвь независимо от её исхода |
| `timeout millis e` | завершается с `TimeoutError`, если время истекло раньше |
| `timeout_option millis e` | `None`, если время истекло раньше; остальные сбои сохраняются |

До возврата результата комбинатор прерывает проигравшие ветви и ждёт их
завершения. Если ветвь готова сразу, она может выиграть ещё до запуска другой.

## Исходы

`try … with` обрабатывает первую типизированную ошибку в причине сбоя.
Если причина содержит ещё и дефект, обработчик не запускается, а типизированные
ошибки становятся дефектами. Причина, состоящая только из прерывания,
не содержит ошибки. Если подходящей ветви нет, исходная причина
распространяется без изменений:

| Причина | Восстановление |
| - | - |
| `Fail(A)` | `A` |
| `Fail(A), Fail(B)` | `A`, первая |
| `Fail(A), Interrupt` | `A` |
| `Fail(A), Die(D)` | нет: ошибки становятся дефектами |
| `Interrupt` | нет |
| `Fail(B), Fail(A)`, ветви только для `A` | нет: причина распространяется дальше |

`Exit e a`, `Failure e` и `RawCause` непрозрачны. `Failure.primary` возвращает
ошибку, которую выбрал бы обработчик; `Failure.rethrow` завершается сбоем
с исходной причиной. `Failure.inspect` и `RawCause.inspect` возвращают
`CauseReport` — замороженные данные без прототипа. Для каждой причины
в отчёте указан её вид (`fail`, `die`, `interrupt`), а также `_tag` или
сообщение об ошибке, прочитанные из собственных свойств данных.
Если прочитать их таким способом нельзя, используется заполнитель.
Построение отчёта никогда не выполняет код, связанный с данными ошибки:
геттеры, `toString`, `toJSON` или ловушки Proxy.

## Слои

`provide layer { body }` также создаёт лексического владельца. Слой строится
до выполнения тела; если построение завершается со сбоем, тело не выполняется.
В пределах одного построения повторные обращения к слою используют общий
результат; вложенный в тело `provide` также использует результат внешнего построения того же
значения слоя. Два `provide` рядом строят его дважды. Сервисы слоя доступны только
в теле, вместе с сервисами окружающего контекста. Финализаторы слоя выполняются
после завершения тела, с теми сервисами, с которыми они были зарегистрированы.

## Средство запуска точки входа

`flick-main.js` выполняет `main` под корневым владельцем. Сигналы SIGINT и SIGTERM
прерывают `main` и закрывают корневого владельца по тому же протоколу.
Процесс продолжает работать до завершения очистки. Если она занимает больше
двух секунд, процесс сообщает об этом в stderr; задержку задаёт
`FLICK_SHUTDOWN_NOTICE_MS`:

```text
shutting down: waiting for cleanup to finish
```

| Код завершения | Условие |
| - | - |
| `0` | `main` и очистка завершились успешно |
| `1` | типизированная ошибка (`error: <message>` для `AppError`), дефект (выводится его причина), сбой очистки, дефект супервизора или прерывание не из-за сигнала |
| `2` | установленная версия Effect не поддерживается средой выполнения |
| `130` / `143` | `main` остановлен только сигналом SIGINT / SIGTERM, очистка прошла успешно |

Сбой приложения или очистки сохраняет код `1`, даже если одновременно
пришёл сигнал. В выведенной причине перечислены все сбои и дефекты: для
`Error` — стек до первого кадра цикла выполнения Effect, для другого
значения — его `message` или JSON.

## Покрытие Effect

Стандартная библиотека оборачивает закреплённую версию Effect
(см. [Граница языкового ядра](../../spec/05-errors-and-concurrency/#граница-языкового-ядра)).
Для каждого публичного экспорта из точек входа `effect`, `effect/cli`, `effect/devtools`,
`effect/http`, `effect/http-api`, `effect/observability`, `effect/process`, `effect/reactivity` и `effect/rpc` есть типизированная обёртка или явно
записанное решение. Линтер, который выполняется в `cargo test`,
следит за тем, чтобы при обновлении Effect ни один экспорт не остался без решения.

### Снимок

`packages/effect-ts/coverage/snapshot.json` описывает API установленной версии Effect.
Снимок записывается командой `node tools/dts-importer/index.mjs surface > packages/effect-ts/coverage/snapshot.json`
и содержит все точки входа из её `package.json`. Для девяти оборачиваемых
точек входа в нём перечислены все экспорты каждого модуля в виде `Module.name`.
У каждого экспорта указаны категория (`value`, `type` или `value+type`)
и отпечаток — 16 шестнадцатеричных цифр SHA-256 от объявлений, напечатанных
без комментариев. Изменение документирующего комментария не меняет отпечаток,
а изменение сигнатуры меняет.

### Манифест

`packages/effect-ts/coverage/surface/entrypoints.toml` определяет, как обрабатывается
каждая точка входа: либо её модули описываются в указанном каталоге,
либо она исключается целиком. Для каждой новой точки входа Effect
тоже нужно выбрать один из этих вариантов.

```toml
"effect" = { modules = "core" }
"effect/ai" = { excluded = "AI provider clients are outside the 0.1.0 standard library" }
```

Файл `packages/effect-ts/coverage/surface/<dir>/<Module>.toml` (или `<Module>.<part>.toml`
для большого модуля) задаёт ровно один статус для каждого экспорта:

```toml
[wrapped]
spaced = "Schedule.spaced 498f22b480d2397e"

[language]
gen = "a runtime function body: direct calls"

[excluded]
isSchedule = "TS-only: a type guard; Flick values are typed statically"

[pending]
cron = "cron expressions need a parser of their own"
```

| Статус | Значение | Смысл |
| - | - | - |
| `wrapped` | `"<Flick.Name> <fingerprint>"` | типизированный символ стандартной библиотеки, проверенный по этому отпечатку |
| `language` | конструкция | возможность уже есть в языке: вместо `Effect.gen` используются прямые вызовы, вместо `Context.Service` — `service`, вместо `Data.TaggedError` — `type error`, вместо `Layer.provide` — `provide`, вместо `Match` — `match` |
| `excluded` | причина | возможность нужна только в TypeScript (`HKT`, `Types`, проверки типов, извлечение типов) либо противоречит инварианту языка (`unsafe*`, `Mutable*`, порождение задачи без владельца, выполнение эффекта вне средства запуска точки входа, управление потоком через канал ошибок) |
| `pending` | чего не хватает | обёртки временно нет |

Запись `"*"` распространяется на все экспорты модуля, у которых нет собственной записи.

### Линтер

`packages/effect-ts/tools/surface/tests/coverage.rs` завершается с ошибкой и указывает
`Module.name` и причину, если:

- у экспорта или точки входа нет решения;
- решение относится к несуществующему экспорту или точке входа;
- отпечаток экспорта `wrapped` отличается от проверенного;
- стандартная библиотека не экспортирует символ `wrapped` или ни один тест
  в `tests/run/stdlib/` на него не ссылается (ссылки разрешает модуль проверки типов);
- у решения `language`, `excluded` или `pending` не указана причина;
- версия снимка отличается от закреплённой в `packages/effect-ts/package.json`.

`just effect-coverage` выводит число экспортов по статусам и модулям.
CI добавляет эти данные в сводку запуска.

### Переход на другую версию

`just effect-bump <version>` загружает указанную версию и записывает её снимок.
Команда выводит добавленные, удалённые и изменённые элементы, а также возможности,
которых недостаёт в матрице возможностей среды выполнения. Она также обновляет
закреплённые версии в `packages/effect-ts/package.json`, `packages/effect-ts/src/capabilities.ts`,
тесте версии среды выполнения.
Линтер продолжает завершаться с ошибкой, пока манифест не будет согласован
с новым снимком.

### Нестабильные модули

Effect помечает `effect/reactivity` как `@stability unstable` в закреплённом выпуске, и так
же помечены его привязки: `Reactivity.Atom` (атомы, сервис `Registry`,
который хранит их значения, и его `layer`) и `Reactivity.AsyncResult`
(значение атома, вычисленное задачей). Их API может измениться с любым
выпуском Effect; стабильный API предоставляют построенные на них модули UI.

`effect/rpc` тоже нестабилен, как и `Rpc`: процедуры описываются кодеками,
тип группы — запись её обработчиков, `listen` обслуживает группу по HTTP,
пока не закроется её область, а `call` и `call_stream` вызывают процедуру
того же значения. Сообщения пишутся в NDJSON, если `ServeOptions` и
`call_with` / `call_stream_with` не выбирают `json`, `json_rpc`, `ndjson_rpc`
или `binary` (бинарные кадры Effect, которые попадают в бандл, только если
программа их называет). `listen_websocket` обслуживает ту же группу
по WebSocket, а клиент обращается к ней с `transport = Rpc.websocket`;
`listen_tcp` — по TCP в Node, с `Rpc.tcp` и сериализацией, которая делит
поток на кадры; `serve_stdio` отвечает на вызовы через stdin и stdout, а
`spawn` запускает такую программу и подключается к ней; `serve_worker`/`worker`
делают то же для Web Worker, `serve_node_worker`/`node_worker` — для потока
worker_threads Node; `with_middleware`
выполняет хук над payload и заголовками каждого вызова до обработчика, а
`with_headers` добавляет заголовки к вызовам задачи; `uninterruptible`
заставляет сервер довести обработчик до конца, даже если клиент ушёл;
`call_local` и `call_stream_local` вызывают группу в памяти — для тестов;
`connect` поддерживает одно соединение, совместно используемое `call_on` и
`call_stream_on`.

`effect/observability` тоже нестабилен, как и `Otlp` и `Prometheus`.
`Otlp.layer`, `traces`, `logs` и `metrics` экспортируют span'ы, записи журнала
и метрики по протоколу OpenTelemetry через HTTP с JSON, каждый со своим
fetch-клиентом. `Otlp.settings url service` и `layer_with`, `traces_with`,
`logs_with`, `metrics_with` добавляют версию и атрибуты сервиса, заголовки
запросов, gzip, protobuf (`Otlp.protobuf` попадает в бандл, только если его
назвать), интервалы отправки, размер пачки и таймаут завершения.
`Otlp.from_config` экспортирует сигналы, указанные в конфигурации `OTEL_`
текущего `ConfigProvider`; сигнал отправляется, только если его
`OTEL_<SIGNAL>_EXPORTER` называет `otlp`.
`Prometheus.format` выдаёт записанные метрики в текстовом формате Prometheus,
`format_with` — с префиксом или переименованными, а `Prometheus.route path` —
маршрут `Http.Router`, который их отдаёт.

`effect/devtools` нестабилен, как и `DevTools`: `DevTools.layer url` отправляет
span'ы программы по WebSocket в Effect DevTools, которые слушают `url`, а
`DevTools.layer_with { url; headers }` добавляет заголовки к рукопожатию
(в Node).

### Привязки

Обёртка обращается к экспорту по ключу своего модуля, `flick:<Module>`. Ключ не
называет пакет какой-либо цели. При сборке на Effect ключу соответствует
`@flick-lang/effect-ts/effect/<Module>` (`packages/effect-ts/src/effect/<Module>.ts`):
этот модуль реэкспортирует обёрнутый модуль Effect.
Поэтому скомпилированный код по-прежнему импортирует только пакет среды выполнения.

Если значение нельзя передать как есть в виде значения Flick, в том же файле
размещается адаптер с именем `flick<Name>`. Например, он нужен для записи
параметров с полями `Option` или для ошибки Effect, которая во Flick
становится `type error`.

```flick
# import Schedule exposing (Schedule)
#
/// Recurs forever, each step the duration after the previous one ended.
spaced : Duration.Duration -> Schedule none none i Float
foreign pure spaced from "flick:Schedule" "spaced"

retry :
  forall c r e a r2 e2 o.
  Schedule.Schedule r2 e2 (Errors e) o -> (Eff r e a)^c ->{Async | r + r2; e + e2} a
foreign effect retry from "flick:Effect" "retry"
  arity 1
  retention call
```

Имена записываются в snake_case, а основной аргумент передаётся последним.
Поэтому `task |> Effect.retry
schedule` можно читать слева направо. Указание `arity 1` вызывает вариант API
Effect с основным аргументом в конце: сначала он принимает расписание
и возвращает функцию от основного аргумента. В записях, передаваемых
в Effect, сохраняются его имена полей (`elapsedSincePrevious`).
