`flick` — исполняемый файл с командами компилятора. Все команды принимают
глобальные параметры `--project <path>`, `--package <name>` (`-p`, участник
[workspace](../project/#workspace)), `--diagnostics human|json`,
`--warnings-as-errors`, `--color auto|always|never`, `--quiet` (псевдоним `--silent`)/`--verbose`,
`--timings` ([на что ушло время](#тайминги)),
`--offline` (без сети: [плагины](../plugins/#доступ-вовне) отвечают из
снимков проекта, то же значит заданная `CI`, а `install` ставит из
хранилища), `--allow-tool <tool>` (разрешает выбранному бэкенду запускать
инструмент хоста при сборке вне проекта; проект разрешает
свои инструменты в [`[tools]`](../project/#flicktoml), а флаг в нём —
`FLICK-P051`) и `--help`. Команда `flick help <command>` выводит справку по выбранной команде,
а `flick --version` — версию компилятора. Остальные сведения показывает `flick doctor`.

Встроенные плагины, бэкенд проекта и плагины его зависимостей могут добавлять
свои команды. `flick --help` перечисляет их по контрибьюторам, а запускаются
они как `flick <команда>` или `flick <контрибьютор>:<команда>` (см.
[Команды плагинов и официальные бэкенды](#команды-плагинов-и-официальные-бэкенды)
и [Добавленные команды](../commands/)).

## Команды

| Команда | Действие |
| - | - |
| `new <dir> [--target <name>] [--template <name>] [--from <source> [--tag <tag> [--subdir <dir>] \| --sha256 <hex>]]` | создаёт проект по шаблону, который предоставляет выбранный целевой бэкенд (см. [Шаблоны проектов](#шаблоны-проектов-new-и-init)) или сторонний пакет `--from` (локальный путь, URL tar.gz-архива с `--sha256` или git-репозиторий с `--tag` и необязательным `--subdir`); все файлы шаблона, включая `flick.toml`, приходят от контрибьютора, `--from` закрепляет шаблон в `[[template]]` файла `flick.lock`, неподдерживаемый шаблон даёт `FLICK-P060` со списком доступных, а неизвестный `--target` — `FLICK-P059` |
| `init [--target <name>] [--template <name>] [--from <source> [--tag <tag> [--subdir <dir>] \| --sha256 <hex>]]` | добавляет файлы шаблона в рабочий каталог, сохраняя существующие посторонние файлы; перед записью сообщает обо всех конфликтующих файлах шаблона (`FLICK-P019`), кроме существующего `AGENTS.md` (остаётся как есть) и `flick.lock` (новые закрепления объединяются с ним) |
| `check [paths] [--watch] [--fix [--only codes]]` | проверяет код; если пути не указаны, проверяет корневые каталоги исходников и тестов; `--fix` применяет к этим файлам исправления, не меняющие смысла программы (например, убирает избыточную аннотацию типа, `FLICK-T021`), и сообщает об оставшихся проблемах; `--only E002,F001` применяет только исправления этих кодов — для миграции, которая больше ничего не меняет |
| `prove [paths] [--watch]` | проверяет модули доказательств каталога доказательств (`project.proof-dir`) и контракты функций (`where require ... ensure ...`) из модулей исходников и тестов проекта либо указанных файлов вместе с кодом, который они называют; `check`, `build` и `test` проверяют только типы контрактов, не доказывают и не понижают их и не читают каталог доказательств (см. [контракт доказательств](https://github.com/bondiano/flick-lang/blob/main/docs/formal/proofs.md)) |
| `build [paths] [--target <name>] [--profile] [--labels all\|components\|none] [--emit-ir[=json\|cbor]] [--out-dir] [--watch] [--no-native-overrides] [<опции бэкенда>]` | компилирует проект выбранным бэкендом; специфичные для таргета флаги объявляет выбранный бэкенд (см. [Таргет и опции бэкенда](#таргет-и-опции-бэкенда)); `--emit-ir` добавляет `program.ir.json` (или `program.ir.cbor`) — IR, который получает бэкенд, оптимизированный в release-сборке, с версией IR, в которой он записан; `--no-native-overrides` понижает резервные тела на Flick вместо переопределений `@native` для проверки соответствия; показывает в stderr этапы сборки, затем число модулей и раннеры входов либо число и расположение ошибок; `--silent`/`--quiet` и `--diagnostics json` отключают прогресс и итог |
| `build [paths] --inputs` | выводит консервативный JSON-инвентарь входов (`key`, `files`, `roots`, `modules`), не записывая артефакты и кеш |
| `run [name] [--target <name>] [--vm-tier <tier>] [--entry M] [--profile] [--no-native-overrides] [<опции бэкенда>] -- args` | собирает выбранным бэкендом и запускает `main` входа `name` (единственного, если имя не указано), а с `--target vm` исполняет вход проекта, отдельный файл `.fl` или собранный образ `.fvm` внутри процесса на ВМ; `name`, который не является входом, запускает скрипт из [`[scripts]`](../project/#скрипты): его команды по порядку до первой упавшей, `args` — их `"$@"`; клиентский вход (`target = "client"`) делегируется клиентскому раннеру выбранного бэкенда (`FLICK-P067`, если бэкенд его не предоставляет) |
| `dev [name] [--target <name>] [--entry M] [--profile] [--no-native-overrides] [<опции бэкенда>] -- args` | пересобирает при изменениях и заменяет работающее приложение; в проекте с несколькими входами без имени запускает каждый неклиентский вход и, если есть вход с `target = "client"`, делегирует клиентский раннер выбранному бэкенду |
| `test [paths] [--target <name>] [--vm-tier <tier>] [--filter] [--list] [--forbid-only] [--jobs] [--seed] [--timeout] [--reporter human\|json] [--watch] [--profile] [--no-native-overrides] [<опции бэкенда>]` | запускает тесты из корневого каталога тестов выбранным бэкендом (см. [тестирование](../testing/)) |
| `fmt [paths] [--check] [--stdin --stdin-filepath f]` | записывает код в каноническом формате ([форматирование](../syntax/#форматирование)); если пути не указаны, обрабатывает корневые каталоги исходников и тестов |
| `clean [--cache]` | удаляет артефакты сборки; с `--cache` — также кеш сборки |
| `install [--locked]` | устанавливает зависимости `[dependencies]` Flick из `flick.lock` и делегирует установку пакетов экосистемы выбранному бэкенду; в корне workspace — каждого участника |
| `add <pkg>… [--dev]`, `remove <pkg>…`, `update [pkg]…` | управляет `[dependencies]` Flick (`--path`, `--git`, `--url`) и делегирует операции над пакетами экосистемы выбранному бэкенду (`FLICK-P063`, если бэкенд не управляет собственными пакетами) |
| `deps [--why <pkg>]` | показывает граф зависимостей Flick и делегирует просмотр пакетов экосистемы выбранному бэкенду |
| `plugins` | плагины path-, git- и url-зависимостей проекта, первыми — плагины самого компилятора: откуда каждый, хэш его компонента и закрепляет ли эту сборку `flick.lock` |
| `pack --out-dir <dir> [--target <name>]` | записывает детерминированный tar.gz-архив исходников Flick (печатая `<sha256>  <путь>` в stdout для установки через `flick add --url --sha256`) и необязательный артефакт от команды `pack` выбранного бэкенда; отказывает при `todo` и `echo` (`FLICK-P024`) и предупреждает, если изменения публичного API нарушают совместимость с импортирующим кодом со времени последнего тега |
| `diff [ref]` | изменения публичного API со времени ревизии git (по умолчанию последнего тега): `MAJOR` (удалено или изменено) или `MINOR` (добавлено), и версия, которую они требуют |
| `doc --out-dir <dir> [--source-base-url <url>] [--check-examples] [--target <name>] [--std]` | создаёт Markdown-страницы публичного API: типы, кинды, вариантность, ограничения, эффекты, захваты; с `--check-examples` компилирует и запускает примеры через выбранный бэкенд (или `--target <name>`) |
| `explain <code>` | объясняет сообщение диагностики по его коду, в том числе код плагина, как `std/L001` |
| `expand [paths]` | выводит код, в который раскрывается каждый блок [плагина](../plugins/) проекта или файлов |
| `doctor [--target <name>]` | проверяет компилятор, хранилище пакетов, git, плагины, а также окружение и пакеты выбранного целевого бэкенда |
| `inspect <M> --emit ast\|typed-ir\|output\|iface\|variance\|mapping [--target <name>] [--no-native-overrides] [<опции бэкенда>]` | выводит одно представление модуля; `--emit output` запрашивает сгенерированный код модуля у выбранного бэкенда; `--emit iface` показывает типизированный интерфейс без загрузки какого-либо бэкенда; `--emit variance` печатает выведенную вариантность параметров экспортированных типов и классов (включая установленные пакеты и встроенные модули, отмечая неизвестные метаданные как `inv (unknown)`) |
| `lsp --stdio` | запускает [языковой сервер](../editor/#языковой-сервер); stdio — его единственный транспорт |
| `repl [--target <name>] [--vm-tier <tier>]` | запускает интерактивную сессию REPL на встроенной ВМ (`--target vm` по умолчанию); исполняет объявления и выражения с сохранением привязок, сервисами `Host.live`, автоматическим ожиданием задач `Eff`, прерыванием по `SIGINT` с выполнением финализаторов областей и командами сессии (`:handle`, `:provide`, `:bg`, `:jobs`, `:kill`, `:quit`) |

В корне workspace без `[project]` команды `check`, `build`, `test`, `fmt` и
`clean` без путей, а также `install` выполняются для каждого участника,
сначала для зависимостей.

`check`, `build` и этапы сборки в `run`, `dev` и `test` ничего не устанавливают,
не запускают `main` и не загружают внешние модули. Если версия установленной
зависимости среды выполнения отличается от закреплённой выбранным бэкендом,
эти команды завершаются с `FLICK-P015` (код выхода 2).

`test` выводит human-результаты сразу после освобождения ресурсов каждого теста: маркер успеха или ошибки, счётчик и время, затем общий итог. Бэкенды используют один формат и учитывают `--color`; автоматический цвет проверяет stdout, `NO_COLOR` и `TERM=dumb`. `--reporter json` выводит один итоговый объект в порядке объявления, без цвета и длительностей.

## Таргет и опции бэкенда

Команды `build`, `run`, `dev`, `test`, `pack`, `doctor`, `inspect` и `doc`
(при проверке примеров) принимают `--target <name>` для выбора компонента
бэкенда (короткое имя официального бэкенда, короткое имя закреплённого
`[build.backend]` или, в проекте и с компилятором, собранным из репозитория,
`lua` для его собственного компонента `backends/lua`). Без `--target` таргет берётся из `[build.backend]`, затем
из `[build] target`, затем из префикса бэкенда в `[build] environment`, а иначе
используется целевой бэкенд по умолчанию (см.
[Команды плагинов и официальные бэкенды](#команды-плагинов-и-официальные-бэкенды)).
Вне проекта `flick doctor` без `--target` выполняет только базовые проверки
(компилятор, хранилище, git, плагины) и сообщает, что бэкенд не выбран;
передайте `--target <name>`, чтобы добавить проверки нужного бэкенда.
Неизвестный таргет — `FLICK-P059` (код выхода `2`).

Специфичные для бэкенда флаги объявляет сам выбранный компонент бэкенда —
отдельно для каждой команды. `flick <cmd> --help` и `flick help <cmd>`
показывают только опции выбранного бэкенда для этой команды в разделе
`Options of \`<id>\`:` (передайте `--target <name> --help`, чтобы посмотреть
опции другого таргета). Те же опции задаются постоянно в `flick.toml` в разделе
`[target.<name>]`; флаги CLI имеют приоритет над `flick.toml` (булевы флаги
принимают `--<flag>=false`, чтобы переопределить `true` из `flick.toml`).

Неизвестная опция, опция от другой команды или другого бэкенда либо
недопустимое значение приводят к `FLICK-P058` (код выхода `2`). Прежние жёстко
встроенные целевые флаги (`--emit <target>`, `--emit-dts`, `--rt`) удалены без
псевдонимов совместимости и завершаются с `FLICK-P057` (код выхода `2`),
называя замену через `--target` и `[target.<name>]` (точные замены приведены в
разделах бэкендов в
[Команды плагинов и официальные бэкенды](#команды-плагинов-и-официальные-бэкенды)).

Аргументы после `--` (например, `flick run app -- --rt`) передаются напрямую
программе или скрипту и не разбираются самим `flick`.

### Шаблоны проектов (`new` и `init`)

`flick new <dir>` и `flick init` берут шаблоны проектов у выбранного целевого
бэкенда (`--target <name>` или целевой бэкенд по умолчанию, если флаг не
указан) либо у стороннего пакета, указанного через `--from` (несовместимо с
`--target`). Если `--template <name>` не указан, `flick` выбирает `app`, если
контрибьютор объявляет его, либо единственный шаблон, если он один. Запрос
неподдерживаемого шаблона завершается с `FLICK-P060` (код выхода `2`) и
перечисляет все доступные шаблоны с их описаниями.

Сторонние пакеты шаблонов (`--from <source>`) принимают локальный каталог
(`--from ./my-templates`), URL tar.gz-архива с его контрольной суммой
(`--from https://example.com/tpl.tgz --sha256 <64-hex>`) или тег git
(`--from https://example.com/repo --tag v1.0.0 [--subdir pkg]`), используя ту
же проверку и хранилище пакетов, что и `flick add`. Удалённые URL в `--from`
без `--sha256` или `--tag` отвергаются (`FLICK-P032`). Созданный проект
записывает проверенный источник и хеш компонента в `[[template]]` файла
`flick.lock` (сохраняется командой `flick install`). Официальные бэкенды из
релизных ассетов закрепляются в `[[backend]]` файла `flick.lock`, чтобы
дальнейшие сборки работали без сети. Шаблоны, поставляемые официальными
бэкендами, перечислены в разделе
[Команды плагинов и официальные бэкенды](#команды-плагинов-и-официальные-бэкенды).

Планы шаблонов — это чистые планы файлов: любой шаблон, возвращающий шаги
инструментов хоста, `resume`, `needs` или выходящие за пределы каталога пути,
отвергается с `FLICK-P055` до создания каталога и файлов. `flick init` сохраняет
посторонние файлы и существующий `AGENTS.md`, объединяет новые закрепления с
существующим `flick.lock` и отвергает любые другие конфликтующие файлы с
`FLICK-P019` до записи.

## Выходные файлы и кеш

Сборка записывает файлы в `build.out-dir` (или `--out-dir`) и сохраняет их
список в `.flick/artifacts.json`. После успешной публикации удаляются устаревшие
файлы из прежнего списка, в том числе при смене формата генерации и попадании
в кеш. `clean` удаляет оставшиеся принадлежащие сборке файлы и пустые каталоги.
Пользовательские файлы в общем выходном каталоге сохраняются. Файлы, собранные
отдельно, вне проекта, вместо этого перечисляют записанное сборкой в
`.flick-files` вывода, и следующая сборка в него удаляет те перечисленные
файлы, которые больше не пишет.

Кеш в `.flick/cache/` хранит артефакты каждой сборки. Ключ кеша учитывает
нормализованный набор выбранных корневых файлов отдельно от доступных
исходников проекта, его итоговую конфигурацию, профиль, опции таргета
и вывода, компилятор (версию и исполняемый файл), компонент бэкенда с
закреплёнными графами среды выполнения и входные файлы пакетов, о которых
сообщает выбранный бэкенд (его манифесты, файлы блокировки и исходники Flick
установленных пакетов). Если любые из этих данных изменились, сборку нельзя
взять из кеша. При использовании кеша записываются ровно те файлы, которые
создала бы сборка.

Команды с `--watch` сравнивают состояние каждого пути, включая создание
и удаление файлов. Временная метка одного файла не скрывает изменение другого.

## Запуск и замена приложения

`run` и `dev` собирают проект выбранным целевым бэкендом. Каждая
сборка хранится в атомарно зарезервированном каталоге `.flick/run/<pid>-<n>/`.
После запуска процесса файлы поколения больше не перезаписываются, поэтому
запущенная программа всегда видит исходную версию. CLI владеет поколением от начала
сборки до завершения очистки; `clean` сохраняет каталоги, зарезервированные для активных сборок
и работающие дочерние процессы. После завершения поколение удаляется.

`dev` собирает следующую версию, пока текущая работает. Если сборка не удалась,
текущая версия продолжает работать. После успешной сборки `dev` сначала
останавливает текущую версию так же, как SIGTERM: запускающий процесс прерывает
`main`, ждёт завершения его файберов и выполняет финализаторы. Только после
этого запускается новая версия. Если завершение работы не удалось (код выхода
отличается от 143), `dev` прекращает перезапуски с `FLICK-P021`.
Сообщение запускающего процесса о причине остаётся в stderr.

SIGINT и SIGTERM передаются приложению; `flick` завершается только после него
и с его кодом выхода.

## Зависимости

`install` и `update` сначала скачивают библиотеки Flick, которые закрепляет
`flick.lock`, а `add` с `--git`, `--url` или `--path` и `remove` меняют
`[dependencies]` (см. [проект](../project/#зависимости-flick)). Целевая часть
команд `install`, `add`, `remove`, `update` и `deps` делегируется выбранному
бэкенду проекта вместе с замыканием `[target.<name>.dependencies]` для этого
бэкенда. Если выбранный бэкенд не управляет собственными пакетами, `flick install`
обрабатывает только `[dependencies]` Flick без вызова стороннего пакетного
менеджера, а операции над пакетами экосистемы вроде `flick add <pkg>` (без
`--path`, `--git` или `--url`) завершаются с `FLICK-P063` (код выхода 2),
называя бэкенд и предлагая эти опции источника. Конкретные пакетные менеджеры
и проверки версий описаны в разделе
[Команды плагинов и официальные бэкенды](#команды-плагинов-и-официальные-бэкенды).

`pack` проверяет или собирает проект в профиле release для выбранного таргета,
отказывает при оставшихся `todo` или `echo` (`FLICK-P024`) и предупреждает, если
публичный API нарушает совместимость с импортирующим кодом со времени последнего
тега git. Когда в `flick.toml` задан раздел `[package]` (`name` и `version`),
ядро записывает детерминированный архив исходников Flick `<name>-<version>.tgz`
с `flick.toml`, каталогом исходников (без тестовых компаньонов), объявленным
компонентом `[package] plugin` и файлами readme/лицензии под `package/` без
временных меток и владельцев, так что одни и те же исходники дают одни и те же
байты; stdout печатает `<sha256>  <путь>` для `flick add --url --sha256`.
Библиотека, наследующая `[[workspace.plugins]]`, отвергается (`FLICK-P032`). Если
выбранный бэкенд также объявляет необязательную команду `pack`, ядро проверяет
сгенерированные файлы `.iface` (`FLICK-P020`) и делегирует целевую упаковку
бэкенду (при совпадении имени артефакта бэкенда с архивом исходников Flick он
помещается в `<out-dir>/<target>/`). Бэкенды без команды `pack` выполняют
проверку фронтенда с учётом таргета и записывают только архив исходников Flick.

## Проверяемая документация пакета

`flick doc --out-dir api --check-examples` создаёт Markdown из проверенного
публичного интерфейса и его комментариев `///`, проверяя блоки примеров Flick
с доступными импортами пакета. Запускаемые примеры компилируются в памяти и
выполняются через выбранный бэкенд проекта (или `--target <name>`), используя
собственный набор инструментов и среду выполнения этого таргета. Ошибки
разбора, типов, необъявленного импорта (`FLICK-P062`), невыполненного блока
`fail` (`FLICK-P062`) и ошибки времени выполнения (`FLICK-P061`) сообщаются с
диапазонами внутри исходного комментария `///` и не записывают файлы. Private
declarations не становятся отдельными элементами API. Публичный реэкспорт
использует документацию исходной декларации.

`--source-base-url https://host/repo/blob/REV/package` добавляет ссылки на пути
от корня проекта и исходные строки деклараций. Для воспроизводимости укажите
фиксированную ревизию. Без этой опции удалённый URL не угадывается. `--std`
документирует проверенные встроенные модули компилятора, а не компилирует
стандартную библиотеку как пользовательский проект. С `--std` URL соответствует корню репозитория (`packages/core` и `packages/std`).

[API стандартной библиотеки](../../api/) на сайте использует этот Markdown
напрямую, без отдельной модели сигнатур или doc JSON. Декларации API и исходные
комментарии одинаковы для английской и русской навигации. Гайд
[«Свой типизированный DSL»](../../handbook/typed-dsl/) объясняет генерируемые
декларации и различие ошибок компиляции и предметных ошибок.

## Потоки и коды выхода

В stdout попадает только результат работы команды: вывод приложения, отчёт
о тестах или запрошенное представление модуля. Диагностика и служебные сообщения
идут в stderr. При `--diagnostics json` stderr имеет формат NDJSON: по одному
событию на строку, у каждого события есть `schema-version`. Типы событий:
`diagnostic`, `log` (служебные сообщения), `application-stderr` (stderr приложения
или тестов) и `package-manager-output` (вывод инструмента бэкенда). Последние три имеют вид
`{ "type", "channel", "text" }` без ANSI-кодов. Событие `diagnostic` содержит
`code` (`FLICK-…`), `severity` (`error`, `warning`, `note`), `message`, `path`
и `range` (`start`, `end`: смещения в байтах UTF-8, конец не включается;
оба `null`, если у диагностики нет места в коде); затем `related` — связанные места с их
сообщениями — и `fixes` (сообщение и правки, каждая из `path`, `range`
и `replacement`). В режиме human stderr приложения передаётся как есть.
`test --reporter json` пишет свой объект в stdout, а stdout `flick lsp`
принадлежит только протоколу.

`--silent` — псевдоним `--quiet`, допустимый до и после команды.
Он подавляет служебный вывод, но не предупреждения и ошибки, и сохраняет полезный
stdout: например, JSON от `build --inputs` или вывод приложения. Он несовместим
с `--verbose`; `--warnings-as-errors` по-прежнему повышает предупреждения до ошибок
и меняет код выхода.

### Тайминги

`--timings` выводит в stderr после диагностик, сколько заняли этапы команды,
работа, измеренная внутри них (например, проверка встроенных модулей), десять
модулей с самой долгой проверкой и, при промахе кэша сборки, входы, которые
отличаются от последней закэшированной сборки. Время в процессе, который
команда запускает (приложение или тесты), — этап `Running a child process`.
Следящая команда сообщает о каждом прогоне: `check` и `build` после него,
`test --watch` и `dev` после своей сборки.
С `--diagnostics json` отчёт — одно событие типа `timings` с полями `stages`
и `phases` (у каждого `label` и `micros`), `modules` (у каждого `module`
и `micros`, сначала самые медленные) и `cache-misses`. Измерения не входят
в ключ кэша сборки.

Отчёт также говорит, что кэш модулей сделал с каждым модулем прогона:
`reused` (сохранён в памяти следящей командой), `taken from the store`
(сохранён предыдущим процессом), `not storable` (модуль, который сохранённый
ключ не покрывает, например с вложенными модулями), `no earlier entry` или
входы, которые отличаются от входов последней сохранённой записи: `source`,
`file`, `config`, `mode`, `compiler`, `project modules` (модуль добавлен
в прогон или удалён из него), `plugin inputs`, `plugin output`,
`module arguments` и `import M`, за которым следует то, что изменилось в `M`
(`import App.Base ← source`). Отчёт для человека считает их и перечисляет
модули, проверенные заново, не больше двадцати; с `--diagnostics json`
в событии есть `module-cache`, у каждой записи `module` и её `reason`,
по порядку модулей. Причина называет вход, но не его значение. `cache-misses`
объясняет, почему вся сборка не взята из кэша сборки; эти причины объясняют
проверку каждого модуля.

Явные `build` и `build --watch` показывают одну обновляемую строку с текущим этапом
и прошедшим временем, если stderr — TTY, `TERM` не равен `dumb`, а `CI` не задан.
При перенаправлении в pipe, в CI и dumb-терминалах каждый этап занимает отдельную
строку без анимации. Цвет зависит от `--color` и `NO_COLOR`; отключение цвета
не отключает анимацию. Обновляемая строка стирается до диагностики и итогового сообщения.
Внутренние сборки в `run`, `dev` и `pack` этот прогресс не показывают.
Успешный `build --inputs` выводит только JSON-инвентарь, без прогресса и итога.

| Код | Значение |
| - | - |
| `0` | успех; для `fmt --check` — все файлы отформатированы |
| `1` | ошибки в коде, неудачные тесты, неотформатированный файл, ошибка приложения или очистки |
| `2` | неверный вызов или конфигурация, отсутствующая или неподходящая зависимость либо набор инструментов |
| `3` | внутренняя ошибка Flick |
| `130` / `143` | приложение остановлено сигналом SIGINT / SIGTERM, очистка завершилась успешно |

## Команды плагинов и официальные бэкенды

Все разделы выше описывают нейтральное к экосистемам ядро `flick`. Встроенные
плагины и официальные целевые бэкенды добавляют собственные команды, опции
таргета, шаблоны проектов, управление пакетами, шаги упаковки и проверки
окружения (см. [Добавленные команды](../commands/)).

### Встроенный `std`

| Команда | Действие |
| - | - |
| `schema export <M.codec> --target json-schema-2020-12 --out <file>` | команда `std` (`std:schema export`): выводит строгую JSON Schema кодека `PureCodec Json a`, запуская экспортёр через выбранный бэкенд проекта |
| `schema export <M.api> --target openapi-3.1 --out <file>` | команда `std` (`std:schema export`): выводит значение `HttpApi.Api` как документ OpenAPI 3.1 — тот же, что строит `HttpApi.openapi`, — через выбранный бэкенд проекта (см. [Клиенты и документы](../http-api/#клиенты-и-документы)) |

`schema export` (также вызывается как `flick std:schema export`) компилирует
модуль-экспортёр в памяти в контексте проекта и запускает его через выбранный
бэкенд в изолированном временном поколении, не записывая сгенерированные модули
в дерево проекта. Схема, которую нельзя строго экспортировать, завершается с
`FLICK-D008`, указывая на экспортируемое объявление.

### Бэкенд `flick/js` (`--target js`, по умолчанию)

Выбирается через `--target js`, `[build] target = "js"` или как целевой бэкенд
по умолчанию, если таргет не задан.

| Команда | Действие |
| - | - |
| `ffi import <pkg> --out <dir> [--select a,b]` | команда JavaScript-бэкенда (`js:ffi import`): читает `.d.ts` установленного пакета и записывает `<dir>/<Pkg>/Generated.fl` с отчётом о покрытии; `--select` импортирует только перечисленные экспорты (см. [Импорт `.d.ts` пакета](../ffi/#импорт-dts-пакета)) |
| `ffi check [paths]` | команда JavaScript-бэкенда (`js:ffi check`): сверяет сгенерированные и проверенные привязки и их политики с установленными пакетами; если пути не указаны, проверяет корневой каталог исходников |
| `content-mapper [--declarations <paths>…]` | сессионная команда JavaScript-бэкенда (`js:content-mapper`): обслуживает через stdio запросы [Content Mapper](../editor/#content-mapper) TypeScript для файлов `.fl`; его запускает `@flick-lang/content-mapper`; с `--declarations` вместо этого записывает проекцию каждого файла `.fl` из указанных путей рядом с ним как `Name.d.fl.ts` и завершается |

- **Опции (`[target.js]`)**: `--typescript` (`build`, `inspect`),
  `--declarations` (`build`), `--promise-facade` (`build`), `--schema-aot`
  (`build`; запускает шаг инструмента `node`, требуя `"node"` в `[tools]` или
  `--allow-tool node` вне проекта), `--runtime rt|effect` (`build`, `run`,
  `dev`, `test`, `inspect`; по умолчанию `rt`), `--devtools[=url]` (`run`,
  `dev`; отправляет спаны серверного входа в Effect DevTools, URL по умолчанию
  `ws://localhost:34437`, см. [наблюдаемость](../observability/#devtools)) и
  `--ui <specifier>` (`build`, `run`, `dev`, `test`).
- **Шаблоны проектов**: `app`, `cli` (вход с [блоком `cli`](../cli-dsl/)),
  `fullstack` (серверный и клиентский входы с общим модулем
  [`server fn`](../server-fn/) и Vite), `lib` и `plugin` (библиотека с крейтом
  [плагина](../plugins/) в `plugin/`).
- **Клиентский раннер**: клиентские входы (`target = "client"`) запускаются
  через Vite командами бэкенда `run-client` и `dev-client` (требуя `"node"` в
  `[tools]`).
- **Входы кеша сборки**: `package.json`, `pnpm-lock.yaml`, а также манифесты и
  исходники Flick установленных пакетов.
- **Зависимости**: команды зависимостей запускают `pnpm` (требуется разрешение
  `[tools] "flick/js" = ["pnpm"]` в `flick.toml`, иначе `FLICK-P051`). Перед
  изменением `package.json`, его файла блокировки или дерева зависимостей каждая
  команда проверяет, что `pnpm --version` совпадает с версией, закреплённой в
  `packageManager`. При несовпадении команда завершается с `FLICK-P016` и кодом
  выхода 2, ничего не меняя: сообщение называет закреплённую версию и способ её
  включить, а `flick doctor` показывает обе версии. Вызов `install --locked` без
  `pnpm-lock.yaml` или с устаревшим файлом приводит к `FLICK-P017` с кодом
  выхода 2.
- **Упаковка (`pack`)**: подготавливает `package.json` с полями `bin` для
  входов, проверяет компаньоны `.iface`/`.d.ts` и `exports` и при наличии
  `package.json` у приложения запускает закреплённый `pnpm pack` для создания
  npm-архива.
- **Проверки окружения (`doctor`)**: проверяет Node.js, pnpm,
  `@flick-lang/runtime`, `effect`, Content Mapper и необязательные адаптеры, не
  упоминая Go.

Удалённые прежние флаги (`FLICK-P057`) для `flick/js`:

| Удалённый флаг | Замена |
| - | - |
| `build --emit js` / `test --emit js` | `--target js` (или не указывать; `js` — по умолчанию) |
| `build --emit ts` | `--target js --typescript` (или `[target.js] typescript = true`) |
| `build --emit-dts` | `--declarations` (или `[target.js] declarations = true`) |
| `build\|run\|dev\|test --rt` | `--runtime rt` (по умолчанию для `flick/js`; для Effect — `--runtime effect`) |
| `inspect <M> --emit js` | `inspect <M> --emit output --target js` |
| `inspect <M> --emit ts` | `inspect <M> --emit output --target js --typescript` |

### Бэкенд `flick/go` (`--target go`)

Выбирается через `--target go` или `[build] target = "go"`.

- **Опции (`[target.go]`)**: `--cgo` (`build`, `run`, `dev`, `test`; включает
  `CGO_ENABLED=1`, по умолчанию `false`).
- **Шаблоны проектов**: `app`, `cli`, `lib` и `plugin` (с
  `[build] target = "go"`, `[tools] "flick/go" = ["go"]` и без `package.json`).
- **Зависимости**: не управляет собственными пакетами; `flick install`
  обрабатывает `[dependencies]` Flick без Node и pnpm, а операции над пакетами
  экосистемы вроде `flick add <pkg>` (без `--path`, `--git` или `--url`)
  завершаются с `FLICK-P063`.
- **Клиентский раннер**: клиентские входы (`target = "client"`) не
  поддерживаются (`FLICK-P067`).
- **Упаковка (`pack`)**: не объявляет команду `pack`; выполняет проверку
  фронтенда с учётом таргета и записывает только архив исходников Flick без
  Node, pnpm и `go`.
- **Проверяемые примеры документации (`doc --check-examples`)**: компилирует и
  запускает примеры как нативные исполняемые файлы Go без Node.
- **Проверки окружения (`doctor`)**: проверяет `go` и `[tools]`, не проверяя
  Node.js и pnpm.

Удалённые прежние флаги (`FLICK-P057`) для `flick/go`:

| Удалённый флаг | Замена |
| - | - |
| `build --emit go` / `test --emit go` | `--target go` (или `[build] target = "go"`) |

### Встроенный таргет `flick/vm` (`--target vm`)

Выбирается через `--target vm`, `[build] target = "vm"` или `[build] environment = "vm/native"`.
Исполняет скомпилированные программы и наборы тестов Flick непосредственно внутри процесса на встроенной виртуальной машине без запуска `node` или `go`.

- **Опции (`[target.vm]`)**: `--vm-tier <tier>` (`run`, `test`, `repl`; принимает `0`, `tier0`, `1` или `tier1`, по умолчанию `0`; также настраивается через `[target.vm] tier = "0" | "tier0" | "1" | "tier1"` в `flick.toml`).
- **Сборка (`build`)**: компилирует проект или отдельный файл `.fl` в автономные образы ВМ `.fvm` в `out-dir` (`flick build --target vm` с поддержкой `--profile debug` и `--profile release`). Образы используют самоописываемый бинарный формат `FLKM` с замкнутыми интерфейсами модулей, IR памяти, необязательными метаданными подготовки уровня 1 и точными хешами ревизии компилятора и IR.
- **Запуск (`run`)**: исполняет вход проекта (`flick run --target vm`), отдельный исходный файл (`flick run --target vm path/to/file.fl`) или собранный образ ВМ (`flick run --target vm path/to/main.fvm`) внутри процесса на эталонной ВМ уровня 0 (по умолчанию) или на регистровой байткод-ВМ уровня 1 (`--vm-tier 1|tier1`) с поддержкой `--profile debug` и `--profile release`. Уровень 1 исполняет синхронный код, глубокие однократные обработчики алгебраических эффектов (`tail`, `abort`, `control`), типизированное восстановление `try` и LIFO-финализаторы областей; любая достижимая операция вне этого подмножества (например, `Task`/`Await`, генераторы или `ForeignCall`) завершается с `FLICK-P012` с именем операции и позицией в исходном коде (без скрытого отката на уровень 0).
- **Тестирование (`test`)**: исполняет тесты проекта внутри процесса (`flick test --target vm`) с поддержкой `--filter`, `--list`, `--seed`, `--reporter human|json` и `--profile`.
- **Интерактивный REPL (`repl`)**: запускает постоянные сессии REPL внутри процесса (`flick repl`) с поддержкой сервисов `Host.live`, автоматического ожидания задач `Eff`, прерывания по `SIGINT` с LIFO-финализацией областей и команд сессии `:handle <expr>`, `:provide <expr>`, `:bg <expr>`, `:jobs`, `:kill <n>` и `:quit`/`:q`.
- **Текущие границы поддержки**: `flick dev --target vm` и `flick inspect --emit output --target vm` пока не поддерживаются и завершаются с `FLICK-P012`.
- **Проверки окружения (`doctor`)**: сообщает о доступности встроенной ВМ и активном уровне без проверки Node.js или Go.
- **Фича Cargo**: включена в `flick` по умолчанию (фича `vm`); сборки с `--no-default-features` исключают ВМ и сообщают `FLICK-P013` при выборе `--target vm`.
