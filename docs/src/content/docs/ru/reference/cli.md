`flick` — исполняемый файл с командами компилятора. Все команды принимают
глобальные параметры `--project <path>`, `--package <name>` (`-p`, участник
[workspace](../project/#workspace)), `--diagnostics human|json`,
`--warnings-as-errors`, `--color auto|always|never`, `--quiet` (псевдоним `--silent`)/`--verbose`,
`--offline` (без сети: [плагины](../plugins/#доступ-вовне) отвечают из
снимков проекта, то же значит заданная `CI`, а `install` ставит из
хранилища) и `--help`. Команда `flick help <command>` выводит справку по выбранной команде,
а `flick --version` — версию компилятора. Остальные сведения показывает `flick doctor`.

## Команды

| Команда | Действие |
| - | - |
| `new <dir> [--template app\|cli\|fullstack\|lib\|plugin]` | создаёт проект: `flick.toml`, `package.json`, пример модуля и его тест; `cli` делает `main` [блоком `cli`](../cli-dsl/); `plugin` — библиотека с [плагином](../plugins/), его крейт в `plugin/` и `flick run plugin` для сборки; `fullstack` — серверный вход и страница браузера (`target = "client"`), общие вызовы модуля [`server fn`](../server-fn/), запись под `Server.authenticated`, Vite для страницы |
| `init [--template app\|cli\|fullstack\|lib]` | создаёт те же файлы в рабочем каталоге; перед записью сообщает обо всех файлах, которые уже существуют (`FLICK-P019`) |
| `check [paths] [--watch] [--fix [--only codes]]` | проверяет код; если пути не указаны, проверяет корневые каталоги исходников и тестов; `--fix` применяет к этим файлам исправления, не меняющие смысла программы (например, убирает избыточную аннотацию типа, `FLICK-T021`), и сообщает об оставшихся проблемах; `--only E002,F001` применяет только исправления этих кодов — для миграции, которая больше ничего не меняет |
| `build [paths] [--profile] [--labels all\|components\|none] [--emit js\|ts\|go] [--emit-dts] [--promise-facade] [--emit-ir[=json\|cbor]] [--schema-aot] [--out-dir] [--watch]` | записывает ESM, карты исходников и файлы `.iface` (`--emit go` — исполняемый файл Go для каждого входа, см. [Go-target](../codegen/#go-target)); `--emit-dts` добавляет файлы `.d.ts`, а `--promise-facade` — Promise-фасады `A/B.promise.js` (см. [TypeScript](../codegen/#typescript)); `--emit-ir` добавляет `program.ir.json` (или `program.ir.cbor`) — IR, который получает бэкенд, оптимизированный в release-сборке, с версией IR, в которой он записан; показывает в stderr этапы сборки, затем число модулей и раннеры входов либо число и расположение ошибок; `--silent`/`--quiet` и `--diagnostics json` отключают прогресс и итог |
| `build [paths] --inputs` | выводит консервативный JSON-инвентарь входов (`key`, `files`, `roots`, `modules`), не записывая артефакты и кеш |
| `run [name] [--entry M] [--profile] [--devtools[=url]] -- args` | собирает JavaScript (исполняемый файл Go при `emit = "go"`) и запускает `main` входа `name` (единственного, если имя не указано); `name`, который не является входом, запускает скрипт из [`[scripts]`](../project/#скрипты): его команды по порядку до первой упавшей, `args` — их `"$@"`; клиентский вход (`target = "client"`) собирает страницу через Vite и запускает Vite preview; `--devtools` отправляет спаны серверного входа в Effect DevTools ([наблюдаемость](../observability/#devtools)) |
| `dev [name] [--entry M] [--profile] [--devtools[=url]] -- args` | пересобирает при изменениях и заменяет работающее приложение; в проекте с несколькими входами без имени запускает каждый неклиентский вход и, если есть клиентский, Vite (`node_modules/.bin/vite`) для страниц: изменённый модуль заменяется в странице, а помеченные атомы сохраняют значения |
| `test [paths] [--filter] [--jobs] [--seed] [--reporter human\|json] [--watch] [--profile] [--emit js\|go]` | запускает тесты из корневого каталога тестов на Node или исполняемым файлом Go |
| `fmt [paths] [--check] [--stdin --stdin-filepath f]` | записывает код в каноническом формате ([форматирование](../grammar/#форматирование)); если пути не указаны, обрабатывает корневые каталоги исходников и тестов |
| `clean [--cache]` | удаляет артефакты сборки; с `--cache` — также кеш сборки |
| `install [--locked]` | устанавливает зависимости с помощью pnpm (`--frozen-lockfile`, а с глобальным `--offline` — `--offline`); в корне workspace — каждого участника |
| `add <pkg>… [--dev]`, `remove <pkg>…`, `update [pkg]…` | изменяет зависимости с помощью pnpm |
| `deps [--why <pkg>]` | показывает установленный граф зависимостей и модули Flick каждой прямой зависимости |
| `plugins` | показывает плагины проекта, первыми плагины самого компилятора: откуда каждый, хэш его компонента и закрепляет ли эту сборку `flick.lock` |
| `pack --out-dir <dir>` | собирает проект в профиле release и создаёт tar-архив npm-пакета; отказывает при `todo` и `echo` (`FLICK-P024`) и предупреждает, если изменения публичного API нарушают совместимость с импортирующим кодом со времени последнего тега |
| `diff [ref]` | изменения публичного API со времени ревизии git (по умолчанию последнего тега): `MAJOR` (удалено или изменено) или `MINOR` (добавлено), и версия, которую они требуют, от версии в `package.json` |
| `ffi import <pkg> --out <dir> [--select a,b]` | читает `.d.ts` установленного пакета и записывает `<dir>/<Pkg>/Generated.fl` с отчётом о покрытии; `--select` импортирует только перечисленные экспорты (см. [Импорт `.d.ts` пакета](../ffi/#импорт-dts-пакета)) |
| `ffi check [paths]` | сверяет сгенерированные и проверенные привязки и их политики с установленными пакетами; если пути не указаны, проверяет корневой каталог исходников |
| `schema export <M.codec> --target json-schema-2020-12 --out <file>` | выводит строгую JSON Schema кодека `PureCodec Json a` |
| `schema export <M.api> --target openapi-3.1 --out <file>` | выводит значение `HttpApi.Api` как документ OpenAPI 3.1 — тот же, что строит `HttpApi.openapi` (см. [Клиенты и документы](../http-api/#клиенты-и-документы)) |
| `doc --out-dir <dir>` | создаёт Markdown-страницы публичного API: типы, кинды, ограничения, эффекты, захваты |
| `explain <code>` | объясняет сообщение диагностики по его коду, в том числе код плагина, как `std/L001` |
| `expand [paths]` | выводит код, в который раскрывается каждый блок [плагина](../plugins/) проекта или файлов |
| `doctor` | показывает сведения о компиляторе, Node.js, pnpm, git, Content Mapper для TypeScript, установленной среде выполнения и Effect, о необязательных адаптерах и о Go, если он установлен; всё, кроме компилятора, Node.js и pnpm, — заметка, а не ошибка |
| `inspect <M> --emit ast\|typed-ir\|js\|ts\|iface\|mapping` | выводит одно представление модуля |
| `lsp --stdio` | запускает [языковой сервер](../editor/#языковой-сервер); stdio — его единственный транспорт |
| `content-mapper [--declarations <paths>…]` | обслуживает через stdio запросы [Content Mapper](../editor/#content-mapper) TypeScript для файлов `.fl`; его запускает `@flick-lang/content-mapper`; с `--declarations` вместо этого записывает проекцию каждого файла `.fl` из указанных путей рядом с ним как `Name.d.fl.ts` и завершается |

В корне workspace без `[project]` команды `check`, `build`, `test`, `fmt` и
`clean` без путей, а также `install` выполняются для каждого участника,
сначала для зависимостей.

`check`, `build` и этапы сборки в `run`, `dev` и `test` ничего не устанавливают,
не запускают `main` и не загружают внешние модули. Если версия установленного
`@flick-lang/runtime` или `effect` отличается от закреплённой компилятором,
эти команды завершаются с `FLICK-P015` (код выхода 2).
`schema export` загружает только модуль, создающий кодек, и ничего больше.
Код верхнего уровня этого модуля чистый.

`test` выводит human-результаты сразу после освобождения ресурсов каждого теста: маркер успеха или ошибки, счётчик и время, затем общий итог. Node и Go используют один формат и учитывают `--color`; автоматический цвет проверяет stdout, `NO_COLOR` и `TERM=dumb`. `--reporter json` выводит один итоговый объект в порядке объявления, без цвета и длительностей.

## Выходные файлы и кеш

Сборка записывает файлы в `build.out-dir` (или `--out-dir`) и сохраняет их
список в `.flick/artifacts.json`. После успешной публикации удаляются устаревшие
файлы из прежнего списка, в том числе при смене формата генерации и попадании
в кеш. `clean` удаляет оставшиеся принадлежащие сборке файлы и пустые каталоги.
Пользовательские файлы в общем выходном каталоге сохраняются.

Кеш в `.flick/cache/` хранит артефакты каждой сборки. Ключ кеша учитывает
нормализованный набор выбранных корневых файлов отдельно от доступных
исходников проекта, его итоговую конфигурацию, профиль, настройки генерации
и вывода, компилятор (версию и исполняемый файл), установленные среду выполнения
и Effect, `package.json`, `pnpm-lock.yaml`, а также манифесты и интерфейсы
установленных зависимостей. Если любые из этих данных изменились, сборку
нельзя взять из кеша. При использовании кеша записываются ровно те файлы,
которые создала бы сборка.

Команды с `--watch` сравнивают состояние каждого пути, включая создание
и удаление файлов. Временная метка одного файла не скрывает изменение другого.

## Запуск и замена приложения

`run` и `dev` собирают JavaScript, а при `emit = "go"` — исполняемый файл Go
для каждого входа. Каждая
сборка хранится в атомарно зарезервированном каталоге `.flick/run/<pid>-<n>/`.
После запуска процесса файлы поколения больше не перезаписываются, поэтому
поздний `import()` видит исходную версию. CLI владеет поколением от начала
сборки до завершения очистки; `clean` сохраняет каталоги, зарезервированные для активных сборок
и работающие дочерние процессы. После завершения поколение удаляется.

`dev` собирает следующую версию, пока текущая работает. Если сборка не удалась,
текущая версия продолжает работать. После успешной сборки `dev` сначала
останавливает текущую версию так же, как SIGTERM: запускающий процесс прерывает
`main`, ждёт завершения его файберов и выполняет финализаторы. Только после
этого запускается новая версия. Если завершение работы не удалось (код выхода
отличается от 143), `dev` прекращает перезапуски с `FLICK-P021`.
Сообщение запускающего процесса о причине остаётся в stderr.

SIGINT и SIGTERM передаются приложению; `flick` завершается только после него
и с его кодом выхода.

## Зависимости

`install` и `update` сначала скачивают библиотеки Flick, которые закрепляет
`flick.lock`, а `add` с `--git`, `--url` или `--path` и `remove` меняют
`[dependencies]` (см. [проект](../project/#зависимости-flick)). Для
npm-пакетов команды используют pnpm. Перед изменением `package.json`, его
файла блокировки или дерева зависимостей каждая команда проверяет,
что `pnpm --version` совпадает с версией, закреплённой в `packageManager`.
При несовпадении команда завершается с `FLICK-P016` и кодом выхода 2,
ничего не меняя: сообщение называет закреплённую версию и способ её
включить, а `flick doctor` показывает обе версии. Вызов `install --locked`
без `pnpm-lock.yaml` или с устаревшим файлом приводит к `FLICK-P017`
с кодом выхода 2.

`pack` собирает проект в профиле release и отказывает, если в нём остались
`todo` или `echo` (`FLICK-P024`). Библиотека с `[package]` пакует свои
исходники: `<name>-<version>.tgz` содержит её `flick.toml`, каталог
исходников, readme и лицензию под `package/`, без временных меток и сведений о владельцах,
поэтому одни и те же исходники дают одни и те же байты; в stdout — sha256,
который называет `url`-зависимость. Приложение пакуется во временный пакет
вместе с раннером каждого входа, который подготовленный
`package.json` указывает в `bin` (см. [проект](../project/#точки-входа)).
Затем команда проверяет, что у каждого модуля есть `.iface`
(и `.d.ts` при `emit-dts`), отпечатки интерфейсов внутри пакета согласованы
друг с другом, а пути из `exports` существуют (`FLICK-P020`).
После этого `pack` записывает tar-архив с помощью `pnpm pack`.

## Потоки и коды выхода

В stdout попадает только результат работы команды: вывод приложения, отчёт
о тестах или запрошенное представление модуля. Диагностика и служебные сообщения
идут в stderr. При `--diagnostics json` stderr имеет формат NDJSON: по одному
событию на строку, у каждого события есть `schema-version`. Типы событий:
`diagnostic`, `log` (служебные сообщения), `application-stderr` (stderr приложения
или тестов) и `package-manager-output` (pnpm). Последние три имеют вид
`{ "type", "channel", "text" }` без ANSI-кодов. Событие `diagnostic` содержит
`code` (`FLICK-…`), `severity` (`error`, `warning`, `note`), `message`, `path`
и `range` (`start`, `end`: смещения в байтах UTF-8, конец не включается;
оба `null`, если у диагностики нет места в коде); затем `related` — связанные места с их
сообщениями — и `fixes` (сообщение и правки, каждая из `path`, `range`
и `replacement`). В режиме human stderr приложения передаётся как есть.
`test --reporter json` пишет свой объект в stdout, а stdout `flick lsp`
принадлежит только протоколу.

`--silent` — псевдоним `--quiet`, допустимый до и после команды.
Он подавляет служебный вывод, но не предупреждения и ошибки, и сохраняет полезный
stdout: например, JSON от `build --inputs` или вывод приложения. Он несовместим
с `--verbose`; `--warnings-as-errors` по-прежнему повышает предупреждения до ошибок
и меняет код выхода.

Явные `build` и `build --watch` показывают одну обновляемую строку с текущим этапом
и прошедшим временем, если stderr — TTY, `TERM` не равен `dumb`, а `CI` не задан.
При перенаправлении в pipe, в CI и dumb-терминалах каждый этап занимает отдельную
строку без анимации. Цвет зависит от `--color` и `NO_COLOR`; отключение цвета
не отключает анимацию. Обновляемая строка стирается до диагностики и итогового сообщения.
Внутренние сборки в `run`, `dev` и `pack` этот прогресс не показывают.
Успешный `build --inputs` выводит только JSON-инвентарь, без прогресса и итога.

| Код | Значение |
| - | - |
| `0` | успех; для `fmt --check` — все файлы отформатированы |
| `1` | ошибки в коде, неудачные тесты, неотформатированный файл, ошибка приложения или очистки |
| `2` | неверный вызов или конфигурация, отсутствующая или неподходящая зависимость либо набор инструментов |
| `3` | внутренняя ошибка Flick |
| `130` / `143` | приложение остановлено сигналом SIGINT / SIGTERM, очистка завершилась успешно |
