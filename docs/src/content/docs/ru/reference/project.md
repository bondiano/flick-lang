Проект — каталог с `flick.toml` (см. [CLI компилятора](../cli/)).
Команды ищут ближайший `flick.toml`, начиная с рабочего каталога и поднимаясь
по дереву каталогов. Параметр `--project <path>` позволяет явно указать
каталог проекта или файл конфигурации. Несколько проектов образуют
[workspace](#workspace), и `--package <name>` выбирает одного из его участников.

## `flick.toml`

```toml
schema-version = 1

[project]
kind = "app"
source-dir = "src"
test-dir = "test"
entry = "App.Main"

[build]
out-dir = "dist"
profile = "debug"
target = "js"

[target.js]
typescript = false
declarations = false
promise-facade = false
schema-aot = false
runtime = "rt"

[sql]
dialect = "postgresql"

[lint]
allow = ["FLICK-T021"]
no-let-assert = false
unused-proof-premises = false
max-function-lines = 60
max-nesting = 4
max-complexity = 10
max-params = 5
```

| Ключ | Значения | По умолчанию |
| - | - | - |
| `schema-version` | `1`; обязателен, проверяется до остальных ключей | — |
| `project.kind` | `"app"` или `"lib"`; обязателен | — |
| `project.source-dir` | каталог исходных модулей | `"src"` |
| `project.test-dir` | каталог тестовых модулей | `"test"` |
| `project.proof-dir` | каталог модулей доказательств, которые проверяет только `flick prove` | `"proofs"` |
| `project.entry` | модуль, экспортирующий `main`, свой или реэкспортированный: вход `main` с раннером `flick-main.js` | — |
| `project.entries` | несколько входов, `{ server = "App.Server", cli = "App.Cli" }`: по раннеру `flick-<name>.js` на каждый; вход со своим runner'ом — таблица, `web = { module = "App.Worker", runner = "Runner.Cloudflare" }`; `target = "client"` — вход, который работает в браузере: ничто из достижимого из его `main` не может требовать `Server` (`FLICK-E009` с путём до него), поэтому его бандл не содержит серверных модулей; имена — строчные латинские буквы, цифры и `-`; вместо `entry` | — |
| `project.runner` | модуль, который запускает каждый вход без своего runner'а: экспортирует `type alias Main` — тип, который должен иметь `main` (иначе `FLICK-P026`), — и `run`, который принимает `main`; раннер экспортирует его результат как `default`; встроены `"Runner.Node"`, `"Runner.Browser"` и `"Runner.Cloudflare"` — Worker, чей `fetch` передаёт `main : Runner.Cloudflare.Fetch ->{Runner.Cloudflare.Env; AppError} Http.ServerResponse.ServerResponse` запрос и контекст (`wait_until`), а привязки предоставляет сервисом `Env` (`Runner.Cloudflare.var`, `binding`) вместе с живыми браузерными сервисами `Host.BrowserLive`; так runner может предоставлять сервисы, и `main` может требовать любые из тех, что названы в его `Main`; другой может дать пакет; без него чистый `main` вызывается, а эффект выполняется как на Node | — |
| `build.out-dir` | базовый каталог для артефактов сборки; не корень проекта, не каталог исходников или тестов и не каталог над ними (`FLICK-P028`, до любой записи) | `"dist"` |
| `build.profile` | `"debug"` или `"release"` (см. [генерацию кода](../codegen/)); `--profile` у `build` и `test` переопределяет это значение | `"debug"` |
| `build.target` | короткое имя бэкенда по умолчанию (`"js"`, `"go"` или короткое имя закреплённого `[build.backend]`); переопределяется через `--target <name>` у `build`, `run`, `dev`, `test`, `pack` и `inspect`. Для `"go"` Go должен быть в `PATH` и разрешён в `[tools]` как `"flick/go" = ["go"]` (`FLICK-P029`), достижимые обращения к модулям только для js (`Ui`, `Atom`, `Action`, `Form`, `Otlp`, `DevTools`, `Js`, `Reactivity.*`, runner'ы `Node`/`Browser`/`Cloudflare`) или другим ограниченным модулям дают `FLICK-P064` уже в `flick check`, редакторе и `flick build` (неиспользуемые импорты не считаются ошибкой), а то, что Go-target ещё не компилирует, — `FLICK-P012` (см. [Go-target](../codegen/#go-target)) | `"js"` (или префикс бэкенда из `build.environment`) |
| `build.environment` | пара `<backend>/<host>`, например `"js/node"`, `"js/browser"`, `"js/bun"`, `"js/cloudflare"`, `"go/native"` или хост из пакета зависимости с `[host]`; раскрывается в активные теги бэкенда и теги хоста. Неизвестный бэкенд даёт `FLICK-P059`, неизвестный или несовместимый хост — `FLICK-P065`, неизвестный тег в условии — `FLICK-P066`. `flick check`, редактор и `flick build` делят предварительную проверку достижимости: недоступные модули, пакеты и привязки адаптера Effect дают `FLICK-P064` на месте использования с путём от входа, а достижимые ограниченные эффекты без корневого обработчика — `FLICK-E020`. Неиспользуемые импорты и недостижимые функции не ломают проверку; публичные экспорты библиотек проверяются по политике экспорта | окружение по умолчанию выбранного бэкенда |
| `build.solver-steps` | число шагов разрешения экземпляров классов для одного определения | `100000` |
| `build.solver-depth` | глубина вложенности ограничений классов | `256` |
| `build.labels` | что release-сборка помечает `Module.name` для инструментов отладки: `"all"` (значения всех типов с `@label`: атомы, представления, actions), `"components"` (значения вида `component`: представления и actions) или `"none"`; debug помечает всё; `flick build --labels` переопределяет | `"all"` |
| `sql.dialect` | диалект SQL для `sql table` и `sql { … }` (см. [запросы SQL](../sql/)): `"postgresql"`; `"mysql"`, `"sqlite"`, `"clickhouse"` и `"oracle"` распознаются, но пока не поддерживаются | `"postgresql"` |
| `lint.allow` | коды предупреждений, о которых не сообщается, например `"FLICK-T021"`; ошибки отключить нельзя | `[]` |
| `lint.no-let-assert` | `true` делает каждый `let assert` ошибкой (`FLICK-T027`) в `flick check`, `build`, `test` и в редакторе | `false` |
| `lint.unused-proof-premises` | `true` включает предупреждение о неиспользуемых посылках проверенных доказательств (`FLICK-T092`) в `flick prove` и редакторе | `false` |
| `lint.max-function-lines` | сколько строк может занимать тело функции, дальше — `FLICK-T036` | `60` |
| `lint.max-nesting` | насколько глубоко вкладываются `if`, `match`, `fun`, `do`, `task` и `for`, дальше — `FLICK-T037` | `4` |
| `lint.max-complexity` | сколько ветвлений может быть в функции (цикломатическая сложность), дальше — `FLICK-T038` | `10` |
| `lint.max-params` | сколько параметров может быть у функции, дальше — `FLICK-T039` | `5` |
| `plugins.<пакет>` | к чему плагин зависимости может обращаться для блоков проекта: `fs-read` (пути от корня проекта), `net` (`host` или `host:port`) и `env` (имена); не в корне workspace (см. [Доступ вовне](../plugins/#доступ-вовне)) | ничего |
| `tools.<id>` | инструменты хоста, `"node"` или `"go"`, которые могут запускать шаги сборки бэкенда или плагина `<id>`, например `"flick/go" = ["go"]`; шаг с другим инструментом — `FLICK-P051` до запуска чего-либо. Компилятор находит разрешённый инструмент в `PATH`, закрепляет его хеш и версию и запускает каждый шаг в каталоге рядом с выходным, только с объявленными входами шага и очищенным окружением; выходы публикуются вместе с остальной сборкой или не публикуются вовсе (`FLICK-P050`). Инструменту, который только запускает программу, например Node для `flick run`, запись не нужна | ничего |

Лимиты T036–T038 действуют и для `component`: setup и render измеряются вместе по исходному телу, без сгенерированных обёрток. Локальные функции измеряются отдельно.

### Опции таргета (`[target.<name>]`)

Специфичные для бэкенда опции сборки и выполнения задаются в `[target.<name>]`,
где `<name>` — короткое имя бэкенда (`js` для `flick/js`, `go` для `flick/go`
или часть после `/` в закреплённом `[build.backend]`). В одном `flick.toml`
могут сосуществовать несколько таблиц `[target.<name>]` для мультитаргетных
проектов; каждый вызов проверяет и применяет только таблицу выбранного таргета,
а флаги CLI переопределяют `flick.toml`. Раздел `[target]` запрещён в корне
виртуального workspace (`FLICK-P005`).

| Таблица и ключ | Значения | По умолчанию |
| - | - | - |
| `target.js.typescript` | логическое значение; генерировать `.ts` вместо `.js` | `false` |
| `target.js.declarations` | логическое значение; генерировать публичные объявления TypeScript `.d.ts` | `false` |
| `target.js.promise-facade` | логическое значение; генерировать Promise-фасады `A/B.promise.js` | `false` |
| `target.js.schema-aot` | логическое значение; компилировать чистые кодеки заранее в раннерах входов (требует `"node"` в `[tools]` или `--allow-tool node` вне проекта) | `false` |
| `target.js.runtime` | `"rt"` на собственной среде Flick или `"effect"` через адаптер Effect; библиотека, от которой зависит проект, компилируется с `runtime` проекта | `"rt"` |
| `target.js.devtools` | логическое значение (`true` = `"ws://localhost:34437"`) или строка WebSocket URL для `run` / `dev` | выкл. |
| `target.js.ui` | спецификатор модуля, который рисует и монтирует представления вместо React (экспортирует все имена, которые `Ui` и `Action` берут из `@flick-lang/effect-ts/ui` и `@flick-lang/effect-ts/ui/react`; относительный путь — от корня проекта) | React |
| `target.go.cgo` | логическое значение; включить cgo (`CGO_ENABLED=1`) при сборке исполняемых файлов Go | `false` |

`flick new` берёт файлы шаблона у выбранного целевого бэкенда (`--target js` по умолчанию создаёт проект на RT с `[tools] "flick/js" = ["pnpm"]`, зависимостью от `@flick-lang/runtime` и без Effect; `--target go` создаёт проект под Go с `[build] target = "go"`, `[tools] "flick/go" = ["go"]` и без `package.json`) либо у стороннего пакета через `--from`. Передайте `--runtime rt` командам `build`, `run`, `dev`, `test` или `inspect`, чтобы выбрать RT для одного вызова в проекте на Effect. Если проекту нужен адаптер Effect, явно задайте `[target.js] runtime = "effect"` и добавьте зависимость `@flick-lang/effect-ts`.

Прежние ключи в `[build]` (`emit`, `emit-dts`, `promise-facade`, `schema-aot`, `effect`, `ui`) и таблицы `[js]` / `[js.dependencies]` удалены без псевдонимов совместимости и завершаются с `FLICK-P057`, указывая замену в `[build] target` или `[target.js]`:

| Удалённый ключ или таблица | Замена |
| - | - |
| `[build] emit = "js"` | `[build] target = "js"` (или не указывать; `"js"` — по умолчанию) |
| `[build] emit = "ts"` | `[build] target = "js"` и `[target.js] typescript = true` |
| `[build] emit = "go"` | `[build] target = "go"` |
| `[build] emit-dts = true` | `[target.js] declarations = true` |
| `[build] promise-facade = true` | `[target.js] promise-facade = true` |
| `[build] schema-aot = true` | `[target.js] schema-aot = true` |
| `[build] effect = "rt"` | `[target.js] runtime = "rt"` (или не указывать; `"rt"` — по умолчанию) |
| `[build] effect = "effect"` | `[target.js] runtime = "effect"` |
| `[build] ui = "./renderer.mjs"` | `[target.js] ui = "./renderer.mjs"` |
| `[js.dependencies]` | `[target.js.dependencies]` |

### Окружения, хост-пакеты и условия `when`

Каждый компонент бэкенда объявляет в дескрипторе базовые теги окружения, оси выбора тегов и встроенные хосты:

- `flick/js` публикует тег `js`, взаимоисключающую ось `runtime` (`rt` по умолчанию, `effect`), аддитивную ось `adapter` (`effect-adapter`, активен при наличии `@flick-lang/effect-ts` в зависимостях проекта) и встроенные хосты `node`, `browser`, `bun` и `cloudflare`.
- `flick/go` публикует тег `go`, аддитивную ось `cgo` (`cgo`, активен при `[target.go] cgo = true`) и встроенный хост `native`.
- Сторонние бэкенды публикуют собственные теги, оси и хосты по той же схеме дескриптора.

Библиотека (`kind = "lib"`) может также объявить раздел `[host]`, задавая именованный хост `<backend>/<name>` и дополнительные теги:

```toml
[project]
kind = "lib"

[host]
name = "worker"
backend = "js"
requires = "rt || effect"
tags = ["edge"]
```

- `host.name` — имя хоста в `[build] environment = "<backend>/<name>"` (автоматически добавляется как активный тег).
- `host.backend` — короткое имя или идентификатор бэкенда (например, `"js"` или `"flick/js"`).
- `host.requires` — необязательное булево условие над активными тегами бэкенда; невыполненное условие даёт `FLICK-P065` (код выхода `2`).
- `host.tags` — дополнительные теги окружения, активные при выборе этого хоста.

Пакеты и модули ограничиваются нужными окружениями булевыми условиями над тегами с операторами `&&`, `||`, `!` и скобками:

- `[package] when = "<cond>"` в `flick.toml` ограничивает все модули этого пакета.
- `@when "<cond>"` непосредственно перед `module` (или `private module`) ограничивает один модуль:

```flick
@when "js && !browser"
module App.ServerOnly exposing (ready)

ready : Bool
let ready = true
```

Каждый тег в `@when`, `[package] when` и `[host] requires` проверяется по общему словарю известных бэкендов и загруженных `[host]`-пакетов; опечатка сразу даёт `FLICK-P066` (код выхода `1`) на позиции тега. Достижимые из входов и раннеров приложения (или активных публичных экспортов библиотеки) обращения к ограниченным модулям, пакетам или привязкам адаптера Effect сообщаются как `FLICK-P064` (код выхода `1`) на месте использования с путём от входа — одинаково в `flick check`, редакторе и `flick build`. Неиспользуемые импорты и недостижимые функции не считаются ошибкой, а библиотеки пропускают публичные модули, чьё собственное условие ложно в выбранном окружении.

## Точки входа

Входы приложения — это программы, которые оно собирает: `flick build` пишет
рядом с модулями раннер `flick-<name>.js` для каждого входа, а сами модули —
один раз, поэтому точки входа используют общие копии импортируемых модулей. Раннер импортирует `main`
входа — из модуля, где он определён, если вход его реэкспортирует, — и
запускает его; на таргете JS он начинается с `#!/usr/bin/env node`, поэтому
команда `pack` бэкенда `flick/js` указывает каждый раннер в `bin` npm-пакета,
а единственный вход `main` — под именем пакета. `flick run <name>` и
`flick dev <name>` запускают один из входов; если вход один, имя можно не указывать.

Каждый вход экспортирует `main : Unit -> Unit` либо эффектную функцию,
которая принимает и возвращает `Unit`, не требует сервисов, кроме сервисов
`Host.Live` (с runner'ом — кроме тех, что названы в его `Main`, например `Env`
у `Runner.Cloudflare`), и может завершиться только `AppError` (пустая строка ошибок
тоже допустима). `main`, запущенный без runner'а, получает от раннера живые
реализации тех сервисов `Host`, которые названы в его строке (`Console`,
`Clock`, `Random`, `Environment`, `Arguments`, `Process`); раннер импортирует
только их, поэтому `main`, не называющий ни одного, не несёт ни одной. На
Go-target он получает все шесть. То, что `main` предоставляет сам, имеет
приоритет над ними. В песочнице они такие же, но без переменных окружения и
без аргументов, а дочерний процесс там не запустить (см.
[кто их предоставляет](../services/#кто-их-предоставляет)). Предоставляйте
остальные нужные слои и обрабатывайте остальные ошибки внутри `main`, а не в
раннере.

Чистый `main` вызывается напрямую. Обычно его раннер не импортирует среду
выполнения; при `[target.js] schema-aot = true` всё же импортируются функции установки
схем. Эффектный `main` запускается через средство запуска, наблюдающее
итоговый `Exit` (см. [генерацию кода](../codegen/)). Недопустимая сигнатура
даёт `FLICK-P026` при проверке проекта или при сборке отдельного файла.

```toml
[project]
kind = "app"
entries = { server = "App.Server", migrate = "App.Migrate" }
```

Входы веб-страницы — другое: бандлер вроде Vite принимает JavaScript-модули,
которые импортируют нужные `.fl` (см. [генерацию кода](../codegen/));
`entries` — это программы, которые запускает среда выполнения.
## Workspace

Раздел `[workspace]` в `flick.toml` объединяет проекты в рабочую область:
каталоги проектов-участников перечисляются в `members`:

```toml
schema-version = 1

[workspace]
members = ["contract", "server"]
```

Корень без `[project]` сам проектом не является и допускает только
`[workspace]` и `[scripts]`. В нём `flick check`, `build`, `test`, `fmt` и
`clean` без путей, а также `flick install` проходят по всем участникам,
каждого после тех, от кого он зависит по пути, и завершаются ошибкой, если она
была хотя бы у одного. `flick run` запускает скрипт, а `dev` и остальным
командам нужен участник: `--package <name>`
(`-p`), имя его каталога. Внутри участника команды, как обычно, работают с ним,
а `--package` выбирает другого.

Корень может дать всем участникам плагин — зависимостью и правами:

```toml
[[workspace.plugins]]
package = "mysql"
source = { path = "plugins/mysql" }   # от корня, или источник git или url
grants = { fs-read = ["schema/"], net = ["localhost:3306"] }
```

Тогда каждый участник, кроме пакета самого плагина, зависит от `mysql` и даёт
ему права `grants` корня вдобавок к своим `[plugins.mysql]`; `fs-read`
отсчитывается от каталога участника. Участник, который берёт `mysql` из другого
источника, получает `FLICK-P005`. Участник с плагином идёт раньше остальных, а
`flick pack` отказывается упаковать библиотеку, получившую плагин так: в
опубликованном манифесте его не будет, поэтому его пишут в `[dependencies]`.

## Зависимости Flick

Проект компилирует библиотеки Flick, от которых зависит, из их исходников.
`[dependencies]` называет у каждой один источник: каталог относительно
`flick.toml`, тег git-репозитория (с каталогом библиотеки в нём, `subdir`)
или tar.gz-архив с его sha256:

```toml
[dependencies]
contract = { path = "../contract" }
std = { git = "https://github.com/bondiano/flick-lang", tag = "std-v0.1.0", subdir = "packages/std" }
text = { url = "https://example.com/text-1.0.0.tgz", sha256 = "<64 шестнадцатеричные цифры>" }
```

Проект видит эти неявные пакеты с исходниками, не называя их. Имена модулей
Flick сохраняются: запись импортов `Stream`, `HttpApi` и `Rpc` менять не нужно.

| Пакет | Модули исходников | Использует |
| - | - | - |
| `std` | значения, эффекты, ресурсы и конкурентность | ядро компилятора |
| `stream` | `Channel`, `Sink`, `Stream` и их части | `std` |
| `process` | `ChildProcess` | `std`, `stream` |
| `ui` | реактивность, `Atom`, `Ui`, `Form`, `Action` | `std`, `stream` |
| `http` | `Http.*`, `HttpApi` и `Runner.Cloudflare` | `std`, `stream` |
| `rpc` | `Rpc`, `Server` и `Config` | `std`, `stream`, `http` |
| `observability` | `Otlp`, `Prometheus`, `DevTools` | `std`, `http` |
| `cli` | `Cli.Prompt`, `Cli` | `std`, `rpc` |
| `js` | `Js`, `Js.Array`, `JsError` | ядро компилятора |

`Config` находится вместе с `Server`, поскольку секретной конфигурации нужна
его возможность выполнения только на сервере. Пакет исходников не выбирает
среду выполнения: программе, использующей только привязки с поддержкой RT,
адаптер Effect не нужен. Stream и другим привязкам через адаптер по-прежнему
нужен `@flick-lang/effect-ts`; смешанные программы должны соответствовать ABI
среды выполнения и точным версиям зависимостей из манифеста установленного
адаптера. Ограничения таргетов и коды диагностик плагинов сохраняются.

`flick install` загружает каждый пакет из тега `std-v<версия>` выпуска
компилятора, с `subdir = "packages/<имя>"`, и закрепляет его в `flick.lock`.
Запись с таким именем в `[dependencies]` выбирает другой источник, как `std`
выше. Сохраняйте полный lock: `flick install --locked --offline` переиспользует
установленные пакеты, не меняя закреплённые версии и не обращаясь к сети.
Компилятор, собранный из checkout, берёт пакеты этого checkout вместо релиза.
Несовместимый неявный модуль даёт `FLICK-P043`.

Для подмены исходников `FLICK_STD_PATH` указывает на `packages/std`.
Остальные неявные пакеты должны находиться рядом, каждый со своим
`src/modules.txt`. Для отдельной подмены пакетов укажите для каждого запись
path, git или tarball в `[dependencies]`.

В каталоге библиотеки лежит `flick.toml` с `kind = "lib"`; модули ищутся в
его `source-dir`, а зависимости самой библиотеки подключаются вместе с ней.
Проект с разделом `[package]` (библиотека, которую скачивают другие проекты,
или приложение, упаковываемое в архив исходников Flick, включая Go-проекты)
указывает свои имя и версию, а также какие компиляторы его собирают; последнее
— требование semver:

```toml
[package]
name = "text"
version = "1.0.0"
flick = ">=0.1, <0.2"

[package.abi]
"flick.javascript-ffi" = "0.1.0"
```

Необязательная таблица `[package.abi]` сопоставляет идентификатор ABI значений
бэкенда (например `"flick.javascript-ffi"`) с точной версией semver или
требованием semver (`">=0.1.0, <0.2.0"`). Во время `flick check`, анализа в
редакторе и `flick build` для каждого активного пакета (корневого пакета и
любой зависимости, чьё условие `[package] when` выполняется) соответствующая
запись проверяется против опубликованного `descriptor.value-abi` активного
бэкенда; несовместимая версия завершается ошибкой `FLICK-F014` на позиции в
манифесте вместо молчаливого внешнего вызова.

Библиотека, которая даёт плагин, называет его компонент WebAssembly — путь
внутри библиотеки (см. [plugins.md](../plugins/)):

```toml
[package]
name = "pairs"
version = "1.0.0"
plugin = "pairs.wasm"
```

`watch = ["Ui.Event.queue", "*.parse"]` рядом с `plugin` называет вызовы, о
которых её плагин спрашивают в каждом проверяемом модуле (см.
[plugins.md](../plugins/#проверки-вызовов)); запись, которая не
`Module.name`, не `Module.Sub.name` и не `*.name`, как и `watch` без `plugin`, —
`FLICK-P032`.

`load = ["proto"]` рядом с `plugin` говорит, что её плагин превращает файлы с
этими расширениями в модули: `App/User.proto` — модуль `App.User` (см.
[plugins.md](../plugins/#файлы-других-языков)). Две библиотеки, загружающие
одно расширение, — `FLICK-P045`. `hooks = ["emit"]` позволяет её плагину
переписать файлы, которые пишет `flick build` (см.
[plugins.md](../plugins/#как-переписать-то-что-пишет-сборка)), а
`hooks = ["ir"]` — IR, который компилирует сборка (см.
[plugins.md](../plugins/#как-переписать-ir)).

`flick install` скачивает каждую git- или url-библиотеку, которую называют
манифесты, напрямую или через другую библиотеку, в хранилище пакетов
(`FLICK_STORE`, иначе `flick/pkg` в каталоге кэша пользователя), где она
лежит под хэшем своих файлов, и закрепляет её в `flick.lock`: коммит тега и
этот хэш. `flick.lock` коммитят: сборка читает хранилище через него и ничего
не скачивает. `flick install --offline` берёт только хранилище, `--locked`
завершается ошибкой, а не меняет lock, `flick update <name>` скачивает
библиотеку заново, `flick add <name> --git URL --tag T [--subdir S]` (или
`--url U --sha256 H`, или `--path DIR`) добавляет библиотеку, а
`flick remove <name>` убирает.

Официальный бэкенд, которым собирается проект без собственного закрепления
(`flick/js` или `flick/go` при `[build] target = "go"` либо `--target go`), тоже не входит в компилятор:
это ассет релиза. `flick new`, первая сборка или `flick install` берёт из индекса
бэкендов самый новый релиз, который принимает компилятор, сохраняет его в
хранилище пакетов и закрепляет в `flick.lock` в `[[backend]]`; дальнейшие
сборки работают без сети. `flick update` переводит закрепление на более
новый релиз. Если с `--offline` закреплённого бэкенда нет в хранилище или
хеш компонента не совпадает с закреплённым, сборка завершается ошибкой
`FLICK-P056`, и другой бэкенд не подставляется.

Проекты, созданные или инициализированные из стороннего пакета шаблонов через
`flick new --from` или `flick init --from`, также записывают проверенный
источник шаблона, контрольную сумму дерева, хеш компонента и (для URL-архивов)
хеш архива в `[[template]]` файла `flick.lock`. `flick install` сохраняет записи
`[[template]]`, не связывая `[dependencies]` с пакетом шаблонов.

Плагин библиотеки по пути собирается на месте, поэтому `flick.lock` записывает
и хэш его компонента в `[[plugin]]`. Сборку он не останавливает;
`flick install --locked` завершается ошибкой, если компонент собран заново, а
`flick plugins` это показывает.

`flick plugins` перечисляет плагины, которые называют манифесты проекта, в
порядке их перечисления: `[dependencies]` проекта и `[[workspace.plugins]]`,
которые наследует участник. Скачанная библиотека показывается источником,
закреплённым в `flick.lock`, а не каталогом в хранилище пакетов:

| источник | что показывает `flick plugins` | чем закреплён |
| - | - | - |
| `path` | путь компонента от корня проекта | `[[plugin]]` в `flick.lock` |
| `git` | `git+<url>?tag=<tag>[&subdir=<dir>]#<commit> (<компонент>)` | контрольная сумма `[[package]]` пакета |
| `url` | `url+<url> (<компонент>)` | контрольная сумма `[[package]]` пакета |

Команда читает `flick.lock` и хранилище пакетов, ничего не скачивает и не
собирает: несобранный компонент библиотеки по пути показывается как
отсутствующий. Зависимость, которую не закрепляет lock или которой нет в
хранилище, — `FLICK-P034`. Собственные зависимости библиотеки компилируются
вместе с ней, но не являются записями `flick.toml` проекта, поэтому в списке
не повторяются.

Библиотека компилируется как [пакет с исходниками](#пакеты): под таргет
проекта, без её предупреждений, после собственных модулей проекта, как
другой пакет, поэтому инстансы её классов и типов принадлежат ей. Изменение
исходников или `flick.toml` библиотеки по пути, а также `flick.lock`,
пересобирает проект, и `--watch` за ними следит.

### Внешние модули библиотеки

Модуль библиотеки привязывает файл рядом с собой так же, как модуль проекта:
`foreign pad from "./pad.mjs" "pad"`. Файл `.mjs` или `.cjs` внутри каталога
исходников библиотеки попадает в сборку под js: в выводе он лежит рядом со
скомпилированным модулем вместе с остальными `.mjs` и `.cjs` библиотеки, которые
он может импортировать, поэтому JS-приложение, упакованное командой `pack`
бэкенда `flick/js`, содержит их, а npm-пакеты они находят из проекта. Отсутствие файла, который называет
`foreign`, ссылка за пределы библиотеки или разные файлы двух библиотек по
одному пути — это `FLICK-P041`. Любой другой относительный файл, `.js` или файл
вне каталога исходников, остаётся на месте, и вывод ссылается на него там же,
как для собственных модулей проекта, поэтому ни в какой архив он не попадает.
На таргете go сборка копирует `pad.go` рядом с тем же модулем в модуль Go, и
нужные ему вспомогательные функции лежат в этом файле.

### Целевые пакеты библиотеки

Собственные зависимости проекта для целевой экосистемы остаются в манифесте
бэкенда (для JavaScript — в `package.json`). Библиотека, которой нужны
целевые пакеты во время выполнения, перечисляет их в
`[target.<name>.dependencies]`; синтаксис определяет и проверяет сам бэкенд.
Для `flick/js` записи в `[target.js.dependencies]` задают версии или диапазоны
npm-пакетов из реестра, а не путь, URL или протокол `workspace:`:

```toml
[target.js.dependencies]
left-pad = "^1.3.0"
```

`flick install` и `flick update` собирают `[target.<name>.dependencies]` из
манифеста проекта и каждой библиотеки, от которой он зависит напрямую или через
другую, проверяют совпадение версий для каждой пары `(target, package)`
(`FLICK-P040`) и передают срез выбранного таргета его бэкенду. Для `flick/js`
(при наличии `[tools] "flick/js" = ["pnpm"]`) бэкенд добавляет в `dependencies`
файла `package.json` то, чего там нет, создавая файл при его отсутствии; затем
`pnpm` устанавливает и закрепляет их как собственные зависимости проекта, а
команда `pack` бэкенда `flick/js` кладёт их в npm-манифест приложения. `--locked` завершается ошибкой,
не меняя `package.json`.

Сборка под js без них завершается ошибкой `FLICK-P034`, которая просит
запустить `flick install`; сборка под go игнорирует `[target.js.dependencies]`
и не требует ни Node, ни pnpm. Два пакета должны называть одну целевую
зависимость одинаковым текстом, и манифест бэкенда (например `package.json`)
тоже, иначе сборка и `flick install` сообщают `FLICK-P040`. Прежняя таблица
`[js.dependencies]` удалена и приводит к `FLICK-P057`.

### Упаковка (`flick pack`)

`flick pack [--target <name>] [--out-dir <dir>]` создаёт до двух видов
релизных артефактов, предварительно убедившись, что в проекте не осталось
`todo` и `echo` (`FLICK-P024`), и предупредив в stderr, если публичный API
ломает импортёров со времени последнего git-тега (`flick diff <tag>`):

1. **Архив исходников Flick (ядро, не зависит от бэкенда).** Когда в `flick.toml`
   объявлен `[package]` (`name` и `version`), ядро записывает детерминированный
   `<name>-<version>.tgz` (нормализуя `@scope/name` в `scope-name-<version>.tgz`),
   включающий `flick.toml`, каталог `source-dir` проекта (без тестовых компаньонов,
   `.git`, `.flick`, каталога сборки и каталогов целевых пакетов), объявленный
   компонент `[package] plugin` и корневые файлы `README*` / `LICENSE*` внутри
   `package/` с обнулёнными метками времени и фиксированными правами. В stdout
   печатается `<sha256>  <path>`, так что зависимый проект может сразу установить
   архив через `flick add <name> --url <url> --sha256 <sha256>`. Библиотека,
   наследующая `[[workspace.plugins]]`, отклоняется (`FLICK-P032`), поскольку
   этих плагинов не будет в опубликованном манифесте.
2. **Необязательный артефакт целевой экосистемы.** Если выбранный бэкенд
   объявляет команду `pack`, ядро выполняет release-сборку, проверяет все
   выпущенные файлы `.iface` (`FLICK-P020`) и передаёт целевую упаковку бэкенду
   внутри `.flick/pack/`. Для `flick/js` приложение с `package.json` и
   `[tools] "flick/js" = ["pnpm"]` подготавливает продакшен-версию `package.json`
   (без `devDependencies` и `scripts`, с `"type": "module"`, `"files": ["dist"]`
   и полями `bin` для входов), проверяет JS-компаньоны `.iface`/`.d.ts` и явные
   `exports` (`FLICK-P020`; `[target.js] typescript = true` отклоняется),
   сверяет закреплённый `packageManager` (`FLICK-P016`) и запускает `pnpm pack`.
   Библиотеки и JS-приложения с `[package]` без `package.json` пропускают `pnpm`
   и записывают только архив исходников Flick. Если имя файла артефакта бэкенда
   совпадает с архивом исходников Flick, ядро оставляет архив исходников по пути
   `<out-dir>/<name>-<version>.tgz` (как в stdout), а артефакт бэкенда переносит
   в `<out-dir>/<target>/<filename>`.

Бэкенды без команды `pack` (например, `flick/go`) выполняют проверку фронтенда
под выбранный таргет и записывают только архив исходников Flick без Node и
pnpm; вызов `flick pack` в таком проекте без `[package]` завершается ошибкой
`FLICK-P032`.

## Скрипты

`[scripts]` задаёт команды, которые выполняются по порядку. Каждая — команда
оболочки (`sh -c`, на Windows `cmd /C`) в каталоге этого `flick.toml`, и
запустивший их `flick` стоит первым в `PATH`. Шаг `@name` выполняет другой
скрипт того же файла:

```toml
[scripts]
lint = ["flick fmt --check", "flick check --warnings-as-errors"]
test = "flick test"
ci = ["@lint", "@test"]
```

`flick run ci` ищет скрипт сначала в `flick.toml` проекта, потом в корне
workspace; вход проекта с тем же именем запускается вместо скрипта. Выполнение
останавливается на первом упавшем шаге с его кодом выхода. Аргументы после
`--` каждый шаг получает как `"$@"`.

## `flick check`

Если пути не указаны, `flick check` проверяет все модули в корневых каталогах
исходников и тестов. Тестовые компаньоны рядом с исходниками он пропускает
(см. [тестирование](../testing/#тестовые-компаньоны)). Если пути указаны,
команда проверяет выбранные файлы и каталоги, а также все модули, которые они
импортируют прямо или через другие модули; из компаньонов — только тот,
который назван путём. Вне проекта пути обязательны.

## Пакеты

Пакеты целевой экосистемы обнаруживает выбранный компонент бэкенда, а не ядро
компилятора. Для `flick/js` npm-пакеты задаются в `package.json`, и их
устанавливает `pnpm`; JS-бэкенд читает `package.json` и
`node_modules/<name>/package.json` и сообщает компилятору о каждом пакете с
исходниками Flick:

```json
{ "name": "@acme/contract", "flick": { "source-dir": "src" } }
```

Каждый зависимый проект компилирует его модули под свой таргет, js или go,
как модули этого пакета. Внутри одного репозитория или между разными таргетами
(например, Go-сервер и JS-клиент) библиотеку подключают как
[зависимость Flick](#зависимости-flick) в `[dependencies]`, так что на стороне
Go не нужны ни `node_modules`, ни `package.json`. Его модули проверяются под таргет
и окружение зависимого проекта, поэтому на go достижимое обращение к модулю только
для js — `FLICK-P064` (неиспользуемые импорты не считаются ошибкой).
Предупреждения пакета зависимый проект не показывает. Свои модули проекта идут
первыми: модуль, который объявляет проект, в пакете не ищется.

| Проблема | Диагностика |
| - | - |
| импортируемый модуль не найден, при этом одна из зависимостей не установлена | `FLICK-P009`: выполните `flick install` (код выхода `2`) |
| импортируемый модуль не найден | `FLICK-R003`: добавьте пакет с помощью `flick add <package>` |
| у зависимости нет источника или их два, либо `[package]` не semver | `FLICK-P032` |
| требование `flick` библиотеки не включает этот компилятор | `FLICK-P033` |
| git- или url-библиотеки нет в `flick.lock` или в хранилище | `FLICK-P034`: выполните `flick install` |
| плагин, который импортирует модуль, не найден или не загружается | `FLICK-P035` |
| плагин не дал кода для блока или упал | `FLICK-P036` |
