Проект — каталог с `flick.toml` (см. [CLI компилятора](../cli/)).
Команды ищут ближайший `flick.toml`, начиная с рабочего каталога и поднимаясь
по дереву каталогов. Параметр `--project <path>` позволяет явно указать
каталог проекта или файл конфигурации. Несколько проектов образуют
[workspace](#workspace), и `--package <name>` выбирает одного из его участников.

## `flick.toml`

```toml
schema-version = 1

[project]
kind = "app"
source-dir = "src"
test-dir = "test"
entry = "App.Main"

[build]
out-dir = "dist"
profile = "debug"
emit = "js"
emit-dts = false
promise-facade = false
schema-aot = false

[sql]
dialect = "postgresql"

[lint]
allow = ["FLICK-T021"]
no-let-assert = false
max-function-lines = 60
max-nesting = 4
max-complexity = 10
max-params = 5
```

| Ключ | Значения | По умолчанию |
| - | - | - |
| `schema-version` | `1`; обязателен, проверяется до остальных ключей | — |
| `project.kind` | `"app"` или `"lib"`; обязателен | — |
| `project.source-dir` | каталог исходных модулей | `"src"` |
| `project.test-dir` | каталог тестовых модулей | `"test"` |
| `project.entry` | модуль, экспортирующий `main`, свой или реэкспортированный: вход `main` с раннером `flick-main.js` | — |
| `project.entries` | несколько входов, `{ server = "App.Server", cli = "App.Cli" }`: по раннеру `flick-<name>.js` на каждый; вход со своим runner'ом — таблица, `web = { module = "App.Worker", runner = "Runner.Cloudflare" }`; `target = "client"` — вход, который работает в браузере: ничто из достижимого из его `main` не может требовать `Server` (`FLICK-E009` с путём до него), поэтому его бандл не содержит серверных модулей; имена — строчные латинские буквы, цифры и `-`; вместо `entry` | — |
| `project.runner` | модуль, который запускает каждый вход без своего runner'а: экспортирует `type alias Main` — тип, который должен иметь `main` (иначе `FLICK-P026`), — и `run`, который принимает `main`; раннер экспортирует его результат как `default`; встроены `"Runner.Node"`, `"Runner.Browser"` и `"Runner.Cloudflare"` — Worker, чей `fetch` передаёт `main : Runner.Cloudflare.Fetch ->{Runner.Cloudflare.Env; AppError} Http.ServerResponse.ServerResponse` запрос и контекст (`wait_until`), а привязки предоставляет сервисом `Env` (`Runner.Cloudflare.var`, `binding`); так runner может предоставлять сервисы, и `main` может требовать любые из тех, что названы в его `Main`; другой может дать пакет; без него чистый `main` вызывается, а эффект выполняется как на Node | — |
| `build.out-dir` | базовый каталог для артефактов сборки; не корень проекта, не каталог исходников или тестов и не каталог над ними (`FLICK-P028`, до любой записи) | `"dist"` |
| `build.profile` | `"debug"` или `"release"` (см. [генерацию кода](../codegen/)); `--profile` у `build` и `test` переопределяет это значение | `"debug"` |
| `build.emit` | `"js"`, `"ts"` или `"go"`: Go-модуль на каждый вход в `go/<entry>/`, который `go build` собирает в исполняемый файл `flick-<entry>`; Go должен быть в `PATH` (`FLICK-P029`), импорт модуля только для js (`Ui`, `Atom`, `Action`, `Rpc`, `Otlp`, `DevTools`, `Js`, runner'ы `Node`/`Browser`/`Cloudflare`) или пакета, собранного не для go, — `FLICK-P030` уже в `flick check`, а то, что Go-target ещё не компилирует, — `FLICK-P012` (см. [Go-target](../codegen/#go-target)) | `"js"` |
| `build.emit-dts` | логическое значение | `false` |
| `build.promise-facade` | логическое значение | `false` |
| `build.schema-aot` | логическое значение | `false` |
| `build.solver-steps` | число шагов разрешения экземпляров классов для одного определения | `100000` |
| `build.solver-depth` | глубина вложенности ограничений классов | `256` |
| `build.labels` | что release-сборка помечает `Module.name` для инструментов отладки: `"all"` (атомы, представления, actions), `"components"` (представления и actions) или `"none"`; debug помечает всё; `flick build --labels` переопределяет | `"all"` |
| `build.effect` | на чём выполняются эффекты: `"effect"`, или `"none"` для простого JavaScript, который импортирует только `@flick-lang/runtime/core`: тогда `main` — `Unit -> Unit`, вызов времени выполнения — `FLICK-E001`, а `task`, уточнённый тип, схема или встроенный модуль вне `Prelude`, `List`, `Option`, `Result`, `String`, `Float` и `Bool` — `FLICK-E008`. Библиотека на Effect дополнительно пишет в `_core/` своего вывода модули, которым Effect не нужен; библиотека, от которой зависит проект, компилируется с `effect` проекта | `"effect"` |
| `build.ui` | модуль, который рисует и монтирует представления вместо React: экспортирует все имена, которые `Ui` и `Action` берут из `@flick-lang/runtime/ui` и `@flick-lang/runtime/ui/react`; относительный путь — от корня проекта | React |
| `sql.dialect` | диалект SQL для `sql table` и `sql { … }` (см. [запросы SQL](../sql/)): `"postgresql"`; `"mysql"`, `"sqlite"`, `"clickhouse"` и `"oracle"` распознаются, но пока не поддерживаются | `"postgresql"` |
| `lint.allow` | коды предупреждений, о которых не сообщается, например `"FLICK-T021"`; ошибки отключить нельзя | `[]` |
| `lint.no-let-assert` | `true` делает каждый `let assert` ошибкой (`FLICK-T027`) в `flick check`, `build`, `test` и в редакторе | `false` |
| `lint.max-function-lines` | сколько строк может занимать тело функции, дальше — `FLICK-T036` | `60` |
| `lint.max-nesting` | насколько глубоко вкладываются `if`, `match`, `fun`, `do`, `task` и `for`, дальше — `FLICK-T037` | `4` |
| `lint.max-complexity` | сколько ветвлений может быть в функции (цикломатическая сложность), дальше — `FLICK-T038` | `10` |
| `lint.max-params` | сколько параметров может быть у функции, дальше — `FLICK-T039` | `5` |
| `plugins.<пакет>` | к чему плагин зависимости может обращаться для блоков проекта: `fs-read` (пути от корня проекта), `net` (`host` или `host:port`) и `env` (имена); не в корне workspace (см. [Доступ вовне](../plugins/#доступ-вовне)) | ничего |

Ошибки конфигурации приводят к завершению с кодом `2`:

| Проблема | Диагностика |
| - | - |
| ошибка синтаксиса TOML, неизвестный ключ, значение неверного типа или вне допустимого набора | `FLICK-P005` |
| `schema-version` отличается от `1` или отсутствует | `FLICK-P006` |
| `kind = "app"` без `entry` и `entries` или с пустым `entries` | `FLICK-P007` |
| одновременно `entry` и `entries`, или недопустимое имя входа | `FLICK-P005` |
| проект не найден или `--project` не указывает на проект | `FLICK-P008` |
| команде нужен проект в корне workspace, `--package` не называет участника, у участника нет `flick.toml`, зависимость по пути — не библиотека, или зависимости образуют цикл | `FLICK-P031` |
| вход не является исходным модулем, экспортирующим `main` | `FLICK-P011` |
| `main` входа не принимает и не возвращает `Unit`, требует сервис или может завершиться ошибкой, отличной от `AppError` | `FLICK-P026` |
| `sql.dialect` указывает известный, но пока не поддерживаемый диалект | `FLICK-P022` |
| `sql.dialect` содержит неизвестное имя диалекта; в сообщении перечислены известные имена | `FLICK-P023` |
| `lint.allow` содержит неизвестный код | `FLICK-P005` |


## Точки входа

Входы приложения — это программы, которые оно собирает: `flick build` пишет
рядом с модулями раннер `flick-<name>.js` для каждого входа, а сами модули —
один раз, так что входы делят то, что импортируют. Раннер импортирует `main`
входа — из модуля, где он определён, если вход его реэкспортирует, — и
запускает его; он начинается с `#!/usr/bin/env node`, поэтому `flick pack`
указывает каждый раннер в `bin` пакета, а единственный вход `main` — под
именем пакета. `flick run <name>` и `flick dev <name>` запускают один из
входов; если вход один, имя можно не указывать.

Каждый вход экспортирует `main : Unit -> Unit` либо эффектную функцию,
которая принимает и возвращает `Unit`, не требует сервисов и может
завершиться только `AppError` (пустая строка ошибок тоже допустима).
Предоставляйте нужные слои и обрабатывайте остальные ошибки внутри `main`,
а не в раннере.

Чистый `main` вызывается напрямую. Обычно его раннер не импортирует среду
выполнения; при `schema-aot = true` всё же импортируются функции установки
схем. Эффектный `main` запускается через средство запуска, наблюдающее
итоговый `Exit` (см. [генерацию кода](../codegen/)). Недопустимая сигнатура
даёт `FLICK-P026` при проверке проекта или при сборке отдельного файла.

```toml
[project]
kind = "app"
entries = { server = "App.Server", migrate = "App.Migrate" }
```

Входы веб-страницы — другое: бандлер вроде Vite принимает JavaScript-модули,
которые импортируют нужные `.fl` (см. [генерацию кода](../codegen/));
`entries` — это программы, которые запускает среда выполнения.
## Workspace

`flick.toml` с разделом `[workspace]` объединяет проекты, своих участников,
по их каталогам:

```toml
schema-version = 1

[workspace]
members = ["contract", "server"]
```

Корень без `[project]` сам проектом не является и допускает только
`[workspace]` и `[scripts]`. В нём `flick check`, `build`, `test`, `fmt` и
`clean` без путей, а также `flick install` проходят по всем участникам,
каждого после тех, от кого он зависит по пути, и завершаются ошибкой, если она
была хотя бы у одного. `flick run` запускает скрипт, а `dev` и остальным
командам нужен участник: `--package <name>`
(`-p`), имя его каталога. Внутри участника команды, как обычно, работают с ним,
а `--package` выбирает другого.

Корень может дать всем участникам плагин — зависимостью и правами:

```toml
[[workspace.plugins]]
package = "mysql"
source = { path = "plugins/mysql" }   # от корня, или источник git или url
grants = { fs-read = ["schema/"], net = ["localhost:3306"] }
```

Тогда каждый участник, кроме пакета самого плагина, зависит от `mysql` и даёт
ему права `grants` корня вдобавок к своим `[plugins.mysql]`; `fs-read`
отсчитывается от каталога участника. Участник, который берёт `mysql` из другого
источника, получает `FLICK-P005`. Участник с плагином идёт раньше остальных, а
`flick pack` отказывается упаковать библиотеку, получившую плагин так: в
опубликованном манифесте его не будет, поэтому его пишут в `[dependencies]`.

## Зависимости Flick

Проект компилирует библиотеки Flick, от которых зависит, из их исходников.
`[dependencies]` называет у каждой один источник: каталог относительно
`flick.toml`, тег git-репозитория (с каталогом библиотеки в нём, `subdir`)
или tar.gz-архив с его sha256:

```toml
[dependencies]
contract = { path = "../contract" }
std = { git = "https://github.com/bondiano/flick-lang", tag = "std-v0.1.0", subdir = "packages/std" }
text = { url = "https://example.com/text-1.0.0.tgz", sha256 = "<64 шестнадцатеричные цифры>" }
```

Проект видит неявные пакеты, сегодня это `std`, не называя их: `flick install`
скачивает каждый из них для релиза этого компилятора, а запись с таким именем в
`[dependencies]` выбирает для него другой источник, как `std` выше.
Компилятор, собранный из checkout, вместо релиза берёт пакеты этого checkout, а
`std`, который не проверяется этим компилятором, даёт `FLICK-P043`.

В каталоге библиотеки лежит `flick.toml` с `kind = "lib"`; модули ищутся в
его `source-dir`, а зависимости самой библиотеки подключаются вместе с ней.
Библиотека, которую скачивают другие, говорит, что она такое и какие
компиляторы её собирают; последнее — требование semver:

```toml
[package]
name = "text"
version = "1.0.0"
flick = ">=0.1, <0.2"
```

Библиотека, которая даёт плагин, называет его компонент WebAssembly — путь
внутри библиотеки (см. [plugins.md](../plugins/)):

```toml
[package]
name = "pairs"
version = "1.0.0"
plugin = "pairs.wasm"
```

`flick install` скачивает каждую git- или url-библиотеку, которую называют
манифесты, напрямую или через другую библиотеку, в хранилище пакетов
(`FLICK_STORE`, иначе `flick/pkg` в каталоге кэша пользователя), где она
лежит под хэшем своих файлов, и закрепляет её в `flick.lock`: коммит тега и
этот хэш. `flick.lock` коммитят: сборка читает хранилище через него и ничего
не скачивает. `flick install --offline` берёт только хранилище, `--locked`
завершается ошибкой, а не меняет lock, `flick update <name>` скачивает
библиотеку заново, `flick add <name> --git URL --tag T [--subdir S]` (или
`--url U --sha256 H`, или `--path DIR`) добавляет библиотеку, а
`flick remove <name>` убирает.

Плагин библиотеки по пути собирается на месте, поэтому `flick.lock` записывает
и хэш его компонента в `[[plugin]]`. Сборку он не останавливает;
`flick install --locked` завершается ошибкой, если компонент собран заново, а
`flick plugins` это показывает.

Библиотека компилируется как [пакет с исходниками](#пакеты): под таргет
проекта, без её предупреждений, после собственных модулей проекта, как
другой пакет, поэтому инстансы её классов и типов принадлежат ей. Изменение
исходников или `flick.toml` библиотеки по пути, а также `flick.lock`,
пересобирает проект, и `--watch` за ними следит.

### Внешние модули библиотеки

Модуль библиотеки привязывает файл рядом с собой так же, как модуль проекта:
`foreign pad from "./pad.mjs" "pad"`. Файл `.mjs` или `.cjs` внутри каталога
исходников библиотеки попадает в сборку под js: в выводе он лежит рядом со
скомпилированным модулем вместе с остальными `.mjs` и `.cjs` библиотеки, которые
он может импортировать, поэтому приложение, упакованное `flick pack`, содержит
их, а npm-пакеты они находят из проекта. Отсутствие файла, который называет
`foreign`, ссылка за пределы библиотеки или разные файлы двух библиотек по
одному пути — это `FLICK-P041`. Любой другой относительный файл, `.js` или файл
вне каталога исходников, остаётся на месте, и вывод ссылается на него там же,
как для собственных модулей проекта, поэтому ни в какой архив он не попадает.
На таргете go сборка копирует `pad.go` рядом с тем же модулем в модуль Go, и
нужные ему вспомогательные функции лежат в этом файле.

### npm-пакеты библиотеки

Собственные npm-зависимости проекта остаются в `package.json`. Библиотека,
которой npm-пакеты нужны во время выполнения на таргете js, называет их в
`[js.dependencies]`, каждый версией или диапазоном реестра, а не путём, URL
или протоколом `workspace:`:

```toml
[js.dependencies]
left-pad = "^1.3.0"
```

`flick install` и `flick update` собирают эти таблицы из манифеста проекта и
из каждой библиотеки, от которой он зависит напрямую или через другую, и
добавляют в `dependencies` файла `package.json` то, чего там нет, создавая
файл, если его у проекта нет; затем pnpm устанавливает и закрепляет их как
собственные зависимости проекта, а `flick pack` кладёт их в манифест
приложения. `--locked` завершается ошибкой, а не меняет `package.json`.

Сборка под js без них завершается ошибкой `FLICK-P034`, которая просит
запустить `flick install`; сборке под go они не нужны. Два пакета должны
называть один npm-пакет одинаковым текстом, и `package.json` тоже, иначе
сборка и `flick install` сообщают `FLICK-P040`.

## Скрипты

`[scripts]` задаёт команды, которые выполняются по порядку. Каждая — команда
оболочки (`sh -c`, на Windows `cmd /C`) в каталоге этого `flick.toml`, и
запустивший их `flick` стоит первым в `PATH`. Шаг `@name` выполняет другой
скрипт того же файла:

```toml
[scripts]
lint = ["flick fmt --check", "flick check --warnings-as-errors"]
test = "flick test"
ci = ["@lint", "@test"]
```

`flick run ci` ищет скрипт сначала в `flick.toml` проекта, потом в корне
workspace; вход проекта с тем же именем запускается вместо скрипта. Выполнение
останавливается на первом упавшем шаге с его кодом выхода. Аргументы после
`--` каждый шаг получает как `"$@"`.

## `flick check`

Если пути не указаны, `flick check` проверяет все модули в корневых каталогах
исходников и тестов. Если пути указаны, команда проверяет выбранные файлы
и каталоги, а также все модули, которые они импортируют прямо или через
другие модули. Вне проекта пути обязательны.

## Пакеты

npm-пакеты задаются в `package.json`, их устанавливает pnpm. Flick читает
установленное дерево: для каждой зависимости из `package.json` он читает
`node_modules/<name>/package.json`. npm-пакет с модулями Flick — пакет с
исходниками, он указывает каталог исходников:

```json
{ "name": "@acme/contract", "flick": { "source-dir": "src" } }
```

Каждый зависимый проект компилирует его модули под свой таргет, js или go,
как модули этого пакета. Поэтому JS-клиент и Go-сервер, которые оба от него
зависят, делят его типы, и у его конструкторов одинаковые теги с обеих сторон.
Своя сборка такому пакету не нужна; внутри одного репозитория его можно
подключить [зависимостью по пути](#зависимости-flick), без `node_modules`. Его модули проверяются под таргет
зависимого проекта, поэтому на go импорт модуля только для js — `FLICK-P030`.
Предупреждения пакета зависимый проект не показывает. Свои модули проекта идут
первыми: модуль, который объявляет проект, в пакете не ищется.

| Проблема | Диагностика |
| - | - |
| импортируемый модуль не найден, при этом одна из зависимостей не установлена | `FLICK-P009`: выполните `flick install` (код выхода `2`) |
