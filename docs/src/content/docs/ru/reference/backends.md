Генерация кода в Flick выполняется через WebAssembly-компоненты, реализующие контракт `flick:backend@0.1.0`, а не через жёстко встроенный в CLI код таргетов. Команды `flick build`, `flick run`, `flick dev`, `flick test`, `flick pack` и `flick inspect` выбирают, проверяют и запускают компонент бэкенда проекта до записи или запуска любых артефактов.

Полная схема `flick.toml` описана в разделе [Проект](../project/), подробности вывода JS и Go — в [Генерации кода](../codegen/), а команды и шаблоны, поставляемые бэкендами, — в [Командах расширений](../commands/).

## Выбор таргета и окружения

Без явного закрепления компонента Flick выбирает официальный бэкенд по `[build] target` (или флагу CLI `--target <name>`):

| Бэкенд | Короткое имя | Окружение по умолчанию | Примечания |
| - | - | - | - |
| `flick/js` | `js` (по умолчанию) | `js/node` | Официальный бэкенд JavaScript и TypeScript; также поддерживает `js/browser`, `js/bun` и `js/cloudflare`. |
| `flick/go` | `go` | `go/native` | Официальный бэкенд Go; генерирует модуль Go для каждого входа или набора тестов и запускает `go build` при разрешении `[tools] "flick/go" = ["go"]`. |
| `flick/vm` | `vm` | `vm/native` | Встроенная внутрипроцессная ВМ на Rust (`flick run --target vm` и `flick test --target vm`) с нативными Rust-сервисами хоста (`Console`, `Clock`, `Random`, `Environment`, `Arguments`, `File`, `FileSystem`, `Process`); не требует Node или Go. |
| `flick/lua` | `lua` | — | Предварительный компонент (не входит в официальный индекс релизов); выбирается через `[build.backend]` с явным окружением (`lua/love`, `lua/wow-retail` или `lua/wow-forever`). |

`[build] environment` задаёт пару `<backend>/<host>`, например `"js/node"`, `"js/browser"`, `"js/bun"`, `"js/cloudflare"`, `"go/native"` или хост из пакета-библиотеки с разделом `[host]`:

```toml
schema-version = 1

[project]
kind = "app"
entry = "App.Main"

[build]
target = "js"
environment = "js/node"

[target.js]
runtime = "rt"
```

Если `[build] target` не указан, но задан `[build] environment`, таргет определяется по префиксу бэкенда в `environment`. Специфичные для бэкенда опции задаются в `[target.<name>]` и через флаги CLI согласно дескриптору `describe` выбранного бэкенда (дескриптор кэшируется по SHA-256 компонента, поэтому `--help` никогда не обращается к сети). Неизвестный таргет даёт `FLICK-P059`, неизвестный или неверный ключ в `[target.<name>]` — `FLICK-P058`, а неподдерживаемое окружение или хост — `FLICK-P065`.

### Явное закрепление компонента (`[build.backend]`)

Чтобы использовать собственный, сторонний или предварительный компонент бэкенда, закрепите его точный идентификатор, версию, хеш SHA-256 и путь в `[build.backend]`:

```toml
[build]
environment = "js/node"

[build.backend]
id = "example/backend"
version = "1.0.0"
sha256 = "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
component = "backends/example.wasm"
```

- `id` и `version`: точные идентификатор и семантическая версия бэкенда (диапазоны версий запрещены). Они должны совпадать с дескриптором, который возвращает компонент.
- `sha256`: 64 строчные шестнадцатеричные цифры, точно совпадающие с байтами файла `.wasm`.
- `component`: путь к файлу WebAssembly-компонента относительно корня проекта (для локальной разработки допускается и абсолютный путь). Хост читает и проверяет файл сам; гостевой компонент не получает доступа к файловой системе.

Отсутствующие или неизвестные поля, некорректный хеш или несовпадение идентификатора компонента останавливают сборку до генерации (`FLICK-P013`).

## Реестр, lock-файл и работа без сети

Официальные бэкенды (`flick/js` и `flick/go`) поставляются как ассеты релизов и не вшиваются в исполняемый файл компилятора.

1. При `flick new`, `flick install` или первой сборке без закрепления компилятор читает индекс бэкендов и выбирает самый новый выпуск нужного бэкенда, чьи диапазоны `backend_api` и `ir` принимают текущий компилятор.
2. Он загружает `component.wasm`, проверяет его хеш SHA-256, сохраняет в `<store>/backends/<sha256>.wasm` (где `<store>` — `FLICK_STORE` или `flick/pkg` в каталоге кэша пользователя) и закрепляет в `flick.lock`:

```toml
[[backend]]
id = "flick/js"
version = "0.2.0"
sha256 = "<64 lowercase hex digits>"
url = "https://github.com/bondiano/flick-lang/releases/download/backend-js-v0.2.0/component.wasm"
```

3. Последующие запуски `build`, `run`, `dev`, `test` и `inspect` берут закреплённый хеш из `flick.lock` и загружают `<store>/backends/<sha256>.wasm` без обращений к сети.

| Флаг или переменная окружения | Поведение |
| - | - |
| `--offline` | Берёт официальные бэкенды только из `flick.lock` и `<store>/backends/<sha256>.wasm`. Отсутствующая запись в lock-файле либо отсутствующий или повреждённый файл в хранилище дают `FLICK-P056`. |
| `flick install --locked` | Проверяет, что каждая нужная запись `[[backend]]` уже закреплена в `flick.lock` и находится в хранилище; завершается ошибкой (`FLICK-P034`), а не обновляет lock-файл. |
| `flick update` | Обновляет закрепления `[[backend]]` в `flick.lock` до самого нового совместимого выпуска из индекса и загружает их в хранилище. |
| `FLICK_BACKENDS_PATH` | Каталог с локальными `<name>/package/{component.wasm,backend.json}` (используется вместо индекса релизов при локальной разработке). |
| `FLICK_BACKENDS_INDEX` | Подменяет индекс бэкендов другим URL или локальным JSON-файлом (имеет приоритет над checkout и `FLICK_BACKENDS_PATH`). |

Отсутствующий бэкенд, несовместимый диапазон API/IR или несовпадение SHA-256 завершаются ошибкой `FLICK-P056` до генерации кода. Компилятор никогда не подставляет другой бэкенд.

## Режимы среды выполнения JavaScript

Для `flick/js` режим среды выполнения JavaScript не зависит от идентификатора компонента:

- `[target.js] runtime = "rt"` (по умолчанию): компиляция под собственное ядро Flick `@flick-lang/runtime` без зависимости от Effect.
- `[target.js] runtime = "effect"`: компиляция через адаптер `@flick-lang/effect-ts`, когда проект использует API, требующие адаптера Effect.

Переопределить среду выполнения для одного запуска можно флагом `--runtime`:

```sh
flick build --runtime rt
flick test --runtime effect
flick run --runtime rt
```

Библиотеки, от которых зависит проект, компилируются с действующим `runtime` этого проекта. Достижимые обращения к привязкам, доступным только через адаптер Effect, при `runtime = "rt"` и отсутствии `@flick-lang/effect-ts` отклоняются на этапе предварительной проверки (`FLICK-P064`) в месте использования, а не во время выполнения.

## Инвалидация кэша, watch/dev/test и изоляция отказов

Ключ кэша генерации учитывает полный `BuildRequest` и состояние хоста:

- Идентификатор, версию и SHA-256 байтов компонента бэкенда (`[build.backend]` или `[[backend]]`).
- Выбранный таргет, `[build] environment`, активные теги, `[build] profile` (`debug` или `release`) и все разрешённые опции `[target.<name>]` и CLI (включая `runtime`).
- Пониженный IR, исходные файлы, внешние (`foreign`) входы, проекции и объявленные зависимости.
- Закреплённые исполняемые файлы инструментов и сред запуска хоста (версия и SHA-256 Node или Go) и разрешённые графы зависимостей среды выполнения.

Изменение любого из этих входов корректно инвалидирует кэш сборки, поколение `flick dev` / `--watch` и тестовое поколение `.flick/test/`:

- **Проверка детерминизма:** для помещения результата в кэш требуются два одинаковых независимых прогона гостевого компонента; недетерминированный результат отклоняется.
- **Никакого скрытого отката:** ошибка загрузки компонента, несовместимость рукопожатия, отказ предварительной проверки (`FLICK-P012`), транспортная ошибка (`FLICK-P013`) либо неразрешённый или упавший инструмент хоста (`FLICK-P051`/`FLICK-P050`) никогда не откатываются молча на нативную генерацию и не переиспользуют устаревший кэш от другого бэкенда или конфигурации.
- **Атомарная публикация:** сгенерированные артефакты, выходы инструментов хоста, удаление устаревших файлов и манифест вывода подготавливаются рядом с выходным каталогом и фиксируются одной транзакцией, поэтому при сбое предыдущий опубликованный вывод остаётся нетронутым.

## Разработка стороннего пакета бэкенда

Любой язык, компилируемый в WebAssembly Component Model, может реализовать бэкенд Flick по миру `flick:backend@0.1.0` (`flick-backend/wit/backend.wit`):

```wit
package flick:backend@0.1.0;

world backend {
    import inputs;
    export describe: func() -> descriptor;
    export check-target: func(request: build-request) -> result<target-support, list<diagnostic>>;
    export generate: func(request: build-request) -> result<build-result, list<diagnostic>>;
    export package-files: func() -> list<string>;
    export packages: func(
        files: list<project-file>,
        dependencies: list<dependency>,
        options: list<option-value>,
    ) -> packages;
    export flick:command/command@0.1.0;
}
```

### Основные гарантии контракта

- **Изолированный чистый гость:** единственный импорт — `inputs.read`. Операции WASI для файловой системы, часов, случайных чисел, сети и процессов запрещены и завершаются ловушкой при вызове. Каждый байт, который читает гость, поступает из контентно-адресуемого манифеста запроса.
- **Явное рукопожатие и предварительная проверка:** `describe` объявляет точные полуоткрытые диапазоны `[minimum, maximum_exclusive)` для `backend-api`, `ir`, `language` и `runtime-abis`, поддерживаемые окружения, профили, режимы, опции, `launch-runtimes`, `host-tools`, метаданные FFI и необязательный `value-abi`. Неподдерживаемые конструкции IR отклоняются с позициями в исходнике в `check-target` (`FLICK-P012`) до запуска генерации.
- **Разрешения на инструменты хоста (`[tools]`):** бэкенд никогда не запускает процессы сам. Вместо этого `BuildResult.steps` описывает DAG записей `toolchain-step`, ссылающихся на закреплённые инструменты хоста (`node`, `go`, `pnpm`). Проект должен явно разрешить каждый такой инструмент в `[tools]`:

```toml
[tools]
"example/backend" = ["go"]
```

  Неразрешённый инструмент останавливает сборку с `FLICK-P051` до запуска любых шагов. Хост вычисляет хеш исполняемого файла в `PATH`, перепроверяет его перед каждым шагом, запускает каждый шаг в свежем изолированном каталоге рядом с выводом с очищенным окружением и забирает обратно только объявленные обычные файлы (`FLICK-P050`).
- **Закрепления запуска:** `BuildResult.launches` связывает точки запуска и тестов с идентификатором артефакта, опционально указывая закреплённый `launch.runtime` (например `node`) или `none` для прямого запуска нативного исполняемого файла. Среды запуска из `descriptor.launch-runtimes` не требуют записи в `[tools]`, но их версия, SHA-256 и закрепления зависимостей среды выполнения перепроверяются перед каждым запуском.

## Матрица поддержки и версий

Контракт переносимой поставки бэкендов версионирует свои поверхности независимо (контракты `0.x` не становятся `1.0` молча):

| Поверхность | Текущая версия | Правило совместимости |
| - | - | - |
| WIT ABI бэкенда (`flick:backend`) | `0.1.0` | Проверяется по диапазону `descriptor.backend-api` во время рукопожатия. |
| Переносимый IR (`flick-ir`) | `0.19.0` | Проверяется по диапазону `descriptor.ir`; метаданные памяти и UI версионируются независимо от версии WIT-пакета. |
| Команды расширений (`flick:command`) | `0.1.0` | Общий интерфейс бэкендов и плагинов; план проверяется целиком до запуска любых шагов. |
| Примитивное ядро (`flick.kernel`) | `0.1.0` | Проверяется через `TargetRequest.runtime-abis`; подтверждается набором `just kernel` по таргетам. |

| Потребитель или адаптер | Роль | Путь поставки | Режимы генерации | Окружения |
| - | - | - | - | - |
| `flick/js@0.2.0` | Официальный JS/TS-компонент | Wasmtime-хост CLI (по умолчанию) и изолированный браузерный воркер (`backend.worker.ts`) | `whole-program` (`per-module` для `inspect`) | `js/node`, `js/browser`, `js/bun`, `js/cloudflare` |
| `flick/go@0.2.0` | Официальный Go-компонент | Wasmtime-хост CLI (по умолчанию для `--target go`) | `whole-program` | `go/native` (`[tools] "flick/go" = ["go"]`) |
| `flick/lua@0.1.0` | Предварительный компонент | Явное закрепление `[build.backend]` | `whole-program` | `lua/love`, `lua/wow-retail`, `lua/wow-forever` |
| Сторонний компонент (`[build.backend]`) | Внешний бэкенд | Wasmtime-хост CLI (только `inputs.read`, закреплённый SHA-256) | `per-module` и/или `whole-program` по `describe` | Любая пара `<backend>/<host>` из `describe` |
| Нативный Rust `flick_backend::Backend` | Адаптер разработки и parity | Только внутрипроцессные тесты Rust (никогда не используется как скрытый откат в релизе) | Совпадает с контрактом компонента | Наборы разработки и проверки эквивалентности |

## Примеры миграции

### 1. Перенос устаревших настроек `[build]` и `[js]` в `[target.js]`

Устаревшие ключи в `[build]` (`emit`, `emit-dts`, `effect`, `promise-facade`, `schema-aot`, `ui`) и таблицы `[js]` / `[js.dependencies]` отклоняются с `FLICK-P057`. Замените их на `[build] target` и `[target.js]`:

Было:

```toml
[build]
emit = "ts"
emit-dts = true
effect = "effect"
promise-facade = true

[js.dependencies]
left-pad = "^1.3.0"
```

Стало:

```toml
[build]
target = "js"

[target.js]
typescript = true
declarations = true
runtime = "effect"
promise-facade = true

[target.js.dependencies]
left-pad = "^1.3.0"
```

### 2. Переключение между `rt` и `effect`

Чтобы перевести существующий проект с Effect на среду по умолчанию `rt` (или проверить совместимость до правки `flick.toml`), сначала проверьте один запуск с `--runtime rt`:

```sh
flick check --runtime rt
flick test --runtime rt
```

Когда предварительная проверка не находит достижимых привязок адаптера Effect (`FLICK-P064`), обновите `flick.toml` и оставьте `@flick-lang/runtime` в `package.json`:

```toml
[target.js]
runtime = "rt"
```

Чтобы включить адаптер Effect для проекта, использующего модули на основе Effect (например `Stream`), задайте `runtime = "effect"` и добавьте `@flick-lang/effect-ts` в `package.json`:

```toml
[target.js]
runtime = "effect"
```

### 3. Закрепление внешнего или предварительного бэкенда

Чтобы закрепить локальный или сторонний компонент бэкенда (например, предварительный компонент `flick/lua` или собственный бэкенд):

```toml
schema-version = 1

[project]
kind = "app"
entry = "App.Main"

[build]
environment = "lua/love"

[build.backend]
id = "flick/lua"
version = "0.1.0"
sha256 = "<sha256 of backends/lua/package/component.wasm>"
component = "../backends/lua/package/component.wasm"

[target.lua]
dialect = "luajit"
```

Если сторонний бэкенд объявляет шаги сборки `ToolchainStep` (например, вызывая `go` или `node`), выдайте разрешение на нужный инструмент в `[tools]`:

```toml
[tools]
"example/backend" = ["go"]
```
