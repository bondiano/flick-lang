Каждый файл `.fl` — отдельный модуль.
Заголовок задаёт имя модуля и список экспортируемых имён.
Импорты делают доступными имена, которые экспортируют другие модули.

## Вложенные модули в одном файле

Inline-модуль группирует объявления в исходном файле. Внутри можно объявлять
значения, типы, классы, экземпляры, сервисы, эффекты, контракты и другие
inline-модули. Тело начинается после `=` с отступом:

```flick
module App.Article exposing (answer)

type Key = Key Int
let seed = 41

module Comments exposing (value) =
  value : Key
  let value = Key (seed + 1)

answer : Key
let answer = Comments.value
```

`Comments` видит предыдущие объявления родителя, в том числе приватные `Key`
и `seed`. Родитель обращается только к членам из `exposing` дочернего блока
через квалификатор, например `Comments.value`. Без `exposing` дочерний блок
ничего не открывает родителю. У дочерних объявлений отдельное пространство
имён: одноимённые типы и классы родителя остаются другими сущностями.
Импорты внутри дочернего блока видны только ему.

Inline-модуль приватен для своего файла. Путь `App.Article.Comments` нельзя
импортировать даже из другого файла того же пакета. Не включайте `Comments`
в `exposing` родителя. Компилятор выпускает один исполняемый модуль на файл
и сохраняет порядок инициализации значений. Попытка импортировать inline-путь
выдаёт `FLICK-R018` на импорте и показывает место объявления.

Классы и сервисы дочернего блока сохраняют собственную номинальную
идентичность. Внутри него можно объявить контракт `type module`. Чтобы
упаковать весь блок как `Module Sig`, внешний контракт может явно требовать
его идентичности через `class Describe = Child.Describe` и
`service Greeter = Child.Greeter`; затем `pack Child as Sig` проверяет
экспортированные члены. Правила абстрактных требований и словарей описаны в
[контрактах модулей](#контракты-модулей-и-параметризованные-модули).

| Ситуация | Диагностика |
| - | - |
| два inline-блока имеют одно имя или путь дочернего блока совпадает с модулем-файлом | `FLICK-R002` на конфликтующем объявлении |
| родитель обращается к имени, которого нет в `exposing` дочернего блока | `FLICK-R004` на квалифицированном имени |
| другой файл импортирует дочерний блок или более глубокий путь через него | `FLICK-R018` на импорте с указанием места inline-объявления |
| внутри дочернего блока объявлено именованное статическое применение параметризованного модуля | `FLICK-R019` на имени применения; результат нужно объявить в модуле-файле |

Префикс `private` в заголовке делает модуль-файл доступным только исходникам
и тестам его пакета:

```flick
private module App.Internal exposing (helper)
# helper : Int -> Int
# let helper x = x
```

Импорт из другого пакета получает `FLICK-R017` на пути импорта. Публичный
модуль того же пакета может реэкспортировать имена приватного модуля; клиент
импортирует этот фасад. Приватность сохраняется при компиляции зависимости из
исходников и при загрузке из кэша пакетов.

```flick
module App.Users exposing (User, load_user)

import App.Domain exposing (User, UserId)
import Effect.Log as Log
#
# load_user : User -> User
# let load_user user = user
```

## Имена модулей и файлы

Имя модуля состоит из частей, разделённых точками; каждая часть начинается
с заглавной буквы. В проекте (см. [проекты](../project/)) имя определяется
путём относительно корня исходников: `App.Users` находится в `src/App/Users.fl`.
Корень тестов содержит отдельный набор модулей с теми же правилами именования.

| Ситуация | Диагностика |
| - | - |
| `src/App/Users.fl` объявляет `module App.User` | `FLICK-R001` с предложением переименовать модуль |
| имя каталога или файла начинается не с заглавной буквы (`src/app/users.fl`) | `FLICK-R001` |
| два файла объявляют одно имя модуля, например `src/App/Users.fl` и `test/App/Users.fl` | `FLICK-R002` для более позднего файла: сначала рассматриваются исходники, затем тесты; внутри каждой группы — по пути |
| локальный модуль и установленный пакет предоставляют один модуль | `FLICK-R002` |

Если заголовка нет, имя модуля определяется по пути файла. Для файла вне
корней проекта или проверяемого без проекта корень выводится отдельно.
Например, файл `x/App/Main.fl`, объявляющий `App.Main`, импортирует
`App.Util` из `x/App/Util.fl`.

## Импорты

| Форма | Что вводит в область видимости |
| - | - |
| `import App.Domain` | квалифицированные имена `App.Domain.name` |
| `import App.Domain as D` | квалифицированные имена `D.name` |
| `import App.Domain exposing (User, load)` | имена `User`, `load` без квалификатора и квалифицированные имена |
| `import App.Domain exposing (Shape(..))` | тип `Shape` и его экспортируемые конструкторы |
| `import App.Domain exposing (..)` | все экспортируемые имена из `App.Domain` |

Из локальных модулей модуль исходников может импортировать только модули
исходников, а тестовый — и исходные, и тестовые. В остальных случаях
импорт разрешается через установленный пакет (см. [пакеты](../project/#пакеты)).

| Ситуация | Диагностика |
| - | - |
| ни файл, ни пакет не предоставляют модуль | `FLICK-R003` с ожидаемым расположением локального модуля и командой `flick add` |
| зависимость из `package.json` не установлена | `FLICK-P009` с командой `flick install` (код завершения `2`) |
| в `exposing (name)` или `M.name` указано имя, которое модуль не экспортирует | `FLICK-R004` |
| `exposing (Type(..))` ссылается на тип, экспортируемый без конструкторов, либо `exposing (Ctor)` или `M.Ctor` ссылается на неэкспортируемый конструктор | `FLICK-R005` |
| импорты образуют цикл | `FLICK-R006` с цепочкой модулей, один раз для каждого цикла |

Сообщение указывает на импорт или квалифицированное имя, вызвавшие ошибку.

## Экспорт

Список `exposing` в заголовке задаёт весь интерфейс модуля.
Если `exposing` отсутствует, модуль ничего не экспортирует.

| Элемент | Что экспортирует |
| - | - |
| `name` | значение: `let`, `foreign`, метод класса |
| `Type` | тип, `error`, `kind`, сервис или класс без конструкторов или членов |
| `Ctor` | отдельный конструктор, если ни у одного типа нет такого имени |
| `Type(..)` | тип с конструкторами, класс с методами или `kind` с его членами |
| `..` | все определения модуля, кроме конструкторов непрозрачных типов |

Экспорт типа сам по себе не экспортирует конструкторы.
Представление `opaque type` всегда остаётся закрытым: `Id(..)`
для непрозрачного `Id` вызывает `FLICK-R011`. Та же ошибка возникает
для `Alias(..)`, если у типа нет конструкторов, и для имени,
которое модуль не определяет и не импортирует.

Модуль может реэкспортировать импортированное имя. Это та же сущность,
а не копия. Поэтому импорт `User` одновременно из `App.Domain`
и из модуля, который его реэкспортирует, не создаёт неоднозначности,
а реэкспортированный сервис доступен по пути реэкспортирующего модуля так же,
как по своему: `M.S` в строке, `M.S.op`, `M.S.Impl` и `M.S` как значение.
С реэкспортированным `main` модуль тоже может быть входом: его раннер
импортирует `main` оттуда, где он определён; реэкспортированный `tests` не
делает модуль тестовым.

```flick
module App.Users exposing (User, load_user)

import App.Domain exposing (User)
#
# load_user : User -> User
# let load_user user = user
```

## Определения верхнего уровня

В каждом пространстве имён модуля имя можно определить только один раз.
Пространств имён три:

- значения;
- типы, ошибки, кинды и их члены, сервисы, классы;
- конструкторы.

Сигнатура и соответствующий `let` считаются одним определением.
Повторное определение вызывает `FLICK-R008`.

В прозрачных псевдонимах не допускаются циклы: `type alias A = List A`
и цикл через несколько псевдонимов вызывают `FLICK-R007`.
Для рекурсии нужен номинальный тип. Он может ссылаться на себя
и на другие типы того же файла:

```flick
type Tree a = Leaf | Node a (Forest a)
type alias Forest a = List (Tree a)
```

Функции, вызывающие себя или друг друга, объявляются через `let rec` или
в одной группе `rec { … }` (см. [Рекурсия](../types/#рекурсия)).

## Контракты модулей и параметризованные модули

`type module` задаёт структурный контракт модуля. Требование `type Key`
скрывает тип за абстрактным именем; `type Key = String` требует доказуемого
равенства. Конкретный модуль может экспортировать и другие члены.

```text
type module Source =
  type Key
  value : Key

module App.Make(S : App.Contracts.Source) exposing (answer)
// App/Make.fl использует S.Key и S.value

module App.Parent exposing (Chosen)
module Chosen = App.Make(App.Argument)
// App.Parent.Chosen можно импортировать из другого файла
```

Параметризованный модуль принимает именованный модуль, известный во время компиляции.
Каждое объявление `module Chosen = App.Make(App.Argument)` создаёт отдельный
модуль результата и отдельное тождество его абстрактных типов. Импорт одного
результата в несколько файлов сохраняет тождество. Родитель должен включить
`Chosen` в `exposing`, чтобы другие модули могли импортировать
`App.Parent.Chosen`. Тело параметризованного модуля видит только члены и равенства контракта.

Например, `CaseInsensitiveSet.Set` и `ExactSet.Set` различаются, даже если
обе политики используют ключ `String`. Два файла, импортировавшие один
результат `CaseInsensitiveSet`, могут передавать набор друг другу. Передача
его набора операции `ExactSet` даёт `FLICK-T003` с полными путями обоих типов.
Если смена политики нужна, преобразуйте значение явно через экспортируемые
операции, например `to_list` и `from_list`.

Контракт может требовать классы и сервисы. Их тождество номинально: одинаковая
форма методов или операций не делает два объявления одним. Записи
`class Eq = Prelude.Eq` и `service Clock = Time.Clock` закрепляют существующее
тождество. Абстрактное требование класса или сервиса допустимо для статического
параметризованного модуля, но для `pack` нужна форма с явным тождеством.

```text
type module Policy =
  type Key = String
  class Eq = Prelude.Eq
  equality : Eq.Dict Key
  instance Eq Key from equality

let equality = Eq.dictionary { eq = fun _ _ -> false }
let hashing = Hash.dictionary {
  Eq = equality
  hash = fun _ -> 0
}
```

`instance Eq Key from equality` использует именованный словарь только в теле
параметризованного модуля или `unpack`. Явно переданный словарь имеет наивысший приоритет;
затем выбирается локальный словарь, после него — глобальный экземпляр.
Требование не создаёт глобальный экземпляр. Если два аргумента параметризованного модуля дают
один и тот же constraint, возникает `FLICK-T066`. Для класса с суперклассом
словарь должен явно содержать его поле, как `Hash.dictionary` выше.

Статический параметризованный модуль может требовать класс, чьё тождество задаёт аргумент.
В контракте разрешено назвать тип его словаря и метод. В теле параметризованного модуля
`K.equal` использует словарь, названный в `instance`:

```text
type module EqualityPolicy =
  class Equality a =
    equal : a -> a -> Bool
  equality : Equality.Dict String
  instance Equality String from equality

module App.Make(K : App.Contracts.EqualityPolicy) exposing (answer)
answer : Bool
let answer = K.equal "A" "A"
```

### Генеративные типы результата

В этом примере один функтор дважды применяется к одному аргументу. Каждый
блок — полный файл; сохраните его по пути из заголовка. Функтор экспортирует
`Token` без конструктора, и каждое применение создаёт отдельный тип токена.

```text title="src/App/Contracts.fl"
module App.Contracts exposing (Source)

type module Source =
  seed : String
```

```text title="src/App/Argument.fl"
module App.Argument exposing (seed)

seed : String
let seed = "Ada"
```

```text title="src/App/Make.fl"
module App.Make(S : App.Contracts.Source) exposing (Token, value)

type Token = Token String

value : Token
let value = Token S.seed
```

```text title="src/App/Instances.fl"
module App.Instances exposing (A, B)

module A = App.Make(App.Argument)
module B = App.Make(App.Argument)
```

Оба файла ниже импортируют **один результат**, `App.Instances.A`, поэтому
могут обмениваться его токенами. `flick check src/App/Consumer.fl` проходит:
повторный импорт `A` не создаёт новый тип.

```text title="src/App/Producer.fl"
module App.Producer exposing (value)

import App.Instances.A as A

value : A.Token
let value = A.value
```

```text title="src/App/Consumer.fl"
module App.Consumer exposing (value)

import App.Instances.A as A
import App.Producer

value : A.Token
let value = App.Producer.value
```

Второе применение, `B`, имеет собственный тип. Добавьте этот файл и выполните
`flick check src/App/Bad.fl`: компилятор выдаст `FLICK-T003`, ожидая
`App.Instances.B.Token` вместо полученного `App.Instances.A.Token`.

```text title="src/App/Bad.fl"
module App.Bad exposing (value)

import App.Instances.A as A
import App.Instances.B as B

value : B.Token
let value = A.value
```

Объявления `module A = …` и `module B = …` создают тождества типов,
а импорты сохраняют их. Тесты документации проверяют эти файлы вместе
и требуют от последнего файла ошибку `FLICK-T003`.

## Сигнатуры модулей высшего порядка

Контракт модуля может описывать функтор. Именованный параметр доступен в
сигнатуре результата. `with type` раскрывает равенство, на которое может
полагаться клиент; оно не добавляет отсутствующего члена и не может
противоречить существующему равенству.

```flick
# module App.Contracts exposing (..)
type module Input =
  type Key

type module Output =
  type Value
  value : Value

type module Factory =
  (K : Input) -> Output with type Value = K.Key
```

Стрелка задаёт статическую сигнатуру модуля отдельно от типа функции над
значениями. Реализация может предъявлять меньше требований к аргументу и
возвращать больше членов, чем требует сигнатура. Аннотация результата скрывает
члены и равенства типов, которые контракт не раскрывает. Runtime-значения
`Module Sig` не могут содержать функторы, в том числе через вложенные члены
модуля (`FLICK-T068`).

## Упакованные модули и экзистенциальные результаты

`pack Argument as Source` имеет тип `Module Source`. Форма `unpack packed as K
in ...` открывает его в лексической области. Каждое открытие создаёт нового
свидетеля абстрактных типов, поэтому значение типа `K.Key` не может потерять
свидетеля незаметно. Если оно выходит из `unpack`, результат экзистенциален;
для публичного значения нужна явная сигнатура:

```text
result : exists K : Box. K.Key
let result = unpack (pack Argument as Box) as K in K.value

answer : Int
let answer = unpack result as K, item in (fun _ -> 42) item
```

`unpack result as K, item in ...` открывает модуль-свидетель и вложенное
значение. Два независимых открытия дают разные абстрактные свидетели.
`Module Sig` не содержит вложенного значения и открывается через `as K in`.
Аргумент параметризованного модуля — статический именованный модуль, а не значение `Module Sig`.
В TypeScript экспортированное экзистенциальное значение получает безопасный
тип `unknown`: TS не выражает свежего свидетеля.

Диагностики различают отсутствие члена (`FLICK-T060`), несовместимость типа
или раскрытого равенства (`FLICK-T061`), иное номинальное тождество класса
или сервиса (`FLICK-T062`), абстрактное номинальное требование при `pack`
(`FLICK-T063`), потерю свидетеля или отсутствие публичной сигнатуры
(`FLICK-T064`), некорректное требование словаря (`FLICK-T065`) и конфликт
локальных словарей (`FLICK-T066`).

## Инициализация и модули входа

При загрузке модуля вычисляются его значения верхнего уровня, поэтому их
определения должны быть чистыми: эффектный вызов там вызывает `FLICK-E001`, `task` на верхнем
уровне допустим, так как его тело выполняется позже (см. [Стадии](../effects/#стадии)),
а из внешних функций при загрузке может выполняться только `pure`
(см. [Режимы](../ffi/#режимы)). Больше импорт модуля, в том числе модуля
библиотеки, ничего не запускает.

Приложение называет модули входа в `flick.toml` через `entry` или `entries`
(см. [Точки входа](../project/#точки-входа)). Каждый из них экспортирует `main` —
собственный или реэкспортированный. Чистый `main : Unit -> Unit` вызывается
напрямую; `main` среды выполнения принимает и возвращает `Unit`, не требует
сервисов и может завершиться ошибкой только с `AppError` (иначе `FLICK-P026`),
поэтому сам предоставляет свои слои и обрабатывает остальные ошибки.

Вход с `target = "client"` работает в браузере: никакой код, достижимый из его `main`,
не может требовать `Server` (`FLICK-E009` с путём до этого места), поэтому
в его бандле нет ни серверных модулей, ни секретов. Такой код обращается
к серверу через [`server fn`](../server-fn/): клиент вызывает функцию по имени
и не требует для этого сервисов, а серверный вход обслуживает её
через `Server.handler`. `flick new --template fullstack` создаёт такую пару,
а `flick dev` запускает серверный вход и Vite для страницы:

```toml
[project]
kind = "app"
runner = "Runner.Node"
entries = { server = "App.Server", web = { module = "App.Web", runner = "Runner.Browser", target = "client" } }
```

## Затенение и неоднозначность

При разрешении имён учитываются сами имена и имена модулей, но не порядок
импортов. Перестановка импортов не меняет диагностику.

1. Локальное связывание (параметр, образец, `let`, `scope`) затеняет
   любое имя верхнего уровня или импортированное имя. Это разрешено.
2. Определение верхнего уровня без предупреждения затеняет имя из импорта
   `exposing (..)`. Но если имя явно импортировано через `exposing (name)`,
   возникает `FLICK-R009`: переименуйте определение или удалите импорт.
3. Два явных импорта одного имени для разных сущностей вызывают `FLICK-R010`.
   Ошибка указывается на импорте модуля, чьё имя идёт последним при сортировке.
4. Если два импорта `exposing (..)` вводят одно имя для разных сущностей,
   `FLICK-R010` возникает в месте использования имени без квалификатора.
   Если имя не используется, ошибки нет.
5. Два импорта с одним квалификатором (`import A as M`, `import B as M`)
   вызывают `FLICK-R010`.

```flick
import App.Users as Users exposing (..)
import App.Orders as Orders exposing (..)

let first = Users.find
```

Имена внутри `sql { }` относятся к запросу и разрешаются при элаборации SQL.
Об неопределённых именах сообщает проверка типов, которая также учитывает
имена из прелюдии.
