Встроенный `std`, бэкенд проекта и плагины его зависимостей могут добавлять
команды в `flick`, рядом с его собственными. `flick --help` перечисляет их,
сгруппировав по контрибьютору. Встроенный `std` предоставляет `schema export`
(`std:schema export`) в памяти без загрузки WebAssembly-компонента и без
обращения к кэшу дескрипторов.

## Запуск

Добавленная команда запускается по своему имени, `flick pairs-hello you`,
если ни один другой контрибьютор не добавляет то же имя. Полная форма
`flick <контрибьютор>:<команда>` работает для каждой команды, которую
контрибьютору можно добавлять. Часть контрибьютора —
это пакет плагина или последняя часть id бэкенда, так что `test/literal`
становится `literal`:

```sh
flick literal:literal-hello you --out greetings
```

- Если два контрибьютора добавляют одно и то же имя, плоское имя даёт
  `FLICK-P053` с перечнем полных имён.
- Контрибьютор не может занять имя команды самого `flick`, например
  `build`. Такое объявление игнорируется с предупреждением `FLICK-P054`.
  Бэкенды (но не плагины) могут реализовывать делегированные базовые команды
  (`install`, `add`, `remove`, `update`, `deps`, `pack`, `doctor`,
  `run-client`, `dev-client`) как команды стиля `plan`: `flick` передаёт
  целевую часть этих команд выбранному бэкенду вместо того, чтобы игнорировать
  их, и не показывает их в списке добавленных команд `--help`.
- Имя, которое никто не добавляет, — это `FLICK-P052`. Если его добавляет
  официальный бэкенд или контрибьютор, уже известный хранилищу, сообщение
  называет его.

Вне проекта работают команды официальных бэкендов, и их корнем становится
рабочий каталог. Инструменты хоста там им даёт только `--allow-tool`.

## Справка без загрузки

Когда команда контрибьютора запускается впервые, компилятор сохраняет его
дескрипторы в хранилище пакетов по хешу его компонента. `flick --help`
читает только этот кэш. Он никогда не создаёт экземпляр компонента и не
обращается к сети. Контрибьютор, для которого записи в кэше нет, появится
после первой своей команды. Вне проекта справка перечисляет всех
контрибьюторов, уже известных хранилищу.

## Как написать команду

Плагин реализует методы команд `flick_plugin::Plugin`, а бэкенд — те же
методы `flick_backend::Backend`. У плагина они появляются с фичей
`commands` крейта `flick-plugin`, которую включает его фича `guest`,
собирающая компонент:

```rust
use flick_plugin::command::{Descriptor, Diagnostic, File, Invocation, Parameter, Plan, Style, ValueKind};

impl Plugin for Notes {
    fn commands(&self) -> Vec<Descriptor> {
        vec![Descriptor {
            name: "notes add".into(),
            summary: "add a note to notes.txt".into(),
            positionals: vec![Parameter {
                name: "text".into(),
                kind: ValueKind::Text,
                multiple: false,
                required: true,
                help: "what to note".into(),
            }],
            options: vec![],
            writes: vec!["notes.txt".into()],
            style: Style::Plan,
        }]
    }

    fn run(&self, invocation: &Invocation) -> Result<Plan, Vec<Diagnostic>> {
        let text = &invocation.arguments[0].values[0];
        let mut plan = Plan::empty();
        plan.files.push(File { path: "notes.txt".into(), bytes: text.clone().into_bytes(), executable: false });
        Ok(plan)
    }
    // …
}
```

Дескриптор объявляет:

- `name`: одно или несколько слов, например `ffi import`.
- `positionals` и `options`: каждый — флаг, текст или путь, возможно
  повторяющийся. По ним хост разбирает командную строку и передаёт каждый
  путь относительно корня проекта, с разделителем `/`. Путь вне проекта
  хост отвергает до запуска команды.
- `inputs`: файлы, которые хост читает для команды (относительно корня
  проекта) и передаёт в `invocation.inputs`. Каталог означает обычные
  файлы в нём, кроме каталогов пакетов бэкенда и скрытых каталогов. Несуществующий
  путь ничего не даёт.
- `reads`: что шаги инструментов плана могут читать на месте.
- `writes`: пути, которые команда может записывать.
- `style`: `plan` или `session`.

В `inputs`, `reads` и `writes` `$name` обозначает пути, которые даёт
параметр `name`, а `$sources` — корень исходников проекта. Он же лежит в
`invocation.sources`.

## Планы

Команда — это чистый вызов. Она никогда сама не пишет файлы и не запускает
процессы: она возвращает план, который хост проверяет и выполняет.

- **Файлы** пишутся в объявленные пути.
- **Шаги инструментов** запускают инструмент хоста из `invocation.tools`.
  Это инструменты, которые проект разрешает контрибьютору в `[tools]` по
  пакету плагина или id бэкенда; хост закрепляет каждый по хешу и версии
  (разрешённый инструмент, которого нет в `PATH`, передаётся с пустыми
  `version` и `sha256`, чтобы команда могла выдать понятную ошибку; попытка
  запустить его отвергается). `reads` обычного шага должны входить в `reads`
  дескриптора и появляются в его каталоге по тому же относительному пути как
  ссылки на файлы проекта, а не как копии. Шаг с `in_place: true` выполняется
  напрямую в корне проекта после публикации файлов плана (так работают
  менеджеры пакетов бэкендов): он не принимает `inputs` и `reads`, запрещён
  вместе с `resume` и в предпросмотре редактора, а каждый путь в `outputs`
  должен быть объявлен в `descriptor.writes`.
- **Зависимости**: делегированные команды бэкенда также получают
  `invocation.dependencies` — транзитивное замыкание
  `[target.<name>.dependencies]` для этого бэкенда.
- **Необязательная команда `pack`**: реализация `pack` (`writes = [".flick/pack"]`)
  для бэкенда необязательна; без неё (как в `flick/go`) ядро `flick pack`
  записывает только детерминированный архив исходников Flick. Если бэкенд
  объявляет `pack`, хост подготавливает release-сборку в `.flick/pack/dist/`,
  создаёт `.flick/pack/out/`, передаёт контекстные параметры, отфильтрованные по
  дескриптору (`kind`, `has-package`, `entry`, `runner`, `file`, `option`), и
  переносит обычные файлы из `.flick/pack/out/` в `--out-dir` (или в
  `<out-dir>/<target>/` при совпадении имени с архивом исходников Flick).
- **Шаги `run-flick`** компилируют и запускают программу Flick через выбранный
  бэкенд проекта в изолированном временном поколении, не записывая файлы в
  дерево проекта и в кэш модулей на диске. Шаг может накладывать в памяти
  модули `FlickModule` поверх `$sources`, передавать программе `arguments`,
  захватывать stdout в `output` (передаётся в `resume`, если он задан, иначе
  публикуется под `descriptor.writes`) и задавать диапазон `origin` в
  `invocation.inputs`, чтобы диагностики из синтетических модулей указывали на
  исходный код пользователя. Для `run-flick` действуют только разрешения
  `[tools]` самого выбранного бэкенда (например, `"flick/go" = ["go"]` для Go и
  никаких для `flick/js`); сбои выполнения, таймауты и превышение лимита вывода
  дают `FLICK-P061`.
- **Диагностики** сообщаются как собственные диагностики компилятора.
  `span` указывает в файл из `invocation.inputs`, а `help` подсказывает
  пользователю, что делать.
- **`stdout`** — то, что команда печатает.
- **`resume`**, если задан, — состояние, которое хост возвращает после
  выполнения шагов. Вместо записи выходов шагов хост вызывает
  `resume(state, outputs)` и передаёт их туда. Полученный план
  выполняется так же; всего планов может быть не больше 16.

Хост отвергает план с `FLICK-P055` до каких-либо действий, если план пишет
вне объявленных путей или проекта, запускает инструмент, который хост не
закрепил, читает файл, которого в плане нет, или содержит некорректный шаг
`run-flick` (некорректные или повторяющиеся имена модулей, повторяющиеся id
шагов, слишком большие исходники, выходящие за пределы или необъявленные
выходные пути либо диапазон `origin` вне файла). Шаги выполняются по порядку,
каждый шаг инструмента — в отдельном каталоге только со своими входами, как и
шаг сборки (см. [project.md](../project/)). Затем файлы всех планов и выходы
шагов последнего плана публикуются вместе одной транзакцией: сбой оставляет
проект таким, каким он был.

## Сессии

Сессионная команда обслуживает запросы на stdio, пока вызывающий держит её
открытой, как это делает интеграция с редактором. Хост владеет stdio:

- Он читает и пишет сообщения с фреймингом `Content-Length`, как в
  протоколе языкового сервера.
- `open` даёт состояние новой сессии или план, который команда вместо
  этого выполняет один раз, как `content-mapper --declarations`.
- `handle` получает каждое сообщение вместе с текущим состоянием и
  возвращает ответ, если он есть, и следующее состояние.
- Если `handle` нужно то, что вычисляет хост (TypeScript-проекция
  модуля), он возвращает `needs` вместо ответа. Хост вычисляет ответы и
  снова вызывает `handle` с тем же сообщением, возвращённым состоянием и
  ответами. План просит так же, для `resume`.
- Ловушка в `handle` становится ошибкой JSON-RPC `-32603`, а сессия
  сохраняет последнее состояние.
- `$/cancelRequest` останавливает названный в нём запрос: его вызов
  прерывается, а ответом становится ошибка `-32800`.
- `exit` или конец stdin вызывает `close`, чей план хост выполняет. То,
  что печатает этот план, уходит в stderr, поскольку stdout принадлежит
  протоколу.

## Шаблоны

Бэкенды и плагины библиотек также предоставляют шаблоны проектов для `flick new`
и `flick init` через тот же интерфейс `flick:command/command`:

- `templates()` возвращает список `TemplateDescriptor { name, summary }`.
- `scaffold(request)` принимает `TemplateRequest { template, name, compiler, init }`
  (с нормализованным именем пакета и версией запущенного компилятора) и
  возвращает `Plan` со всеми файлами шаблона — включая `flick.toml` — и
  необязательной подсказкой следующих шагов в `stdout`.

Планы шаблонов — это чистые планы файлов: хост отвергает с `FLICK-P055` любой
план шаблона, который содержит шаги хоста (`tool` или `run-flick` в `steps`),
`resume`, `needs` или пути за пределами целевого каталога, ещё до создания
каталога и записи файлов. Неизвестные шаблоны возвращают `FLICK-P060` со
списком доступных шаблонов контрибьютора.

Пользователь выбирает шаблоны официального бэкенда через `--target <name>` (`js`
по умолчанию или `go`) либо загружает сторонний пакет плагина или бэкенда через
`--from <path|url|git>` (с теми же проверками, что и `flick add`, и закреплением
в `[[template]]` файла `flick.lock`).
