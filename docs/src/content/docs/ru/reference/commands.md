Бэкенд проекта и плагины его зависимостей могут добавлять команды в
`flick`, рядом с его собственными. `flick --help` перечисляет их,
сгруппировав по бэкенду или плагину, который их добавляет.

## Запуск

Добавленная команда запускается по своему имени, `flick pairs-hello you`,
если ни один другой контрибьютор не добавляет то же имя. Полная форма
`flick <контрибьютор>:<команда>` работает для каждой команды, которую
контрибьютору можно добавлять. Часть контрибьютора —
это пакет плагина или последняя часть id бэкенда, так что `test/literal`
становится `literal`:

```sh
flick literal:literal-hello you --out greetings
```

- Если два контрибьютора добавляют одно и то же имя, плоское имя даёт
  `FLICK-P053` с перечнем полных имён.
- Контрибьютор не может занять имя команды самого `flick`, например
  `build`. Такое объявление игнорируется с предупреждением `FLICK-P054`.
- Имя, которое никто не добавляет, — это `FLICK-P052`. Если его добавляет
  контрибьютор, уже известный хранилищу, сообщение называет его.

Вне проекта работают только команды ядра, поскольку добавленная команда
принадлежит проекту, чей бэкенд или зависимость её добавляет.

## Справка без загрузки

Когда команда контрибьютора запускается впервые, компилятор сохраняет его
дескрипторы в хранилище пакетов по хешу его компонента. `flick --help`
читает только этот кэш. Он никогда не создаёт экземпляр компонента и не
обращается к сети. Контрибьютор, для которого записи в кэше нет, появится
после первой своей команды. Вне проекта справка перечисляет всех
контрибьюторов, уже известных хранилищу.

## Как написать команду

Плагин реализует методы команд `flick_plugin::Plugin`, а бэкенд — те же
методы `flick_backend::Backend`. У плагина они появляются с фичей
`commands` крейта `flick-plugin`, которую включает его фича `guest`,
собирающая компонент:

```rust
use flick_plugin::command::{Descriptor, Diagnostic, File, Invocation, Parameter, Plan, Style, ValueKind};

impl Plugin for Notes {
    fn commands(&self) -> Vec<Descriptor> {
        vec![Descriptor {
            name: "notes add".into(),
            summary: "add a note to notes.txt".into(),
            positionals: vec![Parameter {
                name: "text".into(),
                kind: ValueKind::Text,
                multiple: false,
                required: true,
                help: "what to note".into(),
            }],
            options: vec![],
            writes: vec!["notes.txt".into()],
            style: Style::Plan,
        }]
    }

    fn run(&self, invocation: &Invocation) -> Result<Plan, Vec<Diagnostic>> {
        let text = &invocation.arguments[0].values[0];
        let mut plan = Plan::empty();
        plan.files.push(File { path: "notes.txt".into(), bytes: text.clone().into_bytes(), executable: false });
        Ok(plan)
    }
    // …
}
```

Дескриптор объявляет:

- `name`: одно или несколько слов, например `ffi import`.
- `positionals` и `options`: каждый — флаг, текст или путь, возможно
  повторяющийся. По ним хост разбирает командную строку и передаёт каждый
  путь относительно корня проекта, с разделителем `/`. Путь вне проекта
  хост отвергает до запуска команды.
- `inputs`: файлы, которые хост читает для команды (относительно корня
  проекта) и передаёт в `invocation.inputs`. Каталог означает обычные
  файлы в нём, кроме `node_modules` и скрытых каталогов. Несуществующий
  путь ничего не даёт.
- `reads`: что шаги инструментов плана могут читать на месте.
- `writes`: пути, которые команда может записывать.
- `style`: `plan` или `session`.

В `inputs`, `reads` и `writes` `$name` обозначает пути, которые даёт
параметр `name`, а `$sources` — корень исходников проекта. Он же лежит в
`invocation.sources`.

## Планы

Команда — это чистый вызов. Она никогда сама не пишет файлы и не запускает
процессы: она возвращает план, который хост проверяет и выполняет.

- **Файлы** пишутся в объявленные пути.
- **Шаги инструментов** запускают инструмент хоста из `invocation.tools`.
  Это инструменты, которые проект разрешает контрибьютору в `[tools]` по
  пакету плагина или id бэкенда; хост закрепляет каждый по хешу и версии.
  `reads` шага должны входить в `reads` дескриптора. Они появляются в
  каталоге шага по тому же относительному пути как ссылки на файлы
  проекта, а не как копии.
- **Диагностики** сообщаются как собственные диагностики компилятора.
  `span` указывает в файл из `invocation.inputs`, а `help` подсказывает
  пользователю, что делать.
- **`stdout`** — то, что команда печатает.
- **`resume`**, если задан, — состояние, которое хост возвращает после
  выполнения шагов. Вместо записи выходов шагов хост вызывает
  `resume(state, outputs)` и передаёт их туда. Полученный план
  выполняется так же; всего планов может быть не больше 16.

Хост отвергает план с `FLICK-P055` до каких-либо действий, если план пишет
вне объявленных путей или проекта, запускает инструмент, который хост не
закрепил, или читает файл, которого в плане нет. Шаг работает в отдельном
каталоге только со своими входами, как и шаг сборки (см.
[project.md](../project/)). Затем файлы всех планов и выходы шагов
последнего плана публикуются вместе одной транзакцией: сбой оставляет
проект таким, каким он был.

## Сессии

Сессионная команда обслуживает запросы на stdio, пока вызывающий держит её
открытой, как это делает интеграция с редактором. Хост владеет stdio:

- Он читает и пишет сообщения с фреймингом `Content-Length`, как в
  протоколе языкового сервера.
- `open` даёт состояние новой сессии.
- `handle` получает каждое сообщение вместе с текущим состоянием и
  возвращает ответ, если он есть, и следующее состояние.
- Ловушка в `handle` становится ошибкой JSON-RPC `-32603`, а сессия
  сохраняет последнее состояние.
- `$/cancelRequest` останавливает названный в нём запрос: его вызов
  прерывается, а ответом становится ошибка `-32800`.
- `exit` или конец stdin вызывает `close`, чей план хост выполняет. То,
  что печатает этот план, уходит в stderr, поскольку stdout принадлежит
  протоколу.
