Плагин обрабатывает блоки в модулях, которые его импортируют: выражения, например
`head { … }`, `head "x" (e) { … }` и `head Shape`, и объявления, например
`head table Name "t" { … }` и `head fn ping x = …`, — и возвращает код для каждого
блока: выражение или объявления модуля. Компилятор проверяет, собирает и
показывает этот код на месте блока, а код пользователя внутри блока остаётся
на своём месте в файле: ошибки, подсказки и переименования попадают в него.

## Как подключить плагин

Плагин поставляется в составе библиотеки; проект зависит от неё как от любой другой (см.
[project.md](../project/)). Модуль импортирует модуль библиотеки и рядом с
его именами открывает головы плагина словом `plugin`:

```flick
module App.Main exposing (point)

import Pairs exposing (Pair, plugin pairs)

point : { x : Float; label : String; blocks : Float }
let point = pairs { x = 1.0 + 2.0; label : String = "a" }
```

Голова считается блоком плагина только в файле, который её импортирует: в
остальных местах `pairs { x = 1 }` по-прежнему вызов с записью, и каждый файл
разбирается сам по себе. Голова — не значение, поэтому то, что идёт за ней на
её строке, — её аргументы: слова, имена, числа, строки, пути вроде
`App.Api.place` и `( … )`, а затем, возможно, тело `{ … }`:

| Форма | Где | Пример |
| - | - | - |
| `head args { body }` | в выражении | `pairs "a" (1.0 + 2.0) { x = 1.0 }`, `sql p { … }` |
| `head args` | в выражении | `named Shape`, `server App.Api.place` |
| `head args { body }` | в начале объявления | `sql table Users "users" { … }` |
| `head args rest` | в начале объявления | `server fn ping (n : Int) = n + 1` |

Аргументы, тело и остаток хранятся токенами, со сбалансированными скобками, —
их читает плагин. Остаток объявления идёт до следующего объявления — строки с
колонки 1, которая не начинается закрывающей скобкой. Сырой текст, например
SQL с `'кавычками'` и `-- комментариями`, — это сырая или многострочная
строка-аргумент, `head migration 1 "init" r#"…"#`; её значение даёт
`flick_plugin::string_value`.

С компилятором поставляется плагин пакета `std` с головами `cli` (см.
[приложения командной строки](../cli-dsl/)), `server` (см.
[серверные функции](../server-fn/)) и `codec` (см.
[DSL кодеков](../schema/#dsl-кодеков)), и `sql`. Эти головы есть в каждом
модуле без импорта: `cli "x" { … }` с телом, а также `server fn f x = …` и
`server f` — блоки плагина `std`, а в остальных местах эти слова — обычные
имена. Импорт `import Cli exposing (plugin cli)` нужен только блоку без `{`,
например `cli Main`; в остальных случаях такой импорт — `FLICK-R012`, и
`flick check --fix` его убирает. Другой плагин эти головы дать не может:
`FLICK-P044`.

Плагин берётся у пакета, которому принадлежит импортируемый модуль; у модуля
самого проекта или встроенного модуля плагина нет. Код, который отдаёт
плагин, разрешается в области видимости файла: его импорты, среди них и
импортируемый модуль, Prelude и собственные объявления модуля. Плагину лучше
называть то, чем он пользуется, квалифицированными именами, например
`Pairs.make`; другой нужный ему модуль импортирует пользователь. Имена кода
плагина — его собственные:

- локальное имя кода, как `x` в `fun x -> …`, видит только этот код, а
  локальное имя пользователя, вокруг блока или в нём, — только код
  пользователя: одно не захватывает другое;
- `Pairs.make` называет модуль `Pairs` по пути, даже в файле, который
  импортирует его как `import Pairs as P`, а модуль, который файл назвал
  `Pairs`, его место не занимает;
- имя, которое объявляет и сам модуль, по-прежнему `FLICK-R008` на блоке:
  то, что объявляет блок, принадлежит модулю.

## Что отдаёт плагин

Плагин — это компонент WebAssembly мира `flick:plugin` из
[`flick-plugin/wit/plugin.wit`](https://github.com/bondiano/flick-lang/blob/main/flick-plugin/wit/plugin.wit)
или значение Rust с трейтом `Plugin` из крейта `flick-plugin`, вкомпилированное
в компилятор. У него три вызова, все чистые:

- `collect(blocks)` узнаёт всё нужное из всех своих блоков группы (исходники
  проекта, его тесты или пакет) — в порядке имён их модулей и мест — и отдаёт
  состояние в байтах;
- `publish(state)` отдаёт то, что блоки других модулей и групп могут
  спросить о состоянии группы: имена модулей, у каждого байты, как столбцы
  таблицы. Все группы публикуют свои данные до раскрытия первого блока, поэтому
  модуль тестов видит опубликованное исходниками;
- `expand(block, state)` отдаёт код одного блока или то, что в нём неверно,
  со span'ами блока.

Блок внутри кода пользователя другого блока, как `subcommand cli "x" { … }`
в блоке `cli`, разворачивается после него, в своём раунде: `collect` узнаёт
о блоках раунда вместе, а блок с глубиной вложенности больше восьми — `FLICK-P036`.

Редакторы тоже спрашивают плагин о его блоках, даже о тех, что не
разворачиваются: `complete(block, state, offset, member)` отдаёт, что
вставить в позиции (пустой список оставляет код пользователя обычному
дополнению; `member` говорит, что пользователь набрал там `name.`, а точки в
блоке нет, и компилятор отвечает на `published`, как при раскрытии блока;
там же `in-scope(ns, fits)` даёт значения или типы в области видимости
модуля блока под теми именами, которыми он их пишет, а с `fits` — типом,
записанным так, как его пишет модуль, или с полностью квалифицированными
именами (`Prelude.PureCodec Prelude.BigInt UserId`), — только значения, тип
которых конкретизируется до него; при раскрытии блока он ничего не даёт),
`hover(block, state, offset)` — что значит span, а `highlight(block, state)` —
span'ы собственных слов плагина, как ключевые слова или параметры.

Форматтер спрашивает у `format(block, state)` раскладку блока: куски слов
плагина, новые строки, уровень внутрь или наружу и дыры — код пользователя,
который форматтер раскладывает как любой другой. Голову перед ними, `{` перед
раскладкой, которая начинается в теле, и `}` после неё пишет компилятор, а
раскладку оставляет, только если объявление разбирается обратно в тот же
код. Без неё, а также для блока с комментариями, кроме строк `///`, блок
остаётся как написан, а отступы его строк изменяются вместе с отступом головы блока. `flick fmt`
спрашивает плагины пакетов проекта, редактор — плагины, которые загрузил его
анализ.

Блок показывает голову; своё место `place` — выражение или объявление; свой
текст — от первого аргумента (или от тела, если аргументов нет) до
закрывающей `}` или до конца; `body` — где в этом тексте начинается тело (его
длина, если тела нет); и токены аргументов, тела и остатка, без `{`. Все
span'ы отсчитываются от начала текста. Код пользователя в нём — «дыры» —
разбирает компилятор: `parse-expr(start, end)`, `parse-type`, `parse-pat` и
`parse-decl` дают самое длинное выражение, тип или образец начиная со
`start` или объявление там, с раскладкой того места, где оно стоит в файле;
`parse-body` даёт тело, как после `=` у `let`: строки блока, если оно
начинается на своей строке; `parse-lines` даёт то же тело, где строки под
вызовом — его аргументы, по одному целому выражению на строку, а в арене его
дыру обозначает `lines`. Ещё блок показывает `module` — модуль, где он
стоит, а объявление прямо под сигнатурой — `signature`: её текст и токены,
span'ы от её начала. Код с типом из сигнатуры, `signed(span)`, забирает её из
модуля; без него сигнатура остаётся на месте, над тем, что объявляет код.
Выражение, которое составляет всё тело `let` модуля, тоже видит сигнатуру
этого `let`, но его код не берёт из неё типов.
`literal-of(name)` говорит, перечисление ли тип `name` так, как его пишет
модуль (`Role`, `Roles.Role`), объявленное в модуле или импортированное, и
даёт его базовый тип, `String` или `Int`: типы ещё не проверены, поэтому
плагин спрашивает, прежде чем писать код для такого типа.
`published(name)` даёт то, что тот же плагин опубликовал об имени `name`
так, как его пишет модуль (`Users`, `Schema.Users`): об имени самого модуля
или импортированного, а `published-names()` — все имена, на которые он
отвечает. Сохранённый результат раскрытия, использовавший этот запрос, остаётся пригодным, пока ответ тот
же.

Код блока-выражения — выражение; код блока-объявления — объявления: они
встают на место блока среди объявлений модуля и принадлежат модулю, как
любые другие, — экспортируются через `exposing`, видны импортирующим, а
сигнатура над блоком относится к первому из них с её именем. `let` или
сигнатура могут объявить компаньон `Users.table` типа `Users` этого модуля: он
экспортируется вместе с типом, и импортирующие называют его `Users.table`.
Строки `///` над блоком-объявлением — `docs` блока; плагин отдаёт их тому, что
объявляет. Переход к определению сгенерированного имени ведёт на span,
который плагин дал его объявлению, — имя пользователя в блоке или весь блок,
а переименовывают такое имя в его блоке. Код — это арена
синтаксиса ядра: каждый узел идёт после узлов, на которые ссылается, и несёт
span блока, который означает:

| Вид | Узлы |
| - | - |
| выражение | имя, число, текст, булево, unit, применение, лямбда, запись, поле, список, кортеж, аннотация, дыра, конкатенация (`a ++ b`), `match` с охранами, `if`, блок из инструкций и его значения, тело с открытым модулем |
| тип | имя, применение, запись, функция, кортеж, текст на уровне типов (`"name"`), `_`, `forall`, строка, дыра, тип из сигнатуры |
| образец | переменная, `_`, конструктор, запись, кортеж, дыра |
| объявление | `let`, сигнатура, `type alias`, `type` с конструкторами и `deriving`, возможно `unboxed`, `instance` с методами, группа из нескольких или ни одного, документация одного, функция со значением, которое читает данную ей константу, дыра |

Компилятор проверяет арену, прежде чем ею пользоваться: имена должны быть
именами, числа — конечными, дыры — лежать в теле и не пересекаться,
выражение или объявление — использоваться один раз (тип может стоять в
нескольких местах, например в сигнатуре и в аннотации, и образец тоже, как
props компонента, которые связывают и его setup, и его render), а размер и
глубина ограничены. Блок бывает только телом `fun` или `let`; его инструкции —
`let`, сигнатуры, дыры для них или выражения, и дыра объявления в нём — это
`let` или сигнатура пользователя. Тело с открытым модулем называет модуль
его путём: в теле имя, которое модуль экспортирует, — именно оно, раньше имён
файла, если его не скрывает локальное; в исходном коде такой формы нет, ею
блок приносит в область видимости имена своей библиотеки. С типом ребёнка вызов
в таком теле даёт последний параметр-список этого типа поэлементно: каждый
аргумент начиная с этого параметра — элемент, ни одного — пустой список, один
аргумент-список — сам список, а литерал списка отвергается (`FLICK-T073`).
С функцией, через которую применяются значения, значение в таком теле, тип
которого совпадает с типом первого параметра функции, применяется через неё:
`badge props` внутри `ui` — это `Ui.component badge props`.
Целое число — целочисленный литерал любого числового типа,
которого требует его использование; блок объявлений с пустой группой
ничего не объявляет. Функции в коде плагина сигнатура не нужна: её тип
выводится.
Версия арены — версия интерфейса,
`0.2.0`. Собирайте
компонент тем `flick-plugin`, что и компилятор, в котором он работает.
Компонент, собранный под другую версию, не загружается: импорт, открывающий
его головы, — `FLICK-P035` с версией, под которую он собран, и той, что
понимает компилятор; так до пересборки.

## Проверки с типами

Код плагина проверяется как код пользователя, а ошибка в нём указывает на соответствующий
фрагмент исходного блока. То, что видно только по типам, например поле, которого нет
в записи, плагин сообщает сам после проверки: каждый `_` его кода — тип,
который выводит чекер, — это факт со span'ом, который ему дал плагин, и
`check` получает их: тип как он показан (`shown`), полный, с раскрытыми
алиасами (`exact`, нет, пока в нём ошибки или неизвестные), точный базовый
тип перечисления (`literal-of`, `String` или `Int`), а для закрытой записи —
её поля. `check` только добавляет ошибки; блок, в коде которого нет
`_`, не спрашивается. `hover` редактора получает те же факты, так что плагин
может показать тип того, что называет его блок, — как `codec` показывает тип
поля над его меткой.

```rust
fn check(&self, block: &Block, _: &[u8], facts: &[Fact]) -> Vec<Diagnostic> {
    facts.iter().map(|f| Diagnostic::error(format!("`_` is `{}`", f.ty.shown), f.span)).collect()
}
```

## Проверки вызовов

Пакет может следить не только за своими блоками, но и за вызовами имён.
`watch` в его `[package]`, рядом с `plugin`, называет их: каждое —
`Module.name`, `Module.Sub.name` или `*.name` для имени в любом модуле.
Можно назвать и сервис, `Module.Service`, и метку, `@maker` или `@cell`; что
плагин о них узнаёт, сказано ниже.

```toml
[package]
name = "ui"
version = "1.0.0"
plugin = "ui.wasm"
watch = ["Ui.Event.queue", "*.parse"]
```

Тогда `check-calls` получает каждое место проверяемого модуля, где
применяют одно из них, вместе с тем, что нашёл чекер: модуль и имя,
span применения, стоит ли оно в коде, который написал плагин, и для каждого
аргумента — где он написан, его тип, каким его видит `check`, константу, в
которую он сворачивается, если она есть, и записан ли он как `fun`.
Вызов с константой несёт ещё и то, как эта константа читается: для `parse`
перечисления — его литералы; для функции, которую код блока объявил вместе
со значением, читающим её константу (`Decl::Checked { by, decl }`), —
синтаксис и разрешённые ссылки этого значения, как проверка уточнённого
типа читает аргумент его `parse`. Эти факты интерпретирует плагин. Все span'ы — в
файле самого модуля, и внутри блока, и вне его, так что диагностика
приходит на код, который написал пользователь.

Каждое место, где названо наблюдаемое значение, применённое или нет, — тоже
место, с фактами `binding` только для чтения и без аргументов: модуль и имя
верхнеуровневого значения, в котором оно стоит (у функции имени нет), span
этого объявления, наличие словаря в схеме, положение ссылки внутри функции и
число аргументов, к которым она применена. Применённое имя даёт поэтому два
места: применение с аргументами и имя с `binding`. UI-плагин читает эти
факты у сериализуемых атомов для `FLICK-U003`; вывод типов они не меняют.

Наблюдаемый сервис, который назван в сигнатуре функции верхнего уровня, —
тоже такое место: на имени функции, без аргументов и с `binding`, где
сказано, какая это функция и, в `gives`, какой тип она даёт после применения
всех стрелок. UI-плагин предупреждает (`FLICK-U007`) там, где функция читает
атомы и даёт `Ui`.

Обработчик, сделанный из `fun` внутри рендера `Ui.view`, находится так же:
вызовы `Ui.view` и конструкторов `Ui.Event` наблюдаются, и плагин
предупреждает (`FLICK-U002`) там, где конструктор, получивший `fun`, стоит
внутри первого аргумента вида, который написан в самом модуле.

Плагин может наблюдать и метку — атрибут, которым помечены значения одного
рода, как `@maker` помечает то, что делает атом, действие или вид. Каждое
место внутри функции, где названо значение, до которого метка доходит, само
или через функции, которые оно вызывает, — тогда место с `tagged`: метка,
имя, как оно написано, помеченное значение, к которому оно приводит, и в
`inside` — функции вокруг места от ближайшей наружу, каждая с сервисами своей
стрелки и с тем, открыт ли её ряд. Задача обработчика выполняется позже,
поэтому функции вокруг `task` не окружают то, что внутри него. Функция,
которой нужен сервис с меткой `@owner`, ни до чего не доходит для тех, кто её
называет: сделанное под таким сервисом принадлежит его обработчику, как
сделанное в setup компонента принадлежит экземпляру (`Setup` помечен так). UI-плагин
отказывает (`FLICK-U006`) создателю, названному в рендере — функции, чьи
сервисы — только `Atom.Read`.

Наблюдаемый сервис — ещё и место, где его называет ожидаемая функция, а
код, данный там, просит большего: сервис или ошибку, которых её ряд не
разрешает. Место несёт `lacking`: ожидаемую функцию, то, что не разрешено,
словами компилятора, сервисы как они показаны и по полным именам, и ошибки.
Компилятор отказывает такому коду сам (`FLICK-E002`); ошибка, которую плагин
даёт на span этого места, встаёт на место ошибки компилятора, так что плагин
может сказать, где этому коду место. UI-плагин делает так для рендера,
который не только читает атомы (`FLICK-U004`), и для setup компонента.

Метка `@cell` помечает тип, значения которого держат по одному значению. Там,
где значение, не являющееся функцией, держало бы такой тип при каждом типе,
за который стоят его переменные, компилятор отказывает (`FLICK-T072`), и это
место — с `tagged`: метка, в `named` — тип значения, как он показан, в
`reaches` — помеченный тип, а `inside` пуст; `binding` называет значение,
если у него есть имя. Ошибка, которую плагин даёт там, встаёт на место
ошибки компилятора, как выше: UI-плагин говорит это об атоме (`FLICK-U005`).

```rust
fn check_calls(&self, calls: &[CallSite], state: &[u8]) -> Vec<Diagnostic> {
    (calls.iter())
        .filter(|c| !matches!(c.arguments.first().and_then(|a| a.constant.as_ref()),
            Some(Constant::Number(n)) if *n > 0.0))
        .map(|c| Diagnostic::error("it counts from one", c.span).with_code("L002"))
        .collect()
}
```

Плагин спрашивают один раз на модуль — о вызовах имён, за которыми следит
его пакет, и с состоянием, которое дал его `collect`; модуль без таких
вызовов до него не доходит, а пакет без `watch` не спрашивают вовсе.
`check-calls` только добавляет ошибки: сам вызов компилятор уже проверил.
Так работают проверки `std`, и у них остаются собственные коды компилятора:
граница политики, не являющаяся положительным целым, — `FLICK-U001`, а
константа, не прошедшая проверку своего уточнённого типа, — `FLICK-D006`.

## Derive

Класс с `@derive` выводит плагин: плагин пакета, где объявлен класс, или
пакета, который назван в атрибуте, — `@derive std`.

```flick
@derive
class Arbitrary a =
  arbitrary : a
```

Тип, который называет такой класс в `deriving`, может передать аргументы
(`deriving Arbitrary { depth = 3 }`). Вызов `derive(target, class, args, module, state)`
плагина делают и такой тип, и `deriving instance Arbitrary (Shapes.Shape)`
для типа из другого модуля пакета:

- `target` — объявление типа как блок и то, что оно объявляет, в span'ах
  этого блока: имя, параметры, конструкторы с типами полей, а у
  перечисления — их литералы; называет ли конструктор GADT тип, который
  строит (`refined`), и хранит ли словари (`constrained`); тип, который обозначает
  псевдоним; а для типа над другим типом, чей конструктор принадлежит
  только его объявлению, — тип, который он оборачивает (`wraps`): база
  уточнённого типа или поле `unboxed type` из блока, конструктор которого
  может назвать только сгенерированный код. Значения такого типа даёт его
  `T.parse`, а читает `T.value`;
- `class` — полное имя класса, `Pairs.Arbitrary`;
- `args` — `{ … }` после класса;
- `module` — все типы, объявленные в модуле.

Плагин отдаёт объявления — экземпляр и то, что к нему прилагается. Они
идут после объявления типа или встают на место `deriving instance`, а их
ошибки стоят на классе в `deriving`. Тип другого модуля называется
квалифицированно, `Shapes.Square`, и его span'ы не дыры. Экземпляр всё
равно принадлежит модулю, и к нему применяется правило сирот (`FLICK-C006`).

Тип, который объявляет код блока, называет свои классы в `deriving` этого
объявления, и вывод каждого класса вызывается для него так же, как для
объявления модуля: блок — его `target`, а поля типа — типы, которые
пользователь написал в блоке. У поля, которое плагин построил сам, span'а
нет, и класс, выводимый плагином, тогда даёт `FLICK-P036`. Выведенный код
идёт вместе с кодом самого блока.

## Как написать плагин на Rust

`flick new demo --template plugin` создаёт библиотеку с плагином: модуль,
который импортируют программы (`src/Tagged.fl`), крейт плагина (`plugin/`),
объяснения его кодов (`explain/`) и скрипт `flick run plugin`, который
собирает компонент `plugin.wasm` — его называет манифест в
`[package] plugin`. Плагин шаблона — `tagged "name" { value }`, который
означает `{ tag = "name"; value = value }`:

```rust
use flick_plugin::{Arena, Block, Builder, Compiler, Diagnostic, Plugin, TokenKind, flick};

pub struct Tagged;

#[cfg(feature = "guest")]
flick_plugin::export!(Tagged);

impl Plugin for Tagged {
    fn collect(&self, _: &[Block], _: &mut dyn Compiler) -> Vec<u8> {
        Vec::new()
    }

    fn expand(
        &self,
        block: &Block,
        _: &[u8],
        compiler: &mut dyn Compiler,
    ) -> Result<Arena, Vec<Diagnostic>> {
        let tag = match block.arguments() {
            [t] if t.kind == TokenKind::String => t.span,
            _ => {
                let message = "`tagged` takes its tag: `tagged \"name\" { value }`";
                return Err(vec![Diagnostic::error(message, block.whole()).with_code("T001")]);
            }
        };
        let mut body = block.body();
        let value = body.expr(compiler).map_err(|d| vec![d])?;
        let mut b = Builder::new(block.whole());
        let record = flick!(b, { tag = #tag; value = #value });
        Ok(b.finish(record))
    }
}
```

`flick!(b, code)` строит переданный ему код, написанный на Flick, при
компиляции плагина: то, что не является Flick из арены, — ошибка
`cargo build`. `#x` и `#(expr)` подставляют значение плагина по месту:

| Значение | В выражении | В типе |
| - | - | - |
| `Span` | код пользователя там, дыра | тип пользователя там |
| `&str`, `String` | текст | текст на уровне типов, как в `Record.Label "x"` |
| `Name("M.f")` | имя | имя |
| `Wildcard` | — | `_` |
| построенный раньше `NodeId` | этот узел | этот узел |

`#(..xs)` подставляет каждый элемент коллекции в список, в аргументы
применения или в поля записи (пары `(label, value)`);
`flick!(b @ span, code)` задаёт узлам origin, а `flick!(b, type T)` строит
тип. Постоянные имена пишутся как есть:
`flick!(b, Cli.flag (Record.label : Record.Label #field) [#(..&aliases)] #help #multi #spec)`.
Код, который начинается как объявление, строит объявление; его имя пишется
как есть или `#(expr)`: `flick!(b, let #(name) x : Float = f x)`,
`flick!(b, size : Int)`, `flick!(b, type alias #(name) = { #(..fields) })`,
`flick!(b, type Color = Red | Rgb Float Float deriving Show)` и
`flick!(b, instance Show #(Name(t)) { let show _ = #t })`; `b.group(ids)`
даёт несколько, `b.doc(&block.docs, id)` документирует одно,
`let #("Users.table")` объявляет компаньон, а `Span` на месте объявления —
объявление пользователя. `flick!(b @ name, let …)` объявляет его в `name`
пользователя — туда и переходит редактор.
`flick!(b, unboxed type #name = #(make) Float)` объявляет собственный тип,
значения которого при работе программы — значения его поля. Конструктор с
именем `Meters$Make` может написать только сгенерированный код, и назвать
его может только код плагина, который его объявил: код другого плагина с
таким именем — `FLICK-P036`, а из модуля тип выходит непрозрачным. Тогда
функции блока — единственные входы в тип и выходы из него.

Блок читают курсором по его токенам — `block.cursor()` с первого или
`block.body()` с тела: `eat(":")`, `ident()`, `strings()`, `rest()`, а
`expr(compiler)`, `ty`, `pat` и `decl` просят у компилятора код пользователя
со следующего токена и проходят за него. `block.arguments()` — токены
аргументов головы, `block.docs_above(offset, " ")` — строки `///` над тем,
что начинается в `offset`. `Plugin::format` отдаёт `Piece::Text`, `Line`, `Indent`,
`Dedent` и `Hole(hole)` — дыру, как её находят `expr` и `ty` курсора.

Тесты шаблона показывают, что плагин делает из блока, через
`flick_core::plugin::testing::expand`:

```rust
let found = expand(&Tagged, "module M exposing (x)\n\nimport Tagged exposing (plugin tagged)\n\nlet x = tagged \"a\" { 1.0 + 2.0 }\n");
assert_eq!(found, [Ok("{ tag = \"a\"; value = (1.0 + 2.0) }".to_owned())]);
```

В программе `flick expand` печатает код, который означает каждый блок
проекта или переданных файлов, с кодом пользователя на месте. С
`crate-type = ["cdylib"]`, фичей `guest` крейта `flick-plugin` и
`--target wasm32-wasip2`, как в скрипте, крейт собирается в компонент.

## Файлы других языков

Плагин может превращать в модуль и файл другого языка. Какие расширения, его
пакет говорит рядом с `plugin`:

```toml
[package]
name = "protos"
version = "0.1.0"
plugin = "protos.wasm"
load = ["proto"]
```

Тогда `import App.User` находит `App/User.proto`, если нет `App/User.fl`, а
`load(path, bytes)` плагина даёт объявления модуля, каждое на span'е файла,
который оно означает: проект проверяет и импортирует их как свои, модуль
открывает их все, редактор переходит от использования к этой строке файла
и присылает серверу правки файла, когда сервер зарегистрирует расширение.
То, что плагин нашёл неверным, стоит на span'ах файла под его собственными
кодами. Код называет std и Prelude полными именами; импортировать другой
модуль проекта он пока не может, файл должен быть текстом UTF-8, а `.fl`
того же модуля рядом с ним — `FLICK-R002`.

## Как переписать IR

Плагин, пакет которого говорит `hooks = ["ir"]`, получает IR модулей проекта
— `Program` IR компилятора в CBOR, без встроенных модулей — после того, как
его прошли проверки эффектов, и до того, как сборка его оптимизирует, в
`flick build`, `run` и `test`, но никогда в `flick check` и в редакторе. Его
`transform` отдаёт программу, которую сборка компилирует вместо исходной.
Компилятор проверяет её только по форме: версия IR, каждый модуль сборки и
никаких других, каждый локал связан там, где используется, каждый глобал —
из существующего модуля, каждый span — из прочитанного сборкой файла; всё
прочее — `FLICK-P047` с именем плагина. Сборка, которую он переписал,
сообщает об этом заметкой `FLICK-P048`: за то, что делает программа, тогда
отвечает плагин, вне проверок Flick и его модели языка, а сборка не
кэшируется. Каждая версия IR ломает такой плагин, пока IR не стабилен.

## Как переписать то, что пишет сборка

Плагин, пакет которого говорит `hooks = ["emit"]` рядом с `plugin`, получает
файлы `flick build` до того, как сборка их запишет: путь каждого в выходном
каталоге и текст, `.js` каждого модуля с его `.map`, если сборка пишет карты,
и `.iface` со сводкой его типов. Его `emit` отдаёт файлы, которые сборка
пишет вместо них; плагины нескольких пакетов работают по очереди в порядке
`[dependencies]`. Плагин, который меняет `.js`, полученный с `.map`,
отдаёт и изменённый `.map`, иначе сборка оставляет файлы как были и сообщает
`FLICK-P046`; `.js` без карты можно менять одному. Спрашивает только
`flick build`: `flick run` и `flick test` собирают без него, так что плагин,
меняющий поведение, проверяет это сам.

## Отключение плагина

Проект может отказаться от части плагина, который получает, в том числе от
плагина самого компилятора, в той же таблице: `disable` называет головы блоков
и классы, которые плагин выводит.

```toml
[plugins.std]
disable = ["sql", "Cli.Value"]
```

Блок с отключённой головой и `deriving` отключённого класса дают `FLICK-P042`
на голове блока или на классе, со строкой манифеста рядом, одинаково в
`flick check` и в редакторе.

## Доступ вовне

По умолчанию плагину доступны только его блоки. Доступ к внешним данным
разрешает использующий его проект в своём `flick.toml`; пакет плагина сам таких
разрешений не задаёт:

```toml
[plugins.sql]
fs-read = ["schema/", "db/extra.sql"]   # от корня проекта: каталог со всем содержимым или файл
net = ["db.example.com", "localhost:8080"]  # хост на любом порту или только на этом
env = ["SQL_TOKEN"]
```

`collect`, `expand` и `derive` просят через компилятор:
`compiler.read_file("schema/users.sql")`, `compiler.env("SQL_TOKEN")` и
`compiler.fetch(&Request { method, url, headers, body })` дают байты,
значение (`None`, если переменной нет) и `Response { status, body }`.
То, что проект не разрешил, — `ReachError::Denied` и `FLICK-P038` на блоке
со строкой, которую нужно добавить, что бы плагин ни сделал с ошибкой. Путь
с `..` или от корня не разрешается никогда, как и URL не `http` и не `https`,
URL с `user@` или с хостом в квадратных скобках. База данных доступна так же:
по HTTP или через схему, которую проект коммитит; драйверов в компиляторе
нет. Блоки модулей библиотеки не достают ничего, как и `complete`, `hover`,
`highlight` и `format`.

Ответ по HTTP сохраняется снимком — JSON-файлом
`.flick/plugin-snapshots/<пакет>/<хэш>.json` в проекте, который коммитят:
хэш считается по методу, URL и телу. Заголовки в него не входят, поэтому
токен передают в заголовке, а не в URL; изменённый заголовок снимок не
меняет. Прогон обращается к сети только за
запросом, на который нет снимка, не следует перенаправлениям, ждёт не больше
30 секунд и берёт не больше 16 МиБ; ответ со статусом 500 и выше не
сохраняется. С `--offline`, при заданной `CI` и в редакторе запрос без
снимка — `ReachError::Offline` и `FLICK-P039`. Удалённый снимок запрашивается
заново. Файлы и переменные читаются такими, какие они в каждом прогоне.

## Лимиты и кэши

Каждый вызов идёт в свежем экземпляре с бюджетом топлива и 64 МиБ памяти, а
любой импорт, кроме импортов компилятора, — ловушка: плагин, который
зацикливается или забирает всю память, останавливают. Релизные сборки `flick`
запускают компоненты; сборка без фичи `wasm-plugins` прямо об этом сообщает.

Раз вызовы чистые, их результаты сохраняются: в памяти на время сессии
редактора и в каталоге кэша пользователя, по ключу из плагина (его пакет и
хэш компонента), текста блока и того, где начинается его тело, и собранного
состояния. Повторная сборка не вызывает ни одного плагина; изменённый блок
стоит одного `collect` и одного `expand`; новый блок меняет то, что узнаёт
`collect`, и все блоки его группы разворачиваются заново. Сохранённый
результат помнит хэш каждого файла, переменной и снимка, к которым обратился
вызов, и действует, только пока все они те же; кэш сборки тоже их учитывает.
`FLICK_PLUGIN_TRACE=<file>` дописывает в файл строку на каждый вызов, на
который ответил плагин.

## Диагностики

| Проблема | Диагностика |
| - | - |
| плагин, который импортирует модуль, не найден или не загружается | `FLICK-P035` на импорте |
| плагин отверг блок, упал или вернул код, недопустимый на месте блока | `FLICK-P036` на блоке или на span'е, который назвал плагин |
| ошибка, которую плагин дал под своим кодом, например `L001` | `<пакет>/L001`, как `std/L001`, на span'е, который он назвал |
| импорт головы плагина `std` из другого пакета | `FLICK-P044` на импорте |
| ошибка в коде пользователя внутри блока | обычная, на этом коде |
| ошибка в коде, который дал плагин | обычная, на коде, который он означает, с пометкой о плагине |
| то, что нашёл `check` плагина | `<пакет>/X001` на span'е, который он назвал; `FLICK-P036`, если `check` упал |
| то, что нашёл `check-calls` плагина | `<пакет>/X001` на span'е, который он назвал; `FLICK-P036` на первом вызове, о котором его спросили, если он упал |
| плагин обращается к файлу, переменной или хосту, которые проект не разрешил | `FLICK-P038` на блоке |
| в офлайн-прогоне нет снимка ответа, который просит плагин | `FLICK-P039` на блоке |

Span на весь текст блока — это весь блок вместе с головой. Код плагина —
заглавные буквы и три цифры; компилятор ставит перед ним пакет, так что
плагин не может выдавать свои диагностики за диагностики другого пакета. `flick explain std/L001` показывает
`explain/L001.md` пакета. Диагностика с кодом может быть предупреждением или
заметкой, `Diagnostic::warning(message, span).with_code("L010")`, и нести
исправления, `.with_fix("rename it", edits, safe)`: их правки заменяют
span'ы блока, а безопасные применяет `flick check --fix`. Диагностика без кода
— ошибка, `FLICK-P036`. Предупреждения о сгенерированном коде не
сообщаются, а исправления, которые бы его правили, отбрасываются.

## Чего пока нет

Плагин предупреждает только из `check` или вместе с отказом: `expand` даёт
код или ошибки, но не код вместе с предупреждениями.
Встроенный
модуль, который файл скрыл псевдонимом, как `import Other as List`, скрыт и от
сгенерированного кода. `collect` видит
модули, которые загрузил прогон, поэтому `flick check one.fl` даёт ему меньше
блоков, чем полная сборка. Пакет, в модулях которого есть блоки плагинов,
проверяется заново в каждой сборке.

### Проверки исходного кода и refined

`check-structure` получает структуру исходных выражений и объявлений блока вместе с порогами lint проекта. Он может выдавать предупреждения без типовых wildcard. Сгенерированные обёртки в факты не входят. Плагин UI использует этот вызов для T036–T038 у `component`.
