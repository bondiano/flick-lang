`Ui r e` (см. [Типовое программирование и eDSL](../../spec/10-type-programming-and-edsl/)) описывает пользовательский интерфейс, обработчики событий
которого нуждаются в сервисах `r` и могут завершаться с ошибками `e`. Его построение
чистое: оно не запускает обработчики, не читает состояние и не обращается к DOM. `Ui.Dom.mount`
отображает его с помощью React 19 (`react-dom/client`) и выполняет каждое событие как задачу.

```flick
type alias SaveButtonProps c =
  {
    label : String;
    disabled : Bool;
    on_save : (Unit ->{Users; SaveError} Unit)^c;
  }

save_button : SaveButtonProps c -> (Ui {Users} {SaveError})^c
let save_button props =
  ui {
    button
      {
        disabled = props.disabled;
        on_click = Ui.Event.exhaust (fun _ ->
          task { props.on_save () }
        );
      }
      [text props.label]
  }
```

`c` — строка захватов (см. [регионы](../regions/#захваты)). Как и любая новая переменная
типа в сигнатуре, она квантифицируется по всей сигнатуре, поэтому
`forall c.` можно опустить ([типы](../types/)).

Два квалификатора `^c` позволяют `save_button` принимать любую функцию обратного вызова.
Тип функции без квалификатора не содержит регионов. Поэтому при `on_save : Unit ->{Users;
SaveError} Unit` функция обратного вызова, использующая `File s` из окружающей `scope`,
отклоняется в месте передачи (`FLICK-G001`), даже если `Ui` никогда
не покидает эту область. С `^c` у поля функция обратного вызова может содержать что угодно,
а `^c` у результата сохраняет эти захваты в `Ui`, так что `Ui`, содержащий
регион, по-прежнему не может покинуть свою область. Один квалификатор у результата
не помогает, поскольку поле всё равно не допускало бы захватов. Сигнатура верхнего уровня
проверяется в записанном виде, поэтому эти квалификаторы никогда не выводятся. Компонент,
функции обратного вызова которого никогда не содержат ресурсов области, может опустить оба квалификатора.

`ui { … }` — блок, в котором имена, экспортируемые `Ui`, не требуют `Ui.`: локальная
привязка по-прежнему имеет приоритет, затем идёт имя из `Ui`, затем собственные имена
модуля. Блок больше ничего не добавляет, поэтому `ui { button … [text …] }` и `Ui.button … [Ui.text
…]` компилируются в одно и то же промежуточное представление.

## Элементы и свойства

Свойства — точные записи: отсутствующее поле, неизвестное поле или неверный тип —
ошибка. Ключ — метаданные, задаваемые через `Ui.keyed`, а не свойство.

| Функция | Элемент | Дочерние элементы |
| - | - | - |
| `text s` | текст через текстовый канал React: разметка остаётся текстом | нет |
| `fragment`, `optional`, `empty` | без элемента | `List`, `Option`, нет |
| `div`, `span` `{ class_name }` | `div`, `span` | `List (Ui r e)` |
| `paragraph`, `heading`, `list`, `item` | `p`, `h1`, `ul`, `li` | `List (Ui r e)` |
| `heading_at level` | `h1` … `h6` для `H1` … `H6` | `List (Ui r e)` |
| `button { disabled; on_click }` | `button type="button"` | `List (Ui r e)` |
| `input { value; placeholder; on_input }` | `input`; `value` — начальный текст | нет |
| `textarea { value; placeholder; on_input }` | `textarea`, как `input` на несколько строк | нет |
| `pre { class_name }` | `pre`: пробелы и переводы строк сохраняются | `List (Ui r e)` |
| `link { href : SafeUrl }` | `a` | `List (Ui r e)` |
| `html (s : SanitizedHtml)` | `div` с HTML | нет |
| `select (SelectProps a r e c)` | `ul role="listbox"`; выбор элемента запускает `on_change` с этим элементом | элементы через `render_item` |
| `panel { header; body; footer }` | `section` с `header`, `main`, `footer` | именованные места |
| `tabs { selected } (NonEmpty (Tab r e))` | список вкладок и выбранная панель | значения `Tab` из `tab label ui` |
| `component c props` | внешний компонент React | его свойства |

`text` имеет тип `forall r e. String -> Ui r e`, поэтому может быть среди дочерних
элементов любого элемента. `SafeUrl` получается только из `Ui.safe_url`, который принимает
относительные URL и схемы `http`, `https`, `mailto` и отклоняет управляющие
символы; `SanitizedHtml` — только из `Ui.trusted_html`, под ответственность самой
программы. `String` не является ни тем, ни другим. Внешний компонент — это `Ui.Component p`,
привязанный через `foreign pure`; его отображает React, Flick никогда его не вызывает.

`with_host attrs node` ставит на элемент атрибуты хоста: `id`,
`class_name`, `role`, `aria_label`, `aria_describedby`, `aria_hidden`,
`aria_pressed`, `aria_live` (`Polite`, `Assertive`, `Off`), `tab_index`,
`data` (пары, записываемые как `data-<name>`) и подсказки ввода текста
`auto_capitalize`, `auto_correct` и `wrap`. Каждый атрибут типизирован и
необязателен: `with_host { host with role = Some "status" } (span { class_name = "s" } […])`.

## Атомы и представления

Атом (`Atom`) описывает значение; реестр, который программа предоставляет
через `provide Reactivity.Atom.layer { … }`, хранит значения прочитанных
через него атомов. `Atom.make value` — состояние, `Atom.derived` — атом,
вычисляемый из прочитанных им атомов, `Atom.set`/`Atom.update` пишут
состояние.

Представление (view) — компонент, чей render читает атомы через сервис
`Atom.Read`. `Ui.Dom.mount` рисует `Ui` с предоставленным реестром, и каждое
представление в нём перерисовывается только когда меняется прочитанный им
атом, а не атом соседа:

```flick
count : Atom.Writable Number
let count = Atom.make 0

counter_view : Ui.View Unit {Reactivity.Atom.Registry} none
let counter_view =
  Ui.view (fun () ->
    ui {
      button
        {
          disabled = false;
          on_click = Ui.Event.exhaust (fun _ -> task { Atom.update count (fun n -> n + 1) });
        }
        [text (Atom.value count |> show)]
    })
```

`Ui.render view props` вставляет представление в `Ui`. Компилятор называет
каждое top-level представление, action и атом `Module.name` — так их
показывают инструменты разработчика React и Effect
(`App.Counter.counter_view`); release-сборка сохраняет имена представлений
и action, а атомов — при `[build] labels = "all"`. `Ui.named` даёт
представлению другое имя. Представление
подписывается на прочитанное после коммита React, а запись между его
рендером и подпиской перерисовывает его снова. Представление вне
`Ui.Dom.mount` падает с подсказкой, что делать. Render читает синхронно:
как и вычисление производного атома, он имеет единственный сервис
`Atom.Read`. Запись, другой сервис или ошибка в нём — `FLICK-U004`:
записывайте атомы в action, запускайте задачу как `Atom.task` и читайте её
результат или дайте сбоям представление через `Ui.suspended`.

Атом создаётся один раз и сохраняет идентичность. У top-level атома один
тип: `let items = Atom.make []` держал бы один список для любого типа
элементов, поэтому в его типе нет переменных, и `FLICK-U005` просит указать
тип значения. Во время рендера тоже ничего не создаётся: атом, action или
представление, созданные в render, который может выполниться снова в любой
момент, начинались бы заново при каждом рендере, поэтому `FLICK-U006` это
запрещает. Создавайте их top-level `let`, а атом на ключ — через
`Atom.family`, который для равного ключа даёт тот же атом; ключу нужен
`Hash`, поэтому функций в нём нет. Задача обработчика выполняется по
событию, а не во время рендера, и может создавать что нужно.

```flick
draft : Number -> Atom.Writable String
let draft = Atom.family (fun _ -> Atom.make "")
```

`Ui.keyed id node` задаёт стабильную идентичность динамического дочернего
узла. Ключи локальны для списка соседей и должны быть уникальны в нём.
Перестановка сохраняет и поддерево React, и состояние политик событий этого
ключа: у занятого `exhaust` не запускается ещё одна задача.

## Задачи в представлениях

`Atom.task t` — атом результата задачи `t`, которую запускает реестр,
первым прочитавший атом: `Atom.Async a e` — это `Loading`, `Loaded a` или
`Failed (Failure e)`. Представление читает его как любой атом и разбирает
три случая; Suspense по умолчанию нет, поэтому загрузка и ошибка видны
там, где читается значение.

`Ui.suspended failed fallback render` — явный выбор: его render может
читать задачу через `Atom.ready`, которая отдаёт значение загруженной
задачи. Пока задача грузится, представление показывает `fallback`, а если
она упала — `failed` от сбоя. Ошибки, которые поднимает `Atom.ready`,
попадают в ряд ошибок render `x`, поэтому для задачи, которая может упасть,
у представления должно быть куда их деть. `Atom.ready` загружающейся задачи
в обычном `Ui.view` — дефект с объяснением.

## Поля, привязанные к состоянию

`Ui.field { bind = query; placeholder = "Найти"; on_input = None }` — поле
ввода, которое показывает состояние `query` и пишет в него каждое нажатие
сразу, внутри события браузера. Поэтому React оставляет курсор там, где его
оставил пользователь, не ломает композицию IME, а запись в `query` из
другого места, например сброс, видна в поле. `on_input`, если задан,
запускается задачей с текстом, когда состояние уже его содержит.
`Ui.field_area` — многострочное поле. Как и представлениям, полям нужен
реестр из `Ui.Dom.mount`.

## Действия

Действие (action) — обработчик, объявленный один раз, обычно на верхнем
уровне, и переданный стольким элементам, скольким нужно: `on_click =
increment`. `Action.exhaust`, `latest`, `queue` и `concurrent` берут политики
`Ui.Event`, но элементы, использующие одно действие, делят состояние его
политики в корне, поэтому `Action.exhaust` игнорирует клик по любой из его
кнопок, пока идёт задача предыдущего. Задачи принадлежат корню, который
прерывает их и дожидается их при размонтировании.

```flick
increment : Action.Action Ui.ClickSnapshot {Reactivity.Atom.Registry} none
let increment = Action.exhaust (fun _ -> task { Atom.update count (fun n -> n + 1) })
```

`Action.with action arg` передаёт действию аргумент как данные: каждый
элемент списка передаёт свой элемент, `on_click = Action.with remove item`, и
все они делят состояние политики `remove`. Обработчик, созданный из `fun`
внутри render представления, — новое замыкание на каждом рендере; это
работает, но `FLICK-U002` предупреждает об этом.

## Обработчики и политики

Поле обработчика имеет непрозрачный тип `Ui.Handler snapshot r e`, который создаётся
только политикой из `Ui.Event`, поэтому ни один обработчик не запускается по принципу «запустил и забыл»:

| Политика | Событие, пришедшее во время выполнения предыдущих задач |
| - | - |
| `exhaust f` | игнорируется |
| `latest f` | прерывает выполняемую задачу, ждёт её остановки, затем выполняется; ожидает не более одного события — самого нового |
| `queue capacity f` | ожидает, не более `capacity` событий; сверх этого отклоняется |
| `concurrent limit f` | выполняется, не более `limit` задач; сверх этого отклоняется |

`capacity` и `limit` — положительные целые числа: константа, не удовлетворяющая
этому условию, даёт `FLICK-U001`, вычисляемое значение проверяется при создании обработчика.
Отклонённое событие — инфраструктурный дефект для супервизора, но никогда не
ошибка из `e`. `f` получает инертный снимок, сделанный внутри функции обратного вызова DOM, —
`ClickSnapshot` (`button`, `alt`, `ctrl`, `shift`, `meta`), `InputSnapshot`
(`value`) или элемент `select`. `Ui.Event.prevent_default decide h`
вызывает чистую `decide` со снимком до возврата из функции обратного вызова и
предотвращает действие по умолчанию, если та так решила; иначе действие по умолчанию
происходит.

Обработчики сохраняют свои захваты: кнопка, обработчик которой содержит файл из
области, не может покинуть эту область (`FLICK-G001`). Построение `Ui` чистое, поэтому
`Ref.get` там — вызов среды выполнения, где он запрещён (`FLICK-E001`); представление читает атомы.

Свойство события сохраняет тот же listener между завершёнными рендерами,
но использует текущий обработчик. Удаление свойства или размонтирование
элемента отсоединяет listener и отбрасывает события, ещё ожидающие в очереди
его политики. Уже запущенные задачи остаются задачами корня: они могут
завершиться, а закрытие корня по-прежнему прерывает их и дожидается остановки.

## Запуск корневого интерфейса

```flick
mount :
  forall c r e.
  Ui.Dom.Container -> (Failure e ->{r; none} Unit)^c -> (Ui r e)^c ->{Reactivity.Atom.Registry | r; none} Never
```

`Ui.Dom.mount container supervisor ui` отображает `ui` один раз; входящие в
него представления перерисовываются, когда меняются прочитанные ими атомы.
Первое монтирование DOM синхронно, последующие рендеры планирует и
объединяет React 19. Каждая задача выполняется с сервисами вызова `mount`, а
реестр — тот, что предоставляет программа:

```flick
main : Unit ->{; AppError} Unit
let main () =
  match Ui.Dom.container "app" with
  | None -> App.fail "missing root"
  | Some root ->
    provide Reactivity.Atom.layer {
      ignore (Ui.Dom.mount root report (Ui.render counter_view ()))
    }
```

Сбой задачи и каждое отклонённое событие передаются в `supervisor`;
прерывание политикой или при закрытии — нет. Сбой самого супервизора
завершает `mount` с дефектом.

`mount` продолжается до прерывания выполняющего его файбера, обычно при завершении
области, породившей его. Закрытие проходит в две фазы: очистка React немедленно прекращает
приём событий и размонтирует дерево, удаляя его слушателей; затем задачи обработчиков
прерываются и ожидаются, включая супервизоры, и только после этого `mount` завершается —
так что область освобождает свои ресурсы после остановки задач.
`Ui.Dom.container id` находит элемент, в который нужно отобразить интерфейс.

Адаптер — `@flick-lang/runtime/ui`; `react` и `react-dom` версии 19 —
peer-зависимости среды выполнения, устанавливаемые приложением.

Корни DOM находятся в отдельном модуле `Ui.Dom`. Сам `Ui` импортирует
только React-адаптер, поэтому скомпилированным программам с `Ui.mount_with`
не нужен `react-dom`. DOM-код использует `Ui.Dom.mount` и `Ui.Dom.container`;
алиасов в `Ui` нет.

## Серверное представление при открытии

`Ui.Server.render ui` даёт разметку `ui`; его представления читают атомы из
предоставленного реестра. Дайте каждому запросу собственный реестр: тогда
одновременно отрисованные запросы не видят атомы друг друга, а поскольку
реестр — сервис `provide`, после окончания `provide` рендерить с ним нельзя
(`FLICK-E002`). Обработчики на сервере не запускаются.

```flick
request : Number ->{} String
let request n =
  provide Reactivity.Atom.layer {
    Atom.set count n
    Ui.Server.render (Ui.render counter_view ())
  }
```

`Ui.Server` берётся из `@flick-lang/runtime/ui/server`, поэтому клиентские
программы не загружают `react-dom/server`. JavaScript-хост может вместо этого
экспортировать из Flick функцию начального представления и выполнить её
холодный эффект на сервере. Передайте полученный `Ui` в `uiRenderStatic`
из `@flick-lang/runtime/ui/react`, затем сериализуйте React-узел через
`renderToString` из `react-dom/server`. Обработчики на сервере не
запускаются; отдельная HTML-реализация виджета не нужна.

Пометьте контейнер атрибутом `data-flick-ssr`. Тогда `Ui.Dom.mount`
использует `hydrateRoot`, а не очищает готовый HTML. Начальное состояние,
ключи и разметка на сервере и клиенте должны совпадать. Введённый до
запуска текст textarea, фокус и выделение сохраняются; перенесите такой
текст в состояние Flick перед проверкой или отправкой. Сначала монтируйте
корень, затем запускайте фоновые задачи, уведомляющие его обработчики.

Этот путь используют шапка документации и Play/Transpile. Без атрибута
обычное клиентское монтирование не меняется.

### Сериализуемые атомы

`Atom.serializable wire state` помечает состояние, значение которого сервер
может передать клиенту, закодировав его JSON-кодеком `wire`. Ключ атома —
имя определяющего его top-level-биндинга, `Module.name`; его подставляет
компилятор. У атома из `Atom.serializable_family` ключ `Module.name/key`.
В любом другом месте, например внутри функции, без применения к состоянию
или дважды в одном биндинге, один ключ мог бы обозначать много атомов, и
`FLICK-U003` это запрещает. `PureCodec` кодирует синхронно и без сервисов.

```flick
count : Atom.Writable Number
let count = Atom.serializable (Codec.json Schema.number) (Atom.make 0)

draft : String -> Atom.Writable String
let draft = Atom.serializable_family (Codec.json Schema.string) (fun _ -> Atom.make "")
```

Сервер передаёт их через `Ui.Server.state "app"`: это
`<script type="application/json" id="flick-state-app">` с сериализуемыми
атомами реестра для контейнера `app`, который кладут в страницу, когда
контейнер отрисован. `Ui.Dom.mount` на этом контейнере записывает их в свой
реестр до первого рендера и удаляет скрипт, поэтому клиент начинает со
значений сервера, а не запрашивает их заново, и повторное монтирование не
перезапишет изменённые с тех пор значения. Каждый корень страницы читает
только скрипт своего контейнера. Атом, значение которого кодек не кодирует, — дефект с именем
его ключа, а не молча пропущенное значение.

```flick
page : Number ->{} String
let page n =
  provide Reactivity.Atom.layer {
    Atom.set count n
    let markup = Ui.Server.render (Ui.render counter_view ())
    "<div id=\"app\" data-flick-ssr>" ++ markup ++ "</div>" ++ Ui.Server.state "app"
  }
```

### Паритет сервера и клиента

Серверная разметка гидратируется, только если первый рендер клиента рисует
то же самое. Поэтому представление читает каждый атом так, как прочитал бы
сервер, и на сервере, и пока его корень гидратируется, а после гидратации
React рендерит его снова со значениями клиента.

У состояния браузера, например URL, нет значения на сервере. Его тип
`Atom.Browser a` — не атом, который читают `Atom.get` или `Atom.value`:
задайте значение, которое рисует сервер, через `Atom.on_server`, или читайте
его через `Atom.client_only`, который даёт `None` на сервере и во время
гидратации. `Atom.search_param name` — параметр поиска `name` в URL; запись
обновляет URL.

```flick
query : Atom.Writable String
let query = Atom.on_server "" (Atom.search_param "q")

tab : Atom.Atom (Option String)
let tab = Atom.client_only (Atom.search_param "tab")
```

### Шаблоны без React

`Ui.Server.to_html ui` даёт HTML `ui` без React — для писем и другой
разметки, которую не гидрирует клиент. Это чистая функция: текст и значения
атрибутов экранируются так же, как `text` оставляет разметку текстом,
обработчики опускаются, а представления читают атомы как сервер, из реестра
только этого вызова, поэтому один и тот же `ui` всегда даёт один и тот же
HTML. Внешний компонент, который рисует только React, — дефект. Функция
берётся из `@flick-lang/runtime/ui/html`, который не импортирует ни React,
ни `react-dom/server`.

```flick
receipt : Order -> String
let receipt order =
  Ui.Server.to_html (ui { div { class_name = "mail" } [paragraph [text ("Спасибо, " ++ order.customer)]] })
```

## Другие рендереры React

`@flick-lang/runtime/ui` — адаптер React DOM.
`@flick-lang/runtime/ui/react` содержит только преобразование узлов React,
представления и жизненный цикл задач; импорт этого подпути не загружает
`react-dom` и не читает `document` или `window`.

Из него экспортируются `uiMountWith` и контракт фабрики рендерера:

```typescript
type Renderer = () => {
  render(node: React.ReactNode): void;
  unmount(): void;
};
```

Фабрика вызывается при запуске Effect корня, а не при построении его
описания. Её `render` передаёт узел React выбранному рендереру, а
`unmount` синхронно отсоединяет корень. Общий runner прекращает приём
событий, размонтирует дерево, прерывает задачи и дожидается их завершения.
Рендерер должен размонтировать все свои компоненты React, а не просто
скрыть поверхность.

В Flick фабрика привязывается через `foreign pure` как непрозрачный
`Ui.Renderer` и запускается вызовом
`Ui.mount_with renderer supervisor ui`. Реестр, сервисы, ошибки, захваты и
порядок завершения те же, что у `Ui.Dom.mount`. Это точка расширения для React
Native, Ink и React Three Fiber, а не готовые адаптеры этих рендереров.
Существующие `div`, `input` и другие HTML-функции остаются DOM-специфичными:
для остальных поверхностей нужны собственные типизированные примитивы и
снимки событий либо внешние компоненты через `Ui.component`. Адаптер
не-DOM-рендерера не должен импортировать DOM-подпуть.

## Elm-like, но ещё не полная TEA

Сейчас есть представления над атомами и обработчики Effect под
супервизором. Ещё нет последовательного цикла `Msg → update`, команд,
возвращаемых из `init`/`update`, и запуска/остановки подписок по модели.
Приоритеты собраны в [списке недостающих возможностей](#приоритеты-недостающих-возможностей)
ниже. Effect, файберы, области и политики конкурентности событий уже
существуют; будущий MVU API должен использовать их, а не создавать ещё один
асинхронный runtime.

### Сравнение с Elmish

Сравнение относится к [`elmish/react` v6.x](https://github.com/elmish/react/tree/v6.x),
а не к полноценному MVU-фреймворку. Его
[`common.fs`](https://github.com/elmish/react/blob/v6.x/react/common.fs)
даёт `lazyViewWith` на основе `React.memo` и ключи соседних узлов
(представление Flick перерисовывается только по прочитанным атомам, поэтому
сравнение ему не нужно);
[`react.fs`](https://github.com/elmish/react/blob/v6.x/react/react.fs) —
проверку идентичности корневой модели, batching через `requestAnimationFrame`,
hydration и `valueOrDefault`. Цикл dispatch и подписки относятся к отдельному
ядру [`elmish/elmish`](https://github.com/elmish/elmish).
Batching React 19 в Flick не обещает расписание по кадрам анимации, как у Elmish.

### Выполненные оптимизации и свидетельства

- Представление перерисовывается только при изменении прочитанного атома.
  React 19 объединяет ожидающие рендеры вместо синхронного commit после
  каждой задачи; синхронным остаётся только первое монтирование DOM.
- Ключи сохраняют идентичность поддерева и состояние занятой политики
  событий при перестановке. Стабильные listeners принадлежат компонентам
  и получают текущий обработчик после commit, не удерживая устаревшее представление.
- `Ui.Renderer`/`Ui.mount_with` используют общий жизненный цикл React без
  импорта `react-dom`. За монтирование DOM отвечает `Ui.Dom`; задачи
  принадлежат корню, а не поверхности DOM.

Реализация находится в
[React-only runner](https://github.com/bondiano/flick-lang/blob/main/runtime/src/ui/react/index.ts),
[DOM-адаптере](https://github.com/bondiano/flick-lang/blob/main/runtime/src/ui/index.ts)
и встроенных модулях
[`Ui`](https://github.com/bondiano/flick-lang/blob/main/flick-core/src/types/builtins/Ui.fl)
и [`Ui.Dom`](https://github.com/bondiano/flick-lang/blob/main/flick-core/src/types/builtins/Ui/Dom.fl).
Регрессионное покрытие хранится рядом с соответствующим поведением:

- [`runtime/test/ui-roots.test.ts`](https://github.com/bondiano/flick-lang/blob/main/runtime/test/ui-roots.test.ts)
  и [`ui-policies.test.ts`](https://github.com/bondiano/flick-lang/blob/main/runtime/test/ui-policies.test.ts):
  представления, ключи, стабильные listeners, StrictMode, supervision,
  unmount/join и импорт React-only подпути без DOM.
- Примеры проверки представлений
  ([pass](https://github.com/bondiano/flick-lang/blob/main/tests/check/pass/ui/views.fl),
  [fail](https://github.com/bondiano/flick-lang/blob/main/tests/check/fail/ui/children.fl)):

- [`tests/run/ui/counter.fl`](https://github.com/bondiano/flick-lang/blob/main/tests/run/ui/counter.fl):
  атомы, действия и пользовательский рендерер.
- [`tests/run/ffi/foreign.fl`](https://github.com/bondiano/flick-lang/blob/main/tests/run/ffi/foreign.fl):
  идентичность unary callback при FFI.

### Приоритеты недостающих возможностей

Эти возможности **ещё не реализованы**. Порядок учитывает будущую поддержку
React Native, Ink и React Three Fiber: перенос DOM-тегов сам по себе
не создаёт новый backend.

| Приоритет | Возможность | Минимальный контракт и причина |
| - | - | - |
| P1 | Renderer-independent MVU program | `init`, чистый `update`, стабильный `dispatch` и последовательная очередь сообщений, включая reentrant dispatch. View не пишет атомы напрямую. Один цикл для DOM, Native, Ink и R3F. |
| P1 | Команды из `init`/`update` | Запуск существующих Effect-задач и преобразование результата в сообщение; supervisor и interrupt/join переиспользуются. Не создавать второй `Cmd`-runtime поверх Effect. |
| P1 | Подписки по модели с устойчивыми ключами | Diff/start/stop подписок по стабильной идентичности, защита от поздних событий, scope-owned cleanup. Таймеры, сокеты, терминал и источники анимации обновляют модель без ожидания завершения UI-handler. |
| P1 | Типизированные host primitives и события | Разделить HTML-конструкторы и renderer-specific `View`/`Text`, Ink host nodes, R3F scene nodes. Props со стилями/числами и снимки событий не должны предполагать DOM `target.value` или `preventDefault`. |
| P1 | Настоящие адаптеры Native / Ink / R3F | Поверх `Renderer` и host primitives: регистрация/монтирование, обновления, синхронное отсоединение и завершение ресурсов. Для R3F отдельно определить связь MVU, frame loop и invalidation; не посылать 60 сообщений/с без необходимости. |
| P2 | Typed React interop | Children/slots внешних компонентов, scoped refs, Context/providers и lifecycle с определённым освобождением ресурсов; сейчас есть только opaque `Ui.component` с props. |
| P2 | Диагностика MVU и разработка | Трасса сообщений/модели, воспроизведение чистого update, HMR с сохранением состояния. Строить на MVU-контракте, не на глобальном mutable singleton. |

Существующие Effect, fibers/scopes, bounded event
policies, supervisor, escaping checks и безопасный text channel не являются
недостающими возможностями и не требуют дублей API.
