`Ui` описывает пользовательский интерфейс и обработчики его событий
(см. [Программирование на уровне типов и eDSL](../../spec/08-type-programming-and-edsl/)).
Задача обработчика только изменяет атомы (`Atom.Write`): другие сервисы
она предоставляет себе сама и свои ошибки обрабатывает сама, поэтому
у `Ui` нет строк эффектов.
Построение `Ui` — чистая операция: оно не запускает обработчики, не читает
состояние и не обращается к DOM. `Ui.Dom.mount` отображает интерфейс
через React 19 (`react-dom/client`) и выполняет каждый обработчик события
как задачу.

```flick
type alias SaveButtonProps c = {
  label : String;
  disabled : Bool;
  on_save : (Unit ->{Atom.Write} Unit)^c;
}

save_button : SaveButtonProps c -> Ui^c
let save_button props = ui {
  button
    {
      disabled = props.disabled;
      on_click = Ui.Event.exhaust (fun _ -> task { props.on_save () });
    }
    [text props.label]
}
```

`c` — строка захватов (см. [регионы](../regions/#захваты)).
Как и любая новая переменная типа в сигнатуре, она неявно квантифицируется
по всей сигнатуре, поэтому `forall c.` можно опустить ([типы](../types/)).

Два квалификатора `^c` связывают то, что нужно `on_save`, с тем, что нужно
результирующему `Ui`. Без квалификатора тип функции не держит живым ни один регион.
Поэтому при `on_save : Unit ->{Atom.Write} Unit` нельзя передать функцию обратного вызова, которая
использует `File s` из окружающей `scope`: возникает `FLICK-G002`,
даже если `Ui` никогда не покидает эту область. Функция обратного вызова,
которой нужен сервис, например сохранение через `Users`, предоставляет его
и обрабатывает его ошибки внутри, записывая результат в атом.

Квалификатор `^c` у поля разрешает функции обратного вызова использовать то,
что держит живым `c`, а `^c` у результата говорит, что это нужно и для
использования `Ui`. Если обратные вызовы используют регион, такой `Ui` не может
покинуть свою область. Одного квалификатора у результата недостаточно: поле
без `^c` всё равно ничего не держит живым.
Компилятор проверяет сигнатуру верхнего уровня в записанном виде
и не добавляет эти квалификаторы сам. Если функции обратного вызова
компонента никогда не используют ресурсы области, оба квалификатора
можно опустить.

В блоке `ui { … }` имена из `Ui` доступны без префикса `Ui.`.
При поиске имени сначала учитывается локальная привязка, затем экспорт
из `Ui`, затем имена текущего модуля. Обычные вызовы
`ui { button … [text …] }` и `Ui.button … [Ui.text …]` компилируются
в одно промежуточное представление. При применении значения типа
`Ui.Component p` к свойствам блок также автоматически вставляет `Ui.component`.

## Элементы и свойства

Свойства задаются точными записями. Пропущенное или неизвестное поле,
как и неверный тип поля, приводит к ошибке.
Ключ задаётся через `Ui.keyed`: это метаданные, а не свойство.

| Функция | Элемент | Дочерние элементы |
| - | - | - |
| `text s` | текстовый узел React; разметка не интерпретируется | нет |
| `fragment`, `optional`, `empty` | без элемента | `List`, `Option`, нет |
| `div`, `span` `{ class_name }` | `div`, `span` | `List Ui` |
| `paragraph`, `heading`, `list`, `item` | `p`, `h1`, `ul`, `li` | `List Ui` |
| `heading_at level` | `h1` … `h6` для `H1` … `H6` | `List Ui` |
| `button { disabled; on_click }` | `button type="button"` | `List Ui` |
| `input { value; placeholder; on_input }` | `input`; `value` — начальный текст | нет |
| `textarea { value; placeholder; on_input }` | многострочный вариант `input` | нет |
| `pre { class_name }` | `pre`: пробелы и переводы строк сохраняются | `List Ui` |
| `link { href : SafeUrl }` | `a` | `List Ui` |
| `route_link { route; url; to }` | `a` на страницу `to`, переход без перезагрузки (ниже) | `List Ui` |
| `nav`, `footer`, `fieldset` `{ class_name }` | `nav`, `footer`, `fieldset` | `List Ui` |
| `icon { class_name }` | `i` иконочного шрифта, иконка выбирается CSS-классами | нет |
| `hr` | `hr` | нет |
| `image { src : SafeUrl; alt; class_name }` | `img` | нет |
| `form { on_submit }` | `form`: отправка запускает `on_submit` и никогда не перезагружает страницу | `List Ui` |
| `submit { disabled }` | `button type="submit"`, отправляет содержащую его форму | `List Ui` |
| `html (s : SanitizedHtml)` | `div` с HTML | нет |
| `select (SelectProps a c)` | `ul role="listbox"`; выбор элемента запускает `on_change` с этим элементом | элементы через `render_item` |
| `panel { header; body; footer }` | `section` с `header`, `main`, `footer` | задаются именованными полями |
| `tabs { selected } (NonEmpty Tab)` | список вкладок и выбранная панель | значения `Tab` из `tab label ui` |
| `c props`, где `c : Ui.Component p` | внешний компонент React | его свойства |

`text` имеет тип `String -> Ui`, поэтому его можно
включить в список дочерних элементов любого элемента.
`SafeUrl` можно получить только через `Ui.safe_url`: функция принимает
относительные URL и схемы `http`, `https`, `mailto`, но отклоняет
управляющие символы. `SanitizedHtml` создаётся только через `Ui.trusted_html`;
за безопасность такого HTML отвечает программа. Обычная `String`
не заменяет ни один из этих типов.

Внешний компонент имеет тип `Ui.Component p` и привязывается через
`foreign pure`. Его отображает React; Flick никогда не вызывает его сам.

Внутри `ui` вместо `Ui.component badge props` достаточно `badge props`:

```flick
badge : Ui.Component { label : String }
foreign pure badge from "./badge.mjs" "Badge"

example : Ui
let example = ui { div { class_name = "badges" } [badge { label = "new" }] }
```

Это работает и для локальных привязок, полей записей, значений,
возвращённых функциями, и конвейеров (`props |> badge`). Сокращается
только применение: само `badge` сохраняет тип `Ui.Component`.
Проверки свойств и захватов не меняются. Вне `ui` нужен
`Ui.component badge props`.

`with_host attrs node` задаёт элементу атрибуты хоста: `id`,
`class_name`, `role`, `aria_label`, `aria_describedby`, `aria_hidden`,
`aria_invalid`, `aria_pressed`, `aria_live` (`Polite`, `Assertive`, `Off`), `tab_index`,
`data` (пары, которые записываются как `data-<name>`), подсказки для ввода
текста `auto_capitalize`, `auto_correct` и `wrap`, а также `name` поля формы и
`input_type` (`TextInput`, `PasswordInput`, `EmailInput`, его `type`). Каждый
атрибут типизирован и необязателен:
`with_host { host with role = Some "status" } (span { class_name = "s" } […])`.
Так же любой элемент получает классы, в том числе тот, у пропсов которого нет
`class_name`: `with_host { host with class_name = Some "nav-link" } (route_link …)`.

`route_link { route; url; to } children` — ссылка внутри приложения на
страницу `to` состояния маршрута `route = Atom.route url fallback`. Её `href` —
`Route.print url to`, поэтому разметка сервера, клик для новой вкладки и клик
средней кнопкой идут по нему, как обычно в браузере. Обычный клик левой
кнопкой без клавиш-модификаторов вместо этого записывает `to` в `route`: URL
добавляется в историю без перезагрузки, и представления, которые читают
`route`, показывают новую страницу.

## Атомы и представления

Атом (`Atom`) описывает значение. Значения атомов хранит реестр, который
программа предоставляет через `provide Atom.layer { … }`. `Atom.make value`
создаёт состояние, `Atom.derived` — атом, вычисляемый из прочитанных им
атомов. `Atom.set` и `Atom.update` изменяют состояние через сервис
`Atom.Write`: он доступен задаче действия, но не функции рендера.
`Atom.layer` предоставляет один реестр сразу как `Atom.Registry`,
из которого читают корни и серверная разметка, и как `Atom.Write`.
`Atom.Registry` — это `Reactivity.Atom.Registry` из Effect, который `Atom`
реэкспортирует.

Представление — компонент, функция рендера которого читает атомы через
сервис `Atom.Read`. `Ui.Dom.mount` отображает `Ui` с предоставленным
реестром. Каждое представление перерисовывается, только когда меняется
прочитанный им атом, а не атом соседнего представления:

```flick
count : Atom.Writable Float
let count = Atom.make 0

component counter_view () = ui {
  button
    {
      disabled = false;
      on_click = Ui.Event.exhaust (fun _ -> task { Atom.update count (fun n -> n + 1) });
    }
    [text (Atom.value count |> show)]
}
```

`Ui.render view props` вставляет представление в `Ui`. Компилятор даёт
каждому представлению, действию и атому верхнего уровня имя `Module.name`,
под которым их показывают инструменты разработчика React и Effect
(`App.Counter.counter_view`). Сборка release сохраняет все эти имена, а при
`[build] labels = "components"` — только имена представлений и действий. `Ui.named` задаёт
представлению другое имя. Представление подписывается на прочитанные атомы
после фиксации изменений React; если атом изменился между рендером
и подпиской, представление перерисовывается снова. Представление,
отображаемое вне `Ui.Dom.mount`, завершается с ошибкой, в которой сказано,
что делать. Функция рендера читает атомы синхронно: как и вычисление
производного атома, она имеет единственный сервис `Atom.Read`. Поэтому
это Sync-стадия: она компилируется в обычную функцию, а `Atom.get` в ней —
прямой вызов, без Effect. Запись,
другой сервис или ошибка в ней приводят к `FLICK-U004`: изменяйте атомы
в действии, запускайте задачу через `Atom.task` и читайте её результат или
задайте представление для сбоев через `Ui.suspended`.

Атом создаётся один раз и сохраняет идентичность. У атома верхнего уровня
один тип: `let items = Atom.make []` хранил бы один список для любого типа
элементов, поэтому в типе атома не должно быть переменных; `FLICK-U005`
просит указать тип значения. Локальный атом без типа не обобщается: его
единственный тип определяют использования, а сигнатура, аннотация или
аргумент высшего ранга с переменными в типе атома — тоже `FLICK-U005`.
Во время рендера тоже ничего не создаётся:
атом, действие или представление, созданные в функции рендера, которая может
выполниться снова в любой момент, создавались бы заново при каждом рендере.
Поэтому `FLICK-U006` запрещает их, как и вызов любой функции, которая их
создаёт, в этом модуле или в импортированном. Создавайте их привязками
верхнего уровня, а атом для каждого ключа — через `Atom.family`:
`Atom.at family key` для равного ключа возвращает тот же атом. Ключу нужен
экземпляр `Hash`, поэтому функций в нём быть не может. Семейство хранит
атомы через слабые ссылки, но реестр хранит значение состояния, пока
существует сам. `Atom.forget family key` освобождает состояние удалённого
элемента, как только его перестают читать, а следующий `Atom.at` создаст
новое. Задача обработчика выполняется по событию, а не во время рендера,
и может создавать всё, что ей нужно.

```flick
# items : Atom.Writable (List Float)
# let items = Atom.make []
#
drafts : Atom.Family Float (Atom.Writable String)
let drafts = Atom.family (fun _ -> Atom.make "")

remove : Action.Action (Float, Ui.ClickSnapshot)
let remove =
  Action.exhaust (fun (id, _) ->
    task {
      Atom.update items (List.filter (fun i -> i != id))
      Atom.forget drafts id
    })
```

`Ui.keyed id node` позволяет распознавать один и тот же динамический
дочерний узел при перестановках. Ключи действуют только в списке соседних
узлов и должны быть уникальны в нём. При перестановке сохраняются поддерево
React и состояние политики событий этого ключа. Например, если `exhaust`
уже выполняет задачу, ещё одна не запускается.

### Компоненты

`component name (props : P) = body` объявляет представление своих props с
типом `Ui.View P`, которое вставляет `Ui.render name props`. Это блок
плагина пакета `std`, который есть в каждом модуле без импорта. Props — один
образец, обычно запись со своим типом. Тело — блок: его последнее
выражение рендерит компонент, снова при каждом изменении прочитанного
атома или props. Тело из одного этого выражения — это
`let name = Ui.view (fun (props : P) -> e)`:

```flick
component badge (props : { label : String }) = ui { text props.label }

component card (person : { name : String; label : String }) =
  ui { div { class_name = "card" } [text person.name, Ui.render badge { label = person.label }] }
```

Операторы перед последним выражением — setup каждого экземпляра. Он
выполняется один раз, когда экземпляр монтируется, с сервисом `Setup s`
региона экземпляра `s`, а его имена видны в последнем выражении, которое
рендерит с ними. `Atom.local` создаёт атом экземпляра, а конструкторы
`Action` — его action; рендер, который их создаёт, — `FLICK-U006`, а
`Atom.local` вне setup — ошибка эффектов. Setup выполняется один раз,
поэтому атомы в нём не читаются: их читает рендер (`ui { let n = … }` —
тоже блок) или `Atom.derived`, созданный в setup. Компонент — это
`Ui.stateful (fun props -> setup; fun props -> render)` с типом
`forall s. P ->{Setup s} (P ->{Atom.Read} Ui)^{s}`: setup видит первые
props, рендер — текущие. Наведение на `component` показывает этот тип.

```flick
component counter (start : Float) =
  let count = Atom.local start
  let bump = Action.exhaust (fun _ -> task { Atom.update count (fun n -> n + 1) })
  ui {
    let n = Atom.value count
    button { on_click = bump; disabled = false } [text (show n)]
  }
```

Setup выполняется один раз на смонтированный экземпляр, в том числе под
StrictMode в React. Когда экземпляр размонтируется, события action,
созданных его setup, прекращаются, а их задачи прерываются; корень при
закрытии всё равно дожидается этих задач.

#### Работа экземпляра

`Ui.on_mount task` в setup запускает `task`, когда экземпляр смонтирован,
как задачу корня: его unmount прерывает её и дожидается, её финализаторы
выполняются, а дефект уходит супервизору корня. `Ui.watch read run`
запускает `run` от того, что вычисляет `read`, и снова при каждом
изменении атома, который `read` прочитал, сначала прервав предыдущий
запуск. Оба — это `useEffect` из React без списка зависимостей:
`on_mount` выполняется один раз на экземпляр, `watch` следит за
прочитанными атомами. Под StrictMode повторный mount останавливает первый
запуск до начала второго, а сервер рендерит, не запуская ни одного. Их
задачи пишут атомы (`{Atom.Write}`), как задачи action.

```flick
component clock () =
  let seconds = Atom.local 0
  let second = Result.with_default Duration.zero (Duration.seconds 1)
  let _ticking =
    Ui.on_mount
      (task {
        Effect.forever
          (task {
            Effect.sleep second
            Atom.update seconds (fun n -> n + 1)
          })
      })
  ui { text (show (Atom.value seconds)) }
```

#### Элементы экземпляра

`Ui.element ()` в setup создаёт элемент экземпляра с типом тега:
`Ui.Input`, `Ui.Textarea`, `Ui.Button` или `Ui.Div`. Рендер привязывает его
к узлу через `input_at element props`, `textarea_at`, `button_at` или
`div_at`, так что тег проверяет тип; сам рендер элемент только передаёт.
Задача action, `Ui.on_mount` или `Ui.watch` обращается к узлу через сервис
`Ui.Document`, который даёт корень: `Ui.focus`, `Ui.blur`,
`Ui.scroll_into_view` и `Ui.measure` (`{ width; height; top; left }`).
Элемент без смонтированного узла — ошибка `Ui.Detached`, а не `null`: до
рендера экземпляра, после его unmount или с рендерером без DOM. У рендера
и у сервера нет `Ui.Document`, поэтому DOM-операция там — ошибка типов;
при гидрации элемент привязывается к узлу, который отрендерил сервер.

```flick
component search () =
  let field = Ui.element ()
  let focus = Action.exhaust (fun _ -> task { try Ui.focus field with | Ui.Detached -> () })
  ui {
    div
      { class_name = "search" }
      [
        input_at field { value = ""; placeholder = "find"; on_input = Ui.Event.latest (fun _ -> task { () }) },
        button { disabled = false; on_click = focus } [text "focus"],
      ]
  }
```

Это `useRef` из React только для DOM и с типом тега; Elm обращается к
узлу через `Browser.Dom.focus` по строковому id, который тип не
проверяет. Виджет, который императивно управляет DOM, по-прежнему
подключается как внешний компонент, `Ui.component`.

Значения, принадлежащие экземпляру, захватывают его регион: `Atom.local` даёт
`(Atom.Writable a)^{s}`, а `Ui.element` — `(Ui.Element t)^{s}`, поэтому их
нельзя положить туда, откуда их прочитает что-то вне экземпляра
(`FLICK-G001`), а реестр забывает атомы экземпляра при его unmount. Функции
атомов заимствуют то, что принимают, `(Atom.Writable a)^d`, поэтому читают
и пишут такой атом. Функция, которая создаёт состояние экземпляра,
говорит об этом в сигнатуре, `Float ->{Setup s} (Atom.Writable Float)^{s}`,
и вызывается из setup; аннотация тоже называет захват,
`(Ui.Element Ui.Input)^c`. Слово `component` остаётся именем во всех других
местах.

## Задачи в представлениях

`Atom.task t` — атом результата задачи `t`. Задачу запускает реестр,
который первым прочитал атом. `Atom.Async a e` принимает значения `Loading`,
`Loaded a` или `Failed (Failure e)`. Представление читает такой атом как
любой другой и разбирает три случая. Suspense по умолчанию не используется,
поэтому загрузка и ошибка видны там, где читается значение.

`Ui.suspended failed fallback render` включается явно: его функция рендера
может читать задачу через `Atom.ready`, которая возвращает значение
загруженной задачи. Пока задача загружается, представление показывает
`fallback`, а если она завершилась с ошибкой — `failed` для этого сбоя.
Ошибки, которые возвращает `Atom.ready`, попадают в строку ошибок функции
рендера `x`, поэтому для задачи, которая может завершиться с ошибкой,
представление обязано задать их отображение. `Atom.ready` для ещё не
загруженной задачи в обычном `Ui.view` — дефект с объяснением.

`Ui.awaiting failed fallback render` — такое представление для одной
задачи, атом которой передаётся как props: для такого представления не нужны ни
`match`, ни `Atom.ready`. Представление сбоя по-прежнему обязательно; для
задачи `Async a none` оно не вызывается.

```flick
# type error Offline = Offline
# fetch_name : Unit ->{; Offline} String
# let fetch_name () = "Ada"
#
user : Atom.Atom (Atom.Async String {Offline})
let user = Atom.task (task { fetch_name () })

// три случая вручную
component user_view () =
  match Atom.get user with
  | Atom.Loading -> ui { text "…" }
  | Atom.Loaded name -> ui { text name }
  | Atom.Failed _ -> ui { text "offline" }

// то же через `Ui.awaiting`, рендер — `Ui.render awaited user`
awaited : Ui.View (Atom.Atom (Atom.Async String {Offline}))
let awaited = Ui.awaiting (fun _ -> ui { text "offline" }) (ui { text "…" }) (fun name -> ui { text name })
```

### Запросы и мутации

`Atom.query keys t` — это `Atom.task t`, который заново запускает мутация
одного из ключей `keys`. `Atom.mutation keys f` — это `f`, после успеха
которой реестр заново запускает все прочитанные им запросы этих ключей;
неудачная мутация ничего не меняет. Запросы других ключей сохраняют
значение. `Atom.query_stream keys s` показывает последний элемент потока
`s` и перезапускает его после такой мутации; своей мутации у него нет.
Поверх [серверной функции](../server-fn/):

```flick
# import Shop exposing (Order, OutOfStock)
#
orders : Atom.Atom (Atom.Async (List Order) {Rpc.ClientError})
let orders = Atom.query ["orders"] (task { Shop.orders () })

place : Order ->{Atom.Write; Rpc.ClientError, OutOfStock} String
let place = Atom.mutation ["orders"] Shop.place
```

Запрос — атом задачи: `Atom.serializable_task` передаёт его загруженное
значение из серверного рендера клиенту под именем привязки.

## Поля, привязанные к состоянию

`Ui.field { bind = query; placeholder = "Найти"; on_input = None }` — поле
ввода, которое показывает состояние `query` и записывает в него каждое
нажатие сразу, внутри события браузера. Поэтому React оставляет курсор там,
где его оставил пользователь, не прерывает ввод через IME, а изменение
`query` в другом месте, например сброс, сразу видно в поле. Если `on_input`
задан, он запускается задачей с текстом, когда состояние уже его содержит.
`Ui.field_area` — многострочный вариант. Как и представлениям, полям нужен
реестр из `Ui.Dom.mount`.

## Действия

Действие (action) — обработчик, который объявляется один раз, обычно
на верхнем уровне, и передаётся любому числу элементов: `on_click = increment`.
`Action.exhaust`, `latest`, `queue` и `concurrent` используют политики
`Ui.Event`, но элементы с одним действием разделяют состояние его политики
в корне. Поэтому `Action.exhaust` игнорирует нажатие любой из его кнопок,
пока выполняется задача предыдущего нажатия. Задачи принадлежат корню:
при размонтировании он прерывает их и ждёт их завершения.

```flick
# count : Atom.Writable Float
# let count = Atom.make 0
#
increment : Action.Action Ui.ClickSnapshot
let increment = Action.exhaust (fun _ -> task { Atom.update count (fun n -> n + 1) })
```

`Action.with action arg` передаёт действию аргумент как данные: каждый
элемент списка передаёт свой элемент, `on_click = Action.with remove item`,
и у каждого элемента своё состояние политики, которое сохраняется при
перестановке списка с ключами: `exhaust`-сохранение одного элемента не
игнорирует сохранение другого. Обработчик, созданный
из `fun` внутри функции рендера, — новое замыкание при каждом рендере. Это
работает, но `FLICK-U002` выдаёт предупреждение.

## Обработчики и политики

Поле обработчика имеет непрозрачный тип `Ui.Handler snapshot`.
Создать его можно только через политику из `Ui.Event`, поэтому обработчик
нельзя запустить без отслеживания его задачи:

| Политика | Что происходит с событием, если предыдущие задачи ещё выполняются |
| - | - |
| `exhaust f` | событие игнорируется |
| `latest f` | текущая задача прерывается, новая запускается только после её остановки; из ожидающих событий сохраняется последнее |
| `queue capacity f` | событие встаёт в очередь, в которой могут ждать не более `capacity` событий; при переполнении отклоняется |
| `concurrent limit f` | обработчик запускается, если одновременно выполняется меньше `limit` задач; иначе событие отклоняется |

`capacity` и `limit` должны быть положительными целыми числами.
Неверная константа приводит к `FLICK-U001`, а вычисляемое значение
проверяется при создании обработчика. Отклонённое событие передаётся
супервизору как инфраструктурный дефект, но никогда не как ошибка из `e`.

Обработчики сохраняют то, что им нужно. Если обработчик кнопки использует файл
из области владения, кнопка не может покинуть эту область (`FLICK-G001`).
Построение `Ui` должно быть чистым, поэтому вызов `Ref.get` в нём запрещён
как эффектный вызов (`FLICK-E001`); представление читает атомы.

из области владения, кнопка не может покинуть эту область (`FLICK-G001`).
Представление должно быть чистым, поэтому вызов `Ref.get` в нём запрещён

Между завершёнными рендерами свойство события сохраняет того же слушателя,
но передаёт ему актуальный обработчик. Удаление свойства или размонтирование
элемента отсоединяет слушателя и отбрасывает события, ожидающие в очереди
его политики. Уже запущенные задачи остаются задачами корня и могут
завершиться. Закрытие корня по-прежнему прерывает их и ждёт остановки.

## Запуск корневого интерфейса

```flick
mount :
  forall c r.
  Ui.Dom.Container -> (Failure none ->{r; none} Unit)^c -> Ui^c ->{Async, Atom.Registry, Atom.Write | r; none} Never
# let mount = Ui.Dom.mount
```

`Ui.Dom.mount container supervisor ui` отображает `ui` один раз; входящие
в него представления перерисовываются, когда меняются прочитанные ими атомы.
Первое монтирование DOM синхронно, последующие рендеры планирует
и объединяет React 19. Каждая задача изменяет атомы через `Atom.Write`
вызова `mount`, её дефекты получает супервизор, а реестр предоставляет
программа:

```flick
# count : Atom.Writable Float
# let count = Atom.make 0
# component counter_view () = ui { text (Atom.value count |> show) }
# report : Failure none ->{} Unit
# let report _ = ()
#
main : Unit ->{Async; AppError} Unit
let main () =
  match Ui.Dom.container "app" with
  | None -> App.fail "missing root"
  | Some root ->
    provide Atom.layer {
      ignore (Ui.Dom.mount root report (Ui.render counter_view ()))
    }
```

Сбой задачи и каждое отклонённое событие передаются в `supervisor`.
Прерывание политикой или при закрытии туда не передаётся. Сбой самого
супервизора завершает `mount` с дефектом.

`mount` выполняется до прерывания его файбера — обычно при закрытии
области, которая его породила. Завершение проходит в две фазы. Сначала
очистка React немедленно прекращает приём событий, размонтирует дерево
и удаляет слушателей. Затем прерываются задачи обработчиков, включая
супервизоры, и ожидается их остановка. Только после этого завершается
`mount`, поэтому область освобождает ресурсы уже после остановки задач.
`Ui.Dom.container id` находит элемент для отображения интерфейса.

`run` выполняется до прерывания его файбера — обычно при закрытии области,
которая его породила. Завершение проходит в две фазы. Сначала очистка React
немедленно прекращает приём событий, размонтирует дерево и удаляет слушателей.
Затем прерываются задачи обработчиков, включая супервизоры, и ожидается
их остановка. Только после этого завершается `run`, поэтому область
освобождает ресурсы уже после остановки задач.
`Ui.Dom.container id` находит элемент для отображения интерфейса.

Работа с корнями DOM вынесена в модуль `Ui.Dom`. Сам `Ui` импортирует
только React-адаптер, поэтому скомпилированным программам с `Ui.mount_with`
не нужен `react-dom`. Для DOM используются `Ui.Dom.mount` и `Ui.Dom.container`;
алиасов этих функций в `Ui` нет.

## Серверное представление при открытии

`Ui.Server.render ui` возвращает разметку `ui`; представления читают атомы
из предоставленного реестра. Создавайте для каждого запроса собственный
реестр: тогда одновременно обрабатываемые запросы не видят атомы друг друга.
Реестр — сервис `provide`, поэтому после окончания `provide` рендерить с ним
нельзя (`FLICK-E002`). На сервере обработчики не запускаются.

```flick
# count : Atom.Writable Float
# let count = Atom.make 0
# component counter_view () = ui { text (Atom.value count |> show) }
#
request : Float ->{Async} String
let request n =
  provide Atom.layer {
    Atom.set count n
    Ui.Server.render (Ui.render counter_view ())
  }
```

`Ui.Server` берётся из `@flick-lang/effect-ts/ui/server`, поэтому клиентские
программы не загружают `react-dom/server`. Вместо него JavaScript-хост может
экспортировать из Flick функцию начального представления и выполнить её
холодный эффект на сервере. Передайте полученный `Ui` в `uiRenderStatic`
из `@flick-lang/effect-ts/ui/react`, затем сериализуйте React-узел через
`renderToString` из `react-dom/server`. Представления и поля читают атомы
как на сервере: каждый вызов — из собственного реестра. На сервере
обработчики не запускаются. Отдельная HTML-реализация виджета не нужна.

Сервер, который рендерит представления, запускайте с `NODE_ENV=production`,
например `NODE_ENV=production node dist/flick-server.js`. Без этой переменной
React работает в development-сборке и рендерит примерно вдвое медленнее.

Пометьте контейнер атрибутом `data-flick-ssr`. Тогда `Ui.Dom.mount`
использует `hydrateRoot` вместо очистки готового HTML.
Начальное состояние, ключи и разметка на сервере и клиенте должны совпадать.
Введённый до запуска текст textarea, фокус и выделение сохраняются.
Перед проверкой или отправкой перенесите этот текст в состояние Flick.
Сначала монтируйте корень, затем запускайте фоновые задачи,
которые уведомляют его обработчики.

Так устроены шапка документации и песочница.
Без атрибута обычное клиентское монтирование работает как прежде.

### Сериализуемые атомы

`Atom.serializable wire state` помечает состояние, значение которого
сервер может передать клиенту, закодировав его JSON-кодеком `wire`. Ключ
атома — имя определяющей его привязки верхнего уровня, `Module.name`,
его `CallSite.definition`. У атома из `Atom.serializable_family` ключ
`Module.name/key`. В любом другом месте — например, внутри функции, без
применения к состоянию или дважды в одной привязке — один ключ мог бы
обозначать много атомов, поэтому `FLICK-U003` это запрещает. `PureCodec`
кодирует синхронно и без сервисов.

```flick
count : Atom.Writable Float
let count = Atom.serializable (Codec.json Schema.number) (Atom.make 0)

draft : String -> Atom.Writable String
let draft = Atom.serializable_family (Codec.json Schema.string) (fun _ -> Atom.make "")
```

Сервер передаёт их через `Ui.Server.state "app"`. Функция возвращает
`<script type="application/json" id="flick-state-app">` с сериализуемыми
атомами реестра для контейнера `app`; его добавляют на страницу после
отрисовки контейнера. `Ui.Dom.mount` для этого контейнера записывает
значения в свой реестр до первого рендера и удаляет скрипт. Поэтому клиент
начинает со значений сервера, а не запрашивает их заново, и повторное
монтирование не перезапишет значения, изменённые после этого. Каждый корень
страницы читает только скрипт своего контейнера. Атом, значение которого
кодек не может закодировать, — дефект с именем его ключа, а не незаметно
пропущенное значение.

```flick
# count : Atom.Writable Float
# let count = Atom.serializable (Codec.json Schema.number) (Atom.make 0)
# component counter_view () = ui { text (Atom.value count |> show) }
#
page : Float ->{Async} String
let page n =
  provide Atom.layer {
    Atom.set count n
    let markup = Ui.Server.render (Ui.render counter_view ())
    "<div id=\"app\" data-flick-ssr>" ++ markup ++ "</div>" ++ Ui.Server.state "app"
  }
```

### Паритет сервера и клиента

Серверная разметка гидратируется, только если первый рендер на клиенте
даёт тот же результат. Поэтому представление читает каждый атом так, как
прочитал бы его сервер, — и на сервере, и во время гидратации корня. После
гидратации React снова рендерит представление со значениями клиента.

У состояния браузера, например URL, на сервере нет значения. Его тип
`Atom.Browser a` — не атом, который можно прочитать через `Atom.get` или
`Atom.value`. Задайте значение для сервера через `Atom.on_server` или
читайте состояние через `Atom.client_only`, который возвращает `None`
на сервере и во время гидратации. `Atom.search_param name` — параметр
запроса `name` в URL; запись в него обновляет URL. `Atom.stored key` —
текст, который локальное хранилище браузера держит под `key`, или `None`:
запись `Some text` сохраняет его, `None` — удаляет, а запись из другой
вкладки тоже видна.

```flick
query : Atom.Writable String
let query = Atom.on_server "" (Atom.search_param "q")

tab : Atom.Atom (Option String)
let tab = Atom.client_only (Atom.search_param "tab")

token : Atom.Writable (Option String)
let token = Atom.on_server None (Atom.stored "jwtToken")
```

### Потоковый рендер

`Ui.Server.stream "app" ui` сам отображает контейнер `<div id="app"
data-flick-ssr>` и отдаёт разметку частями, по мере того как её рендерит
React, — для потокового ответа. Для представления `Ui.suspended`, читающего
ещё выполняющуюся задачу, сначала отправляется заглушка, а после завершения задачи — разметка представления. Задача, прочитанная вне `Ui.suspended`, представлена состоянием
`Loading`; поток не ждёт её завершения. Сериализуемые атомы идут в потоке
JSON-скриптами: атомы оболочки — перед ней, значение сериализуемой задачи —
перед разметкой, которая его показывает. `Atom.serializable_task wire task`
помечает атом задачи, загруженное значение которого сервер так передаёт; ключ
тот же, что у `Atom.serializable`, и клиент начинает с этого значения, не
запуская задачу снова. `Ui.Dom.mount` на контейнере гидрирует скрипты,
пришедшие после монтирования, по мере их прихода.

```flick
# fetch_name : Unit ->{} String
# let fetch_name () = "Ada"
# let page = ui { text "…" }
#
user : Atom.Atom (Atom.Async String none)
let user = Atom.serializable_task (Codec.json Schema.string) (Atom.task (task { fetch_name () }))

chunks : Unit ->{Async;} List String
let chunks () = provide Atom.layer { Stream.run_collect (Ui.Server.stream "app" page) }
```

### Шаблоны без React

`Ui.Server.to_html ui` возвращает HTML `ui` без React — для писем и другой
разметки, которую клиент не гидратирует. Это чистая функция: текст
и значения атрибутов экранируются так же, как в `text`, обработчики
опускаются, а представления читают атомы так же, как на сервере, из реестра
только этого вызова. Поэтому один и тот же `ui` всегда даёт один и тот же
HTML. Внешний компонент, который умеет отображать только React, — дефект.
Функция находится в `@flick-lang/effect-ts/ui/html`, который не импортирует
ни React, ни `react-dom/server`.

```flick
# type alias Order = { customer : String }
#
receipt : Order -> String
let receipt order =
  Ui.Server.to_html (ui { div { class_name = "mail" } [paragraph [text ("Спасибо, " ++ order.customer)]] })
```

## Другие рендереры React

`@flick-lang/effect-ts/ui` — адаптер React DOM.
`@flick-lang/effect-ts/ui/react` содержит только преобразование узлов React,
представления и управление жизненным циклом задач. Импорт этого подпути
не загружает `react-dom` и не читает `document` или `window`.

Из него экспортируются `uiMountWith` и тип фабрики рендерера:

```typescript
type Renderer = () => {
  render(node: React.ReactNode): void;
  unmount(): void;
};
```

Фабрика вызывается при запуске корневого Effect, а не при построении
его описания. Метод `render` передаёт узел React выбранному рендереру,
а `unmount` синхронно отсоединяет корень.
Общий код запуска прекращает приём событий, размонтирует дерево,
прерывает задачи и ждёт их завершения. Рендерер должен размонтировать
все свои компоненты React. Просто скрыть результат рендеринга недостаточно.

В Flick фабрика привязывается через `foreign pure` как непрозрачный
`Ui.Renderer` и запускается вызовом
`Ui.mount_with renderer supervisor ui`. Реестр, сервисы, ошибки, захваты
и порядок завершения такие же, как у `Ui.Dom.mount`.
Так можно подключить React Native, Ink и React Three Fiber,
но готовых адаптеров для них нет. Функции `div`, `input` и другие
HTML-конструкторы остаются привязанными к DOM: другим платформам нужны
собственные типизированные примитивы и снимки событий либо внешние
компоненты через `Ui.component`. Адаптер рендерера без DOM не должен
импортировать DOM-подпуть.

## Атомы, а не программа TEA

Состояние интерфейса Flick хранится в атомах: представление строится
из атомов, которые читает, а обработчик — задача под управлением
супервизора, которая их изменяет. Цикла `Msg → update` нет и он
не планируется: то, что в Elm делают команды, здесь делает задача
действия, а выполняют её уже существующие файберы, области и политики
событий Effect. Источники, которые сами пишут атомы (подписки Elm), —
среди [ограничений ниже](#ограничения).

### Сравнение с Elmish

Сравнение относится к [`elmish/react` v6.x](https://github.com/elmish/react/tree/v6.x),
а не к полноценному MVU-фреймворку.
В [`common.fs`](https://github.com/elmish/react/blob/v6.x/react/common.fs)
реализованы `lazyViewWith` на основе `React.memo` и ключи соседних узлов;
представлению Flick сравнение не нужно, оно перерисовывается только
при изменении прочитанных атомов.
В [`react.fs`](https://github.com/elmish/react/blob/v6.x/react/react.fs) —
проверка идентичности корневой модели, объединение обновлений через
`requestAnimationFrame`, гидратация и `valueOrDefault`.
Цикл обработки сообщений и подписки относятся к отдельному ядру
[`elmish/elmish`](https://github.com/elmish/elmish).
В Flick обновления объединяет React 19, но он не гарантирует расписания
по кадрам анимации, как у Elmish.

### Реализованные оптимизации и подтверждающие тесты

- Представление перерисовывается только при изменении прочитанного атома.
  React 19 объединяет ожидающие рендеры, а не фиксирует изменения синхронно
  после каждой задачи. Только первое монтирование DOM остаётся синхронным.
- При перестановке ключи сохраняют поддерево и состояние занятой политики
  событий. Стабильные слушатели принадлежат компонентам и получают
  актуальный обработчик после фиксации изменений, не удерживая
  устаревшее представление.
- `Ui.Renderer`/`Ui.mount_with` используют общий жизненный цикл React
  без импорта `react-dom`. За монтирование DOM отвечает `Ui.Dom`;
  задачи принадлежат корню, а не DOM.

Реализация находится в
[коде запуска для React](https://github.com/bondiano/flick-lang/blob/main/packages/effect-ts/src/ui/react/index.ts),
[DOM-адаптере](https://github.com/bondiano/flick-lang/blob/main/packages/effect-ts/src/ui/index.ts)
и встроенных модулях
[`Ui`](https://github.com/bondiano/flick-lang/blob/main/packages/std/src/Ui.fl)
и [`Ui.Dom`](https://github.com/bondiano/flick-lang/blob/main/packages/std/src/Ui/Dom.fl).
Для этих возможностей есть регрессионные тесты:

### Ограничения

Перечисленные возможности **не реализованы**. Для поддержки React Native,
Ink или React Three Fiber одного переноса DOM-тегов недостаточно: каждому
рендереру нужны host primitives и адаптер из таблицы ниже.

| Возможность | Что требуется и зачем |
| - | - |
| Подписки атомов с устойчивыми ключами | Запуск и остановка источников по стабильной идентичности, защита от поздних событий, scope-owned cleanup. Таймеры, сокеты, терминал и источники анимации пишут атомы без ожидания завершения UI-handler. |
| Типизированные host primitives и события | Разделить HTML-конструкторы и renderer-specific `View`/`Text`, Ink host nodes, R3F scene nodes. Props со стилями/числами и снимки событий не должны предполагать DOM `target.value` или `preventDefault`. |
| Настоящие адаптеры Native / Ink / R3F | Поверх `Renderer` и host primitives: регистрация/монтирование, обновления, синхронное отсоединение и завершение ресурсов. Для R3F отдельно определить связь атомов, frame loop и invalidation; не посылать 60 сообщений/с без необходимости. |
| Typed React interop | Children/slots внешних компонентов, scoped refs, Context/providers и lifecycle с определённым освобождением ресурсов; сейчас есть только opaque `Ui.component` с props. |

Effect, файберы и области, политики событий с ограниченной очередью
или параллельностью, супервизор, проверки выхода значений из области
и безопасный вывод текста уже есть. Для них не нужны дублирующие API.
