---
title: "`.iface` — нативный интерфейс модуля"
---

Файл `.iface` содержит интерфейс модуля в формате, который нужен модулю
проверки типов. При импорте компилятор читает этот файл, а не исходник
зависимости: он не читает, не разбирает и не проверяет исходный модуль повторно
(см. [Компилятор Flick и интеграция с Content Mapper](../../spec/11-compiler/)).
Формат `.iface` — JSON с указанием версии. Именно он определяет интерфейс
для импортирующих модулей Flick; `.d.ts` содержит только представление
этого интерфейса для TypeScript.

До версии 0.1.0 схема меняется вместе с компилятором. При каждом изменении
повышается `iface-version`; компилятор принимает только свою версию,
а остальные отклоняет с `FLICK-P010`. Релиз 0.1.0 фиксирует ту версию схемы,
с которой поставляется.

## Версия 2

```json
{
  "iface-version": 2,
  "language": "0.7",
  "module": "App.Shapes",
  "exports": [
    { "module": "App.Shapes", "namespace": "type", "name": "Shape", "decl": "adt" },
    { "module": "App.Shapes", "namespace": "constructor", "name": "Circle", "decl": "constructor", "parent": "Shape" },
    { "module": "App.Shapes", "namespace": "type", "name": "Id", "decl": "opaque" },
    { "module": "App.Domain", "namespace": "type", "name": "User", "decl": "alias" },
    { "module": "App.Shapes", "namespace": "value", "name": "area", "decl": "let" }
  ],
  "hidden": [
    { "name": "Square", "parent": "Shape" }
  ]
}
```

Зависимости, записанные по старой схеме, нужно пересобрать: ручная замена
номера версии не восстанавливает отсутствующую информацию о захватах.

| Поле | Значение |
| - | - |
| `iface-version` | версия схемы; должна совпадать с той, которую использует компилятор |
| `language` | версия языка Flick у компилятора, записавшего файл; должна совпадать с версией языка у читающего компилятора |
| `module` | полное имя описываемого модуля |
| `exports` | интерфейс модуля в порядке его списка `exposing` |
| `hidden` | неэкспортируемые конструкторы экспортируемых типов; нужны для точной диагностики `FLICK-R005` при попытке их импорта; поле опускается, если список пуст |
| `instances` | экземпляры классов этого модуля и всех его зависимостей, кроме встроенных модулей; поле опускается, если список пуст |
| `abi` | представление определений модуля в скомпилированном коде, см. [ABI](#abi); записывается командой `flick build`, отсутствует при `flick check` |
| `dependencies` | отпечатки интерфейсов всех импортируемых модулей на момент сборки; поле опускается, если список пуст |
| `source` | путь к исходнику модуля относительно корня пакета; позволяет редакторам находить объявления в опубликованном пакете; записывается командой `flick build` |

Каждая запись об экспорте указывает **сущность**, которую задают `module`,
`namespace` и `name`. Поле `module` указывает, где сущность *определена*.
При реэкспорте оно не меняется, поэтому импортирующие модули распознают,
что два имени обозначают одну сущность. В примере выше `User` реэкспортирован
из `App.Domain`.

| `namespace` | Сущности |
| - | - |
| `value` | `let`, `foreign`, методы классов |
| `type` | типы, `error`, `kind` и его члены, сервисы, классы |
| `constructor` | конструкторы ADT, конструктор `error` |

| `decl` | Объявление | `parent` |
| - | - | - |
| `let` | `let` или сигнатура, определение которой проверяется позже | — |
| `foreign` | `foreign` | — |
| `method` | сигнатура метода класса | класс |
| `adt` | `type T = A \| B` | — |
| `alias` | `type alias T = …` | — |
| `opaque` | `opaque type` | — |
| `refined` | `refined type` | — |
| `abstract` | `type T` без определения | — |
| `error` | `type error E …` | — |
| `kind` | `kind K = …` | — |
| `kind-member` | член `kind` | кинд |
| `service` | `service` | — |
| `class` | `class` | — |
| `constructor` | конструктор | его тип |

`T(..)` в импорте делает доступными экспорты, у которых `parent` равен `T`.

Вместе с типом экспортируются его сопутствующие значения — сущности `value`
с именами `T$member`. Такие имена нельзя записать в исходном коде.
К ним относятся `T$table` у `sql table`, `T$schema` у типа с выведенным
`Schema`, `T$parse` и `T$value` у уточнённого типа, а также `T$json`
у уточнённого типа со схемой. Для обращения к ним служат `schema T` и `T.parse`.

Если объявление определено в этом модуле, его экспорт содержит поле `at` —
диапазон байтов UTF-8, который занимает имя объявления в `source`.
В поле `definition` класса список `defaults` перечисляет методы
с определением по умолчанию.

### Типы и кинды

При проверке импортирующего модуля компилятор получает типы зависимости
только из её интерфейса, а не из исходника. Если в модуле есть синтаксические
ошибки, он не проходит проверку типов. В этом случае его экспорты не содержат
типов, и импортирующие модули допускают любое использование этих экспортов.

| Поле | Где используется | Содержимое |
| - | - | - |
| `type` | значения, конструкторы | полный тип: `forall` с киндами переменных, ограничениями, стрелками эффектов и строками |
| `definition` | типы, ошибки, сервисы, классы, кинды | `kind` и `form`, см. ниже |

```json
{ "module": "App.Shapes", "namespace": "value", "name": "wrap", "decl": "let",
  "type": { "forall": {
    "vars": [ { "name": "f", "kind": { "arrow": ["type", "type"] } }, { "name": "a", "kind": "type" } ],
    "body": { "fun": {
      "param": { "app": { "head": { "var": "f" }, "arg": { "var": "a" } } },
      "result": { "record": { "entries": [ ["value", { "app": { "head": { "var": "f" }, "arg": { "var": "a" } } }] ] } }
    } }
  } } }
```

Типы представлены объектами с тегами. Строка содержит `entries`,
отсортированные по метке, и необязательный `tail`. Метки строки записи —
имена полей; метки строки сервисов или ошибок — имена элементов вида
`Module.Name`; метки строки захватов — `^` с переменной региона.

| Тип | JSON |
| - | - |
| `Float` | `{ "con": { "module": "Prelude", "name": "Float" } }` |
| переменная типа `a` | `{ "var": "a" }` |
| `F a` | `{ "app": { "head": F, "arg": a } }` |
| `a -> b` | `{ "fun": { "param": a, "result": b } }` |
| `a ->{r; e} b` | `{ "fun": { "param": a, "effects": { "services": r, "errors": e }, "result": b } }` |
| `(a, b)` | `{ "tuple": [a, b] }` |
| `{ x : T \| r }` | `{ "record": { "entries": [["x", T]], "tail": r } }` |
| `{Users \| r}`, `none` | `{ "row": { "entries": [["App.Users.Users", …]], "tail": r } }`, `{ "row": { "entries": [] } }` |
| `r1 + r2` | `{ "union": [r1, r2] }` |
| скрытый квалификатор `T^{s}` | `{ "captured": { "ty": T, "captures": { "row": { "entries": [["^s", { "var": "s" }]] } }, "value": false } }` |
| граница всего обобщённого значения `a^c` | `{ "bounded": { "ty": { "var": "a" }, "captures": { "var": "c" } } }` |
| `forall a. C a => T` | `{ "forall": { "vars": [{ "name": "a", "kind": K }], "constraints": [C a], "body": T } }` |

`bounded` уточняет границу захватов всего обобщённого значения, сохраняя
основной тип и его квалификаторы. `captured` сохраняет скрытый или хранимый
квалификатор. Обязательный флаг `value` равен `false` для явного или хранимого
квалификатора и `true`, когда классификация отложена до границы значения,
например пока неизвестна голова типа высшего кайнда. Импортирующий модуль
должен сохранять оба тега и флаг: сведение их к одному квалификатору или
удаление нулевой строки может нарушить безопасность захватов.
См. [Регионы и захваты](../regions/).

Кинды представлены как `"type"`, `"service-row"`, `"error-row"`, `"capture-row"`,
`"symbol"`, `"region"`, `"constraint"`, `"service"` (элемент строки сервисов),
`{ "row": K }`, `{ "named": { "module": …, "name": … } }` для объявления `kind`
и `{ "arrow": [K1, K2] }`.

| `form` | Поля | Объявление |
| - | - | - |
| `nominal` | — | встроенный тип, `type T`, `opaque type`, `refined type`; также непрозрачный ADT, конструкторы которого остаются скрытыми |
| `adt` | `constructors` | вариантный тип; перечислены все конструкторы, включая неэкспортируемые, для проверки полноты сопоставления |
| `error` | — | `type error E …`; его конструктор — `E` |
| `alias` | `params`, `body` | прозрачный псевдоним |
| `service` | `params`, `operations` (`name`, `type`) | `service`; в `operations` записаны объявленные типы операций без самого сервиса; по ним импортирующий модуль выводит `S.Impl` |
| `class` | `params`, `supers`, `fundeps` (`from`, `to`: позиции параметров), `methods` | `class`; методы экспортируются как `value`, а их тип начинается с ограничения класса |
| `kind` | — | `kind K = …`; поле `kind` указывает объявленный кинд |
| `kind-member` | — | член `kind` |

Прозрачные псевдонимы разворачиваются во всех экспортируемых типах.
Поэтому импортирующему модулю не нужны псевдонимы из модулей, которые он
не импортирует. За пределами своего модуля непрозрачный тип имеет форму
`nominal`: импортирующие модули не видят его представления.

### Экземпляры классов

```json
{ "module": "App.Shapes", "name": "Show (List a)",
  "vars": [ { "name": "a", "kind": "type" } ],
  "context": [ { "app": { "head": { "con": { "module": "App.Shapes", "name": "Show" } }, "arg": { "var": "a" } } } ],
  "head": { "app": { "head": { "con": { "module": "App.Shapes", "name": "Show" } },
                     "arg": { "app": { "head": { "con": { "module": "Prelude", "name": "List" } }, "arg": { "var": "a" } } } } } }
```

Поле `module` указывает модуль, объявивший экземпляр класса, а `name` —
заголовок экземпляра в исходном написании. Поля `head` и `context` используют
переменные из `vars`; прозрачные псевдонимы в них развёрнуты.
Импортирующий модуль учитывает эти экземпляры при проверке своих экземпляров
на пересечение и соблюдение функциональных зависимостей, а также при
разрешении ограничений.

### ABI

```json
"abi": {
  "data": [ { "type": "Shape", "constructors": [
    { "name": "Circle", "tag": "@acme/shapes/App.Shapes.Shape.Circle", "arity": 1 } ] } ],
  "dictionaries": [ { "instance": "Show (List a)", "export": "$i_Show_List_a_19082212",
    "context": 1, "methods": ["show"], "supers": [] } ],
  "values": [ { "name": "area", "stages": ".", "dicts": 0, "partial": false } ]
}
```

| Поле | Содержимое |
| - | - |
| `data` | типы и ошибки, объявленные в модуле, с их конструкторами: `id` — полное имя (пакет, модуль, тип, конструктор); `tag` — значение `_tag`, состоящее из имени и хеша `id` (отсутствует у типов `unboxed` или `untagged`, значения которых представлены полем); `arity` — число полей `_0` … |
| `dictionaries` | экземпляры классов, объявленные в модуле: JS-экспорт `export` словаря, число принимаемых словарей контекста, методы `methods` и суперклассы, для которых есть геттер `$Class` |
| `values` | экспортируемые значения: в `stages` по одному символу на параметр определения — `.` для чистой стрелки и `!` для эффектной; `dicts` — число словарей, принимаемых перед остальными аргументами; `partial` равно `false`, только если применение ко всем параметрам гарантированно завершается и не выбрасывает исключений |

Это представление описано в разделе [генерации кода](../codegen/).

### Отпечатки

Отпечаток интерфейса — 64-битный хеш FNV-1a в виде 16 шестнадцатеричных цифр.
Он вычисляется по JSON интерфейса без полей `dependencies`, `source`
и `at` у экспортов. Поэтому перемещение объявления ничего не меняет
для импортирующих модулей. Равные отпечатки означают, что код, скомпилированный
с одним интерфейсом, корректен и с другим.

Поле `dependencies` хранит отпечатки интерфейсов импортируемых модулей
на момент сборки. Если модуль установленного пакета собран с интерфейсом
зависимости, который отличается от установленного, импортирующий модуль
сообщает `FLICK-P014`.

## Расположение в пакете

Пакет указывает каталог своих интерфейсов в `package.json`, а модуль `A.B`
описывается файлом `<iface-dir>/A/B.iface`:

```json
{ "name": "@acme/text", "flick": { "iface-dir": "iface" } }
```

Скомпилированный модуль находится рядом со своим интерфейсом.
Импортирующий код использует путь `<package>/<iface-dir>/A/B.js`.
Например, при указанной выше конфигурации модуль `Text.Shout` из `@acme/text`
импортируется по пути `@acme/text/iface/Text/Shout.js`.
Если в пакете объявлено поле `exports`, этот путь должен быть в нём доступен.

Команда `flick build` записывает `A/B.iface` рядом с `A/B.js` в выходном
каталоге. Поэтому выходной каталог служит `iface-dir`, а `flick pack`
записывает это поле в `package.json`. Файлы интерфейсов не редактируют вручную.
