## Вычисления и кинды

Тип вычисления записывается как `Eff requirements errors result`. Результат стоит последним, чтобы `Eff r e` был конструктором типов с киндом `Type -> Type`. Кинд — тип самого типа: он отличает обычный тип от конструктора, которому ещё нужны параметры.

```text
Unit, Never, Number, BigInt : Type
Option, List, Ref, Redacted, Schema : Type -> Type
Result, PureCodec : Type -> Type -> Type

Eff : ServiceRow -> ErrorRow -> Type -> Type
Layer : ServiceRow -> ErrorRow -> ServiceRow -> Type
Codec : ServiceRow -> ServiceRow -> Type -> Type -> Type
Errors : ErrorRow -> Type

FieldRow = Row Type
Region, CaptureRow, Symbol : Kind

Eff r e : Type -> Type
```

`FieldRow = Row Type` здесь обозначает равенство форм киндов, а не пользовательское объявление типа. `ServiceRow`, `ErrorRow` и `CaptureRow` — разные встроенные кинды. Метки полей имеют кинд `Symbol`; сервисы и ошибки имеют номинальную идентичность, которую нельзя заменить строковой меткой.

При генерации кода `Eff r e a` отображается в `Effect<A, ErrorUnion<E>, ServiceUnion<R>>`. Строки Flick имеют собственные номинальные идентификаторы, нормализацию и правила ограничений. Объединения типов TS служат выходным представлением; пустая строка в обоих случаях даёт `never`.

## Запись и объединение строк

В позиции отдельной строки используются `none`, переменная `r`, закрытая строка `{Users, Log}` либо открытая `{Users, Log | r}`. В стрелке внешние скобки строк опускаются: `a ->{Users, Log; NotFound} b` и `a ->{Users | r; NotFound | e} b`. Здесь `| r` и `| e` обозначают хвост строки. Без хвоста список закрыт. Порядок элементов несущественен, повторы одного номинального элемента нормализуются.

`r1 + r2` и `e1 + e2` обозначают объединение строк одного кинда, например `Eff (r1 + r2) (e1 + e2) a`. Это встроенная операция решателя ограничений строк, а не пользовательское семейство типов. Сигнатура задаёт верхнюю границу: реализация может требовать меньше сервисов или допускать меньше ошибок. Расширение строки не превращает эффектную стрелку в чистую.

`Errors e` переводит строку ошибок в обычный тип значений: `Errors none = Never`, `Errors {NotFound} = NotFound`, а для нескольких элементов получается сумма номинальных ошибок. Это встроенная проекция анализатора типов. Произвольный тип нельзя автоматически преобразовать обратно в строку: для обобщённого преобразования нужна сохранённая строка `e` либо аннотация, а для отдельной объявленной ошибки доступна строка из одного элемента.

## Пример HKT

```flick
class Functor (f : Type -> Type) =
  map :
    forall c d a b.
    (a -> b)^c -> ((f a)^d -> (f b)^(c + d))^c

instance Functor Option =
  map :
    forall c d a b.
    (a -> b)^c ->
    ((Option a)^d -> (Option b)^(c + d))^c
  let map f value =
    match value with
    | None -> None
    | Some x -> Some (f x)
```

Обычный `Functor.map` принимает чистую функцию. `c` ограничивает её захваты, `d` — захваты входного контейнера. Результат консервативно сохраняет `c + d`, поскольку абстрактный f может отложить применение и удерживать входное значение и переданную функцию. При частичном применении удерживается пока только функция. Option применяет её сразу; его более точный результат укладывается в указанную верхнюю границу. `Eff r e` создаёт холодное описание и сохраняет захваты. Более точный контракт List.map, который выполняет обход сразу, приведён в разделе 6.

## Выбор экземпляров классов и словарей

Фронтенд проверяет кинды, выводит типы и ограничения, выбирает экземпляры классов и вставляет явные аргументы-словари. Во время выполнения словарь — значение с реализациями методов; HKT не требуют отдельного исполнителя типов.

```flick
class Show a =
  show : a -> String

render : Show a => a -> String
let render value =
  show value
```

```ts
interface Show<A> {
  readonly show: (value: A) => string
}

const render =
  <A>(dictionary: Show<A>) =>
  (value: A): string =>
    dictionary.show(value)
```

Похожая передача реализаций используется в PureScript. [Классы типов и сгенерированные словари](https://book.purescript.org/chapter6.html).

## Требования к типовому ядру

- Функции обратного вызова с полиморфизмом высших рангов, вложенным `forall`, проверкой полных сигнатур и выводом типов внутри тела.

- Номинальные ADT, точные структурные записи с полиморфизмом строк и исчерпывающий `match`.

- HKT с конструкторами типов и частичным применением.

- Многопараметрические классы, суперклассы и функциональные зависимости входят в первую версию; решатель ограничений строк использует фиксированные детерминированные операции.

- Уникальные канонические экземпляры классов без перекрытий, экземпляров-сирот и локального неявного поиска; владение определяется пакетом.

- Явные интерфейсы публичных модулей.

Ассоциированные типы, пользовательские открытые и закрытые семейства типов, цепочки экземпляров классов, непредикативное инстанцирование и общий вывод типов высших рангов не входят в первую версию. Полиморфная рекурсия проверяется только по явно написанной полной `forall`-сигнатуре. SQL/UI используют встроенные операции над строками, обычные HKT, ограниченные отношения классов и типизированные AST.

Обобщение обычного чистого `let` и результата эффектного выражения нельзя механически считать одинаковым. Для состояния и FFI нужны правила обобщения и ограничение значений (value restriction), которые предотвращают небезопасное совместное использование полиморфных изменяемых значений.

<div id="полиморфные-callbacks"></div>

## Полиморфные функции обратного вызова

Функции обратного вызова с полиморфизмом высших рангов входят в язык сразу. Вложенный `forall` в полной сигнатуре означает, что вызываемая функция вправе применять одну переданную функцию при разных типах. Для обычных выражений по-прежнему действует локальный вывод типов; на границе с полиморфным аргументом анализатор типов использует ожидаемую сигнатуру. HKT и ранг полиморфизма остаются разными свойствами.

| Правило | Следствие |
| - | - |
| Явный вложенный `forall` | Полиморфизм аргумента виден в полной сигнатуре; угадывать его по нескольким вызовам не нужно |
| Двунаправленная проверка типов | Анализатор выводит обычные типы и проверяет выражение по заданному полиморфному типу |
| Предикативное инстанцирование | Обычная переменная типа заменяется мономорфным типом; произвольный `List (forall a. ...)` автоматически не допускается |
| Ограничения внутри `forall` | При каждом применении переданной функции передаются словари для соответствующего типа |
| Строки во внешней области | Переданная функция может быть полиморфной по результату, сохраняя один и тот же набор сервисов и ошибок |
| Проверка захватов и выхода жёстких переменных типов из области | Полная сигнатура не разрешает скрыть дополнительную ссылку на изменяемый объект или выдать фиксированный тип за произвольный |
| Объём первой версии | Вложенные `forall` в аннотированных функциональных типах; общий вывод типов высших рангов и непредикативность не обещаются |

Простой пример: одна переданная функция вызывается при типах `Number` и `String` в одном теле.

```flick
apply_twice :
  (forall a. a -> a) -> (Number, String)
let apply_twice transform =
  (transform 42, transform "hello")

render_twice :
  (forall a. Show a => a -> String) -> (String, String)
let render_twice render =
  (render 42, render "hello")
```

Эффектная функция обратного вызова тоже может быть полиморфной:

```flick
decode_pair :
  (forall a. Schema a -> Unknown ->{r; SchemaError} a) ->
  Unknown -> Unknown ->{r; SchemaError} (User, Settings)
let decode_pair decode user_input settings_input =
  let user = decode (schema User) user_input
  let settings = decode (schema Settings) settings_input
  (user, settings)
```

Здесь `a` меняется при каждом вызове, а `r` принадлежит внешней сигнатуре. Для примера предполагаются объявленные `User`, `Settings` и их схемы Schema.

Для полиморфизма высших рангов нужны двунаправленная проверка типов, проверка жёстких переменных типов, инстанцирование и диагностика выхода переменных из области действия. Полиморфная рекурсия и обобщение изменяемых значений остаются отдельными проверками. Такой подход к границам с явными аннотациями описан в [GHC](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/rank_polymorphism.html#type-inference). Во Flick его можно применять на полных сигнатурах, которые уже требуются для всех именованных функций.

## Структурность записей

Выбраны **точные закрытые структурные записи и полиморфизм строк полей**. `type alias User = { ... }` — прозрачный псевдоним структуры; номинальность вводится отдельным объявлением opaque/newtype. ADT номинальны. Неявного подтипирования по ширине нет: дополнительные поля принимаются только через явно открытый хвост строки либо удаляются явной проекцией.

| Модель | Что удобно | Цена |
| - | - | - |
| Точные структурные записи с открытыми строками полей — выбрано | Литералы без конструкторов; функции принимают любую явно описанную дополнительную строку; точная структура пригодна для Schema | Нужны унификация строк полей, уникальность меток и правила ограничений для открытого хвоста |
| Структурность с подтипированием по ширине | Объект с дополнительными полями принимается API, которому нужна меньшая структура, почти как в TS | Скрытые поля остаются во время выполнения; сложнее вывод типов, проверка полиморфизма высших рангов, равенство и согласование с точными схемами |
| Номинальные записи | Разные домены могут иметь одинаковые поля и свои экземпляры классов | Дополнительные конструкторы, обёртки и преобразования в FFI; менее удобная работа с повседневными данными |

Строка полей имеет кинд `FieldRow`, эквивалентный `Row Type`; это не строка сервисов или ошибок. Метки уникальны; их порядок не входит в тип. В первой версии доступны встроенные `HasField`, `Lacks`, `Project`, `Remove`, `UnionDisjoint`, `Map` по конструктору с киндом `Type -> Type` и каноническое перечисление меток. Пользовательские экземпляры для этих операций запрещены. `UnionDisjoint` отвергает повтор метки; объединение строк сервисов и ошибок, наоборот, нормализует повтор одного номинального элемента.

```flick
name :
  forall fields. { name : String | fields } -> String
let name value =
  value.name

project_name :
  forall fields. { name : String | fields } -> { name : String }
let project_name value =
  { name = value.name }
```

`name` допускает дополнительные поля через `fields`. `project_name` создаёт объект только с полем `name`; это не приведение типа, которое лишь скрывает ключи. Обновление `{ record with field = value }` заменяет существующее поле значением того же типа. `Record.extend` требует `Lacks`; `Record.merge_disjoint` требует непересекающихся строк. Чтобы сменить тип поля, нужны явные remove/extend либо новая запись. При разворачивании полей нет скрытой перезаписи. Значения полей вычисляются в порядке исходного кода.

<div id="records-instances-и-ffi"></div>

### Записи, экземпляры классов и FFI

Два прозрачных псевдонима одной структуры — один тип и не получают разные глобальные `Eq` или `Hash`. Для закрытой записи действует канонический структурный экземпляр класса, если нужные экземпляры есть для каждого поля. Открытая строка требует ограничений на весь хвост. Структурные экземпляры, заданные компилятором, нельзя переопределить для отдельного псевдонима.

Для другой доменной семантики вводится номинальная обёртка. При взаимодействии с Equal/Hash из Effect она имеет реальную оболочку во время выполнения и собственный протокол. Стирать её допустимо только на участке, где компилятор доказал, что идентичность и протокол нельзя наблюдать через FFI или коллекции. Для альтернативного сравнения без нового типа в коллекцию, которая поддерживает выбор словаря, передаётся явное согласованное свидетельство `EqHash`.

На входе из JS точная запись по умолчанию отвергает лишние ключи; явно выбранное правило проекции создаёт новый объект нужной структуры. Обычное приведение типа этого не делает. Запись представлена обычным объектом JS. На недоверенной границе по умолчанию копируются поддерживаемые неизменяемые данные; изменяемая ссылка на исходный объект не передаётся. Представление только для чтения без копирования допустимо лишь по доверенному контракту владения. `readonly` из `.d.ts` сам по себе такого контракта не доказывает.

[Полиморфизм строк в PureScript](https://github.com/purescript/documentation/blob/master/language/Types.md) показывает подход со строками полей. У [Effect Equal](https://effect.website/docs/v4/trait/equal) обычные объекты сравниваются структурно, поэтому незаметно сохраняемые дополнительные поля влияют на поведение коллекций.

## Выбранное ядро классов и цена альтернатив

Решения о классах принимаются независимо по нескольким вопросам: число параметров; способ выражения связей между типами; выбор экземпляров и владение ими; обобщение привязок `let`. HKT и полиморфизм высших рангов у функций обратного вызова уже выбраны и не требуют автоматически включать все остальные механизмы.

### Что даёт один параметр

```flick
class Show a =
  show : a -> String

unboxed type PrintableUser =
  | PrintableUser User

instance Show PrintableUser =
  show : PrintableUser -> String
  let show value =
    match value with
    | PrintableUser user -> user.name

render : Show a => a -> String
let render value =
  show value
```

PrintableUser — номинальная обёртка, которой владеет пакет, объявляющий экземпляр класса. Прозрачный псевдоним записи User сам по себе не даёт такого права для чужого класса.

`Show a` выбирает реализацию для одного типа. Параметр также может иметь кинд `Type -> Type`: у `Functor f` он один — `f`. Поэтому однопараметрическое ядро поддерживает Functor, Foldable, Traversable, Monad и `Functor (Eff r e)`. Функция обратного вызова с полиморфизмом высших рангов и `forall a. Show a => ...` остаётся доступной.

Цена ограничения видна у отношения между двумя независимыми типами:

```flick
class Convert input output =
  convert : input -> Result ConversionError output
```

Здесь полезны и `Convert String Email`, и `Convert String UserId`. В однопараметрическом ядре это выражается отдельными функциями либо явными значениями преобразователей или кодеков. Наш `Codec rd re i a` уже позволяет передать нужное преобразование напрямую; ему не требуется единственный глобальный экземпляр класса.

### Начальный набор

В первую версию входят **многопараметрические классы, суперклассы и FD**, уникальные канонические экземпляры без перекрытий, владение на уровне пакета и обобщение доказанно чистых построений. Результаты эффектных выражений мономорфны. Такой набор нужен для связей между параметрами SQL/UI eDSL; встроенные операции над строками снимают часть задач, которые библиотеки PureScript решают сложным поиском экземпляров классов.

Ассоциированные типы, общие семейства типов и ослабленное ограничение значений на основе вариантности не входят в первую версию. Сравнения ниже объясняют ограничения этих решений; сами решения уже приняты.

## Параметры классов и зависимости между типами

| Механизм | Пример применения | Цена |
| - | - | - |
| Один параметр и суперклассы | `Eq a`, `Hash a`, `Functor f`, `Traversable f` | Простой поиск экземпляров; сложные отношения между независимыми типами выражаются явными значениями |
| Несколько параметров | `Convert source target` | Иногда оба типа приходится указывать явно из-за неоднозначности |
| Функциональные зависимости | Тип коллекции однозначно определяет тип элемента | Нужны уточнение ограничений, проверка совместимости зависимостей и завершения поиска |
| Ассоциированные типы | `Element collection`, тип результата операции | Решатель ограничений должен нормализовать функции на типах и решать равенства |
| Общие семейства типов | Вычисления над типами и более сложные DSL | Наибольшие затраты в анализаторе типов, интерфейсах модулей и диагностике |

### Многопараметрические классы и функциональные зависимости

```flick
class Collection c a | c -> a =
  empty : c
  insert : forall captures. a^captures -> (c -> c)^captures
```

Квалификатор у insert сохраняет значение a в частично применённой функции; конкретный тип коллекции также сохраняет захваты своих элементов.

Зависимость `c -> a` читается: «конкретный тип коллекции определяет единственный тип элемента». Например, возможны заголовки экземпляров `Collection UserSet User` и `Collection NameSet String`.

```flick
empty_users : UserSet
let empty_users =
  empty
```

Ожидаемый `UserSet` определяет и `User`. Без зависимости у метода был бы тип `Collection c a => c`, где `a` не указан результатом; требуется отдельное основание для однозначного выбора словаря.

Пара `Collection UserSet User` и `Collection UserSet String` нарушает FD. Обратное направление не гарантируется: один `User` может храниться в разных коллекциях. После раскрытия псевдонимов и нормализации встроенных выражений строк переменные определяемой части экземпляра должны входить в определяющую часть — это строгое покрытие. Если определяющие позиции двух заголовков унифицируются, их определяемые позиции должны согласовываться. Ограничения контекста не позволяют обойти проверку покрытия или выбрать между конфликтующими заголовками.

Многопараметрический класс не обязан иметь функциональную зависимость. Для `Convert String Email` и `Convert String UserId` зависимость `input -> output` как раз неверна: String допускает оба результата.

Для FD нужны уточнение переменных по ограничениям, проверка согласованности экземпляров, покрытия и завершения поиска. [Функциональные зависимости в GHC](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/functional_dependencies.html) показывают этот механизм на связи коллекции с элементом. Для Schema/Codec нельзя автоматически назначать единственный формат обмена одному доменному типу.

<div id="associated-types"></div>

### Ассоциированные типы

Ассоциированные типы исключены из первой версии. Для сравнения с выбранным FD тот же сценарий выглядел бы так:

```flick
class Collection c =
  type Item c

  insert : Item c -> c -> c
```

Экземпляр для `UserSet` объявляет `Item UserSet = User`. Полная сигнатура общего метода имеет вид `Collection c => Item c -> c -> c`.

Это удобно, когда сущность определяет свои связанные типы: Repository — Entity и Key, Parser — Output, коллекция — Item. При неизвестном `c` выражение `Item c` может оставаться невычисленным. Из `Item c = User` нельзя восстановить единственный `c`.

Для ассоциированных типов нужен отдельный решатель равенств и механизм нормализации выражений типов. Даже определения только внутри канонических экземпляров добавляют новый механизм в анализатор типов. Первая версия выражает такую связь через MPTC/FD или явное свидетельство.

<div id="type-families-вне-первой-версии"></div>

### Семейства типов вне первой версии

```text
type family Element container =
  | List a -> a
  | Option a -> a
```

Здесь вычисление типов существует независимо от словаря класса и методов, вызываемых во время выполнения. При неизвестном аргументе `Element container` может остаться невычисленным. Потребуются правила применимости уравнений, их совместимости, нормализации и завершения.

[Семейства типов в GHC](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/type_families.html) включают как связанные определения внутри классов, так и самостоятельные семейства. FD и ассоциированные типы можно сочетать, но это отдельные источники сложности.

Полноценный deriving Schema не зависит от принятия общих семейств типов: компилятор генерирует свидетельства по определению типа и получает схемы обобщённых и HKT-параметров явно.

<div id="coherence-и-альтернативные-instances"></div>

## Согласованность и альтернативные экземпляры классов

Согласованность (coherence) означает, что одно ограничение получает согласованную реализацию. Для коллекций смена `Eq`, `Hash` или `Ord` между вставкой и поиском может нарушить их поведение.

| Политика | Выигрыш | Цена |
| - | - | - |
| Один экземпляр без перекрытий и экземпляров-сирот | Предсказуемая семантика и совместимость библиотек | Для чужого класса и чужого типа нужна номинальная обёртка |
| Разрешённые экземпляры-сироты | Удобные пакеты интеграции | Две библиотеки могут предложить несовместимые экземпляры |
| Перекрытия с приоритетами | Общая реализация и специализированные случаи | Усложняется поиск; добавление библиотеки способно изменить выбранную реализацию |
| Локальные неявные экземпляры | Короткая запись локальной настройки | Нужны правила захвата словаря и передачи значений между областями |
| Явные словари | Альтернативное поведение видно в API | Больше аргументов; коллекция должна хранить выбранные Eq/Hash |

Принято: заголовки экземпляров после раскрытия псевдонимов не должны унифицироваться; их контекст не используется для устранения перекрытий. Все переменные контекста должны присутствовать в заголовке. Рекурсивные ограничения классов должны структурно уменьшаться без роста числа вхождений переменной; граф суперклассов ацикличен. Это консервативное условие завершения, без аналога `UndecidableInstances`. Если решатель ограничений исчерпал выделенный ему бюджет, выдаётся диагностика; это никогда не считается успешным разрешением. `Eq a => Eq (List a)` допустим. [Правила завершения экземпляров в GHC](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/instances.html#instance-termination-rules) служат ориентиром для такого консервативного ограничения, а не обещанием поддержать все расширения GHC.

<div id="overlap-на-примере"></div>

### Перекрытие экземпляров на примере

Предположим, объявлены два правила:

```text
Show a => Show (List a)
Show (List Number)
```

Для `List Number` подходят оба. Приоритет более специального экземпляра выглядит удобным, но компилятор должен решить, какое поведение получает уже скомпилированная обобщённая функция и может ли специализация выбрать другую реализацию.

[GHC описывает связь перекрытий со специализацией](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/instances.html#overlapping-instances). Если во Flick есть несколько словарей одного типа, оптимизатор должен сохранять конкретно выбранный словарь. Без перекрытий проще получить прямой вызов метода, а затем встроить его тело.

<div id="orphan-instance-и-внешняя-библиотека"></div>

### Экземпляр-сирота и внешняя библиотека

Пусть `Hash` определён стандартной библиотекой, а `ExternalId` — SDK. При запрете экземпляров-сирот пакет адаптера, не владеющий ни классом, ни исходным типом, не может объявить глобальный `Hash ExternalId`.

```flick
unboxed type LocalExternalId =
  | LocalExternalId ExternalId
```

Теперь адаптер владеет номинальным типом и может дать ему канонические экземпляры классов. `unboxed` оставляет во время выполнения сам `ExternalId`: обёртка не выделяет память и передаётся в SDK как есть, а идентичность и экземпляры классов остаются у номинального типа. Прозрачный псевдоним `type alias LocalExternalId = ExternalId` новой идентичности не создаёт. Другие варианты — экземпляр у владельца класса или типа либо переданный явно словарь.

Владение определяется **пакетом**: объявить экземпляр может пакет класса либо пакет внешнего номинального конструктора **первого параметра заголовка**. Прозрачный псевдоним и структурная запись владельца не создают. Для MPTC владения только более поздним параметром недостаточно: пакет `LocalEmail` не получает право объявить чужой `Convert String LocalEmail`. Для этого нужен явный кодек или словарь, обёртка первого параметра либо экземпляр у владельца класса. Привязка владения к первому параметру исключает конкурирующих владельцев разных параметров, но требует дополнительных обёрток в интеграциях. Привязка FFI не меняет идентичность внешнего типа.

<div id="локальные-implicit-instances"></div>

### Локальные неявные экземпляры

Можно предложить область, внутри которой `Eq String` означает сравнение без учёта регистра. Тогда требуется определить, какой словарь захватывает замыкание и что получает коллекция после выхода из области. Лексический выбор можно сделать детерминированным, но имя типа уже не задаёт единственное поведение.

Для альтернативной сортировки достаточно явной функции сравнения. Хеш-коллекция должна получать и хранить согласованную пару Eq/Hash; смена окружающего экземпляра класса не меняет семантику уже заполненной коллекции.

Выбраны канонические неявные экземпляры, номинальные обёртки и явные словари для альтернативного поведения. Экземпляры-сироты, перекрытия с приоритетами и локальные неявные экземпляры в первой версии запрещены. Набор экземпляров определяется графом зависимостей пакета, а не порядком или формой `import`; конфликты диагностируются при проверке всего доступного графа.

<div id="generalization-при-наличии-ref"></div>

## Обобщение при наличии Ref

Обобщение означает, что тип привязанного значения можно заново инстанцировать при каждом использовании. У `identity : forall a. a -> a` два вызова могут независимо выбрать `Number` и `String`. У одной изменяемой ячейки должен оставаться один тип содержимого. Явная сигнатура `forall` не может сделать небезопасное совместное использование состояния допустимым.

```flick
invalid : Unit ->{} String
let invalid () =
  let cell = Ref.make None
  Ref.set cell (Some 42)
  match Ref.get cell with
  | Some value -> String.trim value
  | None -> ""
```

Программа должна быть отвергнута: запись `Some 42` фиксирует содержимое ячейки как `Option Number`, а `String.trim` требует `String`. Если бы `cell` получила `forall a. Ref (Option a)`, запись и чтение могли бы выбрать разные типы для одного объекта. Проблема полиморфных изменяемых ячеек и ослабленное ограничение значений разобраны в [руководстве OCaml](https://ocaml.org/manual/5.4/polymorphism.html).

| Правило обобщения | Цена реализации | Цена для автора программы |
| - | - | - |
| Только синтаксические значения | Самое простое консервативное правило | Иногда приходится добавлять функцию-обёртку для безопасного выражения |
| Доказанно чистое построение значения | Использует анализ чистоты и эффектов, а также свободных переменных окружения | Меньше вынужденных функций-обёрток; требует правдивых контрактов FFI |
| Дополнительное обобщение по вариантности | Нужен анализ вариантности, включая абстрактные типы | Допускает больше безопасных программ; `Ref a` остаётся инвариантным |
| Эффекты состояния и регионы | Существенно более сложная система состояния | Позволяет скрывать локальную мутацию за чистым API |

Обобщаются **доказанно чистые построения значений** и только по переменным, которые не свободны в окружении и не связаны с локальными жёсткими переменными типов, обязательствами по регионам и захватам или неоднозначными ограничениями. Результат эффектного выражения не обобщается даже при `->{}`. Полная сигнатура не отменяет эти проверки. Ослабленное ограничение значений на основе вариантности в первой версии не используется; изменяемые контейнеры инвариантны. Доверенный чистый FFI обязан соблюдать тот же контракт чистоты.

```flick
make_empty : forall a. Unit ->{} Ref (Option a)
let make_empty () =
  Ref.make None

use_separate_cells : Unit ->{} Unit
let use_separate_cells () =
  let numbers = make_empty ()
  let names = make_empty ()
  Ref.set numbers (Some 42)
  Ref.set names (Some "Ada")
```

Значение функции `make_empty` полиморфно: создание замыкания чистое. Каждый эффектный вызов выделяет новую ячейку; сама `numbers` мономорфна и хранит только `Option Number`, а `names` — только `Option String`. Это различие сохраняет полезный полиморфизм фабрик, не разрешая менять тип уже созданного состояния.

<div id="generalization-на-трёх-небольших-примерах"></div>

### Обобщение на трёх небольших примерах

**Синтаксические значения и доказанная чистота.**

```flick
make_identity : Unit -> (a -> a)
let make_identity () =
  fun value -> value

identity_again : forall a. a -> a
let identity_again =
  make_identity ()
```

Правая часть `make_identity ()` — вызов, а не синтаксическое значение. Строгое правило «обобщать только значения» отвергнет требуемую полиморфную сигнатуру `identity_again`; добавление явного `forall` не отменяет правило. Анализ доказанной чистоты разрешит её: вызов чистый, состояние не выделяется, переменная `a` не захвачена из окружения. Вывод типов высших рангов здесь не требуется.

**Чистое описание вычисления и результат его выполнения.**

```flick
fresh_cell : forall a. Eff none none (Ref (Option a))
let fresh_cell =
  task { Ref.make None }

use_tasks : Unit ->{} Unit
let use_tasks () =
  let numbers = await fresh_cell
  let names = await fresh_cell
  Ref.set numbers (Some 42)
  Ref.set names (Some "Ada")
```

`task` создаёт холодное описание. Поэтому `fresh_cell` можно обобщить: каждый `await` заново выполняет `Ref.make`. Полученные ячейки снова мономорфны. `await` не означает кеширование результата и не запускает отдельный файбер.

```flick
capture_cell : Ref (Option a) -> Eff none none (Ref (Option a))
let capture_cell cell =
  task { cell }
```

Здесь повторные запуски возвращают одну захваченную ячейку. Тип `a` связан с аргументом `cell`: локальное описание не может обобщить переменную, свободную в окружении. Аналогично мемоизация не должна сохранять полиморфизм свежего результата, если превращает его в совместно используемое состояние. Холодность `Eff` сама по себе не доказывает отсутствия захватов.

**Что дополнительно разрешает вариантность.**

```flick
logged_none : Unit ->{Log; none} Option a
let logged_none () =
  Log.info "created an empty result"
  None

use_logged_none : Unit ->{Log; none} (Option Number, Option String)
let use_logged_none () =
  let empty = logged_none ()
  (empty, empty)
```

При консервативном запрете обобщать результаты эффектных выражений `empty` получает один неизвестный тип `Option a`; использовать его в паре сразу как `Option Number` и `Option String` нельзя. Ослабленное ограничение значений может обобщить `a` в ковариантном неизменяемом `Option a`, сохранив один вызов `Log.info`. Это дополнительная выразительность, а не способ выполнить логирование чисто.

| Положение переменной | Пример | Следствие для ослабленного ограничения значений |
| - | - | - |
| Ковариантное | Неизменяемый `Option a` | Кандидат на дополнительное обобщение |
| Инвариантное | `Ref a` | Разделяемое изменяемое содержимое не обобщается |
| Одновременно вход и выход | `a -> a` | Одной проверки ковариантности недостаточно |
| Абстрактный тип | `Container a` из другого модуля | Вариантность должна быть проверена и сохранена в интерфейсе |

Правило первой версии — **доказанная чистота, учёт свободных переменных окружения, проверка времени жизни и однозначности ограничений**. Пример `logged_none` выше намеренно отвергается; он показывает ограничение, к которому приводит отказ от обобщения по вариантности. Дополнительное обобщение по вариантности вынесено за первую версию.

## Deriving и законы классов

`deriving Eq, Ord, Hash, Show` создаёт экземпляры классов; полноценный `deriving Schema` создаёт свидетельство структуры данных, доступное во время выполнения. Deriving Schema охватывает записи, ADT, кортежи, обобщённые и рекурсивные типы, уточнения и расширение через явные свидетельства. Он не объявляет одноимённый класс типов и не требует общего языка семейств типов. Подробный контракт — в разделе 9.

Проверка экземпляра подтверждает его тип, но не доказывает законы класса. Генерация `Eq` и `Hash` должна использовать согласованную семантику полей. Для пользовательских реализаций нужны отдельные проверки законов; сериализация и формат хранения задаются явным кодеком, а не единственным глобальным экземпляром класса.

## Monad и объединение строк

```text
bind :
  forall c d m a b.
  Monad m => (m a)^c ->
  ((a -> (m b)^d)^d -> (m b)^(c + d))^c

bind_eff :
  forall c d r1 r2 e1 e2 a b.
  (Eff r1 e1 a)^c ->
  ((a -> (Eff r2 e2 b)^d)^d ->
    (Eff (r1 + r2) (e1 + e2) b)^(c + d))^c
```

Строки захватов задают верхние границы; результат сохраняет захваты исходного описания и продолжения. Частичное применение удерживает пока только первый аргумент.

Обычный `Monad (Eff r e)` фиксирует `r` и `e`; допускается их явное или выведенное расширение до общей строки. Для прямых эффектных вызовов используется отдельный встроенный механизм последовательного выполнения с объединением строк, без обращения к экземпляру `Monad`.

Фронтенд вычисляет объединения строк требований и ошибок для прямых вызовов и сохраняет захваты описаний и переданных функций. Индексированные и градуированные абстракции не входят в первую версию. Обобщённый `do` раскрывается прямо в методы `Monad` и `Alternative` из прелюдии, какие бы имена ни были в области видимости; с `Monad (Eff r e)` строки остаются фиксированными, поэтому для Eff основным стилем остаются прямые вызовы.

**Решение типового ядра:** MPTC, суперклассы и FD со строгим покрытием и структурным условием завершения; владение на уровне пакета класса или первого номинального параметра; запрет перекрытий, экземпляров-сирот и локального неявного поиска; фиксированные операции над строками; обобщение только доказанно чистых построений. Функции обратного вызова с полиморфизмом высших рангов проверяются по явным вложенным `forall`; эта возможность не ослабляет ни согласованность экземпляров, ни ограничения состояния.
