## Ожидаемые ошибки

У каждой ошибки есть номинальная идентичность и данные. `try ... with` обрабатывает выбранную ожидаемую ошибку по правилам Effect. Данные каждого конструктора ошибки не зависят от регионов: в них нельзя хранить значение региона (дескриптор ресурса области вроде `File s`), ячейку (`Ref`), вычисление (`Eff`), слой, эффектную функцию или `Unknown`, в том числе через используемые типы (`FLICK-E005`, см. [Регионы и захваты](../../reference/regions/#что-не-может-покинуть-область)). Проверка действует, даже если ошибку перехватывают локально. Поэтому в ошибку передают путь, идентификатор или копию данных, а не живой ресурс.

Ошибка объявляется через `type error`. Её единственный конструктор называется так же, как сама ошибка. Поля перечисляются как у варианта ADT: `type error NotFound = NotFound UserId`. Ошибка без полей записывается как `type error Timeout`.

```flick
# type UserId = UserId String
# type alias User = { id : UserId; name : String }
# service Users =
#   get : UserId ->{; NotFound} User
#
type error NotFound = NotFound UserId

load_optional : UserId ->{Users; none} Option User
let load_optional id =
  try
    Some (Users.get id)
  with
  | NotFound _ -> None
```

Если `Users.get` имеет тип `Users.get : UserId ->{Users; NotFound} User`, то `load_optional` возвращает `Option User`, по-прежнему требует `{Users}`, но больше не содержит выбранных ожидаемых ошибок в своей строке ошибок. Полная причина завершения, нативный Cause, может содержать дополнительные сбои для диагностики. Их данные нельзя считать значениями остаточной строки `e`.

Ошибка может иметь параметры. `type error RetryExhausted e = RetryExhausted e Float` хранит последнюю причину после исчерпания попыток, а `type error SendFailed a = SendFailed a` возвращает значение, которое не удалось отправить. Строка ошибок различает элементы по номинальному имени `Module.Name`, а не по аргументам типа. Поэтому в одной строке может быть не больше одного элемента с данным именем. Аргументы двух `RetryExhausted` в одной строке унифицируются: совместное присутствие `RetryExhausted DbError` и `RetryExhausted String` приводит к ошибке типов (`FLICK-T003`).

Проекция в TypeScript следует тому же правилу: `_tag` не зависит от аргументов типа, `RetryExhausted<E>` встречается в объединении ошибок `Effect` не более одного раза, а `catchTag` однозначно сужает тип. Пользовательская функция `retry` тогда могла бы иметь такой тип:

```flick
type error RetryExhausted e = RetryExhausted e Float

retry : Float -> Eff r e a ->{r; RetryExhausted (Errors e)} a
# let retry times body =
#   try await body with
#   | cause -> from_result (Err (RetryExhausted cause times))
```

Обработчик может удалить ошибку из строки, только если полностью покрывает её номинальный вариант. Условие ветки или образец, который подходит лишь части данных ошибки, оставляет её в строке. Требования и ошибки самого обработчика добавляются к результату. Удаление из строки относится к выбранной ожидаемой ошибке и не доказывает, что такой же тег отсутствует среди вторичных сбоев в полной причине завершения.

Ожидаемая ошибка, дефект и прерывание остаются разными исходами. Пустая строка ошибок не гарантирует, что вычисление завершится, не столкнётся с дефектом или не будет отменено. Effect сохраняет дефекты и прерывания в причине завершения, а не в обычном параметре `E`. [Виды ошибок Effect](https://effect.website/docs/v4/error-management/two-error-types).

`try ... with` компилируется в обработку типизированной ошибки Effect; на цели Go — в восстановление причины, с которой паникует упавшее вычисление. JavaScript `try/catch`, который охватывает только построение значения Effect, не выполняет этот контракт.

## Сервисы и классы типов

| Механизм | Как выбирается реализация | Для чего нужен |
| - | - | - |
| Класс типов | Анализатор типов выбирает экземпляр класса и передаёт словарь его методов | `Eq`, `Show`, `Functor` и другие операции над типами |
| Сервис | Реализация предоставляется для конкретного вычисления | База данных, HTTP, логирование, тестовое окружение |
| Layer | Среда выполнения строит сервисы из зависимостей | Инициализация, получение ресурсов и построение окружения |

Чистая операция `show user` не требует Effect Context. Подмена рабочего сервиса тестовым не меняет глобальный выбор экземпляра класса типов.

В прямом API `Users.get` — сгенерированная эффектная операция: её выполнение ищет сервис, поэтому у неё эффектная стрелка и требование `Users`. В реализации сервиса метод может возвращать `Effect`.

Идентичность сервисов и ошибок включает пакет и модуль; сервис — ключ времени выполнения `M.S`. Объявление сервиса перечисляет полные сигнатуры методов; компилятор генерирует операции и тип записи с реализацией:

```flick
service Time =
  now : Unit ->{} Float

time_impl : Time.Impl
let time_impl =
  { now = Clock.current_time_millis }

time_layer : Layer none none {Time}
let time_layer =
  Layer.succeed Time time_impl
```

`Clock.current_time_millis` — функция стандартной библиотеки, которая читает часы файбера. `Time.now` требует сервис `Time`. `Time.Impl` — запись операций с типами, как они объявлены; слой, которому нужен ресурс, получает его при построении (`Layer.effect`). Методы сервиса не становятся экземплярами классов типов. Подробности — в [Эффекты, ошибки и сервисы](../../reference/effects/#сервисы). [Сервисы Effect](https://effect.website/docs/v4/requirements-management/services).

## Предоставление окружения

Порядок параметров слоя — `Layer inputs errors outputs`. Например:

```text
users_live :
  Layer {Config} {ConnectError} {Users}
```

Блок `provide layer { ... }` устанавливает окружение до выполнения тела:

```flick
# type UserId = UserId String
# type alias User = { id : UserId; name : String }
# type error NotFound = NotFound UserId
# service Users =
#   get : UserId ->{; NotFound} User
# service Log =
#   info : String ->{} Unit
# service Config =
#   url : Unit ->{} String
# type error ConnectError = ConnectError
# users_live : Layer {Config} {ConnectError} {Users}
# let users_live = Layer.effect Users (task { from_result (Err ConnectError) })
# load_name : UserId ->{Users, Log; NotFound} String
# let load_name id = (Users.get id).name
#
application : UserId ->{Config, Log; NotFound, ConnectError} String
let application id =
  provide users_live {
    load_name id
  }
```

Если `load_name` требует `{Users, Log}` и допускает `{NotFound}`, после предоставления `users_live` остаются требования `{Config, Log}`, ошибки `{NotFound, ConnectError}` и тот же результат `String`.

Предоставление слоя убирает требования к обеспеченным сервисам, но добавляет зависимости и ошибки построения слоя. Если вместо специального блока используется обычная функция, ей нужно передать `task { ... }`. Иначе строгий порядок вычисления запустит тело ещё до установки окружения. [Слои Effect](https://effect.website/docs/v4/requirements-management/layers).

## Ресурсы

`scope` сочетает финализацию во время выполнения со статическим запретом использовать ресурс за пределами его области. Получение ресурса регистрирует завершающее действие, или финализатор, у лексического владельца. В безопасном API ресурсов, привязанных к области, **нет раннего закрытия**. Отдельные привязки с ручным управлением ресурсом этой гарантии не получают. Библиотечный владелец, который заменяет или вытесняет свои ресурсы (`ScopedRef`, `Resource`, `ScopedCache`), отдаёт значение только в аренду и освобождает его, когда аренд не осталось. Благодаря этому ресурсам не нужны ни линейные типы, ни отражение состояний «открыт» и «закрыт» в типе.

Свежие регионы и транзитивный учёт захватов не позволяют получить через безопасный API пригодное к использованию право доступа к ресурсу уже завершённого региона. Нативный Cause может физически удерживать закрытый внешний объект, но безопасная оболочка не раскрывает его. Аффинной или линейной системы типов нет. На цели JS финализацию выполняет нативный [Effect Scope](https://effect.website/docs/v4/resource-management/scope); статическая проверка принадлежит анализатору типов, а двухфазное закрытие владельца — адаптеру среды выполнения ([Адаптер среды выполнения](../../reference/runtime/#владельцы-и-области)).

Финализатор ресурса, привязанного к области, имеет пустую строку ожидаемых ошибок; его сбой сохраняется как дефект в полном исходе. `Resource.bracket`, напротив, допускает отдельную типизированную ошибку освобождения и добавляет её к строке ошибок. Это разные операции. Первичная ошибка и сбои освобождения сохраняются по нативному контракту Cause. Освобождение нельзя заменить обычным JS `finally`, который теряет исходный сбой.

## Конкурентность

Основной API — `parallel` и `parallel_all`, которые структурированно выполняют холодные `Eff`: сами операции управляют временем жизни своих веток. При сбое они отменяют активные ветки и ждут их завершения. `parallel_all` требует конечный положительный целый предел конкурентности; успешные результаты следуют порядку входных значений.

Несколько уже наблюдённых сбоев сохраняются в нативном Cause; API не обещает собрать все ошибки, которые могли бы возникнуть в дальнейшем. `parallel_results` отдельно накапливает выбранные типизированные ошибки как `Result`, а `parallel_exits` — непрозрачные полные исходы. Дефекты и внешнее прерывание не маскируются обычным успешным списком.

`Fiber.spawn` требует явно указать лексического владельца и супервизор — обработчик исходов фоновой задачи. `Fiber.join` ожидает конкретный файбер и восстанавливает его сбой. Ошибки дочерней задачи не добавляются автоматически в строку ошибок родителя. Поэтому супервизор обязателен, даже если вызывающий код может проигнорировать дескриптор файбера. В безопасном API нет запуска неограниченно живущих фоновых файберов с локальными захватами. [Файберы Effect](https://effect.website/docs/v4/concurrency/fibers).

## Граница языкового ядра

Повторные попытки, расписания, потоки, очереди, кеш, трассировка и HTTP — часть типизированной стандартной библиотеки ([Покрытие Effect](../../reference/effect-surface/)). Для повторного запуска и конкурентного выполнения она принимает описания вычислений. Специального синтаксиса для них нет.

`deriving Schema` и кодеки внешних форматов входят в язык. Параметрические типы, рекурсия, уточнения, политики полей и эффектные преобразования разобраны в [Schema и стандартные типы данных](../07-schema/).

Сервисы и `provide` не являются универсальными обработчиками алгебраических эффектов, которые захватывают продолжение и могут возобновлять его несколько раз: операции языка опираются на конкретные механизмы Effect, а на цели Go — на такие же механизмы `runtime-go/flickrt`.

## Контракты выполнения и времени жизни

Правила ниже описывают поведение программы, которое не зависит от способа генерации кода и от цели. Более сложные режимы — отдельные библиотечные операции.

| Область | Контракт |
| - | - |
| Типизированные ошибки | Номинальные ошибки с данными без зависимостей от регионов; `e` описывает выбранную ошибку для обычной обработки, поэтому не всякий необработанный Fail — значение `Errors e` |
| Дефекты и прерывания | Сохраняются вне `e`; доступны через непрозрачные Failure/Exit; обычный обработчик не перехватывает все виды сбоев |
| Предоставление окружения | Сначала строится Layer, затем выполняется тело; конфликт — ошибка, если не задана явная замена |
| Повторное использование слоёв | Один и тот же Layer используется повторно внутри одной сборки; между независимыми provide нужна явная мемоизация с владельцем |
| Область ресурсов | Свежие регионы и учёт захватов; сначала завершаются дочерние задачи, затем ресурсы освобождаются в обратном порядке; закрытие может ждать непрерываемую или внешнюю работу |
| Ошибки освобождения | Финализатор области не имеет ожидаемых ошибок; типизированная ошибка освобождения доступна через `Resource.bracket`; ошибки динамически зарегистрированных финализаторов не объединяются в `e` |
| Параллельное выполнение | При сбое активные ветки отменяются; операция ждёт освобождения ресурсов; результаты следуют порядку входа; собираются не все возможные сбои |
| Запуск фоновой задачи | Явный владелец и обязательный супервизор; join восстанавливает сбой; успех родителя не означает успех фоновых задач |
| Гонки и таймауты | Нативный выбор победителя и ожидание проигравших веток; нет жёсткого предельного времени и автоматического добавления сбоев проигравших |

Среда выполнения Go (`runtime-go/flickrt`) реализует ту же семантику Cause и Layer: упавшее вычисление несёт причину из типизированных сбоев, дефектов и прерываний, которую `try`, `Failure` и средство запуска обрабатывают по правилам ниже, а слои строятся и разделяются через таблицу мемоизации так же, как на цели JS ([генерация кода, цель Go](../../reference/codegen/#go-target)).

## Ошибка как данные и ошибка выполнения

Чистая функция может вернуть `Result`, не запуская Effect. Порядок параметров `Result error value` во Flick удобен для типов высших порядков (HKT). Во время выполнения используется нативный `Result.Result<A, E>` из [Effect v4](https://effect.website/docs/v4/data-types/result), поэтому проекция в TypeScript переставляет параметры. Параметр `error` здесь имеет кинд `Type`, а строка ошибок эффектного вычисления — кинд `ErrorRow`. Это разные позиции.

```text
parse_config :
  String -> Result ParseError Config

fetch_config :
  Url ->{Http; NetworkError} Config
```

`Result` переводится в типизированную ошибку выполнения функцией прелюдии `from_result : Result (Errors e) a ->{; e} a`. Для `Result NotFound User` используется строка из одного элемента `{NotFound}`. В случае `Result String a` сначала нужно преобразовать строку в объявленную номинальную ошибку. Операция не перехватывает дефекты или прерывания. Обычный `try ... with` обрабатывает ожидаемые ошибки, а отдельный API `Exit`/`Failure` — полный исход. [Разделение ошибок Effect](https://effect.website/docs/v4/error-management/two-error-types).

```flick
# type UserId = UserId String
# type alias User = { id : UserId; name : String }
# service Users =
#   get : UserId ->{; NotFound} User
#
type error NotFound = NotFound UserId
type error DbUnavailable = DbUnavailable String

find_user :
  UserId ->{Users; NotFound, DbUnavailable} User
# let find_user id = Users.get id

find_optional :
  UserId ->{Users; DbUnavailable} Option User
let find_optional id =
  try
    Some (find_user id)
  with
  | NotFound _ -> None
```

### Сложный Cause: что обещает строка ошибок

`e` описывает **ошибку, доступную обычному типизированному обработчику**. Полный нативный Cause может содержать вторичные данные ошибок вне остаточной `e`. Безопасный API не предоставляет функцию `Failure e -> List (Errors e)`, которая возвращала бы все его Fail.

Обработка следует Effect 4.1.2, где Cause — плоский список причин `Fail`, `Die` и `Interrupt` ([Cause](https://effect.website/docs/v4/data-types/cause)): `try` обрабатывает первый `Fail`; причина, где есть ещё и `Die`, не обрабатывается, а её сбои становятся дефектами; причина из одних прерываний ошибки не содержит; без подходящей ветки исходная причина распространяется без изменений. Таблица случаев — в [Адаптер среды выполнения, «Исходы»](../../reference/runtime/#исходы). В частности, для `Fail(B), Fail(A)` с веткой только для `A` обработчик не вызывается: нативный `catchTag(A)` сужает E в сигнатуре TypeScript, хотя вторичный A может остаться в полном Cause. Поэтому не всякий необработанный `Fail` можно считать значением `Errors e`.

Flick сохраняет нативную обработку и непрозрачный `RawCause`: обработчик соответствует выбранной ожидаемой ошибке, а повторное распространение сохраняет нативный Cause. Полностью типизированный Cause не позволил бы частичным обработчикам сужать `e`.

`Exit e a`, `Failure e` и `RawCause` — непрозрачные типы. Внутри сохраняется нативное представление; типизированный и диагностический интерфейсы разделены.

```text
Failure.primary :
  Failure e -> Option (Errors e)

Failure.raw_cause :
  Failure e -> RawCause

Failure.inspect :
  Failure e ->{} CauseReport

RawCause.inspect :
  RawCause ->{} CauseReport

Failure.rethrow :
  Failure e ->{; e} a
```

Успешный `Exit` содержит `a` и сохраняет захваты этого значения. `Failure.primary` выдаёт только выбранную типизированную ошибку; `rethrow` восстанавливает исходный Cause с той же `e` либо с её допустимым расширением. Безопасного преобразования `RawCause -> Exit e a` для произвольной `e` нет. Эти операции не могут стирать известные захваты. Данные типизированных ошибок не зависят от регионов; произвольные дефекты внешнего кода остаются запечатанными.

Безопасный `RawCause` **не раскрывает исходный `JsValue`**. `CauseReport` содержит инертные сведения о видах причин, безопасно полученные теги и текст, а также метаданные прерывания. Инспекция не вызывает пользовательские геттеры, `toString` или `toJSON`; вместо неподдерживаемых данных она показывает обозначение-заполнитель. Доступ к исходному графу JS-объектов возможен только через явный небезопасный FFI.

Агрегатная ошибка для `parallel` (`CompositeError`) изменила бы прикладной API: обработка `NotFound` не равна обработке агрегата, внутри которого есть NotFound. Вместо неё исходы всех веток дают `parallel_results` и `parallel_exits`.

Успешная обработка может поглотить причину и связанные с ней вторичные диагностические сведения. Если они нужны в логах, причину нужно наблюдать до обработки. Правило выбора ошибки из списка не позволяет обработчику произвольно отключить уже запрошенную отмену файбера: состоянием прерывания управляет среда выполнения.

<div id="lifetime-и-sharing-при-provide"></div>

## Время жизни и повторное использование сервисов при provide

`provide` сначала полностью строит Layer и лишь затем выполняет тело. При ошибке построения тело не запускается. Реализации сервисов, привязанные к области, принадлежат лексическому владельцу provide. После выхода восстанавливается внешнее окружение и выполняется двухфазное закрытие. Захваты сервиса, записи с реализацией, замыкания, `Eff`, UI или кодека сохраняются в интерфейсах и не могут пережить владельца. Работа, которую владелец держит до закрытия своей области, выполняется с сервисами места запуска, поэтому они должны пережить этого владельца (`Fiber.Provided`, `FLICK-G003`).

`task { service_call () }` ищет требуемый сервис при запуске в текущем окружении. Если задача уже захватила конкретный экземпляр сервиса, она сохраняет зависимость от его времени жизни. Финализатор получает контекст, сохранённый при регистрации, а не случайный сервис из окружения, в котором позже началось закрытие.

Один и тот же Layer используется повторно внутри одной сборки графа, а `provide`, вложенный в тело другого, повторно использует внешнюю сборку того же слоя. Независимые `provide`, стоящие рядом, строят независимые экземпляры; глобального единственного экземпляра нет. Для длительного совместного использования построенных сервисов нужна явная мемоизация с владельцем. Две реализации с одним ключом сервиса в графе считаются ошибкой (`FLICK-E004`), если не использован `Layer.override`. Это правило опирается на [мемоизацию слоёв Effect](https://effect.website/docs/v4/requirements-management/layer-memoization), а анализатор типов дополнительно контролирует время жизни.

## Финализация и границы ресурса

```flick
# import File exposing (File, Path, FileSystem, OpenError, ReadError)
#
read_config :
  Path ->{FileSystem; OpenError, ReadError} String
let read_config path =
  scope {
    let file = File.open_scoped path
    File.read_all file
  }
```

`File.open_scoped` требует лексический `Scope s`, который предоставляет `scope`. После успешного получения ресурса регистрируется финализатор. Вычисление возвращает итог, только когда завершатся все дочерние задачи области, а затем будут освобождены ресурсы. Финализаторы ресурсов выполняются в обратном порядке регистрации, то есть по правилу LIFO. Дочерние задачи и ресурсы — разные группы: ресурс, полученный после запуска дочерней задачи, всё равно освобождается после её завершения. [Scope API](https://effect.website/docs/v4/api/effect/Scope).

`Resource.acquire_release` требует освобождения без ожидаемых ошибок; `Resource.bracket` допускает типизированную ошибку освобождения. Дефекты освобождения сохраняются в полном исходе; проверка типов не доказывает, что каждый внешний ресурс удастся закрыть.

Для безопасного API ресурсов области компилятор проверяет все способы прямого и косвенного выхода ресурса за её пределы: результат, замыкания, задачи, контейнеры, экзистенциальные обёртки, запись во внешнее состояние и передачу в FFI, который удерживает аргумент. Ресурс можно использовать многократно внутри своей области, если его API это разрешает. Статическая проверка времени жизни сама по себе не доказывает отсутствие гонок или безопасность конкурентного использования дескриптора.

<div id="статические-regions-и-захваты"></div>

### Статические регионы и захваты

Каждый `scope s { ... }` создаёт свежий регион `s` и его владельца в среде выполнения. В `scope { ... }` имя региона выводится и остаётся скрытым. Дескриптор ресурса области имеет тип вроде `File s`. Компилятор передаёт владельца лексически: один обычный поиск в Context не подходит, потому что во вложенной области он мог бы выбрать другой scope.

```flick fail
# import File exposing (File, Path, FileSystem, OpenError, ReadError)
#
bad_deferred :
  Path ->{FileSystem; OpenError} Eff {FileSystem} {ReadError} String
let bad_deferred path =
  scope {
    let file = File.open_scoped path
    task { File.read_all file }
  }
```

Это ошибка (`FLICK-G001`): задача захватывает `file`, а её пытаются вернуть после закрытия области. Обычный тип `Eff {FileSystem} {ReadError} String` не показывает эту зависимость, поэтому одной проверки `s` в типе результата недостаточно.

Чтобы вернуть задачу, нужно перенести получение ресурса внутрь отложенного выполнения:

```flick
# import File exposing (File, Path, FileSystem, OpenError, ReadError)
#
deferred_read :
  Path -> Eff {FileSystem} {OpenError, ReadError} String
let deferred_read path =
  task {
    scope {
      let file = File.open_scoped path
      File.read_all file
    }
  }
```

Теперь каждый `await` получает собственную область и ресурс. Возвращаемая строка может пережить файл.

Та же проверка действует для обычной функции обратного вызова:

```flick fail
# import File exposing (File, Path, FileSystem, OpenError, ReadError)
#
bad_callback :
  Path ->{FileSystem; OpenError} (Unit ->{FileSystem; ReadError} String)
let bad_callback path =
  scope {
    let file = File.open_scoped path
    fun () -> File.read_all file
  }
```

Такую функцию тоже нельзя вернуть. Полиморфизм высших рангов с `forall s` препятствует прямому выходу `File s` за пределы области. Но без дополнительного учёта захватов он не доказывает, что ресурс не захвачен функцией обратного вызова, задачей или параметрическим контейнером.

| Путь утечки | Требование проверки типов |
| - | - |
| Прямой результат или вложенная запись/ADT | Регион не переживает владельца; зависимость распространяется транзитивно |
| Замыкание или Eff | Захваты сохраняются при передаче, обобщении и через интерфейсы модулей |
| Экзистенциальная или непрозрачная упаковка | Номинальная идентичность и скрытие типа не стирают время жизни |
| Запись во внешний Ref или кеш | Время жизни хранилища не превышает допустимое время жизни записываемого значения |
| Ошибка, Exit или диагностическое значение | Проверяются все выходы, включая данные ошибок; ошибочный исход не позволяет обойти ограничения времени жизни |
| Внешний вызов | Для аргумента, привязанного к региону, нужен проверенный контракт удержания |

Захваты — отдельное статическое свойство, а не третья строка эффекта. Запись `T^{s, t}` задаёт конкретные регионы, `T^c` — строку с киндом CaptureRow, а `T^(c + d)` — их объединение. Явная аннотация захватов задаёт верхнюю границу полного набора захватов, через которые значение может получить доступ к ресурсам. Известные из T зависимости обязаны входить в эту границу. Её можно расширять, но нельзя небезопасно сужать.

Тип T без аннотации не добавляет скрытых захватов и не стирает зависимости, уже выраженные в самом типе: File s и List (File s) зависят от s. Само упоминание s во входном типе функции не означает, что её замыкание удерживает ресурс s. Компилятор отслеживает достижимость прав доступа к ресурсу, а не все имена в сигнатуре.

```text
read_later :
  forall s.
  File s -> (Eff {FileSystem} {ReadError} String)^{s}

scoped_callback :
  forall s.
  File s -> (Unit ->{FileSystem; ReadError} String)^{s}
```

Это интерфейсные сигнатуры. Локальные захваты выводятся; публичные сигнатуры и `.iface` сохраняют их. Захваты сохраняются при частичном применении, в записях, непрозрачных и экзистенциальных типах, словарях и `Unknown^{s}`. Чтобы передать функцию обратного вызова через параметрический API высшего порядка, нужен контракт, полиморфный по захватам, как у `List.map_effect`. В коротких примерах с областями имя региона опущено в синтаксисе, но компилятор продолжает его учитывать. Изменяемые хранилища инвариантны: более долгоживущий Ref или кеш не может получить право доступа к ресурсу с более коротким временем жизни. Полные правила — в [Регионы и захваты](../../reference/regions/).

<div id="объём-сильного-контракта"></div>

### Гарантии и ограничения

| Свойство | Контракт |
| - | - |
| Многократное использование дескриптора в живой области | Разрешено, если API ресурса допускает это |
| Раннее закрытие | Отсутствует в безопасном API ресурсов области |
| Полная линейность | Не вводится; время жизни проверяется через регионы и захваты |
| Конкурентный доступ | Привязка объявляет операции, безопасные для совместного использования, либо сериализует доступ; время жизни не доказывает отсутствие гонок |
| Освобождение ресурсов | Среда выполнения выполняет финализаторы; компилятор не доказывает, что внешнее закрытие физически завершилось успешно |
| Типизированные ошибки | Данные не зависят от регионов даже при локальной обработке |
| Нативный Cause | Живые данные внешних объектов запечатаны; безопасно доступен только инертный отчёт |
| Непроверенный JS | Требует явно объявленного доверенного или небезопасного контракта |

<div id="владелец-fibers-и-порядок-освобождения"></div>

### Владелец файберов и порядок освобождения

Задача может захватывать ресурсы своей области и более долгоживущих областей. Передать её более долгоживущему владельцу можно, только если у неё нет захватов с более коротким временем жизни (`Fiber.Outlives`, `FLICK-G003`). У подписки или функции обратного вызова, которую удерживает внешняя библиотека, тоже должен быть проверяемый владелец.

При закрытии области обязателен следующий порядок: **запретить новую работу → запросить отмену дочерних задач → дождаться конечного состояния каждой → дождаться внешней работы → выполнить финализаторы ресурсов в порядке LIFO → вернуть итоговый Exit**. Если дочерняя задача не завершает непрерываемый участок, закрытие ждёт. Освобождать ресурс, которым продолжает пользоваться дочерняя задача, запрещено; таймаут не отменяет это правило.

Конечное состояние файбера ещё не доказывает, что внешняя операция Promise остановилась. Асинхронный FFI с захватами ресурсов области обязан перед завершением отмены дождаться подтверждения остановки либо фактического окончания внешней работы. Одного `AbortSignal` недостаточно. Если операция не отменяется, адаптер ждёт её окончания. Отсоединить её от текущего владельца можно, только если у неё нет захватов с более коротким временем жизни или владение явно и безопасно передано.

Области, которая автоматически добавляет ошибки дочерних задач в строку ошибок тела (nursery), нет. Структурированные конкурентные операции владеют своими ветками; фоновый файбер, привязанный к области, отменяется при закрытии владельца. Ошибки фоновой работы всегда наблюдает явно переданный супервизор, а `join` дополнительно восстанавливает сбой для ожидающего.

## Конкурентные операции с разными контрактами

```flick
# type UserId = UserId String
# type alias User = { id : UserId; name : String }
# type error NotFound = NotFound UserId
# service Users =
#   get : UserId ->{; NotFound} User
#
load_pair : UserId -> UserId ->{Users; NotFound} (User, User)
let load_pair first_id second_id =
  parallel
    (task { Users.get first_id })
    (task { Users.get second_id })
```

Для `parallel` порядок результатов совпадает с порядком аргументов. При сбое операция прекращает запуск новой работы, запрашивает отмену остальных активных веток и ждёт их завершения. При этом собираются наблюдённые причины, кроме Interrupt, в том числе некоторые сбои останавливаемых веток. Получение всех возможных будущих ошибок не гарантируется.

Операция не закрывает внешний `Scope`: зарегистрированные в нём ресурсы живут до его закрытия. Если ресурс нужно закрыть вместе с веткой, она создаёт собственный `scope`. Освобождение, защищённое от прерывания, может задержать завершение. Для `parallel_all` обязателен конечный положительный целый предел конкурентности, а результаты сохраняют порядок входных значений.

`parallel_results` переводит выбранные ожидаемые ошибки в `Result` и позволяет дождаться остальных веток. Дефекты и внешнее прерывание по-прежнему управляют выполнением, а не становятся значениями списка. `parallel_exits` возвращает непрозрачные полные исходы завершённых веток; внешняя отмена группы всё равно распространяется. Безопасный API не обещает собрать все потенциальные ошибки операции, которая отменяет работу при первом сбое.

Привязка к scope задаёт время жизни, а `join` ожидает конкретный результат. Структурированные конкурентные операции выполняют ветки в отдельной группе дочерних задач, отменяя и ожидая все активные ветки, потому что `joinAll` из Effect при ошибке прекращает ожидание, но сам не прерывает остальные файберы.

<div id="конкурентность-три-модели"></div>

### Дочерние задачи под надзором

`Fiber.spawn owner supervisor task` регистрирует дочернюю задачу у owner; task и supervisor не могут захватывать более короткоживущий регион. Потеря дескриптора файбера не приводит к потере ошибки: супервизор получает полный `Failure`, который отличает прерывание закрывающимся владельцем. Дефект супервизора передаётся корневому обработчику сбоев среды выполнения и завершает запуск с ошибкой. Долгоживущая работа требует явно указанного более долгоживущего владельца. Безопасного запуска неограниченно живущего фонового файбера с короткими захватами нет. Сигнатура и правила — в [Регионы и захваты, «Дочерние файберы»](../../reference/regions/#дочерние-файберы).

Привязка времени жизни к области не означает ожидания естественного успешного завершения дочерних задач. Обычный файбер области останавливается при её закрытии; его ошибка не присоединяется к результату тела. Функция обратного вызова с полиморфизмом высших рангов помогает ограничить право доступа к области, но сама по себе не учитывает ошибки дочерних задач и не доказывает, что ресурс не выйдет за пределы области.

<div id="race-и-timeout"></div>

### Гонки и таймауты

`race_success` возвращает первый успех, `race_first` — первое завершение; проигравшие ветки прерываются и ожидаются, выбранный результат сохраняется. Их Exit не добавляются к результату, поэтому дефект освобождения в проигравшей ветке не становится ошибкой победителя: контракт `parallel` на гонку не переносится.

`timeout` и `timeout_option` используют нативный выбор между вычислением и таймером, затем прерывают и ожидают проигравшие ветки. `timeout` добавляет `TimeoutError`; `timeout_option` представляет именно таймаут через `None`, сохраняя другие ошибки. Строгой гарантии по фактически прошедшему времени нет: синхронный JS, непрерываемый участок и освобождение ресурсов могут задержать возврат, а таймаут никогда не возвращает результат, пока дочерние задачи области ещё работают. Если победитель завершается синхронно, запуск всех веток не гарантируется. При одновременной готовности веток победитель может меняться.

**Контракт среды выполнения:** нативная обработка типизированных ошибок, непрозрачные Failure/Exit/RawCause и инертная диагностика; свежие регионы и учёт захватов; двухфазное закрытие scope с обязательным ожиданием остановки внешней работы; структурированные конкурентные операции и наблюдение за фоновыми задачами области; нативные гонки и таймауты. Оптимизации обязаны сохранять эти гарантии, исходный Cause при повторном распространении, контекст сервисов и выполнение финализаторов.
