**Принято для первой версии:** библиотечные DSL для SQL/UI/CLI с ML-синтаксисом `sql params { ... }`, `ui { ... }` и `cli "name" { ... }`; реализация для PostgreSQL, адаптер React и Effect CLI. Все они используют общее ядро типизации: строки, метки, конечные индексы, HKT и MPTC/FD. Примеры ниже написаны на Flick, а не на Selda или Droplet.

## Что показывают Selda и Droplet

[Selda](https://github.com/Kamirus/purescript-selda) строит SQL через чистую монаду состояния и типизированные выражения колонок; [Droplet](https://github.com/easafe/purescript-droplet) ближе к SQL-комбинаторам, где тип AST содержит части запроса, поля и проекцию. Обе библиотеки связывают структуру запроса с типом результата через строки, многопараметрические классы и функциональные зависимости.

| Задача | Наблюдение по исходникам | Решение для Flick |
| - | - | - |
| Создание запроса | У Selda `Query s a` оборачивает чистый `State GenState a` | AST строится чисто; обращение к БД — отдельный эффектный вызов |
| Поля таблицы и результата | Строка полей преобразуется в запись SQL-выражений, затем в запись значений | Универсальные операции над строками; пользователь работает с обычными полями |
| LEFT JOIN | В обеих библиотеках правая сторона допускает NULL без удвоения Maybe | Допустимость NULL — отдельный индекс SQL-выражения; на выходе получается `Option a` |
| Вывод проекции | У Droplet `ToQuery q projection` имеет зависимость `q -> projection` | Тип результата однозначно вычисляется из завершённого запроса |
| Скрытие большого типа | Внутренний `buildQuery` Droplet стирает AST в SQL и параметры, сохраняя проекцию | Публичный непрозрачный Query с короткой сигнатурой; тип всего AST писать не нужно |
| Разбор частных случаев | В исходниках есть упорядоченные цепочки `else instance` | Прямой перенос нарушает правило непересечения; нужны непересекающиеся индексы и детерминированные операции над строками и типами |

Проверены исходники Selda на коммите `a81f47f9054e9ea893d5ef79586be70068462249`: [Query.Type](https://github.com/Kamirus/purescript-selda/blob/a81f47f9054e9ea893d5ef79586be70068462249/src/Selda/Query/Type.purs), [FromTable и JOIN с возможным NULL](https://github.com/Kamirus/purescript-selda/blob/a81f47f9054e9ea893d5ef79586be70068462249/src/Selda/Query.purs#L197-L302). Для Droplet — коммит `990dd8ce078436bdb6c9ffe280dfdc97c516802b`: [ToQuery](https://github.com/easafe/purescript-droplet/blob/990dd8ce078436bdb6c9ffe280dfdc97c516802b/src/Droplet/Language/Internal/Translate.purs#L99-L145), [цепочки экземпляров класса для типов, допускающих NULL](https://github.com/easafe/purescript-droplet/blob/990dd8ce078436bdb6c9ffe280dfdc97c516802b/src/Droplet/Language/Internal/Syntax.purs#L1507-L1516), [внутренний buildQuery](https://github.com/easafe/purescript-droplet/blob/990dd8ce078436bdb6c9ffe280dfdc97c516802b/src/Droplet/Language/Internal/Translate.purs#L1161-L1172).

Для поддержки SQL выбраны ограниченные MPTC/FD и примитивы строк, которыми управляет компилятор. Непересекающиеся индексы и типизированный AST заменяют случаи, где исходные PureScript-библиотеки используют упорядоченные цепочки экземпляров класса. Буквальный перенос таких экземпляров не гарантируется; исходные правила согласованности сохраняются.

## Минимальные возможности на уровне типов

| Механизм первой версии | Что выражает | Граница |
| - | - | - |
| Type, FieldRow = Row Type, Symbol, Constraint, Region, CaptureRow | Данные, поля, ограничения и время жизни | Строки разных киндов не смешиваются |
| Пользовательские конечные кинды | Замкнутые индексы допустимости NULL и фаз | Только конечный набор нульарных конструкторов; без общего механизма использования значений на уровне типов и зависимых значений |
| Точные структурные записи и полиморфизм строк | Известные поля и открытый хвост | Нет неявного подтипирования по ширине |
| HasField, Lacks, Project, Remove, UnionDisjoint | Доступ к полям, проекция, отсутствие и коллизии полей | Детерминированные примитивы, которыми управляет компилятор |
| Map по строке и канонические метки | Преобразование типа каждого поля конструктором Type → Type | Не общий язык семейств типов |
| MPTC, суперклассы, FD | Связи AST, проекции и параметров | Строгое покрытие, непересечение и завершаемость |
| Непрозрачный AST с индексами | Область видимости, фаза, допустимость NULL и проверенный Query | Нельзя обойти через публичный конструктор |
| Функции обратного вызова с полиморфизмом высших рангов и захваты | Новые изолированные области DSL и переданные функции | Явные forall; происхождение значений сохраняется |
| Диагностические ограничения | Ошибка с меткой и диапазоном исходного текста | Не произвольный JS во время компиляции |

HKT сам по себе не вычисляет, какие поля появятся после JOIN. Полиморфизм высших рангов сам по себе не преобразует запись. Нужны именно операции над структурой типов.

Пользовательский конечный кинд объявляется, например, `kind Nullability = NonNull | Nullable`; его конструкторы — только индексы на уровне типов. Такие объявления не создают значений при выполнении и не вводят общего механизма использования значений на уровне типов. Пользовательские открытые и закрытые функции над типами, ассоциированные типы, цепочки экземпляров класса, импредикативность и зависимые типы не входят в первую версию. Если отношение не проходит строгое покрытие, библиотека переносит вычисляемую проекцию в параметр типизированного AST или использует фиксированный примитив строк, а не включает UndecidableInstances.

### Три способа реализовать вычисления над типами

| Подход | Выгода | Цена |
| - | - | - |
| Специальная проверка SQL в компиляторе | Прямой способ получить понятную диагностику SQL | Компилятор знает предметную область; новым DSL нужны новые специальные правила |
| Библиотечные отношения на MPTC/FD и примитивах строк | Расширение обычными библиотеками; тот же механизм нужен Schema и UI | Нужны завершаемость, согласованность и понятная диагностика |
| Закрытые функции над типами | Удобная запись преобразований проекции, значений по умолчанию и допустимости NULL | Отдельный нормализатор и правила редукции равенств; открытые входы могут оставаться невычисленными |

Выбран второй путь: общие примитивы строк и библиотечные отношения. Преобразователь SQL-синтаксиса переводит его в типизированные конструкторы и прикрепляет диапазоны исходного текста; общая проверка типов не получает специальных правил семантики PostgreSQL. Закрытые функции над типами исключены из первой версии.

Нормализация кешируется и имеет явные пределы: по умолчанию 100 000 шагов решателя на проверяемое определение и глубина 256 ограничений классов. Настройка сборки может повысить предел; при превышении компилятор выдаёт диагностику с цепочкой ограничений. Лимит не заменяет правила завершаемости и не позволяет принять непроверенный код. Вычисления на уровне типов не запускают произвольный JS и не обращаются к сети или БД.

## SQL: короткая сигнатура, полный вывод результата

Публичный API использует разные непрозрачные типы:

- `Sql.Template dialect params result` — план формы запроса с именованными параметрами, которым ещё не заданы значения.

- `Sql.Query dialect result` — запрос со связанными значениями параметров.

- Внутренние фрагменты и выражения — промежуточные типы с индексами области видимости и фазы; непосредственно выполнить их нельзя.

`Template` не гарантирует PREPARE на сервере: это отдельная оптимизация драйвера. При завершении построения запроса проверяются все ссылки и части запроса, после чего большой тип AST скрывается. Правило полной сигнатуры над каждой именованной функцией сохраняется, а публичный тип запроса не требует `_`.

Допустим, описаны таблицы Users и Accounts. `Users.id` и `Accounts.user_id` имеют тип UserId, `Users.name` — String, а исходный `Accounts.balance` имеет тип BigDecimal и не допускает NULL.

```flick
type alias BalanceRow =
  {
    name : String
    balance : Option BigDecimal
  }

balances :
  Sql.Template Pg { user_id : UserId } BalanceRow
let balances =
  sql params {
    from user in Users
    left_join account in Accounts
      on account.user_id == user.id
    where user.id == params.user_id
    select {
      name = user.name
      balance = account.balance
    }
  }

load_balances :
  UserId ->{Database; EncodeError, DbError, DecodeError} List BalanceRow
let load_balances user_id =
  let query = Sql.bind balances { user_id = user_id }
  Database.query query
```

`params` — имя, связывающее параметры в SQL-грамматике; его поля выводятся из ожидаемого Template. `Sql.bind` чисто связывает инертные значения, не выполняя I/O. В первой версии кодеки параметров и ответов сертифицированы как чистые; их ожидаемые ошибки не теряются. `Database.query` имеет контракт `Sql.Query Pg a ->{Database; EncodeError, DbError, DecodeError} List a`: кодирует параметры, выполняет запрос и проверяет ответ. Дополнительные эффектные операции с результатом выполняются после запроса обычным эффектным кодом; SQL-кодеки, которым нужны сервисы, отложены.

Тип balance становится `Option BigDecimal` именно из-за LEFT JOIN. Если заменить это соединение на INNER JOIN, оно больше не будет причиной возможного NULL, но колонка, которая допускала NULL изначально, продолжит его допускать. Повторный LEFT JOIN не должен давать вложенные `Option (Option a)` лишь из-за двух одинаковых причин отсутствия.

Вызов `load_balances` — обычный прямой эффектный вызов. Чтобы отложить его, используют:

```flick
deferred_balances :
  UserId -> Eff {Database} {EncodeError, DbError, DecodeError} (List BalanceRow)
let deferred_balances user_id =
  task { load_balances user_id }
```

`sql params { ... }` строит чистый AST; без синтаксического сахара доступны те же библиотечные комбинаторы. Обычный let не связывает произвольную монаду. Обобщённая do-нотация в первую версию не входит.

Блок `sql params { … }` состоит из частей запроса — по одной на строку или через `;`; продолжение части пишется с большим отступом. Необязательное имя после `sql` связывает параметры запроса. `from x in T`, `join x in T` и `left_join x in T` вводят псевдоним; `on e` уточняет предыдущее соединение и может стоять на следующей строке. Остальные части начинаются со слова, за которым следуют выражения через запятую: `where`, `group_by`, `having`, `order_by`, `limit`, `offset`, `select`, `union`, `union_all`, `insert_into`, `values`, `update`, `set`, `delete_from`, `returning`. Внутри блока эти слова завершают применение функции, поэтому новая часть может начинаться без разделителя. Синтаксический анализатор фиксирует только эту форму; типы, области видимости, фазы и диалект проверяются при преобразовании SQL в типизированное представление.

### Что проверяется в SQL

| Проверка | Пример отклоняемой программы |
| - | - |
| Поля и типы колонок | `user.nmae`; сравнение UserId с Date |
| Области видимости и псевдонимы | Ссылка на псевдоним соседнего завершённого запроса; неоднозначное неквалифицированное имя |
| Проекция | Два результата с одним именем без явной политики переименования |
| JOIN с возможным NULL | Попытка получить обычный BigDecimal из balance, допускающего NULL |
| Фазы и агрегации | Неагрегированное поле в SELECT агрегатного запроса без допустимой группировки |
| INSERT | Отсутствующее обязательное поле; значение неправильного типа; запись в поле, значение которого всегда генерирует БД |
| Диалект | Операция, которой нет в выбранной реализации диалекта |
| Параметры | Неизвестное имя параметра; неподходящий кодек |

Внутренний непрозрачный `Sql.Expr scope phase nullability sql_type` сохраняет индексы; его конструкторы принадлежат DSL. LEFT JOIN меняет допустимость NULL, group_by создаёт свидетельство группировки, а агрегатное выражение нельзя подставить в WHERE. DSL создаёт новые независимые области видимости псевдонимов; завершённый Query не выпускает локальные выражения. Первая версия поддерживает только некоррелированные подзапросы; внешняя корреляция и LATERAL вынесены за её пределы.

SQL использует свою трёхзначную логику. `==` внутри SQL-блока преобразуется в SQL-сравнение, а не в обычный `Eq` языка. WHERE сохраняет строки с SQL TRUE; SQL UNKNOWN не превращается автоматически в Bool языка Flick. Нужны отдельные `is_null`, `is_not_null` и сравнение на равенство с учётом NULL. У агрегатов тоже собственные правила: MAX по пустому набору может дать NULL, а у COUNT другой контракт.

### Данные и SQL-текст

Параметры и идентификаторы передаются по разным каналам. Драйвер получает отдельно SQL с местами для подстановки и массив пользовательских значений; эти значения не конкатенируются в SQL. Имена таблиц, псевдонимов и колонок берутся из метаданных или проверенного Identifier и корректно кодируются реализацией диалекта. String, полученная при выполнении, не превращается неявно в SQL-фрагмент.

Прямой SQL доступен через отдельный API с явной пометкой unsafe и заданным кодеком результата. Он не получает статические гарантии типизированного AST. Подстановка пользовательского имени таблицы в позицию значения не считается параметризацией.

### Граница Schema и SQL

Первый диалект — **PostgreSQL**. Метаданные таблицы явно задают типы SQL, допустимость NULL, ключи, generated/identity/default и связь с чистыми доменными кодеками и кодеками внешнего формата. Метаданные пишутся на Flick либо генерируются отдельным инструментом из миграций или схемы; обычная компиляция не подключается к БД. Доменная Schema не выводит ограничения SQL автоматически и не превращает любой уточняющий тип в CHECK.

| Часть SQL | Первая версия |
| - | - |
| SELECT/FROM/WHERE и явная проекция | Да |
| INNER JOIN и LEFT JOIN | Да |
| GROUP BY/HAVING, основные агрегаты | Да, с проверкой фаз |
| ORDER BY, LIMIT/OFFSET | Да |
| Некоррелированные подзапросы, EXISTS/IN | Да |
| UNION/UNION ALL | При совместимых проекциях |
| INSERT/UPDATE/DELETE и RETURNING | Да; обязательные поля, значения по умолчанию и генерируемые колонки проверяются |
| Коррелированные подзапросы/LATERAL, рекурсивные CTE, оконные функции | После первой версии |
| RIGHT/FULL JOIN, произвольные расширения, DSL для DDL/миграций | После первой версии |

За пределами безопасного набора операций доступен отдельно названный unsafe/raw API с явным декодировщиком результата.

SQL bigint отображается в BigInt, decimal — в BigDecimal; Number допустим только с явной проверкой диапазона и точности. SQL NULL — индекс выражения и Option на выходе; доменное значение Option языка Flick не подменяет этот индекс. Расхождение схемы БД с описанием и несовпадение ответа дают DecodeError, кодирование параметра — EncodeError, ошибки драйвера, сервера и ограничений БД — DbError с инертной диагностикой. Дефекты и прерывания сохраняют общий контракт среды выполнения.

Отмена не гарантирует откат уже выполненного SQL. Драйвер не возвращает соединение в пул до согласованного завершения обмена, закрытия или подтверждения полной остановки операций. Типы не доказывают актуальность БД, права, стоимость плана, изоляцию транзакций или число строк без отдельного контракта количества строк.

## UI eDSL: свойства, дочерние узлы и действия

Базовая модель — `Ui`: чистое описание интерфейса с отложенными обработчиками. Задача обработчика только изменяет атомы через `Atom.Write`; другие сервисы она предоставляет себе сама и свои ошибки обрабатывает сама, поэтому у `Ui` нет строк сервисов и ошибок. Построение UI не выполняет эти обработчики.

```flick
type alias SaveButtonProps c =
  {
    label : String
    disabled : Bool
    on_save : (Unit ->{Atom.Write;} Unit)^c
  }

save_button :
  SaveButtonProps c -> Ui^c
let save_button props =
  Ui.button
    {
      disabled = props.disabled
      on_click = Ui.Event.exhaust (fun _ ->
        task { props.on_save () }
      )
    }
    [Ui.text props.label]
```

`on_click` имеет непрозрачный тип `(Ui.Handler ClickSnapshot)^c`. Его конструктор принимает функцию, создающую холодный Eff, и явно выбранную политику конкурентного выполнения. В примере Exhaust игнорирует новые клики до завершения текущей задачи. Чистая `save_button` не выполняет `props.on_save` или Ref.get при рендеринге; состояние поступает через модель или свойства. Произвольные эффектные хуки внутри чистого рендеринга запрещены. Захваты свойств и обработчика сохраняются в Ui.

Это согласуется с требованием повторяемого рендеринга у [React](https://react.dev/reference/rules/components-and-hooks-must-be-pure), но проверка чистоты и времени жизни — контракт Flick.

### Синтаксис UI во Flick

`ui { ... }` — синтаксический сахар над теми же проверяемыми вызовами:

```flick
save_button :
  SaveButtonProps c -> Ui^c
let save_button props =
  ui {
    button
      {
        disabled = props.disabled
        on_click = Ui.Event.exhaust (fun _ ->
          task { props.on_save () }
        )
      }
      [text props.label]
  }
```

JSX `<...>` не добавляется в первую версию; `ui { ... }` и обычные функции Ui строят одно представление. Блок открывает имена модуля `Ui`: при разрешении имени сначала учитывается локальная привязка, затем имя из `Ui`, затем имена модуля. Применение значения `Ui.Component p` к свойствам, в том числе `props |> value`, означает `Ui.component value props`. Остальные значения и вызовы сохраняют обычные типы. Обе формы дают одно типизированное IR, сохраняя ML-синтаксис и общие проверки свойств и переданных функций. [Компоненты ReScript](https://rescript-lang.org/docs/react/components-and-props/) — пример типизированного интерфейса к React; синтаксис Flick выбран независимо.

Первый рендерер — **адаптер React**. Собственный механизм согласования дерева и DOM-рендерер, SSR, гидратация, React Server Components и полная модель хуков вынесены за первую версию. Адаптер сохраняет границы компонентов, key/ref и жизненный цикл React; оптимизатор не заменяет компонент произвольным прямым вызовом функции. Изменяемое состояние адаптера находится вне тела чистого компонента.

### Свойства и дочерние узлы

Свойства компонента — точная структурная запись. Отсутствующее обязательное поле, опечатка или неверный тип — ошибка. Разворачивание свойств объединяет непересекающиеся строки; перезапись возможна только через явное обновление. Необязательные поля и значения по умолчанию следуют общим правилам языка, а JS undefined появляется лишь в адаптере. Дочерние узлы передаются обычным аргументом выбранного типа. key/ref — отдельные метаданные рендерера, а не скрытые поля пользовательской записи свойств.

| Контракт дочерних узлов | Тип данных |
| - | - |
| Любое число узлов | `List Ui` |
| Ровно один узел | `Ui` |
| Необязательный узел | `Option Ui` |
| Именованные места | Запись с header/body/footer |
| Непустой набор вкладок | `NonEmpty Tab` |
| Элемент без содержимого | В API нет аргумента для дочерних узлов |

Если компонент должен принимать именно Tab, его тип нужно сохранять до сборки контейнера. После преобразования дочернего узла в общий Ui выяснять его происхождение слишком поздно. Обычная сигнатура также не доказывает уникальность key в динамическом списке.

Обычный обобщённый компонент не требует произвольных семейств типов:

```flick
type alias SelectProps a c =
  {
    items : List a
    selected : Option a
    key : (a -> String)^c
    render_item : (a -> Ui^c)^c
    on_change : (Ui.Handler a)^c
  }
```

`on_change` — обработчик с обязательной политикой (`Ui.Event.latest …`), а снимок события — выбранный элемент. Обычная функция `a -> Eff r e Unit` означала бы неявный запуск задачи без управления её завершением. Все поля связаны одним типом a: нельзя совместить items из User и обработчик для Product. Операции над строками потребуются для универсальных обёрток, значений по умолчанию и контролируемого разворачивания свойств; полиморфизм высших рангов — для специальных полиморфных функций рендеринга, а не для каждого обобщённого компонента. В [TypeScript JSX](https://www.typescriptlang.org/docs/handbook/jsx.html) также разделена проверка свойств встроенных элементов и дочерних узлов; DSL Flick может выразить эти контракты обычными функциями, не воспроизводя всю систему типов TS.

### Обработка событий и время жизни

Обработчик DOM, от которого ожидается void, не исполняет возвращённый Eff. Адаптер обязан получить инертный снимок события, синхронно принять решение о действии браузера по умолчанию, запустить управляемую задачу и наблюдать её завершение. `preventDefault` нельзя откладывать до произвольного асинхронного ожидания; для этого подходят декларативная политика или чистая синхронная функция принятия решения.

Обработчик обрабатывает свои ожидаемые ошибки в своей задаче, поэтому супервизор корня UI получает `Failure none`: инфраструктурные дефекты, например событие, отклонённое заполненной политикой, и прерывание при завершении работы остаются различимыми.

`Ui.Dom.container id` ищет `Ui.Dom.Container`, который может отсутствовать. `Ui.Dom.mount container supervisor ui` отображает `ui` с реестром `Atom.Registry`. Представление (`Ui.view`) читает атомы через `Atom.Read` во время рендера и перерисовывается только при изменении прочитанного атома, а обработчики изменяют атомы через `Atom.set`/`Atom.update` с сервисом `Atom.Write`; `Atom.layer` предоставляет реестр сразу как оба сервиса. Первое монтирование DOM синхронно. React 19 может объединять последующие рендеры; это не гарантирует фиксацию изменений (commit) после каждой задачи или один рендер на кадр анимации. `Ui.Dom.mount` работает до закрытия корня и завершения очистки. Завершение монтирования не гарантирует, что будущие сбои вернутся через его обычный результат. Сбой самого супервизора завершает корень с дефектом и передаётся механизму отчётов среды выполнения, без рекурсивного формирования отчётов.

`Ui.mount_with renderer supervisor ui` сохраняет тот же контракт реестра, сервисов, ошибок, захватов и завершения, но использует непрозрачную фабрику `Ui.Renderer` вместо DOM-контейнера. Фабрика открывает корень только при запуске Effect и предоставляет операции `render(node)` и синхронного `unmount()`. `Ui` импортирует только `@flick-lang/runtime/ui/react`; за монтирование DOM отвечают `Ui.Dom` и `@flick-lang/runtime/ui`, поэтому скомпилированному потребителю `Ui.mount_with` не нужен `react-dom`. HTML-конструкторы остаются привязанными к DOM. Адаптеры React Native, Ink и React Three Fiber и их типизированные примитивы платформы ещё не реализованы.

Ключи соседних узлов сохраняют идентичность поддерева и политик событий при перестановке, а стабильные слушатели событий компонентов получают обработчик из завершённого обновления React (commit). Представления над атомами с обработчиками Effect похожи на Elm, но не реализуют полную TEA: последовательного цикла сообщений, команд из `init`/`update` и подписок по модели ещё нет. Подробности реализации и приоритеты развития — в [справочнике UI](../../reference/ui/#приоритеты-недостающих-возможностей).

У каждого обработчика обязательна политика выполнения; неявного запуска без управления завершением нет.

| Конструктор | Поведение |
| - | - |
| `Ui.Event.exhaust` | Игнорирует новые события, пока текущая задача не завершилась |
| `Ui.Event.latest` | Отменяет предыдущую задачу, дожидается её полной остановки и запускает последний снимок события; хранит не более одного ожидающего снимка |
| `Ui.Event.queue capacity` | Ограниченная очередь FIFO; при заполнении новое событие отвергается, а супервизор получает инфраструктурный дефект переполнения |
| `Ui.Event.concurrent limit` | Не более limit активных задач; при насыщении новое событие отвергается с инфраструктурным дефектом переполнения, без скрытой неограниченной очереди |

Ёмкость очереди и предел параллелизма — проверенные положительные целые: константы проверяет компилятор, динамические значения — проверяемый конструктор. Инфраструктурные дефекты не выдаются за новый элемент типизированной строки `e`. Отмена не откатывает уже совершённое внешнее действие. Действие браузера по умолчанию сохраняется, если декларативная политика или чистое синхронное решение не требует preventDefault.

Проверка захватов проходит через свойства, переданные функции, Eff и Ui. Вернуть кнопку, обработчик которой захватил файл из уже закрытой области владения, — ошибка. Можно открыть файл внутри task либо удерживать UI в пределах времени жизни файла. Наличие `Ui` не доказывает отсутствие захваченного ресурса с ограниченной областью владения.

При очистке React синхронно закрывает приём событий и отменяет регистрацию обработчиков. Отдельная задача закрытия, которой владеет приложение, прерывает его файберы, ждёт их завершения и полной остановки внешних операций, а затем освобождает ресурсы. `Ui.Dom.mount` и `Ui.mount_with` сохраняют область владения приложения открытой до конца этой работы. Рендерер должен размонтировать свои компоненты React, а не просто скрыть интерфейс. Сам обработчик очистки React не гарантирует ожидание асинхронных финализаторов. [React useEffect](https://react.dev/reference/react/useEffect) задаёт жизненный цикл очистки; двухфазное ожидание — дополнительный контракт адаптера Flick.

### Безопасность содержимого и взаимодействие с JavaScript

`Ui.text : String -> Ui` (полиморфна по строкам сервисов и ошибок, чтобы стоять среди дочерних узлов любого элемента) вставляет текст через безопасный текстовый канал. Для URL и HTML, передаваемого без экранирования, действуют отдельные политики и непрозрачные типы, например SafeUrl и SanitizedHtml. Их конструкторы проверяют вход или являются явно доверенными; простое приведение String не доказывает безопасность. Это разделение каналов, а не гарантия автоматической проверки всей HTML-грамматики, доступности и корректности приложения.

`.d.ts` может описать структуру свойств внешнего компонента, но не доказывает его чистоту, правила удержания значений и отмены. Внешний компонент хранится как непрозрачный компонент рендерера; чистая функция построения Flick его не исполняет. Адаптер задаёт политики переданных функций, времени жизни и владельца. Поддерживаемая часть React-экосистемы импортируется через тот же процесс FFI; гарантии, которые нельзя выразить, не стираются.

## CLI eDSL: флаги, аргументы и подкоманды

Приложение командной строки описывается значением `Cli.Command r e`: чистым описанием флагов, позиционных аргументов, подкоманд и отложенного обработчика, которому нужны сервисы r и который может завершиться ошибками e. Построение команды ничего не разбирает и не запускает. За выполнение отвечает [Effect CLI](https://effect.website/docs/v4/api/effect/cli/Command); справка, автодополнение и разбор берутся из неё, а типы опций, полнота и захваты — контракт Flick.

```flick
greet : Cli.Command {Platform} none
let greet =
  cli "greet" {
    description "Печатает приветствие"
    /// Печатать заглавными буквами
    flag loud : Bool
    /// Сколько раз повторить
    flag times "n" : Number = 1
    /// Кому адресовано приветствие
    arg name : String
    handle fun { loud; times; name } ->
      let text = "Hello, " ++ name
      let line = if loud then String.to_upper text else text
      Platform.print_line (String.join "\n" (List.repeat times line))
  }
```

`cli "name" { … }` — синтаксический сахар над функциями `Cli.command`, `Cli.flag`, `Cli.arg`, `Cli.description`, `Cli.subcommands` и `Cli.handle`. Без сахара доступны те же комбинаторы, и обе формы строят одно представление. Блок состоит из конструкций — по одной на строку или через `;`:

| Конструкция | Смысл |
| - | - |
| `description e` | Текст справки команды, `e : String`; не больше одной |
| `flag name "alias"… : T [= default]` | Именованный параметр `--name`; строки после имени — дополнительные имена |
| `arg name : T [= default]` | Позиционный аргумент; порядок конструкций задаёт порядок аргументов в командной строке |
| `subcommand e` | Вложенная команда, `e : Cli.Command r e` |
| `handle f` | Обработчик, `f : Options ->{r; e} Unit` |

Ключевые слова конструкций контекстные: они имеют особое значение только в начале конструкции внутри `cli { … }`. Комментарий документации `///` непосредственно над `flag`, `arg` или `subcommand` становится его текстом в справке; тот же текст показывает `flick doc`.

<div id="опции-как-точный-record"></div>

### Опции как точная запись

При раскрытии DSL компилятор выводит точную запись опций: по полю на каждый `flag` и `arg` в порядке объявления; имя поля берётся из соответствующей конструкции. В примере обработчик получает `{ loud : Bool; times : Number; name : String }`; опечатка в образце записи или обращение к несуществующему полю — обычная ошибка типов. Имя на командной строке получается из имени поля заменой `_` на `-`: `dry_run` → `--dry-run`. Дополнительное имя из одного символа даёт короткую форму `-n`, более длинное — `--name`; дефисы в строке не пишутся.

Тип значения задаёт и разбор, и кратность:

| Тип в конструкции | Поведение |
| - | - |
| `Bool` | Флаг-переключатель; без `= default` равен `false` |
| `T` | Обязательный параметр, если нет `= default` |
| `Option T` | Необязательный; `= default` запрещён |
| `List T` | Повторяемый флаг (0 и больше повторений); у `arg` — хвост переменной длины, допустимый только последним |
| `NonEmpty T` | Как `List T`, но хотя бы одно значение |

Для `T` нужен экземпляр класса `Cli.Value T`, который разбирает строку и при неудаче возвращает типизированную ошибку. Библиотека предоставляет экземпляры для `String`, `Number` (отвергает NaN и пустую строку), `BigInt`, `Path`, `Duration` и `Redacted String`; значение `Redacted` не печатается в справке, ошибках и логах. `deriving Cli.Value` строит экземпляр для ADT из нульарных конструкторов: при разборе выбирается имя конструктора в kebab-case. Для уточняющего типа он строится, если экземпляр есть у базового типа; разбор вызывает `T.parse`. Значение по умолчанию — чистое выражение типа `T`; в справке оно показывается через `Show T`, если такой экземпляр есть.

<div id="подкоманды-и-handler"></div>

### Подкоманды и обработчики

```flick
tool : Cli.Command {Platform} none
let tool =
  cli "tool" {
    description "Утилиты проекта"
    /// Подробный вывод
    flag verbose "v" : Bool
    subcommand greet
    subcommand version
  }
```

Сервисы и ошибки команды — объединение строк её обработчика и подкоманд, как у любого составного выражения. Обработчик подкоманды получает только собственную запись опций; флаги родителя разбираются до имени подкоманды и видны только обработчику родителя. Общая конфигурация для всех подкоманд передаётся сервисом, предоставленным в `main`. Команда без `handle` обязана иметь подкоманды; её вызов без подкоманды печатает справку и завершается `CliError`. Команда с подкомандами не объявляет `arg`, иначе позиционный аргумент неотличим от имени подкоманды.

Ошибки компиляции: повтор имени поля, флага или подкоманды; совпадение длинного или короткого имени, в том числе с зарезервированными `--help`, `-h`, `--version` и `--completions`; `= default` у `Option`; `List`/`NonEmpty` у `arg` не последним; тип без `Cli.Value`; значение по умолчанию неверного типа; `handle` или `description` дважды; команда без `handle` и без подкоманд; `arg` рядом с `subcommand`.

### Запуск

`Cli.run : Cli.Command r e -> List String ->{Platform | r; CliError | e} Unit` разбирает аргументы чистой функцией и только после успешного разбора выполняет обработчик в текущем файбере. `--help`, `--version` и `--completions bash|zsh|fish` печатают результат в стандартный вывод и завершаются без вызова обработчика. Неверный ввод — неизвестный флаг, отсутствующий обязательный аргумент или значение, которое `Cli.Value` не разобрал, — даёт `type error CliError = CliError String` с текстом для пользователя; обработчик не запускается.

```flick
main : Unit ->{; AppError} Unit
let main () =
  provide Platform.live {
    try
      Cli.run tool (Platform.args ())
    with
    | CliError message -> App.fail message
  }
```

Команда остаётся обычным значением: запускающий её вход — обычный
эффектный `main`, а приложение может предоставлять несколько именованных
входов. Коды выхода и порядок освобождения ресурсов следуют общим
правилам раздела 12. SIGINT прерывает обработчик, ресурсы которого
закрываются по контракту владельца из раздела 7. Захваты проходят через
обработчик так же, как через переданные функции UI: команда, захватившая
ресурс области, не может покинуть эту область. Интерактивные запросы
(`Cli.Prompt`) — обычные эффектные функции внутри обработчика,
а не конструкции блока.

## Как SQL и UI проверяют устройство языка

Два обязательных сквозных прототипа проверяют выбранные механизмы. Их результат может выявить дефект спецификации, но выбор механизмов уже сделан:

- SQL: типизированная таблица → LEFT JOIN → проекция с возможным NULL → привязка параметров → выполнение через Effect; отрицательные примеры с неизвестным полем, неверной группировкой, ссылкой на псевдоним за пределами его области видимости и неверным параметром.

- UI: обобщённые свойства → типизированные дочерние узлы → чистый рендеринг → обработчик с task → управляемое завершение; отрицательные примеры с неверным свойством, эффектным вызовом при рендеринге и захватом закрытого ресурса.

Прототипы проверяют выразительность и стоимость вывода типов. Для больших строк полей и вложенных запросов измеряются время проверки и качество диагностики; успешные маленькие примеры не доказывают масштабируемость. Оптимизации могут заранее скомпилировать статическую форму SQL и чистое создание UI, сохраняя параметры, метаданные захватов, границы рендерера и наблюдаемое выполнение Effect.
