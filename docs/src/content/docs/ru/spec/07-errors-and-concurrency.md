## Ожидаемые ошибки

У каждой ошибки есть номинальная идентичность и данные. `try ... with` обрабатывает выбранную ожидаемую ошибку по правилам Effect. В первой версии данные каждого конструктора ошибки обязаны удовлетворять `NoCapture`. В них нельзя сохранить привязанный к области дескриптор ресурса, функцию обратного вызова или задачу с захватом региона, а также ячейку с таким значением. Скрыть право доступа к ресурсу в экзистенциальной упаковке или `Unknown` тоже нельзя. Проверка действует, даже если ошибку перехватывают локально. Поэтому в ошибку передают путь, идентификатор или копию данных, а не живой ресурс.

Ошибка объявляется через `type error`. Её единственный конструктор называется так же, как сама ошибка. Поля перечисляются как у варианта ADT: `type error NotFound = NotFound UserId`. Ошибка без полей записывается как `type error Timeout`.

```flick
type error NotFound = NotFound UserId

load_optional : UserId ->{Users; none} Option User
let load_optional id =
  try
    Some (Users.get id)
  with
  | NotFound _ -> None
```

Если `Users.get` имеет тип `Users.get : UserId ->{Users; NotFound} User`, то `load_optional` возвращает `Option User`, по-прежнему требует `{Users}`, но больше не содержит выбранных ожидаемых ошибок в своей строке ошибок. Полная причина завершения, нативный Cause, может содержать дополнительные сбои для диагностики. Их данные нельзя считать значениями остаточной строки `e`.

Ошибка может иметь параметры. `type error RetryExhausted e = RetryExhausted e Float` хранит последнюю причину после исчерпания попыток, а `type error SendFailed a = SendFailed a` возвращает значение, которое не удалось отправить. Строка ошибок различает элементы по номинальному имени `Module.Name`, а не по аргументам типа. Поэтому в одной строке может быть не больше одного элемента с данным именем. Аргументы двух `RetryExhausted` в одной строке унифицируются: совместное присутствие `RetryExhausted DbError` и `RetryExhausted String` приводит к ошибке типов.

Проекция в TypeScript следует тому же правилу: `_tag` не зависит от аргументов типа, `RetryExhausted<E>` встречается в объединении ошибок `Effect` не более одного раза, а `catchTag` однозначно сужает тип. Java и OCaml по той же причине запрещают параметризованные исключения; во Flick параметры допустимы, потому что строка хранит один элемент на имя.

```flick
type error RetryExhausted e = RetryExhausted e Float

retry : Float -> Eff r e a ->{r; RetryExhausted (Errors e)} a
```

Обработчик может удалить ошибку из строки, только если полностью покрывает её номинальный вариант. Условие ветки или образец, который подходит лишь части данных ошибки, оставляет её в строке. Требования и ошибки самого обработчика добавляются к результату. Удаление из строки относится к выбранной ожидаемой ошибке и не доказывает, что такой же тег отсутствует среди вторичных сбоев в полной причине завершения.

Ожидаемая ошибка, дефект и прерывание остаются разными исходами. Пустая строка ошибок не гарантирует, что вычисление завершится, не столкнётся с дефектом или не будет отменено. Effect сохраняет дефекты и прерывания в причине завершения, а не в обычном параметре `E`. [Виды ошибок Effect](https://effect.website/docs/v4/error-management/two-error-types).

`try ... with` компилируется в обработку типизированной ошибки Effect. JavaScript `try/catch`, который охватывает только построение значения Effect, не выполняет этот контракт.

## Сервисы и классы типов

| Механизм | Как выбирается реализация | Для чего нужен |
| - | - | - |
| Класс типов | Фронтенд компилятора выбирает экземпляр класса и передаёт словарь его методов | `Eq`, `Show`, `Functor` и другие операции над типами |
| Сервис | Реализация предоставляется для конкретного вычисления | База данных, HTTP, логирование, тестовое окружение |
| Layer | Среда выполнения строит сервисы из зависимостей | Инициализация, получение ресурсов и построение окружения |

Чистая операция `show user` не должна требовать Effect Context. Подмена рабочего сервиса тестовым не должна менять глобальный выбор экземпляра класса типов.

В прямом API `Users.get` — сгенерированная эффектная операция. В реализации сервиса метод может возвращать `Effect`. Получение сервиса добавляет требование `Users`; вызов метода уже полученного экземпляра не обязан повторно искать сервис в Context.

Идентичность сервисов и ошибок включает пакет и модуль. Привязка к существующему сервису или ошибке Effect сохраняет его настоящий ключ, тег и представление данных. Объявление сервиса перечисляет полные сигнатуры методов; компилятор генерирует операции и тип записи с реализацией:

```flick
service Clock =
  now : Unit ->{} Float

clock_impl : Clock.Impl
let clock_impl =
  { now = JsClock.now }

clock_layer : Layer none none {Clock}
let clock_layer =
  Layer.succeed Clock clock_impl
```

Здесь `JsClock.now` — явно объявленная эффектная привязка. `Clock.now` требует сервис `Clock`; метод полученного `Clock.Impl` не ищет сервис повторно. Скрытые захваты записи с реализацией сохраняются в её типе и в Layer. Методы сервиса не становятся экземплярами классов типов. [Сервисы Effect](https://effect.website/docs/v4/requirements-management/services).

## Предоставление окружения

Порядок параметров слоя — `Layer inputs errors outputs`. Например:

```text
UsersLive :
  Layer {Config} {ConnectError} {Users}
```

Блок `provide layer { ... }` устанавливает окружение до выполнения тела:

```flick
application : UserId ->{Config, Log; NotFound, ConnectError} String
let application id =
  provide UsersLive {
    load_name id
  }
```

Если `load_name` требует `{Users, Log}` и допускает `{NotFound}`, после предоставления `UsersLive` остаются требования `{Config, Log}`, ошибки `{NotFound, ConnectError}` и тот же результат `String`.

Предоставление слоя убирает требования к обеспеченным сервисам, но добавляет зависимости и ошибки построения слоя. Если вместо специального блока используется обычная функция, ей нужно передать `task { ... }`. Иначе строгий порядок вычисления запустит тело ещё до установки окружения. [Слои Effect](https://effect.website/docs/v4/requirements-management/layers).

## Ресурсы

`scope` сочетает финализацию во время выполнения со статическим запретом использовать ресурс за пределами его области. Получение ресурса регистрирует завершающее действие, или финализатор, у лексического владельца. В безопасном API ресурсов, привязанных к области, **нет раннего закрытия**. Отдельные привязки с ручным управлением ресурсом этой гарантии не получают. Такое ограничение позволяет обойтись без линейных типов и без отражения состояний «открыт» и «закрыт» в типе ресурса.

Для проверки используются свежие регионы и транзитивный учёт захватов. Через безопасный API нельзя получить пригодное к использованию право доступа к ресурсу уже завершённого региона. Нативный Cause может физически удерживать закрытый внешний объект, но безопасная оболочка не раскрывает его. Полная аффинная или линейная система типов не входит в первую версию. Нативный [Effect Scope](https://effect.website/docs/v4/resource-management/scope) выполняет финализацию; статическую проверку и двухфазное закрытие владельца обеспечивают компилятор и адаптер среды выполнения Flick.

Финализатор ресурса, привязанного к области, имеет пустую строку ожидаемых ошибок; его сбой сохраняется как дефект в полном исходе. Лексический `bracket`, напротив, допускает отдельную типизированную ошибку освобождения и добавляет её к строке ошибок. Это разные операции. Первичная ошибка и сбои освобождения сохраняются по нативному контракту Cause. Освобождение нельзя заменить обычным JS `finally`, который теряет исходный сбой.

## Конкурентность

Основной API — `parallel` и `parallel_all`, которые структурированно выполняют холодные `Eff`: сами операции управляют временем жизни своих веток. При сбое они отменяют активные ветки и ждут их завершения. `parallel_all` требует конечный положительный целый предел конкурентности; успешные результаты следуют порядку входных значений.

Несколько уже наблюдённых сбоев сохраняются в нативном Cause; API не обещает собрать все ошибки, которые могли бы возникнуть в дальнейшем. `parallel_results` отдельно накапливает выбранные типизированные ошибки как `Result`, а `parallel_exits` — непрозрачные полные исходы. Дефекты и внешнее прерывание не маскируются обычным успешным списком.

`spawn` требует явно указать лексического владельца и супервизор — обработчик исходов фоновой задачи. `join` ожидает конкретный файбер и восстанавливает его сбой. Ошибки дочерней задачи не добавляются автоматически в строку ошибок родителя. Поэтому супервизор обязателен, даже если вызывающий код может проигнорировать дескриптор файбера. В безопасном API нет запуска неограниченно живущих фоновых файберов с локальными захватами. [Файберы Effect](https://effect.website/docs/v4/concurrency/fibers).

## Граница языкового ядра

Повторные попытки, расписания, потоки, очереди, кеш, трассировка и HTTP остаются частью типизированной стандартной библиотеки. Для повторного запуска и конкурентного выполнения она принимает описания вычислений. Специальных синтаксических конструкций для них в первой версии нет.

Полноценный `deriving Schema` и кодеки внешних форматов входят в целевой язык. Параметрические типы, рекурсия, уточнения, политики полей и эффектные преобразования разобраны в разделе 9.

Сервисы и `provide` не являются универсальными обработчиками алгебраических эффектов, которые захватывают продолжение и могут возобновлять его несколько раз. В первой версии операции языка опираются на конкретные механизмы Effect; универсальные обработчики не входят в этот контракт.

## Контракты выполнения и времени жизни

Базовые правила ниже описывают поведение программы, которое должно сохраняться при изменении способа генерации кода. Более сложные режимы можно добавлять отдельными библиотечными операциями.

| Область | Контракт первой версии | Цена |
| - | - | - |
| Типизированные ошибки | Номинальные ошибки с данными без зависимостей от регионов; `e` описывает выбранную ошибку для обычной обработки | Нельзя считать все необработанные Fail значениями `Errors e` |
| Дефекты и прерывания | Сохраняются вне `e`; доступны через непрозрачные Failure/Exit | Обычный обработчик не перехватывает все виды сбоев |
| Предоставление окружения | Сначала строится Layer, затем выполняется тело; конфликты разрешаются явной заменой | Неоднозначные сервисы не выбираются автоматически |
| Повторное использование слоёв | Один и тот же Layer используется повторно внутри одной сборки | Для повторного использования между provide нужна явная мемоизация с владельцем |
| Область ресурсов | Свежие регионы и учёт захватов; сначала завершаются дочерние задачи, затем ресурсы освобождаются в обратном порядке | Закрытие может ждать непрерываемую или внешнюю работу |
| Ошибки освобождения | Финализатор области не имеет ожидаемых ошибок; типизированная ошибка освобождения доступна через bracket | Ошибки всех динамически зарегистрированных финализаторов не объединяются в e |
| Параллельное выполнение | При сбое активные ветки отменяются; операция ждёт освобождения ресурсов; результаты следуют порядку входа | Не гарантируется получение всех возможных сбоев |
| Запуск фоновой задачи | Явный владелец и обязательный супервизор; join восстанавливает сбой | Успех родителя не означает успех фоновых задач |
| Гонки и таймауты | Нативный выбор победителя и ожидание проигравших веток | Нет жёсткого предельного времени и автоматического добавления сбоев проигравших |

## Ошибка как данные и ошибка выполнения

Чистая функция может вернуть `Result`, не запуская Effect. Порядок параметров `Result error value` во Flick удобен для типов высших порядков (HKT). Во время выполнения используется нативный `Result.Result<A, E>` из [Effect v4](https://effect.website/docs/v4/data-types/result), поэтому проекция в TypeScript переставляет параметры. Параметр `error` здесь имеет кинд `Type`, а строка ошибок эффектного вычисления — кинд `ErrorRow`. Это разные позиции.

```text
parse_config :
  String -> Result ParseError Config

fetch_config :
  Url ->{Http; NetworkError} Config
```

Библиотека предоставляет явную операцию для перевода `Result` в типизированную ошибку выполнения:

```text
from_result : Result (Errors e) a ->{; e} a
```

Для `Result NotFound User` используется строка из одного элемента `{NotFound}`. В случае `Result String a` сначала нужно преобразовать строку в объявленную номинальную ошибку. Операция не перехватывает дефекты или прерывания. Обычный `try ... with` обрабатывает ожидаемые ошибки, а отдельный API `Exit`/`Cause` — полный исход. [Разделение ошибок Effect](https://effect.website/docs/v4/error-management/two-error-types).

```flick
type error NotFound = NotFound UserId
type error DbUnavailable = DbUnavailable String

find_user :
  UserId ->{Users; NotFound, DbUnavailable} User

find_optional :
  UserId ->{Users; DbUnavailable} Option User
let find_optional id =
  try
    Some (find_user id)
  with
  | NotFound _ -> None
```

### Сложный Cause: что обещает строка ошибок

В принятом контракте `e` описывает **ошибку, доступную обычному типизированному обработчику**. Полный нативный Cause может содержать вторичные данные ошибок вне остаточной `e`. Безопасный API не предоставляет функцию `Failure e -> List (Errors e)`, которая возвращала бы все его Fail.

Проверенная версия, на которую опирается контракт, — Effect 4.0.5, коммит `81fc8d9c7855d0f31bf493f379ec7bc2a6150a6f`. В v4 Cause содержит плоский список `Fail`, `Die`, `Interrupt`; представление причин в виде дерева последовательных и параллельных сбоев не входит в контракт. [Cause](https://effect.website/docs/v4/data-types/cause).

| Причина | Нативная обработка типизированных ошибок в проверенной версии |
| - | - |
| Один `Fail(A)` | Выбирается A |
| `Fail(A), Fail(B)` | Выбирается первый Fail; обработчик не обходит весь список |
| `Fail(A), Interrupt` | Сам Interrupt в списке не мешает выбрать A |
| `Fail(A), Die(D)` | Обычная обработка типизированной ошибки недоступна; Fail преобразуются в дефекты |
| Только Interrupt | Обычный типизированный обработчик не получает ошибку |
| `Fail(B), Fail(A)`, обработчик только A | Обработчик не вызывается; распространяется исходная причина |

Последняя строка существенна: нативный `catchTag(A)` сужает E в сигнатуре TypeScript, хотя вторичный A может остаться в полном Cause. Поэтому нельзя механически использовать этот обработчик и одновременно считать каждый необработанный `Fail` значением `Errors e`. Проверены [выбор ошибки для обработки](https://github.com/Effect-TS/effect/blob/81fc8d9c7855d0f31bf493f379ec7bc2a6150a6f/packages/effect/src/internal/effect.ts#L160-L199) и [catchIf/catchTag](https://github.com/Effect-TS/effect/blob/81fc8d9c7855d0f31bf493f379ec7bc2a6150a6f/packages/effect/src/internal/effect.ts#L2947-L3068).

### Выбранный контракт Cause и цена альтернатив

| Модель | Гарантия | Цена |
| - | - | - |
| Нативная обработка и непрозрачный RawCause — выбранная модель | Обработчик получает выбранную ожидаемую ошибку; повторное распространение сохраняет нативный Cause | Безопасная диагностика возвращает инертный отчёт, а не исходные JS-данные ошибок |
| Нормализация остаточной причины — вне первой версии | Все активные Fail принадлежат остаточной e; вторичные исключённые сбои хранятся отдельно | Нужны собственный адаптер для каждого сужающего обработчика и обход причин; поведение отличается от нативного catchCause |
| Полностью типизированный Cause — вне первой версии | Все Fail имеют тип Errors e | Частичный обработчик часто не может уменьшить e; нужны дополнительные доказательства |

`Exit e a`, `Failure e` и `RawCause` — непрозрачные типы. Внутри сохраняется нативное представление Effect; типизированный и диагностический интерфейсы разделены.

```text
Failure.primary :
  Failure e -> Option (Errors e)

Failure.raw_cause :
  Failure e -> RawCause

Failure.inspect :
  Failure e ->{} CauseReport

RawCause.inspect :
  RawCause ->{} CauseReport

Failure.rethrow :
  Failure e ->{; e} a
```

Успешный `Exit` содержит `a` и сохраняет захваты этого значения. `Failure.primary` выдаёт только выбранную типизированную ошибку; `rethrow` восстанавливает исходный Cause с той же `e` либо с её допустимым расширением. Безопасного преобразования `RawCause -> Exit e a` для произвольной `e` нет. Эти операции не могут стирать известные захваты. Данные типизированных ошибок проверены на отсутствие зависимостей от регионов; произвольные дефекты внешнего кода остаются запечатанными.

Безопасный `RawCause` **не раскрывает исходный `JsValue`**. `CauseReport` содержит инертные сведения о видах причин, безопасно полученные теги и текст, а также метаданные прерывания. Инспекция не вызывает пользовательские геттеры, `toString` или `toJSON`; вместо неподдерживаемых данных она показывает обозначение-заполнитель. Доступ к исходному графу JS-объектов возможен только через явный небезопасный FFI. Привязки к нативным преобразованиям Cause проверяются отдельно: нельзя приписать остаточную `e` каждому вторичному Fail или вызвать для него переданную функцию под ложным типом.

Во второй модели `[Fail(B), Fail(A)]` после обработчика A превращается в активный `Fail(B)`, а исходный A остаётся в диагностике. Переводить этот A в `Die` нельзя: это изменит последующую обработку типизированных ошибок. В третьей модели правило «сложную причину просто пропускаем, но A всё равно вычитаем» тоже некорректно.

Ещё один вариант для `parallel` — явный `CompositeError`. Он меняет прикладной API: обработка `NotFound` не равна обработке агрегата, внутри которого есть NotFound. Такой тип полезен как отдельная библиотечная операция, но не обязателен для всех вычислений.

Успешная обработка может поглотить причину и связанные с ней вторичные диагностические сведения. Если они нужны в логах, причину нужно наблюдать до обработки. Правило выбора ошибки из списка не позволяет обработчику произвольно отключить уже запрошенную отмену файбера: состоянием прерывания управляет среда выполнения.

<div id="lifetime-и-sharing-при-provide"></div>

## Время жизни и повторное использование сервисов при provide

`provide` сначала полностью строит Layer и лишь затем выполняет тело. При ошибке построения тело не запускается. Реализации сервисов, привязанные к области, принадлежат лексическому владельцу provide. После выхода восстанавливается внешнее окружение и выполняется двухфазное закрытие. Захваты сервиса, записи с реализацией, замыкания, `Eff`, UI или кодека сохраняются в интерфейсах и не могут пережить владельца.

`task { service_call () }` ищет требуемый сервис при запуске в текущем окружении. Если задача уже захватила конкретный экземпляр сервиса, она сохраняет зависимость от его времени жизни. Финализатор получает контекст, сохранённый при регистрации, а не случайный сервис из окружения, в котором позже началось закрытие.

Один и тот же Layer используется повторно внутри одной сборки графа. Независимые `provide` строят независимые экземпляры; глобального единственного экземпляра нет. Для длительного совместного использования построенных сервисов нужна явная мемоизация с владельцем. Две реализации с одним ключом сервиса в графе считаются ошибкой, если не использована явная операция замены. Это правило опирается на [мемоизацию слоёв Effect](https://effect.website/docs/v4/requirements-management/layer-memoization), а проверка исходных типов дополнительно контролирует время жизни.

## Финализация и границы ресурса

```flick
read_config :
  Path ->{FileSystem; OpenError, ReadError} String
let read_config path =
  scope {
    let file = File.open_scoped path
    File.read_all file
  }
```

`File.open_scoped` требует лексический `Scope s`, который предоставляет `scope`. После успешного получения ресурса регистрируется финализатор. Вычисление возвращает итог, только когда завершатся все дочерние задачи области, а затем будут освобождены ресурсы. Финализаторы ресурсов выполняются в обратном порядке регистрации, то есть по правилу LIFO. Один общий LIFO-список дочерних задач и ресурсов не обеспечивает этот порядок, если ресурс зарегистрирован после запуска дочерней задачи. [Scope API](https://effect.website/docs/v4/api/effect/Scope).

Операция `acquireRelease` для ресурса области требует освобождения без ожидаемых ошибок. Лексический `bracket` на базе `acquireUseRelease` допускает типизированную ошибку освобождения. Именно это разделение принято в языке. Дефекты освобождения сохраняются в полном исходе; проверка типов не доказывает, что каждый внешний ресурс удастся закрыть. [Нативные операции Effect](https://github.com/Effect-TS/effect/blob/81fc8d9c7855d0f31bf493f379ec7bc2a6150a6f/packages/effect/src/Effect.ts).

Для безопасного API ресурсов области компилятор проверяет все способы прямого и косвенного выхода ресурса за её пределы: результат, замыкания, задачи, контейнеры, экзистенциальные обёртки, запись во внешнее состояние и передачу в FFI, который удерживает аргумент. Ресурс можно использовать многократно внутри своей области, если его API это разрешает. Статическая проверка времени жизни сама по себе не доказывает отсутствие гонок или безопасность конкурентного использования дескриптора.

<div id="статические-regions-и-захваты"></div>

### Статические регионы и захваты

Каждый `scope s { ... }` создаёт свежий регион `s` и его владельца в среде выполнения. В `scope { ... }` имя региона выводится и остаётся скрытым. Дескриптор ресурса области имеет тип вроде `File s`. Компилятор передаёт владельца лексически: один обычный поиск в Context не подходит, потому что во вложенной области он мог бы выбрать другой scope.

```flick
bad_deferred :
  Path ->{FileSystem; OpenError} Eff none {ReadError} String
let bad_deferred path =
  scope {
    let file = File.open_scoped path
    task { File.read_all file }
  }
```

Это ошибка: задача захватывает `file`, а её пытаются вернуть после закрытия области. Обычный тип `Eff none {ReadError} String` не показывает эту зависимость, поэтому одной проверки `s` в типе результата недостаточно.

Чтобы вернуть задачу, нужно перенести получение ресурса внутрь отложенного выполнения:

```flick
deferred_read :
  Path -> Eff {FileSystem} {OpenError, ReadError} String
let deferred_read path =
  task {
    scope {
      let file = File.open_scoped path
      File.read_all file
    }
  }
```

Теперь каждый `await` получает собственную область и ресурс. Возвращаемая строка может пережить файл.

Та же проверка нужна для обычной функции обратного вызова:

```flick
bad_callback :
  Path ->{FileSystem; OpenError} (Unit ->{; ReadError} String)
let bad_callback path =
  scope {
    let file = File.open_scoped path
    fun () -> File.read_all file
  }
```

Такую функцию тоже нельзя вернуть. Полиморфизм высших рангов с `forall s` препятствует прямому выходу `File s` за пределы области. Но без дополнительного учёта захватов он не доказывает, что ресурс не захвачен функцией обратного вызова, задачей или параметрическим контейнером.

| Путь утечки | Требование проверки типов |
| - | - |
| Прямой результат или вложенная запись/ADT | Регион не переживает владельца; зависимость распространяется транзитивно |
| Замыкание или Eff | Захваты сохраняются при передаче, обобщении и через интерфейсы модулей |
| Экзистенциальная или непрозрачная упаковка | Номинальная идентичность и скрытие типа не стирают время жизни |
| Запись во внешний Ref или кеш | Время жизни хранилища не превышает допустимое время жизни записываемого значения |
| Ошибка, Exit или диагностическое значение | Проверяются все выходы, включая данные ошибок; ошибочный исход не позволяет обойти ограничения времени жизни |
| Внешний вызов | Для аргумента, привязанного к региону, нужен проверенный контракт удержания |

Захваты — отдельное статическое свойство, а не третья строка эффекта. Запись `T^{s, t}` задаёт конкретные регионы, `T^c` — строку с киндом CaptureRow, а `T^(c + d)` — их объединение. Явная аннотация захватов задаёт верхнюю границу полного набора захватов, через которые значение может получить доступ к ресурсам. Известные из T зависимости обязаны входить в эту границу. Её можно расширять, но нельзя небезопасно сужать.

Тип T без аннотации не добавляет скрытых захватов и не стирает зависимости, уже выраженные в самом типе: File s и List (File s) зависят от s. Само упоминание s во входном типе функции не означает, что её замыкание удерживает ресурс s. Компилятор отслеживает достижимость прав доступа к ресурсу, а не все имена в сигнатуре.

```text
read_later :
  forall s.
  File s -> (Eff none {ReadError} String)^{s}

scoped_callback :
  forall s.
  File s -> (Unit ->{; ReadError} String)^{s}
```

Это интерфейсные сигнатуры. Локальные захваты выводятся; публичные сигнатуры и `.iface` сохраняют их. Захваты сохраняются при частичном применении, в записях, непрозрачных и экзистенциальных типах, словарях и `Unknown^{s}`. Чтобы передать функцию обратного вызова через параметрический API высшего порядка, нужен контракт, полиморфный по захватам, как у `List.map_effect`. В коротких примерах с областями имя региона опущено в синтаксисе, но компилятор продолжает его учитывать. Изменяемые хранилища инвариантны: более долгоживущий Ref или кеш не может получить право доступа к ресурсу с более коротким временем жизни.

Проверка захватов в [Scala](https://docs.scala-lang.org/scala3/reference/experimental/cc.html) даёт полезный ориентир для замыканий и контейнеров, но не является готовой реализацией проверки типов Flick.

### Гарантии и ограничения

| Свойство | Контракт первой версии |
| - | - |
| Многократное использование дескриптора в живой области | Разрешено, если API ресурса допускает это |
| Раннее закрытие | Отсутствует в безопасном API ресурсов области |

| Конкурентный доступ | Привязка объявляет операции, безопасные для совместного использования, либо сериализует доступ; время жизни не доказывает отсутствие гонок |
| Освобождение ресурсов | Effect выполняет финализаторы; компилятор не доказывает, что внешнее закрытие физически завершилось успешно |
| Типизированные ошибки | Данные не зависят от регионов даже при локальной обработке |

| Непроверенный JS | Требует явно объявленного доверенного или небезопасного контракта |

<div id="владелец-fibers-и-порядок-освобождения"></div>

### Владелец файберов и порядок освобождения

Задача может захватывать ресурсы своей области и более долгоживущих областей. Передать её более долгоживущему владельцу можно, только если у неё нет захватов с более коротким временем жизни. У подписки или функции обратного вызова, которую удерживает внешняя библиотека, тоже должен быть проверяемый владелец.

При закрытии области обязателен следующий порядок: **запретить новую работу → запросить отмену дочерних задач → дождаться конечного состояния каждой → выполнить финализаторы ресурсов в порядке LIFO → вернуть итоговый Exit**. Если дочерняя задача не завершает непрерываемый участок, закрытие ждёт. Освобождать ресурс, которым продолжает пользоваться дочерняя задача, запрещено; таймаут не отменяет это правило.

Конечное состояние файбера Effect ещё не доказывает, что внешняя операция Promise остановилась. Асинхронный FFI с захватами ресурсов области обязан перед завершением отмены дождаться подтверждения остановки либо фактического окончания внешней работы. Одного `AbortSignal` недостаточно. Если операция не отменяется, адаптер ждёт её окончания. Отсоединить её от текущего владельца можно, только если у неё нет захватов с более коротким временем жизни или владение явно и безопасно передано.

Если просто смешать `forkScoped` и финализаторы ресурсов в одном LIFO-списке, порядок будет зависеть от регистрации. Генератор кода должен использовать отдельную группу дочерних задач или эквивалентное разбиение на области. Это требует адаптера поверх Effect.

Область с автоматическим учётом дочерних задач и их ошибок — nursery — в первую версию не входит. Структурированные конкурентные операции владеют своими ветками; фоновый файбер, привязанный к области, отменяется при закрытии владельца. Ошибки фоновой работы всегда наблюдает явно переданный супервизор, а `join` дополнительно восстанавливает сбой для ожидающего. Это не означает, что ошибки дочерних задач автоматически добавляются в строку ошибок тела scope.

## Конкурентные операции с разными контрактами

```flick
load_pair : UserId -> UserId ->{Users; NotFound} (User, User)
let load_pair first_id second_id =
  parallel
    (task { Users.get first_id })
    (task { Users.get second_id })
```

Для `parallel` порядок результатов совпадает с порядком аргументов. При сбое операция прекращает запуск новой работы, запрашивает отмену остальных активных веток и ждёт их завершения. В проверенной реализации Effect при этом собираются наблюдённые причины, кроме Interrupt, в том числе некоторые сбои останавливаемых веток. Получение всех возможных будущих ошибок не гарантируется.

Операция не закрывает внешний `Scope`: зарегистрированные в нём ресурсы живут до его закрытия. Если ресурс нужно закрыть вместе с веткой, она создаёт собственный `scope`. Освобождение, защищённое от прерывания, может задержать завершение. Для `parallel_all` обязателен конечный положительный целый предел конкурентности, а результаты сохраняют порядок входных значений. [Реализация конкурентного обхода Effect](https://github.com/Effect-TS/effect/blob/81fc8d9c7855d0f31bf493f379ec7bc2a6150a6f/packages/effect/src/internal/effect.ts#L5098-L5252).

`parallel_results` переводит выбранные ожидаемые ошибки в `Result` и позволяет дождаться остальных веток. Дефекты и внешнее прерывание по-прежнему управляют выполнением, а не становятся значениями списка. `parallel_exits` возвращает непрозрачные полные исходы завершённых веток; внешняя отмена группы всё равно распространяется. Безопасный API не обещает собрать все потенциальные ошибки операции, которая отменяет работу при первом сбое.

Привязка к scope задаёт время жизни, а `join` ожидает конкретный результат. В текущем [Fiber API](https://effect.website/docs/v4/api/effect/Fiber#joinAll) `joinAll` при ошибке прекращает ожидание, но сам не прерывает остальные файберы. Поэтому генератор кода реализует структурированные конкурентные операции через отдельную группу дочерних задач: он отменяет и ожидает все активные ветки, а не ограничивается одним вызовом joinAll.

### Конкурентность: три модели

| Модель | Завершение и ошибки | Цена |
| - | - | - |
| Структурированные операции и явные файберы области — выбранная модель | `parallel` владеет ветками; фоновые задачи запускаются отдельной операцией, их исходы получает обязательный супервизор и, при необходимости, ожидающий через join | Для динамических групп нужно явно передавать управление группой |
| Языковая nursery | Обычный выход ожидает дочерние задачи; ошибка тела или дочерней задачи отменяет связанных участников; ошибки дочерних задач учитываются даже без join | Нужны реестр дочерних задач, правила объединения причин и учёт их строки ошибок в типе nursery |
| Наблюдение за фоновыми задачами области | Закрытие scope отменяет фоновые задачи; ошибки получает супервизор, лог или канал | Успех родителя не означает успех всех фоновых задач; нужна явная политика наблюдения |

В первой версии используются структурированные операции и наблюдение за фоновыми задачами области. `spawn owner supervisor task` регистрирует дочернюю задачу у owner; task и supervisor не могут захватывать более короткоживущий регион. Потеря дескриптора файбера не приводит к потере ошибки: супервизор получает полный `Failure` и различает ожидаемое прерывание при остановке. Дефект супервизора передаётся корневому обработчику сбоев среды выполнения. Для UI дополнительно действует правило: сбой супервизора корневой задачи завершает эту задачу. Долгоживущая работа требует явно указанного более долгоживущего владельца. Безопасного запуска неограниченно живущего фонового файбера с короткими захватами нет.

Привязка времени жизни к области не означает ожидания естественного успешного завершения дочерних задач. Обычный файбер области останавливается при её закрытии; его ошибка не присоединяется автоматически к результату тела. В nursery такое присоединение было бы отдельной гарантией. Функция обратного вызова с полиморфизмом высших рангов помогает ограничить право доступа к области, но сама по себе не учитывает ошибки дочерних задач и не доказывает, что ресурс не выйдет за пределы области.

<div id="race-и-timeout"></div>

### Гонки и таймауты

| Контракт | Поведение | Цена |
| - | - | - |
| Нативные операции — выбранный вариант | `race_success` выбирает первый успех, `race_first` — первое завершение; проигравшие ветки прерываются и ожидаются; выбранный результат сохраняется | Их Exit не добавляются автоматически к результату; дефект освобождения в проигравшей ветке может не стать ошибкой победителя |
| `race_checked` вне первой версии | После выбора результат проверяется по исходам остановки проигравших веток | Победитель может быть отвергнут; нужно различать ранние ошибки и сбои освобождения |
| Ранний таймаут вне первой версии | Ответ возвращается после выбора таймера; завершением работы управляет более долгоживущий владелец | Работа продолжается после ответа; обязательны область, супервизор и правила обработки последующих ошибок |

В проверенной реализации [Effect race](https://github.com/Effect-TS/effect/blob/81fc8d9c7855d0f31bf493f379ec7bc2a6150a6f/packages/effect/src/internal/effect.ts#L1649-L1739) ожидание проигравших веток не добавляет их Exit к выбранному результату. Поэтому контракт `parallel` нельзя автоматически переносить на гонку.

`timeout` и `timeout_option` используют нативный выбор между вычислением и таймером, затем прерывают и ожидают проигравшие ветки. `timeout` добавляет `TimeoutError`; `timeout_option` представляет именно таймаут через `None`, сохраняя другие ошибки. Строгой гарантии по фактически прошедшему времени нет: синхронный JS, непрерываемый участок и освобождение ресурсов могут задержать возврат. `race_checked` и ранний возврат с ещё работающими дочерними задачами области в первую версию не входят. Если победитель завершается синхронно, запуск всех веток не гарантируется. При одновременной готовности веток победитель может меняться.

**Среда выполнения первой версии:** нативная обработка типизированных ошибок, непрозрачные Failure/Exit/RawCause и инертная диагностика; свежие регионы и учёт захватов; двухфазное закрытие scope с обязательным ожиданием остановки внешней работы; структурированные конкурентные операции и наблюдение за фоновыми задачами области; нативные гонки и таймауты. Оптимизации обязаны сохранять эти гарантии, исходный Cause при повторном распространении, контекст сервисов и выполнение финализаторов.
