CLI называется `flick`. Ниже описан интерфейс первой версии Flick; наличие команды в спецификации не означает, что она уже реализована. Все команды используют общее ядро на Rust и один генератор кода для Effect.

## Имена файлов и конфигурация проекта

| Объект | Соглашение |
| - | - |
| Язык и инструменты | Flick; по-русски — «флик»; исполняемый файл — `flick` |
| Исходный файл | `.fl`, например `src/App/Main.fl` для модуля `App.Main` |
| Конфигурация компилятора | `flick.toml`; схема конфигурации имеет собственную версию |
| Пакет и зависимости | `package.json`; первый поддерживаемый менеджер пакетов — pnpm |
| Зафиксированное дерево зависимостей | Один `pnpm-lock.yaml` на проект или рабочую область pnpm |
| Собственный интерфейс Flick | JSON `.iface` с указанием версии; сохраняет полные типы и ABI Flick |
| Публичный интерфейс для TS | `.d.ts`, если он запрошен и выбранный фасад API представим в TS |
| Артефакты сборки | По умолчанию `dist/debug/` и `dist/release/` |
| Локальный кеш и служебные файлы | `.flick/`; кеш отделён от исходников и файла фиксации зависимостей |

Один файл `.fl` объявляет один модуль. Для обычных исходников путь относительно корневого каталога соответствует имени модуля: `App.Users` размещается в `src/App/Users.fl`. Корневой каталог тестов образует отдельный набор модулей с теми же правилами. Совпадение полных имён модулей вызывает диагностическую ошибку. Единственное расширение исходников в первой версии — `.fl`.

```toml
schema-version = 1

[project]
kind = "app"
source-dir = "src"
test-dir = "test"
entry = "App.Main"

[build]
out-dir = "dist"
profile = "debug"
emit = "js"
emit-dts = false
schema-aot = false
```

`kind` принимает `app` или `lib`; библиотеке `entry` не нужен. `entry` указывает модуль с экспортированным `main`. Имена пакетов, их версии и зависимости хранятся в `package.json`, настройки Flick — в `flick.toml`. Команда ищет ближайший `flick.toml`, поднимаясь от рабочего каталога к корню; `--project <path>` явно выбирает каталог проекта или конфигурационный файл.

## Повседневные команды

| Команда | Назначение и контракт |
| - | - |
| `flick new <directory> --template app` | Создать новый каталог с конфигурацией, `package.json` и примером приложения. `--template cli` создаёт приложение командной строки, чей `main` — блок `cli`, `--template lib` — библиотеку. |
| `flick init --template app` | Добавить тот же каркас в текущий каталог; существующие файлы не перезаписываются, конфликт показывается до записи. |
| `flick check [paths...]` | Проверить синтаксис, кинды, типы, эффекты, экземпляры классов, захваты, импорты и `.iface`. Без аргументов проверяет исходники и тесты проекта. |
| `flick build` | Проверить проект и записать ESM, карты исходного кода и собственные интерфейсы Flick в каталог выбранного профиля. |
| `flick run -- [args...]` | Собрать JS и запустить `main` из конфигурации; аргументы после `--` передать приложению. `--entry App.Main` явно выбирает модуль входа. |
| `flick dev -- [args...]` | Следить за исходниками, пересобирать приложение и последовательно заменять запущенную версию после корректного завершения её работы. |
| `flick test [paths...]` | Собрать и выполнить тесты из корневого каталога тестов; каждый тест получает собственного владельца области. |
| `flick fmt [paths...]` | Форматировать исходники Flick. `--check` проверяет формат без записи; `--stdin --stdin-filepath <file>` обслуживает редактор. |
| `flick clean` | Удалить только учтённые артефакты этого проекта; `--cache` дополнительно удаляет его кеш Flick. |

`new` и `init` по умолчанию только создают файлы; установка выполняется отдельной командой `install`. `check`, `build` и этапы сборки в `run`/`dev`/`test` не устанавливают зависимости, не запускают `main` и не выполняют эффектную инициализацию внешних модулей. Обычная проверка SQL не подключается к БД. Если зависимость отсутствует, команда выдаёт диагностическое сообщение с инструкцией по установке.

Выбор `paths` задаёт корни проверки, но не отключает проверку транзитивных импортов, согласованности экземпляров классов и ABI. `check --watch` только перепроверяет код; `build --watch` обновляет артефакты; запуском и перезапуском приложения управляет `dev`.

## Зависимости и упаковка

Загрузку пакетов и выбор их версий выполняет pnpm средствами npm-экосистемы. Flick проверяет типизированные импорты, `.iface`, канонические экземпляры классов и ABI среды выполнения по установленному дереву зависимостей. Отдельного решателя версий, реестра пакетов и второго файла фиксации зависимостей у Flick нет. Первый адаптер поддерживает pnpm; адаптеры для других менеджеров пакетов можно добавить позже без изменения системы модулей.

| Команда | Назначение |
| - | - |
| `flick install` | Установить зависимости через закреплённый pnpm и проверить совместимость набора инструментов и среды выполнения. |
| `flick install --locked` | Установить строго по существующему файлу фиксации зависимостей; его отсутствие или расхождение с манифестом — ошибка. |
| `flick install --locked --offline` | Та же установка только из локального хранилища; недостающий пакет — ошибка. |
| `flick add <package-spec> [--dev]` | Добавить npm-совместимый пакет в раздел dependencies или devDependencies и обновить файл фиксации зависимостей. Импорт его JS API по-прежнему требует FFI. |
| `flick remove <package>` | Удалить прямую зависимость через менеджер пакетов; на оставшиеся импорты в исходниках затем укажет проверяющий модуль. |
| `flick update [package]` | Обновить разрешённые версии в пределах ограничений манифеста. Зафиксированные версии компилятора, среды выполнения и Effect не меняются неявно. |
| `flick deps [--why <package>]` | Показать установленный граф, причины появления зависимости и сведения о доступных интерфейсах Flick. |
| `flick pack --out-dir artifacts` | Собрать пакет в профиле release и локальный npm-совместимый tarball с ESM, `.iface` и объявленными TS-фасадами. |

`install --locked` соответствует вызову `pnpm install --frozen-lockfile`, а `--offline` — одноимённому флагу pnpm. Эти режимы и их поведение описаны в [pnpm install](https://pnpm.io/cli/install). Манифест и зависимости используют обычный [package.json](https://pnpm.io/package_json); добавление пакетов выполняет [pnpm add](https://pnpm.io/cli/add).

Шаблон проекта закрепляет конкретные версии компилятора, адаптера среды выполнения и Effect, а также версию pnpm через `packageManager`. Команды проверяют соответствие локального набора инструментов и матрицы возможностей среды выполнения из раздела 11; несовместимый ABI нельзя обойти через TS-проекцию. Прежде чем менять манифест, файл фиксации зависимостей или установленное дерево, адаптер проверяет фактическую версию вызываемого pnpm. Если закреплённая версия недоступна, команда завершается с кодом `2` и инструкцией по установке; произвольная доступная версия не подставляется. Для поддержки дополнительных версий Effect требуется проверить контракты, а не только изменить диапазон semver.

`pack` проверяет комплектность объявленных экспортов, `.iface`, отпечатков зависимостей и файлов пакета. Импорт упакованной библиотеки не запускает приложение. Tarball публикуется отдельно обычным менеджером пакетов.

## Сборка и оптимизации

`build`, `run`, `dev` и `test` принимают `--profile debug` или `--profile release`; по умолчанию используется профиль из конфигурации. `debug` выполняет консервативное эталонное преобразование в исполняемый код. `release` включает разрешённые проходы оптимизации типизированного IR из раздела 8 и сохраняет ту же среду выполнения Effect и наблюдаемые контракты.

| Параметр сборки | Значение |
| - | - |
| `--emit js` | Исполняемые ESM-модули; основной формат вывода генератора кода. |
| `--emit ts` | TS-представление исполняемого кода для дальнейшей обработки инструментами JS; это не виртуальная проекция для редактора. |
| `--emit-dts` | Проверяемый публичный TS-фасад. Непредставимый экспорт требует явной обёртки или изменения выбранного фасада; неявной подстановки `any` нет. |
| `--schema-aot` | Включить выбранную AOT-оптимизацию Schema; неподдерживаемый узел может сохранить семантику интерпретатора. |
| `--out-dir <directory>` | Изменить базовый каталог артефактов; профили сохраняются в отдельных подкаталогах. |
| `--watch` | Пересобирать при изменениях; при ошибке сохранять последний успешно опубликованный набор артефактов. |

`run`, `dev` и `test` всегда собирают исполняемый JS независимо от настройки `emit` и режима вывода `build --emit ts`. Первая поддерживаемая платформа этих команд — Node.js. Код для браузера и React выпускается как ESM и подключается к среде исполнения JS и сборщику. Этот CLI не предусматривает отдельной генерации кода для Rust/WASM или автоматического запуска браузерного приложения.

Кеш учитывает исходники, версии компилятора и языка, нормализованную итоговую конфигурацию проекта и компилятора, включая корневые каталоги исходников и тестов и `schema-aot`, профиль и параметры генерации кода, версии стандартной библиотеки и среды выполнения, файл фиксации зависимостей, `.iface` и отпечатки зависимостей, контракты FFI и версии задействованных TS-инструментов.

Артефакты новой сборки объявляются готовыми только после успешной сборки всего набора. Запущенная версия использует неизменяемый набор исполняемых модулей и разрешённых зависимостей, например в `.flick/run/<generation>/`; поздний импорт не должен увидеть файлы следующей сборки. Этот набор сохраняется до завершения работы версии. Параллельная замена дерева зависимостей допустима только при сохранении такого снимка; иначе изменение отклоняется до записи с диагностикой занятого дерева. `clean` работает по манифесту артефактов Flick, сохраняет активные версии и их блокировки и не удаляет пользовательские файлы в общем каталоге вывода.

## Запуск и безопасный перезапуск

`run <name>` запускает выбранный вход через одно внешнее средство запуска
платформы; если вход один, имя можно опустить. Чистый
`main : Unit -> Unit` вызывается напрямую. Эффектный вход принимает
и возвращает `Unit`, не требует сервисов и может завершиться только
`AppError`; зависимости и слои предоставляются внутри `main`.
CLI не превращает каждый прямой вызов или `await` в отдельный запуск
среды выполнения. Аргументы командной строки доступны через явное API
платформы. В эффектном входе нормальный возврат, `AppError`, дефект
или прерывание закрывают корневого владельца; результат команды
известен только после освобождения ресурсов. Средство запуска тестов
соблюдает тот же порядок завершения для каждого теста.

`dev` может проверять и собирать следующую версию, пока работает текущая, сохраняя описанную выше изоляцию сборок. При ошибке сборки текущая версия продолжает работать. После успешной сборки средство запуска закрывает приём новой работы для старой версии, запрашивает прерывание, дожидается завершения дочерних файберов и прекращения доступа зарегистрированных внешних операций к ресурсам (quiescence), затем выполняет финализаторы в порядке LIFO. Новая версия запускается только после подтверждённого завершения работы старой; ошибка освобождения ресурсов останавливает автоматический перезапуск.

SIGINT/SIGTERM запускают тот же протокол завершения. Пока ресурсы не освобождены, команда не сообщает об успешном выходе; при задержке показывает состояние завершения работы. Жёсткого срока остановки нет: работа, которую нельзя прервать, может её задержать. Принудительное завершение процесса средствами ОС не доказывает, что финализаторы выполнились. Автоматическая горячая перезагрузка внутри процесса с сохранением старых дескрипторов областей владения в первую версию не входит.

## Тесты и воспроизводимость

`test` поддерживает `--filter <text>` по полному имени теста, `--jobs <positive-number>` для явного предела параллелизма, `--watch` и `--reporter human` или `--reporter json`. По умолчанию `--jobs 1`. Повторный запуск тестов начинается после закрытия владельцев предыдущего запуска; отмена теста не позволяет пропустить освобождение ресурсов.

Human-репортёр выводит каждый результат сразу после освобождения ресурсов теста, в порядке завершения: `✓`/`✗`, счётчик завершённых тестов и время в миллисекундах. Итог содержит число успешных, проваленных и всех тестов, а также общее время исполнения без компиляции. Формат одинаков на Node и Go. `--color auto` проверяет терминал stdout и отключает цвет при `NO_COLOR` или `TERM=dumb`; `always` включает цвет независимо от этих условий, `never` отключает. JSON остаётся одним итоговым объектом `{seed,passed,failed,tests}` в порядке объявления, без цвета и длительностей. Прерванный запуск сообщает о завершении освобождения ресурсов вместо обычного итога.

Тестовая библиотека поддерживает чистые и эффектные тесты, а также отдельные тесты свойств с явными генераторами. `--seed <integer>` задаёт начальное значение для генераторов и выводится при провале; оно не гарантирует воспроизведения расписания файберов, сети или внешней БД. Провалы утверждений, типизированные ошибки, дефекты и ошибки освобождения ресурсов отражаются в результате теста раздельно.

Обычный CI проверяет приложение в выбранном профиле. Для компилятора и среды выполнения Flick наборы регрессионных тестов семантики запускаются в `debug` и `release`, чтобы проверить сохранение установленных наблюдаемых контрактов. Два успешных запуска не считаются общим доказательством эквивалентности всех программ.

## FFI, Schema, документация и редактор

| Команда | Контракт |
| - | - |
| `flick ffi import <package> --out <directory>` | Прочитать установленные `.d.ts`, сгенерировать поддерживаемые привязки и отчёт о покрытии; `--select <names>` ограничивает набор импортируемых имён. |
| `flick ffi check` | Проверить сгенерированные привязки, отдельно хранимые проверенные вручную переопределения, отпечатки и обязательные политики адаптеров после изменения зависимостей. |
| `flick schema export <Module.codec> --target json-schema-2020-12 --out <file>` | Экспортировать статически представимый кодек JSON-представления по строгому контракту; для неподдерживаемого контракта указать узел и путь в диагностике. |
| `flick schema export <Module.api> --target openapi-3.1 --out <file>` | Экспортировать OpenAPI 3.1 для значения `HttpApi` по строгому контракту; для неподдерживаемой схемы указать эндпоинт и путь в диагностике. |
| `flick doc --out-dir docs` | Сформировать документацию публичного API: типы Flick, кинды, ограничения, эффекты, захваты и сигнатуры экспортируемых значений. |
| `flick lsp --stdio` | Запустить языковой сервер для исходного кода с тем же ядром на Rust и конфигурацией проекта. |
| `flick explain <diagnostic-code>` | Объяснить диагностику Flick и показать небольшие примеры исправлений. |
| `flick doctor` | Проверить компилятор, Node.js, pnpm, ABI среды выполнения и Effect, а также состояние подключённых адаптеров TS и редактора. |
| `flick inspect <module> --emit <representation>` | Вывести `ast`, `typed-ir`, `js`, `ts`, `iface` или `mapping` для исследования генерации кода и карт исходного кода. |

`ffi import` разделяет экспорты на поддерживаемые, требующие недостающей политики и неподдерживаемые. Обязательные правила чистоты, выполнения, удержания, отмены и владения не выводятся автоматически из `.d.ts`. Проверенные вручную переопределения не перезаписываются при повторной генерации. Имена заблокированных экспортов сохраняются; их запрос или использование даёт ошибку, но не мешает независимым поддерживаемым экспортам.

`schema export` использует строгий контракт внешнего представления из раздела 9. Ради экспорта команда не запускает точку входа приложения и не выполняет произвольные пользовательские преобразования, требующие среды выполнения. Динамически построенные схемы экспортируются через явное API среды выполнения. Standard Schema V1 и Arbitrary остаются библиотечными адаптерами и генераторами, а не статическими JSON-файлами. OpenAPI 3.1 экспортируется из статически известного значения `HttpApi` по тому же строгому контракту (`--target openapi-3.1`): документ не содержит `{}`/`any`, а неподдерживаемая схема эндпоинта даёт ExportError с путём. Swagger UI и Scalar — библиотечные слои, которые отдают этот же документ, а не строят его приближённую версию.

`lsp` предоставляет диагностику по исходному коду, подсказки при наведении, переход к определению, автодополнение, переименование и форматирование. Его stdout целиком принадлежит протоколу; логи идут в stderr. Content Mapper остаётся отдельной интеграцией с указанием версии и не требуется для работы проверяющего модуля Flick. Отсутствие необязательного адаптера Mapper в `doctor` само по себе не блокирует компиляцию.

## Общие параметры и диагностика

| Параметр | Назначение |
| - | - |
| `--project <path>` | Явно выбрать проект. |
| `--diagnostics human` или `--diagnostics json` | Формат диагностики в stderr; JSON использует поток NDJSON с версией схемы. |
| `--warnings-as-errors` | Сделать предупреждения ошибками для результата команды. |
| `--color auto`, `--color always`, `--color never` | Управлять оформлением человекочитаемого вывода. |
| `--quiet` или `--verbose` | Сократить служебный вывод либо включить подробные сведения. |
| `--help` и `flick help <command>` | Справка по CLI или конкретной команде. |
| `--version` | Версия компилятора Flick; подробные сведения о совместимости доступны через `doctor`. |

Диагностическое сообщение содержит стабильный код с префиксом `FLICK-`, уровень важности, текст, исходный путь, диапазон байтов UTF-8, связанные диапазоны и возможные исправления. Если соответствие известно, диапазон относится к исходнику `.fl`; ошибку внешнего JS/TS нельзя приписывать произвольному участку исходного кода. Адаптер LSP переводит диапазон в кодировку позиций редактора.

stdout предназначен для результата команды, stdout приложения или выбранного протокола; служебные и диагностические сообщения не вмешиваются в этот поток. При `--diagnostics json` весь stderr принадлежит одному сериализатору NDJSON с версией схемы: диагностика компилятора, служебные логи, stderr приложения и вывод менеджера пакетов становятся типизированными событиями `diagnostic`, `log`, `application-stderr`, `package-manager-output`. Для перехваченного вывода сохраняются исходный канал и текст; необработанные строки дочерних процессов и ANSI-коды в этот поток не подмешиваются.

В режиме human stderr приложения может передаваться напрямую. `test --reporter json` отдельно выдаёт в stdout структурированные события тестов и включает захваченные логи тестов как поля событий. stdout LSP всегда принадлежит только его протоколу.

| Код завершения | Значение |
| - | - |
| `0` | Успех; для `fmt --check` форматирование уже соответствует правилам. |
| `1` | Ошибка проверки или сборки, провал тестов, несоответствие форматирования либо ошибка выполнения приложения или освобождения ресурсов. |
| `2` | Неверный вызов или конфигурация, отсутствующая зависимость, занятое дерево зависимостей или несовместимый набор инструментов либо ABI. |
| `3` | Внутренняя ошибка компилятора или инструментов Flick. |
| `130` / `143` | SIGINT / SIGTERM, если причиной остановки было только прерывание от сигнала и ресурсы успешно освобождены. |

Ошибка приложения или освобождения ресурсов сохраняет код `1` и диагностику итогового `Cause`, даже если одновременно пришёл сигнал. Пока освобождение ресурсов не завершено, команда не сообщает об успешном завершении или окончательном коде выхода.

## Примеры работы

```sh
flick new my-app --template app
cd my-app
flick install
flick check
flick dev -- --port 3000
```

```sh
flick fmt --check
flick check --diagnostics json
flick test --filter Users --jobs 4
flick build --profile release
flick run --profile release -- --port 3000
```

```sh
flick add date-fns
flick ffi import date-fns --out src/Foreign/DateFns
flick ffi check
flick schema export App.Domain.user_json --target json-schema-2020-12 --out schema/user.schema.json
flick doc --out-dir docs
```

Пример с `date-fns` показывает последовательность действий, но не гарантирует покрытия всего его API. После импорта разработчик задаёт и проверяет требуемые политики адаптеров; `ffi check` проверяет их соответствие контрактам. `App.Domain.user_json` в примере — явно объявленный JSON-кодек проекта.

```sh
flick install --locked
flick fmt --check
flick check --warnings-as-errors
flick test --profile release
flick build --profile release
```

Последний набор команд — базовый CI. Отсутствие записи в кеше не меняет результат команды; файл фиксации зависимостей и закреплённые версии инструментов входят в ключ кеширования. Обновление зависимостей выполняется отдельно от CI-проверки.

## Порядок реализации команд

| Этап | Состав |
| - | - |
| Первый исполняемый прототип | `new`, `init`, `check`, `build`, `run`, `fmt`, help/version и минимальный `install`; один проект и платформа Node.js. |
| Цикл разработки | `dev`, `test`, `clean`, остальные команды зависимостей, `lsp`, `doctor`, `explain`; стабильная диагностика в JSON и инкрементальный кеш. |
| Полный набор инструментов первой версии | `ffi import`, `ffi check`, `schema export`, `doc`, `pack`, `inspect`; соответствующие языковые возможности остаются частью выбранного дизайна первой версии. |
| После первой версии | REPL, отдельное средство запуска бенчмарков, отчёты о покрытии, интерактивная документация, дополнительные адаптеры менеджеров пакетов и автоматизированная интеграция с React и сборщиками. |

Этапы задают порядок реализации, а не альтернативные версии семантики. Публичные команды обращаются к общей модели проекта и одному проверяющему модулю; оптимизация, импорт FFI и редакторная проекция не определяют типы независимо от него.
